# Sub-Questions — EDITLINK Operation

**Inquiry:** What happens when a link is to be edited — its endsets modified — given that the substrate makes links permanent and immutable once created (L12)? What is allocated and what record is made of the relationship between what was and what is now, what relationship must the edited link bear to the original — must the original remain readable by its address, must readers be able to recognize the edit as supersession rather than as an independent new link, and by what mechanism does the system express this relationship — among alternatives that include a separate supersession link, a supersedes field on the link's structure, a version-of-link convention analogous to document versioning, or a typed relation distinct from any of these, what does committing to one such architecture (rather than another) reveal about the difference between editing-as-permanence-preserving and editing-as-mutation, and what invariants must any choice maintain about the original link's continued discoverability and resolution, the chain semantics under repeated edits, multi-editor convergence and conflict, and the reader's ability to identify the current successor without ambiguity?

1. [theory] When a link's endsets must be modified, must the system allocate a wholly new link with its own permanent identity, leaving the original untouched in every respect?
2. [theory] Must the original link remain forever readable at its original address after it has been superseded, exactly as it was before the edit?
3. [theory] Must a reader who encounters the superseded link be able to discover that a successor exists, or is it acceptable for the old link to give no sign that it has been replaced?
4. [theory] Must the relationship between an edited link and its original be recognizable as supersession specifically — distinguishable by readers from two independent links that merely happen to resemble one another?
5. [theory] Should the supersession relationship be expressed as its own first-class link, as a field within the new link's structure, or as a typed relation — and what does the design gain or lose with each choice?
6. [theory] Should editing a link follow the same version-of conventions that govern document versions, or does link identity demand a distinct versioning discipline of its own?
7. [theory] Under repeated edits to the same link, must the chain of supersessions remain fully traversable from any member to both the earliest original and the current successor?
8. [theory] Must the system guarantee that a reader asking for the current version of an edited link receives exactly one unambiguous answer, even after many successive edits?
9. [theory] When two editors independently supersede the same link, must the design permit the resulting fork to coexist permanently, and what must readers be told about the divergence?
10. [theory] If editing a link never mutates anything but only adds, what guarantee distinguishes a system that preserves permanence under editing from one that merely simulates editing by deletion and recreation?
11. [evidence] Is there any backend code path that mutates an existing link orgl's endsets in place in the granfilade, or does every endset change necessarily require allocating a new link orgl with a fresh I-address under `findisatoinsertnonmolecule`?
12. [evidence] `findnextlinkvsa` computes max+1 over the POOM's link subspace: after DELETEVSPAN removes the highest link's `2.N` entry, does a subsequently created replacement link reuse V-position `2.N` while I-address allocation (which queries the append-only granfilade) still advances — so the same V-position can refer to two different link orgls across time?
13. [evidence] Can `findisatoinsertnonmolecule` allocate a successor link as a child of the original link's ISA (e.g., `docISA.0.2.N.0.1`), analogous to how version addresses nest under a source document, or does the bounded upper limit (`docISA.2.3`) and the per-document link counter force all successors to be flat siblings at `2.N+1`?
14. [evidence] Does the link orgl structure contain any field beyond the three endsets (source, target, type) — for instance, an entry in the reserved `3.x` subspace — where a predecessor reference could be stored, or are the three endsets the entirety of a link orgl's structure?
15. [evidence] Can a link's source or target endset contain another link orgl's I-address span (`docISA.0.2.N`), and does `insertendsetsinspanf` index such link-orgl I-spans in the spanfilade exactly as it indexes text I-spans — making a separate link-between-links mechanically expressible as a supersession record?
16. [evidence] When a replacement link is created, the original's endset entries remain in the write-only spanfilade: is there any structural marker that distinguishes a superseded link's spanfilade entries from a current link's, or do both sets of DOCISPAN/endset entries remain equally live with no way to tell which link is the successor?
17. [evidence] After the original link's POOM entry is removed from the link subspace (reverse-orphaning it), what is required to resolve the original link orgl by its ISA — is resolution purely a granfilade lookup, or does it depend on a surviving POOM entry or a BERT-opened home document?
18. [evidence] If two sessions each create a successor to the same link `2.N` in the same home document, does the run-to-completion event loop simply allocate them V-positions `2.N+1` and `2.N+2` with no detection that both claim to replace `2.N` — leaving the fork between competing successors unrecorded in any enfilade?
19. [evidence] Is the type namespace at `1.0.2.x` extensible at runtime — could a client register a "supersedes" link type there without backend changes — and does the backend ever interpret a type endset's content, or is the type purely an opaque I-span that only conventions among clients give meaning to?
