## Question 2 [theory]

> Did the design intend the link-type vocabulary itself to be queryable as a domain — e.g., "which types of links are in use on this document," "how many types appear here" — or do types enter queries only as caller-supplied selectors, with the open-ended type vocabulary never enumerated or aggregated by the system?

The page images aren't present in this checkout (no `page-*.png` anywhere under the repo, and `resources/literary-machines/raw/` doesn't exist), so this answer rests on the curated extractions, with one detail flagged for raw verification below.

## Answer

Types enter queries only as caller-supplied selectors. Nowhere in the design is the type vocabulary itself a queryable domain — there is no operation whose *result* is a set of types, no "enumerate the types in use here," no count-by-type. And this is not an omission so much as a consequence of what a type *is* in the design: an address, not an object. There is no type table for an enumeration command to read.

**The command set treats types strictly as input constraints.** Of the 17 commands in XU.87.1 (4/61), the link-query family takes the type as part of the request: FINDLINKSFROMTOTHREE "returns a list of all links which are (1) in `<home set>`, (2) from all or any part of `<from set>`, and (3) to all or any part of `<to set>` and `<three set>`" (4/69). FINDNUMOFLINKSFROMTOTHREE counts links matching supplied endset criteria. The satisfaction model is per-link selection — "A link satisfies a search request if one span of each endset satisfies a corresponding part of the request" (4/58) — so the result domain is always links, never types. Tellingly, the one per-document aggregate the protocol does offer, RETRIEVEDOCVSPANSET, "returns a span-set indicating both the number of characters of text and the number of links in document `<doc id>`" (4/68) — a raw link count with no type breakdown. Aggregation exists in the protocol; it just never runs over the type dimension.

**There is nothing for the system to enumerate.** "The search mechanism does not actually look at what is stored under the 'type' it is searching for; it merely considers the type's address" (4/44–4/45), and "there is no need for the presence of elements at the addresses specified. Link types may be ghost elements" (4/45). A type "exists" only as a convention plus the references in links' three-sets. Since "the set of link types is open-ended, and indeed any user may define his or her link types for a particular purpose" (4/43), there is no registry to consult — the vocabulary has no system-level existence apart from its use.

**Vocabulary knowledge was meant to live in the documentary/social layer, not the protocol.** Nelson's own type list is explicitly a publication, not a system artifact: "A TENTATIVE LISTING OF SOME LINK TYPES. Link types are open-ended, so this is not the original beginning, but a first provisional, to give the flavor of current thinking" (4/52), with "Standardization of a working set of link types" as a roadmap item (4/52). This matches the system's general anti-catalog stance: "there is no system directory; rather, we encourage the on-line publishing of directory documents by users" (4/41). The intended pattern for a shared, inspectable vocabulary is publishing it as documents — and, for structure, reifying it as links: "Note that this mechanism can be used for hierarchical link types, subtypes and supertypes. It is searchable for upper- and under-links, and all final data matter below" (4/51). That is, the vocabulary becomes queryable exactly to the extent users build it *into the docuverse* as content; the back end still only matches addresses.

**The census is derivable client-side, though, and the design knows where that work belongs.** Selectors can be maximally wide — "A digit of 'one' may be used to designate … the entire docuverse" (4/38); "If the home-set is the whole docuverse, all links between these two elements are returned" (4/63) — so a front end can fetch all links on a document with a wildcard three-set and then inspect them: RETRIEVEENDSETS "returns a list of all link end-sets that are in `<spec set>`" (4/70). Aggregating distinct type addresses from that is the client's job, and Nelson is explicit that such derived scanning is *not* back-end work: people "insist that scanning should be part of the Xanadu back end" (4/72), and he pushes back — it belongs in the middle end. So "which types appear on this document" is, in this architecture, a middle-end computation over back-end primitives, never a primitive itself.

**One verification gap:** whether RETRIEVEENDSETS returns the three-set alongside from/to is ambiguous in my materials — the command description says "all link end-sets" (4/70), but the concept-operation glosses describe it as returning only the from-set and to-set. On the narrow reading, even client-side type enumeration requires probing type-by-type (each per-type query implicitly reveals its type); on the broad reading, one wildcard query plus endset retrieval yields the full per-document type census. NEED_RAW: 4/69-4/70.

**Bottom line:** the open-ended type vocabulary was never meant to be enumerated or aggregated by the system. Types are ghost addresses matched as selectors; the back end answers "find/count links satisfying these endset constraints," and only that. If you want the vocabulary itself as a surveyable domain, the design's answer is to publish it — as directory documents and as link-built type hierarchies — and to let the front/middle end compute any census from link retrievals.
