# Review of ASN-0100

## REVISE

### Issue 1: Case (ii) "forced" inconsistency for V_{s_L}(d) = ∅
**ASN-0100, "The Operation: Formal Contract" → Substrate Decomposition (case ii)**: The ASN states K.μ⁻ omission in case (ii) is "Canonical-decomposition choice when V_{s_L}(d) ≠ ∅; forced when V_{s_L}(d) = ∅".
**Problem**: For V_{s_L}(d) ≠ ∅, the ASN explicitly identifies an alternative decomposition: "an alternative decomposition could fire K.μ⁻ with n'_{s_C} < N (admissible since s_C is non-empty here) and follow with a K.μ⁺ that re-adds the discarded s_C positions before adding Insertion, reaching the same Σ'." The same alternative is available when V_{s_L}(d) = ∅: with n'_{s_C} < N (admissible since case (ii) requires N ≥ 1 and V_{s_C}(d) is non-empty) and n'_{s_L} = 0 = n_{s_L}, K.μ⁻'s strict-shrinkage clause `(E S :: n'_S < n_S)` is satisfied via s_C alone. K.μ⁻ fires; K.μ⁺ then re-adds the discarded s_C positions plus Insertion, reaching the same Σ'. This alternative uses only K.μ⁻ + K.μ⁺ (the ASN's stated vocabulary scope), requires no K.μ⁺_L, and is admissible. Under the ASN's own definition of "forced" — "no admissible K.μ⁻ firing exists under the canonical retention parameters and INSERT's frame" combined with the alternative-decomposition treatment of V_{s_L}(d) ≠ ∅ — case (ii) with V_{s_L}(d) = ∅ should be classified as "canonical-decomposition choice", not "forced".
**Required**: Either (a) reclassify case (ii) V_{s_L}(d) = ∅ as "canonical-decomposition choice" (consistent with the V_{s_L}(d) ≠ ∅ treatment), or (b) explain why the alternative decomposition with n'_{s_C} < N that the ASN admits for V_{s_L}(d) ≠ ∅ is not considered for V_{s_L}(d) = ∅. As written, the two subcases of case (ii) receive inconsistent treatment for the same available alternative.

### Issue 2: S4 misclassified as entity-set invariant
**ASN-0100, "Atomicity and Canonical Order"**: "*Entity-set invariants* — P8 (EntityHierarchy), NodeLineage (NodeDescentFromBootstrap), S4 (OriginBasedIdentity), M0 (DocumentTumblerWellFormed; ASN-0093). The entity set E (equivalently dom(M) for documents under ValidComposite★) is unchanged at every intermediate: no K.δ fires, no K.σ fires. Each invariant is a predicate over E (or dom(M)) and so holds at every intermediate by inheritance from the pre-state."
**Problem**: S4 (OriginBasedIdentity, ASN-0036) is a predicate over dom(C), not over E or dom(M). Its preconditions explicitly quantify `a₁, a₂ ∈ dom(Σ.C)`, and its postcondition asserts distinctness of content addresses produced by distinct allocation events. INSERT extends dom(C) by n new K.α firings, so S4 must be discharged against the changed dom(C) at intermediate states — not inherited from the pre-state by frame. The "no K.δ, no K.σ" argument preserves E-predicates and is sound for P8, NodeLineage, M0, but does not discharge S4. The correct preservation argument requires: (i) pre-state pairs remain distinct (by P0 monotonicity), (ii) new a_k are distinct from pre-state addresses (by K.α freshness), and (iii) the n new addresses {a_0, …, a_{n−1}} are pairwise distinct (by ChainEnumerationInjectivity, ASN-0093, since a_{k+1} = inc(a_k, 0) > a_k). The Effect One discussion establishes (ii) and (iii) implicitly, but the connection to S4's preservation is not made explicit, and the ASN's stated reason for "trivial preservation" of S4 is structurally incorrect.
**Required**: Move S4 out of the "Entity-set invariants" group. Either group it as a content-allocation invariant requiring per-step verification (and discharge it explicitly via ChainEnumerationInjectivity + freshness at each K.α intermediate), or rewrite the "trivially preserved" justification so the chain-injectivity reasoning that actually establishes S4 is named rather than the inapplicable "no K.δ fires" reasoning.

### Issue 3: I3-V disclaimer wording ambiguity
**ASN-0100, "Effect Three: Shift" → disclaimed I3 lemmas**: "Applied to INSERT, this would exclude the Insertion positions `shift(p, k)` from `dom(M'(d))` — directly contradicting INS.M-insert."
**Problem**: I3-V's quantifier ranges over `v ∈ dom(M(d))` (pre-state positions). The conflict with INS.M-insert occurs precisely at Insertion positions `shift(p, k)` that coincide with pre-state positions — concretely, those with `k ≤ N − p_m`. For example, with V_{s_C}(d) = {[1,1], ..., [1,5]}, p = [1,3], n = 2: I3-V constrains both [1,3] and [1,4] (both pre-state, both Insertion). For the append case (p_m = N+1), no Insertion position coincides with a pre-state position, and I3-V is vacuous. The current wording reads as a blanket exclusion of all Insertion positions, which obscures both (a) why the append case is unaffected and (b) which specific positions create the conflict in the interior/beginning cases.
**Required**: Tighten the disclaimer to identify the precise scope of the conflict, e.g., "for any Insertion position `shift(p, k)` that coincides with a pre-state position (those with k ≤ N − p_m in the non-empty case), I3-V would force `shift(p, k) ∉ dom(M'(d))`, contradicting INS.M-insert; the append and empty cases produce no such coincidences and are unaffected by I3-V's quantifier".

## OUT_OF_SCOPE

None — the ASN appropriately limits itself to INSERT for the content subspace and explicitly excludes DELETE, COPY, REARRANGE, link semantics, version creation, and replication. The brief discussion of COPY's identity character (under "INSERT vs. COPY") is clearly demarcated as a comparative note rather than a specification of COPY; the version-derivation corollary explicitly notes that K.δ-IsDocument version derivation is out of scope while applying INSERT to derived versions.

VERDICT: REVISE
