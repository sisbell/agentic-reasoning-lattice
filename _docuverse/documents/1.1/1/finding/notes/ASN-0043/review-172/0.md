### Issue 1: L1c's chain condition encodes only the k=2 zero-count guard, omitting the k=1 guard that "T10a-conforming" requires
**ASN-0043, L1c — LinkAllocatorConformance (formal *Chain* statement)**: "`(A i : 1 ≤ i ≤ n : tᵢ = inc(tᵢ₋₁, kᵢ) ∧ kᵢ ∈ {0, 1, 2} ∧ (kᵢ = 2 ⟹ zeros(tᵢ₋₁) ≤ 2))`"

**Problem**: L1c claims each link address is "a T10a-conforming allocator output," but T10a's discipline (via TA5a) imposes **two** child-spawn guards: `k' = 1 ⟹ zeros(t) ≤ 3` *and* `k' = 2 ⟹ zeros(t) ≤ 2`. The encoded condition states only the `k = 2` guard; the `k = 1 ⟹ zeros(tᵢ₋₁) ≤ 3` conjunct is absent. As literally written, the existential admits chains with a `k = 1` step on an input of `zeros = 4` — not a T10a-conforming chain, and one on which TA5a does not preserve T4. The omission is in fact *recoverable* (a T4-valid seed plus inductive T4-preservation keeps `zeros ≤ 3` at every step, so the `k = 1` guard is met automatically), but that reasoning is never stated, and the asymmetry — encode the guard that can fail for a T4-valid input (`k = 2` at `zeros = 3`), drop the one that cannot — is left for the reader to reconstruct.

This is corroborated by an internal inconsistency: the worked-example L1c verification *does* invoke the `k = 1` guard explicitly — step (iii): "child at depth 2 (`k₃ = 1`, **requiring `zeros(1.0.1.0.1.0.2) ≤ 3` by TA5a**; satisfied since `zeros(…) = 3`)". The example checks a guard the governing axiom does not encode.

**Required**: Either (a) add the companion conjunct `(kᵢ = 1 ⟹ zeros(tᵢ₋₁) ≤ 3)` so the chain condition literally matches T10a-conformance, or (b) keep the minimal form and add one line stating that the `k = 1` guard is omitted because it is discharged automatically by the chain's inductively-maintained T4-validity (`zeros ≤ 3`), whereas the `k = 2` guard is the only child-spawn constraint that can fail on a T4-valid input. Reconcile the worked example with whichever form is chosen.
