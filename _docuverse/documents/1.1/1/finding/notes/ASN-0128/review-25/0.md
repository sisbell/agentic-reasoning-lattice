### Issue 1: The born-nullified example grounds the exclusion in the covering retraction's *activity*, which the mechanism does not use
**ASN-0128, An abstract registry example, "Born-nullified case (I3)"**: "Suppose a pre-existing active R-tuple has to-endset covering some address `a*`…" and "By ASN-0086's active-subset semantics, `a*` is covered by an active retraction, so the new tuple is not in `A_{fanout}^{Σ'}`".
**Problem**: The operative condition is C3's existential over the **audit slice** `L_R^Σ` — exactly as I3 states it, as ASN-0126's WP states it, and as `nullified` is defined (ASN-0086). The covering R-tuple's own status is immaterial: R6b is explicit that the membership test consults `L_R`, not `A_R`, and that retraction-of-retraction is non-fixpoint — a covering retraction tuple that has itself been nullified still bars the deposit. The note's own text is consistent everywhere else (I2's caveat carries no activity qualifier; DR's sufficiency argument quantifies over `L_R^Θ`). The example is the one place the qualifier appears, twice, and in a section whose purpose is to verify the mechanism against a concrete scenario. An implementer who validates a born-nullified check against this example can implement the test against `A_R^Σ`, pass the example, and diverge from R6b the first time a retractor is itself retracted.
**Required**: Drop both "active" qualifiers (or state explicitly that the covering tuple's status is immaterial, citing R6b), and name C3 over `L_R^{Σ}` as the operative test. The "By ASN-0086's active-subset semantics" citation is right for the fanout side (`A_K = L_K` minus `nullified`) but should not be made to carry the retraction-side hypothesis.
