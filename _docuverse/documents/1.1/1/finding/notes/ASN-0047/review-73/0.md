### Issue 1: Notational category-mismatch for `parent(A_v(t))` / `parent(A_c(t))` in K.δ section
**ASN-0047, "Operational T10a allocator for live-operand sub-cases (named)"**: "with `parent(A_v(t)) = t`, `spawnPt(A_v(t)) = t`, `spawnParam(A_v(t)) = 1`" (k = 1 sub-case); "with `parent(A_c(t)) = t`, `spawnPt(A_c(t)) = t`, `spawnParam(A_c(t)) = 2`" (k = 2 sub-case).

**Problem**: T10a (ASN-0034) defines the spawning triple with `parent(A) ∈ 𝒯` — i.e., an allocator. The same paragraph then cites "the rule requires `parent(A_v(t)) ∈ Act(s)`", consistent with parent being an allocator (since `Act(s) ⊆ 𝒯` per AllocatedSet, ASN-0034). The "Characterization of `parent(A_v(t))`'s tracked domain" paragraph (later in the same K.δ section) explicitly clarifies: "The allocator `parent(A_v(t))` named here is the document sub-allocator under `t`'s parent account — i.e., `A_doc(parent(t))`". The initial statement `parent(A_v(t)) = t` is therefore a literal category-mismatch: t is a tumbler (an element of T), not an allocator (an element of 𝒯). A reader processing the spawning-triple description before reaching the Characterization paragraph gets a wrong reading that the ASN's own subsequent text must overturn.

**Required**: Either (a) replace `parent(A_v(t)) = t` with `parent(A_v(t)) = A_doc(parent(t))` (and the analog for A_c(t)), aligning notation with T10a's framework and the Characterization paragraph from the outset; or (b) introduce an explicit notational convention upfront declaring that `parent(A_v(t)) = t` is shorthand for "the parent allocator is the unique T10a allocator whose tracking domain contains t at state s", so the apparent category mismatch is resolved before the load-bearing T2 spawning analysis consumes it.
