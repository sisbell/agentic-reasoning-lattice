# Review: M6 — Content Retrieval & Query

I worked the design against the seven lenses, cross-checking every upstream call against M1–M5 as given and every operation against its ASN. M6 is, for six of its seven operations, genuinely buildable: the depth-2 collapse of `m_S(d) ≡ 2` is exploited correctly, the extent synthesis from `content_count`/`link_count` reproduces 0112/0113 (including the cross-subspace bounding box via `from_endpoints`, which is always valid here because all V-positions are depth-2), COMPARE's I-axis interval join is sound and fan-out-complete (overlap ⟹ co-chain, so the ordinal arithmetic is total), and the registered-empty-vs-unallocated gate is applied per the resolved model. The re-homing of the R⁻¹ index to M5 (`docs_containing`) is the correct reading of M5's *as-built* interface over the decomposition's tentative allocation.

But one operation is built on a method that does not exist, and that blocks the build.

## Revision list

**1. [DEFECT] `show_deletions` calls `m5.cross_deletions(d_a, d_b)`, which M5's interface does not provide — SHOWDELETIONS is unbuildable as written.** M5's published provenance surface is exactly `ever_placed`, `deletions`, `docs_containing` (interface §E); its M6 seam *explicitly* says SHOWDELETIONS is served by `deletions` ("read straight off it; M5 does the per-level-class difference"). There is no `cross_deletions`. The design's own "Conflicts resolved 1" admits it is *requesting* this seam ("the `cross_deletions` seam is requested of M5"). A builder will go to M5, find no such method, and stop. This is both an invented upstream call and a contradiction of M5's stated seam. The diagnosis behind it is sound — M6 genuinely *cannot* perform the cross-document `DELETED(·,d_A) ∧ CURRENT(·,d_B)` intersection, because `deletions(d_A)` arrives as an opaque, possibly mixed-length `SpanSet`, M1 exposes no SpanSet enumeration/partition, and `intersect_sets`/`normalize` fault on mixed-length input — so the real conclusion is that **M5's interface is insufficient for SHOWDELETIONS**. Fix: do not present `cross_deletions` as an existing call. Either (a) mark SHOWDELETIONS as *blocked on a required M5 amendment*, specify the exact demanded signature `fn cross_deletions(&M5State, d_a, &Address, d_b: &Address) -> (SpanSet, SpanSet)` **and pin its output contract** (must be an *exact* unit-span cover per level-class, else the "lossless re-encoding to coverage" claim in Conflicts-9 fails and the result over-approximates `dom(C)`), as a cross-module change that M5's design must actually adopt; or (b) build it from M5's published surface (the design shows this is impossible — so (a) is forced). As it stands, M6 cannot be compiled against M5.

**2. [SHARPENING] Record SHOWORIGIN_I's de-scope as a formal decomposition + M10 amendment, and verify no consumer needs it.** The de-scope is *sound* — `origins_I` needs an I-interval enumeration of `dom(C)` that M4 (point-only, `Ord` deliberately unused, range/prefix scans forbidden) and M3 (`is_allocated` point-only) genuinely cannot supply, and inventing an M4 scan would itself be an upstream-overreach defect. But the decomposition's Provenance-R note says "the SHOWORIGIN *operation* itself — whose **I-span/V-span resolvers** read arrangement state — is correctly in M6," implying both arities, and M10 sources ASN-0077. So the drop currently diverges from the system docs silently. Make it a recorded decomposition amendment (new I-ordered index as a hint over M4's append-only writes) and confirm M10's FEBE surface does not promise SHOWORIGIN-over-I to clients. If it does, this escalates to a DEFECT (a real capability hole). Also soften "the V-arity is *the* reader-facing one (ASN-0077's V-span resolver)" — 0077 designates neither arity as reader-facing; that is M6's ruling, not the note's.

**3. [SHARPENING] Pin the COMPARE helper signatures and bodies.** `reach_i`, `ordinal_gap`, `vpos_shift`, `max_tumbler`, `min_tumbler`, `interval_join`, `canonicalize` are named with prose/comment semantics but no bodies, and the shown `if !(lo < hi)` mixes `Address` (from `max_tumbler(&pb.i_start, …)`) with `Tumbler` (from `reach_i` via `shift`) — it will not typecheck until the builder threads `.tumbler()` consistently. Specify them as operating on `Tumbler` (e.g. `reach_i = shift(i_start.tumbler(), width)`, `ordinal_gap = ordinal(hi) − ordinal(lo)`), and **state the co-chain precondition** that makes `ordinal_gap` total: it is only ever called on overlapping (hence same-content-chain, equal-length) addresses, which is why a bare ordinal subtraction is valid.

**4. [SHARPENING] Make COMPARE's V-reconstruction lemma explicit and assert it.** `resolve_blocks` sets `v_start = span.start()` for the first run and accumulates by run width — load-bearing for X12-R1 soundness, and correct *only because* content is gap-free (D-CTG★) so the first run's V-start equals `span.start()` and runs tile V contiguously. State this as the lemma it is and add a `debug_assert` that the first run begins at `span.start()`, so a future M5 regression to V-gapped content runs fails loudly rather than silently mis-aligning `u1`/`u2`.

**5. [SHARPENING] Close the `retrieve_v` subspace dispatch.** The `if sub == s_c() {…} else if sub == s_l() {…}` has no final arm; a `sub ∉ {1,2}` span passes `gate_vspec` (which checks zero-freeness/depth/ordinal-level but not subspace ∈ {1,2}) yet is harmless only because `resolve` returns no runs for it. Make the unreachable-for-active-positions case explicit (a `debug_assert`/comment), so the silent-drop is documented intent, not an oversight.

**6. [SHARPENING] Note the by-construction normal form and the inert non-content spans.** `doc_vspanset` returns `union(...)` (concatenation, never normalizes) yet promises W0's "normalized span-set" — true here because `ext_C`/`ext_L` are subspace-separated, but worth a one-line `is_normalized()` debug assert or comment so the contract is visible. Separately, `find_docs_containing` never gates `Region` spans to the content subspace; that is *correct* (FD's `image_C` content-restriction is achieved downstream — link/foreign-subspace coverage is inert against R⁻¹ and content-only `project`), but stating the reliance prevents a builder from adding a spurious gate or worrying the result is unsound.

The design is faithful and buildable for RETRIEVEV, both extent queries, SHOWORIGIN_V, COMPARE, and FINDDOCSCONTAINING — but SHOWDELETIONS rests on a phantom upstream method, so a builder cannot implement M6 from this document as written.

VERDICT: REVISE
