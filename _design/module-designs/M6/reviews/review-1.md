I reviewed M6's design against the M1–M5 interfaces (as given), the seven source notes' formal statements, the decomposition, and the composition contract. The read-only model, snapshot-consistency discharge, the `m_S ≡ 2` collapse, the registered-empty-vs-unallocated gate via `is_registered_document`, the "never open M4 in COMPARE" discipline, and the per-position delivery are all faithful and well-reasoned. But several owned operations are unbuildable or wrong against the upstream surfaces as given.

## Revision list

**1. [DEFECT] SHOWDELETIONS is unbuildable: `intersect_by_level_class`/`group_by_start_len` requires decomposing a `SpanSet`, which M1 does not expose.** The design intersects two *raw, mixed-length* covers in M6: `del_a = m5.deletions(d_a)` (a `SpanSet`) with `cur_b = content_image(d_b)`. To dodge `LevelMismatch`, `group_by_start_len(a: &SpanSet)` must iterate `a`'s constituent spans and bucket by `#start`. But M1's `SpanSet` has a **private** `im::Vector<Span>` and exposes no iterator / `.spans()` / partition (only `empty`/`singleton`/`normalize`/`is_normalized`/`denotes`). `content_image` is fine (M6 builds it from `content_runs(d_b): Vec<Run>`, which it *can* group), but the `deletions(d_A)`/`ever_placed(d_A)` operand arrives only as a `SpanSet` and cannot be partitioned — and `intersect_sets`/`normalize` both fault on mixed-length input, so it can't be sidestepped. Fix by moving the cross-document intersection into M5 (which has run-level access to both documents and already applies the level-class discipline internally for `project`/`deletions`), **or** have M5 expose the DELETED side decomposably (e.g. `deletions_runs(d) -> Vec<Run>` or pre-partitioned by class), **or** add an M1 `SpanSet` partition/iterate surface. This contradicts the design's own Conflict-1 logic (co-locate coverage ops with M5) — the chosen "M6 owns the level-class discipline HERE" is the unbuildable branch.

**2. [DEFECT] COMPARE `overlap_pair` computes the second foot's V-position with the wrong block's I-start — unsound output.** 
```rust
d2: qb.doc.clone(), u2: vpos_shift(&qb.v_start, &ordinal_gap(&lo, &pb.i_start)),
```
`u2` must offset `qb.v_start` by `lo ⊖ qb.i_start` (lo's position *within the Q-block*), not `lo ⊖ pb.i_start`. Whenever `pb.i_start ≠ qb.i_start` — i.e. the normal cross-document case where `lo = max(pb.i_start, qb.i_start)` is one operand's start — the reported `u2` is shifted by the inter-block gap, so `res_Σ(d2, u2) ≠ a`. That violates X12 **R1 (soundness)**: the listed pair is no longer a correspondence. Change to `&ordinal_gap(&lo, &qb.i_start)`.

**3. [DEFECT] SHOWORIGIN_I is a chartered M6 operation left undeliverable.** The decomposition assigns SHOWORIGIN (ASN-0077) to M6 and the Provenance-R note explicitly places *both* the I-span and V-span resolvers here. The design correctly diagnoses that `origins_I(σ) = {document_of(a) : a ∈ ⟦σ⟧ ∩ dom(C)}` needs an I-interval enumeration over `dom(C)` that M4 (point-only, `Ord` deliberately unused) and M3 (point-only `is_allocated`) genuinely don't expose — but it then ships `Err(ISpanIndexUnavailable)` and files the operation under "Open build decisions." Delivering a chartered operation is not a builder's discretionary choice. This needs a ruling, not a stub: either commit to adding the M4 recomputable I-ordered content index seam (`allocated_content_in(span)`) the design already sketches — and then build the boundary-walk body — **or** formally de-scope the I-arity out of M6's mandate (amend the decomposition). As written, M6 under-delivers an owned capability.

**4. [DEFECT] `SpanSet::from_normalized_ordered(members)` and `SpanSet::is_empty()` are invented M1 APIs.** Neither exists on M1's `SpanSet` (and M6 can't add inherent methods to a foreign type). Both are trivially expressible with the real surface, so rewrite against it: build the ≤2-member extent set in `doc_vspanset` via `union(&SpanSet::singleton(content), &SpanSet::singleton(link))` (concatenation preserves the already-disjoint-ordered W13 normal form); test the FINDDOCSCONTAINING filter as `m5.project(d, &coverage) == SpanSet::empty()` (derived `PartialEq`) rather than `.is_empty()`. Low severity, but as written each is a factually-false call against the upstream interface.

**5. [SHARPENING] State that ordinal-level is a *forced* narrowing of the source-note preconditions, driven by M5's `resolve`.** `gate_vspec` requires ordinal-level for all three resolve-based ops, but ASN-0077 WF_V(iv) only requires `actionPoint(ℓ) ≤ #u` and ASN-0122 X12 only requires T12-well-formed + content-start. The narrowing is sound (M5's `resolve` accepts only `#start==2 ∧ #width==2 ∧ width.get(1)==0`, so a non-ordinal-level span resolves to ⟨⟩ upstream regardless, and the same selection is expressible ordinally), but it should be recorded in *Conflicts resolved* as a deliberate, upstream-forced restriction rather than left implicit.

**6. [SHARPENING] SHOWORIGIN_V's unbound-range check hard-codes depth 2.** `&resolved < span.width().get(2)` reads the nominal count at the fixed index 2; since `gate_vspec` admits `#start ≥ 2` (not `== 2`), a depth-3 span slips through the gate and then returns `Ok([])` instead of rejecting (the count read lands on a `0`). Use `ordinal(span.width())` (depth-agnostic last component) for the count, or tighten `gate_vspec`/`show_origin_v` to `#start == 2`. (Unreal in the depth-2 model, hence non-load-bearing, but it removes a latent inconsistency between the gate and the count read.)

**7. [SHARPENING] Clarify COMPARE's canonicalization claim.** The design says `canonicalize` produces "maximal runs (X11)," but its stated merge criterion ("both feet advance by one, *addresses contiguous*") will not reach X11-maximal when a correspondence runs over a non-contiguous address sequence (X10(c) permits any `a_k`). That's fine for conformance — X12 R4 (maximal form) is explicitly *not required*; R1–R3 admit finer-than-maximal presentations — so either drop the "maximal/X11" claim and state the report only satisfies R1–R3, or merge on feet-succ-adjacency (successor pair also a correspondence) rather than address contiguity if maximal is actually wanted.

**8. [SHARPENING] Define `S_C`/`S_L`.** They're used throughout (`sub == S_C`, `vpos(S_C, …)`) but never defined; since `Nat = BigUint` they can't be `const` — provide them as `Nat`-returning helpers (or `1u8.into()`/`2u8.into()` at the call sites).

**9. [SHARPENING] Confirm the SpanSet-coverage SHOWDELETIONS output is acceptable.** `Deletions { a_with_b: SpanSet, … }` is a lossless re-encoding of ASN-0075's `dom(C)` address sets, but because M5 returns `deletions` as a `SpanSet` and M1 offers no SpanSet enumeration, no downstream consumer can recover the individual I-addresses that D-IDENT ("the returned reference is precisely the I-address `a`") and D-ORD speak of. This is inherited from the M5/M1 surfaces, not M6's fault, but the restore consumer's reliance on coverage-only output should be confirmed (or an enumeration seam requested).

VERDICT: REVISE
