I checked the seven operations against the M1–M5 interfaces and the source notes (ASN-0115/0112/0113/0077/0075/0122/0124). Most of the design holds up well — the COMPARE interval-join with its co-chain totality argument, the SHOWDELETIONS membership-test combine, the extent synthesis from counts, and the SHOWORIGIN_I de-scope are all sound and faithfully built against the upstream interfaces as given. One faithfulness defect, plus several sharpenings.

## Revision list

**1. [DEFECT] `gate_vspec`'s depth-2 rejection (`StartNotDepth2`) breaks R6 for RETRIEVEV and X12-totality for COMPARE — it treats depth-*compatibility* as well-formedness.** ASN-0115 defines VSpec well-formedness as `zeros(s)=0 ∧ #s≥2 ∧ (∀i: sᵢ>0)` (so a `#s≥3` start is *well-formed*) and states **explicitly**: *"Depth compatibility is a consulting-state predicate, **not** a well-formedness condition."* R6 (SilentGapFiltering) then mandates that a depth-incompatible spec yields `act=∅` and *"delivery succeeds … without failure."* In the `m_S≡2` model, depth-incompatibility is exactly `#s≥3`. The design instead rejects every `#s≠2` start as `MalformedSpec(StartNotDepth2)` — a whole-request rejection — so a multi-spec request containing one `#s≥3` spec fails outright instead of delivering the valid specs and `∅` for the incompatible one. This directly contradicts R6/R3 and the note's explicit "not a well-formedness condition" commitment, and it self-contradicts: `retrieve_v`'s own doc comment claims *"depth-incompat … degrade to silent empty contributions, never an error (R6)."* The same over-rejection hits COMPARE: a depth-3 T12-well-formed content span has empty region (`R_Σ(ρ)=∅`, no depth-2 positions), which X12 reports as success-with-empty, but the design rejects the whole request.
   **Fix:** in `gate_vspec`, relax the depth check to reject only `#s < 2` (genuine `#s≥2` violation), and let `#s≥3` pass — M5's `resolve` already returns `⟨⟩` for non-depth-2 spans, giving RETRIEVEV the R6 silent-empty contribution and COMPARE the empty region. Keep the `NotOrdinalLevel`/`NotLevelUniform`/`StartNotZeroFree` checks (those *are* genuine ASN-0115 VSpec well-formedness, so rejecting is faithful for RETRIEVEV). SHOWORIGIN_V's depth-2 requirement is correct (ASN-0077 WF_V(v) makes the common depth a precondition); under the relaxed gate a `#s≥3` SHOWORIGIN_V still rejects via the existing `resolved < ordinal(width)` ⇒ `RangeNotPresent` path, which is the correct outcome there. (Note for the reviser: the COMPARE `ordinal-level`/`level-uniform` narrowing *beyond* X12's T12-only precondition is acceptable as recorded in *Conflicts resolved 8* — every query is expressible ordinal-level; only the **depth** narrowing is the over-reach.)

**2. [SHARPENING] `find_docs_containing` applies no well-formedness gate, so a non-ordinal-level depth-2 *content* region span silently under-resolves.** `resolve_coverage` inherits `resolve`'s `#width.get(1)==0` restriction and returns `⟨⟩` for e.g. `[s_C,3]` width `[1,0]`, whose FD `image_C` is the non-empty `[s_C,3..n_C]`. That silently drops containers (FD-COMPLETE incompleteness, relative to the intended `I=resolve(Q)`), and is inconsistent with the design's own "typed rejection over silent empty" principle used everywhere else. The design's no-gate rationale only justifies *subspace* inertness (link spans stay inert against the content-only `docs_containing`/`project`), not the ordinal-level under-resolution. Apply `gate_vspec` to each region span (it checks well-formedness, *not* subspace — link spans `[s_L,·]` still pass and stay inert), or document an explicit "region spans must be ordinal-level depth-2" precondition.

**3. [SHARPENING] COMPARE's `MalformedSpan { index }` is ambiguous across operands.** `rho1.iter().chain(rho2).enumerate()` produces a combined offset, so `index: 5` cannot be resolved to `rho1[5]` vs `rho2[5−len(rho1)]`. Carry an operand discriminator (or per-operand index) so M10 can surface a precise typed rejection.

**4. [SHARPENING] The SHOWDELETIONS `denotes`-exactness justification is imprecise.** The text rests exactness on content-address prefix-freeness (which rules out *subtree* phantoms only). The actual guarantee against *interval* phantoms is that `deletions(d)` covers are confined to one origin's content chain — foreign-origin addresses cannot fall inside a chain-pinned interval, native-chain placements are contiguous by J0/J1★, and `merge` only coalesces consecutive same-chain (hence placed) addresses. The conclusion holds; state the chain-confinement reason, or lean on the already-documented `ever_placed`-based fallback as the v1 default.

**5. [SHARPENING] SHOWORIGIN_V maps a foreign start subspace (∉ {s_C, s_L}) to `EmptySubspace`.** Semantically `V_S(d)=∅` so it is WF_V(iii)-defensible, but a `NoSuchSubspace` distinction (or a one-line note that foreign subspaces fold into `EmptySubspace` deliberately) would prevent a builder reading it as "the named real subspace is empty."

VERDICT: REVISE
