Reviewing M3 against buildability, upstream fidelity, source-note faithfulness, boundary discipline, conflict resolution, altitude, and internal consistency. I traced the allocator's `decompose`/`next_in` round-trip, the `(parent, g)` keying for the version/document separation, the ω resolver, and the delegation gate against ASN-0040/0042/0047/0093/0103/0123 and the M1/M2 interfaces. The allocator core (level-aware frontier, `shift`-based `cₘ₊₁`, content/link/version/document namespace separation, subspace-identifier discipline) is correct and faithful. Three defects remain.

## Revision list

**1. [DEFECT] `delegate`'s tier gate admits internal node minting — violating ASN-0047 NodeBaptism and the design's own node-provenance guarantee.** Condition (iii) is stated as `zeros(new_prefix) ≤ 1` (verbatim O15(iii)), and §6 claims "(i)+(iii) force [an account]." That is false. A **node-tier** delegator (the bootstrap `[1]`) supplying `new_prefix = [1,1]` passes every condition: (i) `[1] ≺ [1,1]`; (ii) `ω([1,1]) = bootstrap`; (iii) `zeros=0 ≤ 1`; (iv) none below; (v) `[1,1] ∉ nodes`; id-fresh; parent-reg `entity_level([1]) = Some(Node)`; and next-form, since `next_in(namespace([1,1])) = next_in(([1],1)) = inc([1],1) = [1,1]`. The gate therefore **mints a child node `[1,1]` and registers a principal there** — but ASN-0047 NodeBaptism states "No docuverse transition mints a node address" (the design's own `register_node` comment says "provisioning mints node addresses OUTSIDE the docuverse"), and this contradicts the design's claim that "nodes arrive only via register_node." Fix: tighten (iii) to `zeros(new_prefix) == 1` strictly (a node-tier delegate ⇒ `NotAccountTier`); state the resolution explicitly as a narrowing of O15(iii) `≤1`→`==1` (and a suppression of ASN-0040's `baptize(node,1)` child-node capability) forced by NodeBaptism. Also correct the inaccurate claim "ASN-0040 ... has no node-admission mechanism" (`baptize(node,1)` *does* admit child nodes), and note the consequence: node principals beyond bootstrap become uncreatable (delegation is account-tier only), so all provisioned nodes are bootstrap-owned via ω unless an account is delegated beneath them — flag in Open decisions if per-node principals are wanted.

**2. [DEFECT] The M5→M3 VERSION seam is internally contradictory — M5 cannot build VERSION from it.** The seam says (a) "M5 takes that key from the matching `*_lock_key` constructor for transact's `keys` arg **before** the closure" *and* (b) for the cross-owner branch "M5 reads `effective_owner(d_src)` **inside** its VERSION closure ... **never a pre-transaction snapshot read**." But the *matching* namespace lock is branch-dependent — `version_lock_key(d_src)` (owned) vs `document_lock_key(pfx(forker))` (cross-owner) — and the branch *is* `ω(d_src)`. M5 cannot pick the matching key before the closure while forbidden from reading ω before the closure. Resolution: `ω(d_src)` is provably **stable** for an existing `d_src` — its account, hence the account's principal, is fixed, and no principal prefix `≼ d_src` longer than the account can ever be created (the account is already allocated, so `!is_allocated` blocks re-delegation there, and accounts/principals are co-created by `delegate`). So M5 may safely **pre-read** `ω(d_src)` off a snapshot, resolve the branch, and hold the single matching namespace lock (the design already pre-reads stable values — see `fork` reading `principal_prefix(caller)` pre-transaction). Relatedly, correct §6/§8/Invariants: `principals_lock_key()` + in-closure-ω is **harmless-redundant, not load-bearing**, for `create_new_document` and M5-VERSION (the "a concurrent sub-account delegation can move `ω(account)`/`ω(d_src)`" justification is false — sub-accounts sit *below* the account and never cover it); `principals_lock` is genuinely load-bearing only for `delegate`, where `new_prefix` is *fresh* and the id-freshness / top-down / next-form reads race against concurrent same-target delegations. (Alternative resolution: keep the in-closure read and have M5 hold *both* candidate namespace locks — but that is unnecessary given stability; recommend the pre-read.)

**3. [DEFECT] The B-section transact-driving ops cannot stage their deltas — `stg.push(M3Rec)` doesn't typecheck.** `create_new_document`/`delegate`/`register_node`/`fork` are `impl<W: WorldState + HasM3> Namespace<W>` and "stage `M3Rec`," but `Staging<W>::push` takes `W::Record`, and `HasM3` exposes only `m3() -> &M3State` (a read accessor). The design's claim that M3 "codes against this contract [HasM3], not against W directly" is therefore false for the write path: there is no `M3Rec → W::Record` lift. Specify it — e.g. bound the impl `where W::Record: From<M3Rec>` and push via `stg.push(rec.into())`, or extend the engine accessor trait with a record-lift method — symmetric to the read-side `m3()` already provided. (The `apply`-dispatch side is engine-wired and fine; this is only the B-ops' write path.)

**4. [SHARPENING] B-section ops discard the committed `Seq`.** `transact` returns `(T, Seq)`; `create_new_document`/`delegate`/`register_node`/`fork` return `Result<Address, TxnError<…>>`, dropping the `last_seq`. M2's seam notes M10 "may report `last_seq`" as the operation's linearization coordinate. Return `(Address, Seq)` (or a small result struct) so M10 can surface the linearization point uniformly across M3-driven and store-driven ops; the commit-before-ack guarantee itself is unaffected (the `Ok` return is already post-commit).

**5. [SHARPENING] The `LockKey` in each `mint_*` return triple is unusable by the caller for locking.** M5/M7 must pass the namespace key to `transact` *before* the closure (from `content_lock_key(d)` etc.), but the mint runs *inside* the closure, so its returned `LockKey` arrives too late to lock with — its only use is an in-closure `assert_eq!` against the pre-closure key. Either document it explicitly as a byte-identity assertion/debug aid, or drop it from the return and let callers obtain the key solely from the `*_lock_key` constructors (which §1 already guarantees are byte-identical to the advanced frontier key).

VERDICT: REVISE
