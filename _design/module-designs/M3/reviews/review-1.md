I reviewed M3 against the decomposition, the two upstream interfaces (M1, M2), and all seven source notes (ASN‑0040/0093/0047/0034/0042/0103/0123). The allocator (`Chain`), the registry/admission model, genesis, `register_node`, and the `ω` longest‑match algorithm are mostly sound and faithfully traced. Two material problems block a clean build, plus several worthwhile sharpenings.

## Revision list

**1. [DEFECT] `create_document` authorizes with `owns` (containment), not `ω` (effective ownership) — it reproduces the very ownership‑divergence the design forbids.** §B and §2 both state the precondition as `owns(by, account)` = `is_prefix(by, account)`. But §3 itself says "Authorization over a possibly‑delegated region uses `ω`; containment is sound only within a principal's own *undelegated* subtree," and conflict‑resolution #6 says "authorization over possibly‑delegated regions uses `ω`, never containment." An `account` can be delegated. With the containment check, a node operator `by=[1]` passes `owns([1],[1,0,2])` and can baptize a document in a *delegate's* account `[1,0,2]` — `allocated_by([1], d)` with `ω(d)=`the delegate, violating ASN‑0042 **O5** (allocator must be the longest‑prefix coverer), O2/O3/O8, and the `ownership-divergence` finding. ASN‑0103's literal `pfx(π)≼A` (CND.pre) is the *pre‑delegation* form; ASN‑0103 explicitly defers delegation, so the integrated module must sharpen it. **Fix:** change the precondition to `effective_owner(ns, account) == Some(*by)` (equivalently, the O5 most‑specific‑coverer test), enforced server‑side (per ASN‑0123's "treat the claimed account as untrusted"); update §2, §B, the invariants list (add an "authorization uses `ω`" entry covering `create_document`), and conflict‑resolution #1/#6 to state the resolution. `fork`/`delegate`/`alloc_version_identity` are unaffected (they allocate strictly under `by`, so `by=ω` holds), but verify `fork` once the check is `ω`.

**2. [DEFECT] `Chain::next`'s signature can't run its own body and matches none of the Open‑decision options.** §A declares `next<'a>(&self, members: impl DoubleEndedIterator<Item=&'a Tumbler>) -> Address`, but §1's body calls `members.range(span)…` — `DoubleEndedIterator` has no `range`. A bare iterator forces an O(n)‑over‑all‑members `filter+max`, contradicting the data‑model claim that "ordered keys give the rightmost‑descent frontier max in O(log n)." It must also serve both `entities: OrdSet<Tumbler>` *and* content/link `OrdMap<Tumbler,V>`, which share no `range` trait; the three Open‑decision resolutions (generic `OrdMap` / `ChainView` trait / caller‑extracts‑max) each imply a *different* signature, none of them `DoubleEndedIterator`. **Fix:** commit one rangeable abstraction — a `ChainView` trait exposing `range(&self, &Span) -> impl DoubleEndedIterator<Item=&Tumbler>` implemented for both `OrdSet<Tumbler>` and `OrdMap<Tumbler,V>`‑keys (recommended) — and align `alloc_content_address`/`alloc_link_address` and the entity callers to it. Also state the `span → start..reach` conversion the body elides.

**3. [SHARPENING] Make `fork`'s account‑tier scope explicit (or implement O10's node case).** `fork ≡ create_document(by's account, by)` only yields a document and, for a node‑tier `by`, hits `CreateDocErr::NotAnAccount`. O10 specifies `zeros(a')=zeros(pfx(π))+1` for *any* principal (a node's fork is an account, via `next(pfx,2)`). Either restrict `fork`'s signature/precondition to account‑tier principals and say so, or branch node‑tier `by` to `Chain` with g=2 from the node.

**4. [SHARPENING] Specify where `frontier_key` gets its central space‑tag.** §A's `frontier_key(home, mode) -> LockKey` returns a complete key "from the central tag enum," but M2 mandates the 1‑byte tag come from the engine crate's single central enum (above M3), and the signature has no tag input — risking the per‑store collision M2 warns of. Not a v1 blocker (keys are subsumed by the single applier), but for the per‑key realization either thread the engine‑owned tag in (param/const via `HasNamespace`) or have `frontier_key` return a tag‑less body the engine completes.

**5. [SHARPENING] State which `ChainMode` the sub‑account chain uses.** `ChainMode` lacks a `Subaccount` variant; the subaccount chain `(acct,1)` and document chain `(acct,2)` coexist under one account‑home and must key distinctly. Mapping subaccount→`ChainMode::Account` is collision‑free (no home is both node and account), but say so explicitly.

**6. [SHARPENING] Spell out the EntityKind/derivation rule and its V9 caveat.** "kind is derivable from the address (classify + document_field length)" understates it: `classify` returns `Document` for both base documents and versions; Version requires `document_field` length ≥ 2. Note that a *cross‑owner* version (allocated as a document in the forker's account) derives as `Document`, length 1 — which is correct per V9 (state‑indistinguishable) but should be flagged, and clarify that the `kind` carried in `RegisterEntity` is advisory (apply stores membership only).

**7. [SHARPENING] Reconcile `DelegateErr`.** The interface comment says "(iii),(v) checked," but §3 and the body treat (v) fresh‑valid as holding by construction (frontier + `checked_inc`) — and there is no error variant for a (v) failure. Either mark (v) by‑construction (matching the body) or add the variant.

**8. [SHARPENING] Pin the version‑allocation seam M5 codes against.** Clarify that `alloc_version_identity` assumes `src` registered (M5 discharges P8 via its `is_registered(src)` precondition; `SourceNotDocument` is the class check), and that the version's frontier *key* differs by branch (`frontier_key(src, Version)` owned vs `frontier_key(by, Document)` cross‑owner) — so for the per‑key realization M5 must resolve owned‑vs‑cross‑owner (an `ω(src)` test) before opening its `transact`; consider exposing a `version_frontier_key(ns, src, by)` helper.

VERDICT: REVISE
