# Review of M3 — Namespace: Allocation, Registry & Ownership

I traced the centerpiece allocator on the worked examples (correct), verified the ω-gate's divergence-prevention against ASN-0042 O2/O5 (correct and a genuine improvement over ASN-0103's containment precondition), confirmed the lazy-arrangement boundary against the decomposition's M3→M5 cycle-break, and checked the frame/permanence discipline and M2/M1 call fidelity. The core is largely sound. The defects below are real and require revision.

## Revision list

**1. [DEFECT] — Delegation is silently restricted to node→account, justified by a *false* claim about O1a; account-tier sub-delegation that ASN-0042 permits is dropped.** `create_account`'s gate is `caller ∈ Π ∧ Node(caller)`, justified as "(tier floor O1a forces node→account)" (§B), and §3 restates "the tier floor makes account→account ancestry impossible." **Both claims are factually false about the source note.** O1a is `zeros(pfx(π)) ≤ 1` — it *bounds* principal prefixes to node/account tier; it does not forbid account→account delegation. ASN-0042's O15/DelegationPredicate admits a delegate `π'` with `zeros(pfx(π')) ≤ 1` and `pfx(π) ≺ pfx(π')`; an account-tier delegator (zeros=1) can delegate a sub-account via `inc(pfx(π),1)` (e.g. `[1,0,1] → [1,0,1,1]`, zeros=1), satisfying (i)/(iii). ASN-0042's own worked example reaches `[1,0,2,3]` — an account with a multi-component user field — which M3 (single-component user fields only, via node→account g=2) can never register. This drops a delegation capability the decomposition assigns M3. Fix: delete both false claims; then either (a) explicitly scope M3 to node→account as a *stated* decision (deferring account sub-delegation), noting the real obstruction is the allocator limitation in item 2 — *not* O1a; or (b) implement account sub-delegation with a level-filtered allocator (it cannot use `next_in_namespace(E, account, 1)` — see item 2). Note that ω already resolves correctly either way (because `acct(a)` is always registered for any registered `a` — state *that* as the reason the ancestor-walk is sound, replacing the false "account→account impossible" reasoning in §3).

**2. [DEFECT] — `next_in_namespace`'s published contract over-claims "T4-by-construction over ANY ordered address set"; it is false for g=1 over a set containing g=2-descendants of `p`.** The §C doc-comment guarantees "Next address in sibling stream S(p,g) over ANY ordered address set … g ∈ {1,2} … Gap-free, monotone, level-aware, T4-by-construction." Counterexample: with `E ⊇ {[1,0,1], [1,0,1,0,1]}` (account `[1,0,1]` holding document `[1,0,1,0,1]`), `next_in_namespace(&E, &[1,0,1], 1)` computes `inc(truncate([1,0,1,0,1], 4), 0) = inc([1,0,1,0], 0)`; since `sig([1,0,1,0]) = 3`, this returns **`[1,0,2,0]`** — a trailing-zero, T4-*invalid*, and semantically wrong address. Truncate-then-increment is only correct when the truncation point `m[sib_len]` is nonzero (i.e. the max-under-`p` does not pass through a separator at position `#p+1`); for g=1 this fails exactly when the set holds g=2-descendants of `p`. The four current call sites are safe (version g=1 over E has no `[d,0,·]` entities — those are element-level non-entities; content/link g=1 over `dom` are flat siblings; document/account g=2 always truncates onto an ordinal), so the bug is latent — but it is a false guarantee on the centerpiece pure-surface function and the unstated reason account sub-delegation (item 1) cannot reuse it. Fix: state the real precondition on `next_in_namespace` (g=1 requires no g=2-descendant of `p` in `addrs`) and confirm the four supported patterns satisfy it; the §Internal-1 "robust … normalizing it back to the target level" prose should carry the same caveat.

**3. [DEFECT] — The §B op signatures return `Result<…, NsError>`, but `transact` returns `Result<(T, Seq), TxnError<NsError>>`; the pseudocode does not typecheck and contradicts the M10 seam.** `create_document`/`create_account`/`fork_address`/`register_node` are declared `-> Result<…, NsError>`, yet their bodies call `k.transact(…)?`, which yields `TxnError<NsError>` (variants `Rejected`/`Durability(io::Error)`/`Poisoned`). `NsError` has no representation for `Durability`/`Poisoned`, and no `From<TxnError<NsError>> for NsError` is given, so `?` cannot reconcile the types. Worse, the §Dependencies M10 seam states M10 "surfaces `TxnError::Rejected(E)` as a typed rejection … and treats `TxnError::Poisoned` as a halt condition" — which is only possible if M3's ops surface `TxnError<NsError>`. The doc asserts two incompatible things. Fix: change the §B return types to `Result<(Address, Seq), TxnError<NsError>>` (and `register_node` to `Result<Seq, TxnError<NsError>>`), consistent with `transact` and the M10 seam.

**4. [SHARPENING] — Define the load-bearing helper functions used but never specified.** `truncate(t, k)` (used 3× in the centerpiece allocator), `account_prefix(a)`, `node_field_truncations(a)`, and `effective_owner_eq(account, caller)` appear as if they exist. Each is trivial over M1 primitives (`Tumbler::new`/`get`/`len`, `node_field`/`account_field`, `is_prefix`), but the allocator and ω depend on them — add one-line definitions (or note they are local wrappers over M1), and reconcile `effective_owner` being declared a free function in §A yet called as a method (`ns.effective_owner(…)`, `ns.effective_owner_eq(…)`) in §Internal 3/6.

**5. [SHARPENING] — `ns_key`'s `discriminant: u8` conflates M2's mandatory central SpaceTag with the per-namespace mode/subspace.** M2 requires the 1-byte keyspace tag to be drawn from a single central enum to guarantee cross-store uniqueness, but `ns_key(home, discriminant)` is called with raw mode/subspace values (`ns_key(account, 2)`, `ns_key(d, s_C)`) where the central tag belongs. Separate them in the signature (e.g. `ns_key(home, tag: SpaceTag, mode: u8)`); the §Open-decisions note acknowledges the layout is open, but the signature as drawn invites aliasing M3's `(home,mode)` keys with M5/M7's `(doc,subspace)` keys.

**6. [SHARPENING] — `create_document(caller, account)` parameters are forced equal by the ω-gate.** Since `ω(account) = account` (SelfOwnership, O2) for any registered account, the gate `effective_owner(account) == Some(caller)` requires `caller == account`. Either document the "session-is-the-account" requirement explicitly (the node operator is correctly rejected — good) or drop the redundant `account` parameter. Relatedly, specify the `From<T4Error> for NsError` conversion `validate(d)?` needs (or note `validate` cannot fail here — `d` is T4-valid by construction — and map defensively to `GateViolation`), and make explicit the `&Tumbler`→`Address` wrapping that `inc_preserves_t4`/field projections require at the `account_as_address` site.

**7. [SHARPENING] — State `register_node`'s authorization model.** It takes no `caller` and admits any externally-minted node as a principal. This is presumably the trusted NodeBaptism provisioning boundary (M10/operator-gated), but the doc should say so — as written, an unauthenticated entry point that carves new ownership roots out of `n₀`'s subtree reads as an omission rather than the intended trusted boundary.

VERDICT: REVISE
