I reviewed M3 against M1/M2 as given and the six source notes. The allocator core, the count-compressed registry, the ω resolver, and the four conflict resolutions are largely sound and well-reasoned. But three load-bearing problems would mislead or trip a builder, the first two materially.

## Revision list

**1. [DEFECT] Fix the `lock_key` serialization seam — it cannot key the namespaces it must serialize.** The data model correctly puts content, link, and version on *distinct* frontier keys: `(b_C(d),1)`, `(b_L(d),1)`, `(d,1)` (distinct because `b_C(d) ≠ b_L(d) ≠ d`). But the public primitive is `lock_key(home: &Address, g: u8)` with `g ∈ {1,2}` and the inline convention "content: `lock_key(d, /*s_C anchor*/ ..)`". With `home = d`, content `(b_C(d),1)` and version `(d,1)` collapse to the same key (`lock_key(d,1)`) — three g=1 chains under one document cannot get three distinct keys from `g ∈ {1,2}`. The comment's "s_C anchor" is not even a parameter. Consequence: either over-serialization of content vs. version under `d` (loses the B7 concurrency the design claims as the mechanism for "Same-namespace uniqueness"), or — if M5/M7 reconstruct `b_C(d)` themselves at one call site and pass `d` at another — *different* keys for the *same* namespace → concurrent same-namespace mints → address reuse, the one fatal error. (Latent under M2 v1's global applier lock, which masks it until per-key concurrency is enabled — worse, not better.) Fix: have `mint_content`/`mint_link`/`mint_version`/`mint_document` *return* the namespace `LockKey` (computed inside M3 from the true `NsKey`, parent = `b_C(d)`/`b_L(d)`/`d`/`A`) alongside `(Address, M3Rec)`, so M5/M7 never reconstruct anchors and the lock keys mirror the frontier keys exactly. If `lock_key` stays a standalone fn, it must take an `NsKey` (or a chain-kind discriminator), not `(home_doc, g)`.

**2. [DEFECT] `delegate` does not discharge P8 for the new account's parent node — an unresolved ASN‑0042 vs ASN‑0047 conflict.** The 5+2 conditions in §6 never check that `parent(new_prefix) ∈ E`. A node-tier delegator (e.g. π₀ at `[1]`) can pass every condition for `new_prefix = [1.5.0.1]` (ancestry `[1] ≺ [1.5.0.1]`; `ω([1.5.0.1]) = π₀`; account-tier; top-down; fresh; next-form `[1.5.0.1] == next_in(([1.5],2))`) while node `[1.5]` is **not** in `nodes`, baptizing an account whose parent node is not an entity. This violates ASN‑0047 P8 (`parent(e) ∈ E` for non-node `e`) — which the design explicitly lists under "By active enforcement (P8/P6…)". The root cause is an unresolved note conflict: ASN‑0040/0042 permit baptism under an unbaptized parent (B6 does not require `p ∈ B`), whereas ASN‑0047 P8 forbids it; the design commits to P8 but builds `delegate` to the weaker model. Fix: add `entity_level(parent(new_prefix)).is_some()` (i.e. the account's node — or, for sub-account delegation, the delegator's account — is a registered entity) to the gate, with a `ParentNotRegistered` variant; and state this resolution in "Conflicts resolved" (P8 wins for delegated accounts). `mint_document`/`mint_version` already discharge P8 via their `entity_level` checks — `delegate` is the only account-minting path that skips it.

**3. [DEFECT] "Builder may relax `NotNextForm`" is unsound under the chosen counter representation.** §6 annotates next-form with "(builder may relax)" and Open decisions offers "drop the `NotNextForm` check" as a viable option. But with the count-compressed frontier, accepting a non-next supplied prefix (e.g. `[1.0.5]` while the frontier is 1) sets `frontiers[(N,2)] := 5`, after which `is_allocated([1.0.2])` returns `true` for an address that was never baptized — phantom entities, breaking B1/B3 and the entity registry's correctness. Only "*mint* the next slot" is safe, and that contradicts the `delegate(new_prefix)` signature (it would ignore the supplied prefix). Fix: state that next-form is **mandatory** under the counter rep (relaxing it requires switching to an explicit allocated-set), and reconcile the "mint next slot" open option with the API (it implies `delegate` should not take `new_prefix`).

**4. [SHARPENING] Define `with_trailing_ordinal` or use M1's `shift`.** `next_in` calls an undefined `with_trailing_ordinal(&c1, m+1)`. M1 already provides this: `shift(c1, m)` computes `c1 ⊕ δ(m,#c1)` = `cₘ₊₁` for all four namespaces, and is safe here because `c1` is a full address with the ordinal in its last position (not a bare `doc·0·subspace` base). Replace the helper with `shift`, or define it as "rebuild the tumbler with last component `m+1`, then `validate`."

**5. [SHARPENING] Fix `fork`'s scoping rationale and note the dropped O10 case.** §7/Conflicts cite "ASN‑0123 V9's account-tier scoping" to justify `fork` rejecting node-tier callers — but `fork`'s source is ASN‑0042 **O10** (DenialAsFork), which is *not* account-tier-scoped (O10 mints `a'` one tier below `pfx(π)` for any tier; a node-tier π forks to an *account*). State plainly that `fork` implements O10's account-tier (document) case only, that the node-tier case is rerouted through `delegate`, and cite O10 (V9 governs cross-owner VERSION, a different operation). Confirm the node-tier rejection is the typed `NotAnAccount`, not a silent failure.

**6. [SHARPENING] List `effective_owner` in the `M5 → M3` seam.** M5's CREATENEWVERSION must read `ω(d_src)` to choose the owned branch (`mint_version`, namespace `(d_src,1)`) vs. the cross-owner branch (`mint_document(pfx(π))`, namespace `(pfx(π),2)`) per ASN‑0123 V8/V9. The seam list under `M5 → M3` names both mints but omits `effective_owner`, which the branch decision requires.

**7. [SHARPENING] Pin loose details.** Fix `π₀`'s `PrincipalId` to a named constant in `genesis()` (the `ω(account).id == caller` gate depends on it). Spell out `principal_tier_prefixes` (it's described but not given). State the safe default for the open Π-locking question: under per-key concurrency, `create_new_document`/`delegate` must additionally hold the Π/account-chain key, or a concurrent delegation can change `ω(account)` between a stale-base auth check and commit (an O8 hole; harmless only under v1's global lock).

VERDICT: REVISE
