**Review of M3 — Namespace: Allocation, Registry & Ownership**

I checked every shown signature and body against M1/M2's interfaces as given, traced the frontier/membership math against ASN-0040/0093/0123's canonical forms, and audited the delegation/ownership machinery against ASN-0042/0047. The design is very strong — the counter-compressed frontier, the single-sourced `NsKey`→`LockKey` path, the level-aware `(p,g)` keying, the in-closure gate discipline, and the eight conflict resolutions are all sound and concretely buildable. I found one material problem.

**Revision list**

1. **[DEFECT] — `delegate` has a reachable panic on externally supplied input, backed by a factually false safety claim.** §6 states that validate-lifting `new_prefix` "makes `namespace(new_prefix)`/`parent(new_prefix)`/`zeros(new_prefix)` safe to compute," and `decompose`'s doc-comment asserts its `parent(&ad).expect("a decomposed address is never a 1-component node")` cannot fire on "delegate's validated `new_prefix`." Both claims are false: a 1-component tumbler such as `[7]` is T4-valid (a bare node address — M1's `parent` returns `None` exactly for this case), and `delegate` computes `ns_lock_key(namespace(new_prefix))` in its pure pre-work, *before* the in-closure tier check (iii) runs. A builder following the stated order ships a panic — reachable from M10's external command surface via a client-supplied prefix — where the spec promises a typed `NotAccountTier`/`NotValid` rejection. Fix: hoist condition (iii) (`zeros(new_prefix) == 1`, which also guarantees ≥ 3 components) into `delegate`'s pure pre-work, immediately after the validate-lift and before any `namespace()`/lock-key construction (the design's own gate table already marks (iii) as monotone/pure, so hoisting is consistent with the in-closure discipline, which is needed only for the race-prone conditions); alternatively make `decompose`/`namespace` fallible and map the 1-component case to `NotAccountTier`. Correct the two false safety claims either way.

2. **[SHARPENING] — Conflicts §6's "load-bearing reason" for dropping node-tier `fork` overclaims.** The ω-stability of an existing account (and hence `create_new_document`'s ω-gate soundness) follows from delegation freshness (v) plus O1a alone: every `zeros ≤ 1` prefix of a registered account is already baptized (its user-field prefix chain is registered by the delegation induction, its node ancestors by P8), so no concurrent delegation can introduce a new coverer — independent of the "every registered account carries its own account principal" invariant. A hypothetical principal-less, node-owned account would still authorize correctly (`ω(account)` resolves to the node principal, and `p.id == caller` then correctly admits exactly that principal — which is O10's intent). Restate the drop as a deliberate API-scoping decision, and soften the Open-decisions line claiming re-admission "requires relaxing the invariant that ω-authorization leans on" — it doesn't.

3. **[SHARPENING] — Minor Rust-level fixes in the shown bodies so they compile as written:** `Nat::one() <= *ordinal(a.tumbler())` moves out of a shared `&Nat` (`BigUint` is not `Copy`) — compare by reference; `m.is_zero()` needs `num_traits::Zero` in scope; `apply_ns` and `genesis` must be `pub` for the engine crate to wire `World::apply` and the `open(cfg, genesis)` seed; and `Namespace<W>` is described only inside a comment — add its one-line declaration (`pub struct Namespace<W: WorldState> { kernel: Arc<Kernel<W>> }`).

4. **[SHARPENING] — Put the misuse warning on `owns` itself.** The "authorization must use ω, never bare `owns`" discipline (the ownership-divergence trap) lives in §5 prose and the Invariants table, but `owns` is the one public API a hurried consumer will reach for; add a doc-comment at the signature ("containment test, O1 — never an authorization check; use `effective_owner`").

The remaining deliberate deviations — three `Space` tags instead of one, M3-owned `ns_lock_key` superseding the base-crate `key(home,…)` sketch, the O15(iii) narrowing, the suppressed `baptize(node,1)`, the (A,1) sixth chain family, mint-vs-validate, lazy arrangement, ω-over-`owns` — are all explicitly argued conflict resolutions with sound reasoning and documented escape hatches, and I verified each against the notes; none is a defect.

VERDICT: REVISE
