## Review of M3 — Namespace: Allocation, Registry & Ownership

This is a strong, careful design. The frontier allocator (the `(parent, g)` keying, the `shift`-from-gated-`c₁` trick, the count-compressed registry), the entity/`is_allocated` membership via `decompose`, and the ω resolver all typecheck against M1 and are faithful to ASN-0040/0042/0093/0123. The conflict resolutions (mint-not-validate, M3-owns-content-frontier, lazy-arrangement, ω-not-`owns`, P8-for-delegated-accounts) are sound and well-argued. I verified the four namespaces (`content`/`link`/`version`/`document`) never collide, that `decompose` recovers each correctly, that `shift` is safe in all four (operand always carries its ordinal in the trailing position), and that document↔version separation holds at *query* time too. One material problem, plus sharpenings.

### Revision list

1. **[DEFECT] The non-monotone gates in `delegate`, `create_new_document`, and cross-owner VERSION must be evaluated *inside* the `transact` closure against `stg.base()/working().m3()`, not on a pre-transaction `snapshot()`.** §6 says delegate "runs O15's five conditions plus id-freshness plus P8 plus next-form **against the snapshot**, and — in one transaction — baptizes … and registers," and the interface comment says "pre-checks read `snapshot()`, the closure mints off `working()`." Taken literally this is racy, and it directly contradicts §8's claim that the held `principals_lock_key()`/namespace lock "serializes the ω-reader and ω-mutator" — a lock only serializes reads performed *within* the locked region, and the pre-check runs **before** `transact` acquires any lock. Concrete harm even under M2 v1's global applier lock: two concurrent `delegate` calls to the same node both pre-check `next-form`/`fresh`/`id-fresh` on a stale snapshot, both pass, then commit in turn — `apply(RegisterPrincipal{[N.0.1], id_B})` **overwrites** principal A at the same prefix and the same address is handed to two principals (an O1b/O13 violation and exactly the "one fatal error," address reuse). Fix: move the authoritative gate evaluation into the closure under the already-held locks — for `delegate` the non-monotone conditions are authorization (ii), top-down (iv), fresh-valid (v), id-fresh, and next-form (only ancestry (i)/account-tier (iii)/parent-reg P8 are stale-safe); for `create_new_document`/fork and M5's cross-owner VERSION the `effective_owner(account).id == caller` branch must likewise be re-read in-closure (ω(account) *can* change via a concurrent intermediate sub-account delegation). State that the pre-snapshot read is at most a fail-fast, and correct the §6 / interface wording.

2. **[SHARPENING] Name the `W → &M3State` accessor as an explicit trait bound.** The design references `W::m3()` pervasively and bounds `Namespace<W>` on "`W: WorldState`, with `W::m3() -> &M3State`," but never declares the trait that supplies it. Since M3 is built before the engine `W` exists (topological order), give it a concrete bound (e.g. `trait HasM3 { fn m3(&self) -> &M3State; }`, with `Namespace<W: WorldState + HasM3>`), so M3's generic ops and the `snapshot.world().m3()` / `stg.working().m3()` call sites compile against a named contract rather than an implied one.

3. **[SHARPENING] `delegate`'s caller cannot obtain a valid `new_prefix` from M3's public surface.** Next-form is mandatory (§6), but `next_in(namespace(new_prefix))` reads M3's private `frontiers`; M3 exposes no "next account slot" query, so M10 can only guess-and-retry-on-`NotNextForm` (workable, since a single authority owns each account chain and can track its own count, but fragile). Either expose a `next_account_prefix(node_or_account) -> Address` peek, or commit to Open-decision option (b) (drop `new_prefix`, mint by construction). This is flagged as Open, so it isn't blocking — but the current signature is awkward to call correctly.

4. **[SHARPENING] Reconcile the `is_allocated` link-branch consumer.** §2 states `is_allocated` is "the content/link referential-integrity oracle M5 (COPY) **and M7** depend on," but the M7 → M3 seam lists only `mint_link` + `is_registered_document`. Either name M7's `is_allocated` call site or drop the M7 claim (the uniform Element branch is free either way; this is just a stale cross-reference).

5. **[SHARPENING] `document_of` is listed as an M1 dependency with no call site.** The Dependencies section cites `document_of`, but `decompose`/`entity_level`/`is_allocated` all use `parent` instead. Either cite the actual site or drop it from the M1-calls list.

6. **[SHARPENING] `next_in`'s `expect("registered parents are T4-valid")` message is imprecise for content/link.** For `mint_content`/`mint_link` the `NsKey.parent` is the *anchor* `b_C(d)`/`b_L(d)` (`#E = 1`), which is T4-valid but **not** a registered entity. The `validate` succeeds on T4-validity alone, so the assertion is sound — reword the panic message to "namespace parents are T4-valid by construction" to avoid implying the anchor is registered.

VERDICT: REVISE
