I checked the load-bearing algorithms by hand: `next_in` (closed-form `c_{m+1}` via `checked_inc`+`shift`), `decompose`/`namespace` (and proved that for any T4-valid `a`, `a` is *uniquely* the ordinal-th member of its decomposed `(parent,g)` namespace, so `entity_level`/`is_allocated` have no false positives), `effective_owner` (O(depth) longest-first, with the account-tier > node-tier length argument), and the `delegate` gate (O15 five conditions + id-fresh + P8 + next-form, in-closure under held locks). ## Revision list

1. **[SHARPENING] Fix the principal-lock rationale: id-freshness is *cross-target*, so the lock must be global; flag the per-subtree open option as unsafe.** §6/§8 say the principals reads "race against concurrent **same-target** delegations," and Open-decisions offers "a finer **per-account-subtree** key" as a live alternative. But id-freshness (`principal_by_id(new_id).is_none()`) races against same-***id*** delegations, which can sit in *different* subtrees: two `delegate`s with different `new_prefix` but the same `new_id` under a per-subtree lock would hold *different* locks, both pass id-freshness off stale `base()`, and both commit `RegisterPrincipal{_, new_id}` → duplicate id (an O1b-mirror violation). The *implemented default* (single global `principals_lock_key()`) is already correct; only the prose and the open-option need fixing — say "same-id (and same-namespace)" and either drop the per-subtree alternative or replace it with a per-***id*** key (`Space::Principals` + `new_id` bytes), which is the only finer granularity that preserves id-freshness.

2. **[SHARPENING] Strengthen the node-tier O10-fork drop rationale.** §6 justifies dropping node-tier `fork` with "an account is the natural home of a principal," which understates it: node-tier fork would register an account with **no account principal** (owned by the node principal only via ω), breaking the implicit "every registered account carries an account principal" invariant that `create_new_document`'s ω-authorization leans on (it assumes `ω(registered_account)` = that account's own principal, never an ancestor). State that as the load-bearing reason; it makes the drop clearly sound rather than a stylistic preference.

3. **[SHARPENING] Reconcile the three-tag use with the composition contract, and place the tags precisely.** The contract says "each store is assigned one tag"; M3 takes three (`Namespace`/`Principals`/`Nodes`). Note explicitly that the contract's *hard* rule is tag **uniqueness** (which three distinct tags satisfy) and that the three M3 variants are defined in **skep-kernel's** central `Space` enum — the design's "the **assembler** must reserve all three" conflates skep-kernel (which owns `Space`) with skep-engine (which assembles `World`/`Record`). Optionally mention sub-tagging under one `Space::M3` as the stricter-conformance alternative.

4. **[SHARPENING] Generalize the `decompose`/`namespace` panic message.** `validate(addr.clone()).expect("minted addresses are T4-valid")` also fires (harmlessly) on `delegate`'s **supplied-and-validated** `new_prefix` via `namespace(new_prefix)`. Reword to "T4-valid by caller contract" so a builder reading the panic site isn't misled into thinking the path is mint-only.

5. **[SHARPENING] Make §1 presentation match the interface, and spell out the three remaining mints.** `content_lock_key`/`link_lock_key`/`version_lock_key`/`document_lock_key` and `principals_lock_key`/`node_lock_key` are listed as `impl M3State` associated functions in the Public interface but written as free `fn` in §1 — show them in the `impl` block. Likewise give the one-line bodies of `mint_link`/`mint_version`/`mint_document` (precondition + `next_in(*_ns(..))`) rather than only the delta-from-`mint_content` description.

6. **[SHARPENING] Record the membership-correctness invariant.** `entity_level`/`is_allocated` are correct because a T4-valid `a` decomposes to a `(parent,g)` for which `a == parent ++ [0]^(g-1) ++ [ordinal]` is *exactly* `c_ordinal` (g determined by whether `a`-minus-last is itself T4-valid). The code relies on this implicitly; stating it as a one-line invariant lets a builder verify the decompose-and-range check is genuinely chain membership, not an approximation.
