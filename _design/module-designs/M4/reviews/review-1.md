## Review: M4 — Content Store (Istream)

I went looking for what breaks a builder, not what reads well. The design is unusually clean — faithful to ASN-0036/0093, disciplined about the M3/M5/M6 boundaries, and the engine-plug surface matches the composition contract's `content`/`ContentWrite`/`HasContent`/`apply_write` names exactly. It correctly re-homes recovery to M2, sides with the overview's "content store is authoritative in its own right" over the decomposition's stale "(a hint)" phrasing, distinguishes `contains` (content-presence) from M3 allocation (ghost elements), and splits S0(b) into the no-modify (by-construction) and no-overwrite (guarded) halves. The `stage_write`-as-sole-constructor (private `ContentWrite` fields) guard is a genuine strength.

But one upstream-fidelity gap blocks a clean build, and it's the one the design itself half-flagged.

### Revision list

1. **[DEFECT] Harden the serde dependency on `Tumbler` from a hedge into a stated, confirmed upstream precondition.** M1's interface *as given* derives only `Clone, PartialEq, Eq, Hash` on `Tumbler` (and `Address`) — serde is absent. M4's `ContentStore { map: im::HashMap<Tumbler, Val, …> }` and `ContentWrite { addr: Tumbler, … }` both `#[derive(Serialize, Deserialize)]`, which requires `Tumbler: Serialize + DeserializeOwned`. So M4 *will not compile* against M1 as given, and M4 cannot fix it locally (orphan rule: both `serde::Serialize` and `Tumbler` are foreign to M4's crate). The design's "M1 designates `Tumbler` 'the storage/journal key,' which implies this, but *if* M1's published derive list genuinely omits serde…" is over-optimistic: prose designation ≠ a derive, and the omission is confirmed. Replace the conditional with a firm requirement: **M4 depends on M1 deriving `Serialize + DeserializeOwned` on `Tumbler`** (which entails enabling `num-bigint`'s `serde` feature so `Nat = BigUint` serializes), as an M1/shared-base-crate obligation. Note plainly that without it no store can journal or checkpoint at all — this is the cross-module precondition M4 surfaces, not an M4-internal choice.

2. **[SHARPENING] Drop `Ord` from M4's stated M1 reliance.** The M1-dependency line lists "`Tumbler` (… `Ord/Eq/Hash` …)", but M4 deliberately chose `im::HashMap` (needs only `Hash + Eq`) precisely to *avoid* needing tumbler order, and uses `Ord` nowhere. State the relied-upon traits as `Eq + Hash` + serde, so a builder doesn't wire an unused `Ord` bound (and so this doesn't read as contradicting Conflict-resolution #3).

3. **[SHARPENING] Re-attribute S7 (StructuralAttribution) out of "By construction."** S7 is an ASN-0036 *theorem* established by the allocation discipline (S7a/S7b/S7d, T4, T10a — M3) and computed by M1's `document_of`; M4 neither establishes nor enforces it. What is genuinely "by construction" in M4 is the *complementary* fact that M4 stores **no** origin/author metadata, so there is no denormalized copy to diverge from the structural origin. List S7 under "Discharged upstream (M3 mint) + projected by M1," with M4's contribution stated as "holds only `address → Val`, no redundant origin field."

4. **[SHARPENING] Name SD (StoreDisjointness, `dom(C) ∩ dom(L) = ∅`, ASN-0093) in the Invariants section.** Its substance is present (Conflict #4 + the L0 discharge), but the named cross-store guarantee isn't listed. Add it under "Discharged upstream / cross-store": M4 upholds its half by storing only content-subspace (`s_C`) addresses it is routed (M5), with M7 the disjoint `L` store; M4 cannot enforce SD alone, and the optional `NotContentAddress` assertion is the only local guard against a mis-routed `s_L` address landing in `dom(C)`.

5. **[SHARPENING] Pin the home of `s_C` and the shared `key(...)` constructor.** M4's lock key `key(document_of(addr), s_C)` must produce *byte-identical* keys to M3's alloc and M5's placement, so `s_C` and the `key` constructor must come from a single shared location below the stores (consistent with the M2 seam examples' `key(d, s_C)` and the composition contract's "shared low-level types in `skep-kernel`/a base crate"). Reference that source explicitly (rather than "the shared SubspaceConventionAxiom constant") so three modules don't each re-spell `1`.

VERDICT: REVISE
