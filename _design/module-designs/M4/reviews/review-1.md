## Revision list

1. **[SHARPENING] Fix the `M1` invariant mis‑citation (two occurrences).** In the by‑construction invariant "**S0(a) domain‑persistence; S1 / M1 growth** (ASN‑0036 S0/S1; ASN‑0093 C0)" and again in the Internal‑design prose ("S0 domain‑persistence, S1/M1 growth fall straight out"), the token "M1" is wrong: ASN‑0093 **M1 is *ArrangementMonotonicity* (`dom(M) ⊆ dom(M')`)** — a *neighbor's* (M5/M3) invariant about the arrangement, not content. The content‑growth invariant is ASN‑0093 **C0**, which the parenthetical already cites correctly. Replace "M1" with "C0" (or drop it). The operative claim and its sources are otherwise correct, so this is a stray label, not a weakened contract — but it should not name another store's invariant inside M4's invariants section.

2. **[SHARPENING] State the reliance on `Tumbler: Serialize + Deserialize`.** The contract (and M2's journaling) require `ContentStore`/`ContentWrite` to be `Serialize/Deserialize`, which requires serde on `Tumbler`. M1's published derive list is only `Clone, PartialEq, Eq, Hash`; serializability is *implied* by M1 designating `Tumbler` "the storage/journal key," but the design should make the dependency explicit (and, if M1 genuinely does not expose serde on `Tumbler`, that is a precondition gap to escalate upstream — no store could journal without it).

3. **[SHARPENING] Pin `Val`'s serde approach.** `#[derive(Serialize, Deserialize)] struct Val(Arc<[u8]>)` will not compile without serde's `rc` feature (and relies on the `Arc<[u8]>` impls). Say so — "serializes as a byte blob" should name the mechanism (enable `rc`, or a manual `&[u8]` ⇄ `Vec<u8>→Arc::from` round‑trip) so the derive is unambiguous to a builder.

4. **[SHARPENING] Soften the per‑key‑concurrency claim.** "Distinct documents' content writes … may proceed concurrently under M2's per‑key model" describes a capability M2 lists as **deferred** (its boundary: per‑key‑concurrent realizations deferred; v1 serializes under the global applier lock, signatures invariant). Reframe as: distinct keys *delimit independent serialization scopes* (the invariant seam); actual concurrent execution is M2's later realization. M4's correctness doesn't hinge on it anyway (write‑once ⇒ no content write‑write conflict ever), which the design already says.

5. **[SHARPENING] Handle `document_of(addr) == None` in standalone `write`.** Deriving `key(document_of(addr), s_C)` uses an `Option<Address>`; `?` on it doesn't fit a `Result<_, TxnError<ContentError>>`. For a content address (zeros = 3) it's always `Some`, so either map the `None` to a `ContentError`/`NotContentAddress` or use a documented `expect` on the trusted address — a one‑line gap, but it should be shown for the test‑only op.

6. **[SHARPENING] Add C‑fin to the by‑construction invariants.** ASN‑0093 C‑fin (`|dom(C)| < ∞`) is trivially maintained (finite commits, no growth path to infinity) but is a content‑store invariant and belongs in the by‑construction list for completeness alongside S0/S1/S4/S5.

7. **[SHARPENING] (optional) `value_at` return type.** `Option<&Val>` ties the borrow to the pinning `Snapshot` (correctly noted). Since `Val` is `Arc<[u8]>` with O(1) clone, returning `Val`/`Option<Val>` would decouple the value's lifetime from the snapshot for callers like M6 — a minor ergonomics call worth recording as an Open build decision rather than left implicit.
