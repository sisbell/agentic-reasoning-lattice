## Review: M4 — Content Store (Istream)

I went looking for unbuildable components, invented upstream calls, dropped note-contracts, holes/overreach, and internal inconsistency. I found none that are load-bearing. The design is unusually disciplined: every owned capability has a concrete signature and algorithm; the engine-plug names match the composition contract exactly (`ContentStore`/`ContentWrite`/`HasContent::content`/`apply_write`/`Record::Content`); the two composable forms (`stage_write` pure + `write` standalone) are both present and typecheck against M2's `transact`/`Staging`/`Snapshot` and the `From<XRec>` lifting rule; and the note contracts are honored and correctly *partitioned* (S0(b) split into "no-modify-op-exists" + actively-guarded "no-overwrite"; S3 sited at `contains`=`dom(C)` exactly where the formal statement puts it; S4/S5/S7 by-construction-or-omission; K.α reduced to its storage half `C' = C ∪ {a↦v}`). The conflicts (journal/recovery re-homed to M2, ordered-map rejected because no `M3→M4` edge exists, membership=content-presence vs allocation) are resolved soundly, and the choice of `im::HashMap` is correctly *forced* by the DAG (M3 cannot read M4, so no prefix-scan consumer exists).

One firm cross-module precondition is correctly surfaced and **needs no M4 action**: M4's derives require `Tumbler: Serialize + DeserializeOwned`, which M1 *as given* does not provide (`#[derive(Clone, PartialEq, Eq, Hash)]` only). The design rightly diagnoses this as unfixable in M4 (orphan rule) and escalates it as an M1/shared-base obligation. That is exemplary seam hygiene, not an M4 defect — but the integrator must land the M1 derive before *any* store compiles.

### Revision list (all non-load-bearing)

1. **[SHARPENING]** Split the crate-home claim for `key` vs `s_C`. The `key(home: &Address, …) -> LockKey` constructor needs *both* `Address` (M1) **and** `LockKey` + the space-tag enum (M2), so it must live in a shared base crate depending on *both* `skep-address` and `skep-kernel`. It **cannot** live in `skep-kernel` alone — M2 carries no edge to M1 (stated explicitly in the DAG), so skep-kernel cannot name `Address`. Drop the "(`skep-kernel`, or a shared base crate)" interchangeability for `key`; reserve the skep-kernel option for `s_C` and the tag enum, which name no M1 type. (Buildable either way once the M1+M2 base crate is chosen; this only tightens M4's own composition reasoning.)

2. **[SHARPENING]** Make the standalone `write` body sketch literally typecheck. `document_of(addr)` returns `Option<Address>` and `key` takes a reference, so the sketch should read `key(&document_of(addr).expect("content addr has zeros=3 ⇒ Some"), s_C)`, not `key(document_of(addr), s_C)`. The surrounding prose already specifies the `expect`; align the code with it so a builder copies a compiling line.

3. **[SHARPENING]** Give `FixedHasher` a concrete default alias at the definition site (e.g. `type FixedHasher = std::hash::BuildHasherDefault<FxHasher>;`), so the slice struct `im::HashMap<Tumbler, Val, FixedHasher>` is compile-ready as written, with Open decision 5 governing only a later swap. As it stands, `FixedHasher` is a bare type name the builder must invent before the struct (and its `Default`/`Deserialize` derives, which need `S: Default + BuildHasher`) will build.

VERDICT: CONVERGED
