## Revision list

1. **[DEFECT] Remove the false claim that M1 lacks serde on `Tumbler`/`Address`.** The "Upstream serde precondition" paragraph asserts "M1 *as given* derives only `Clone, PartialEq, Eq, Hash` on Tumbler/Address; serde is absent, so M4's derives **do not compile against M1 today** … a hard obligation on M1 … (M1's 'storage/journal key' designation implies it, but a prose designation is not a derive)." This is **factually wrong against the M1 interface as given**: M1 derives `#[derive(Clone, PartialEq, Eq, Hash, Serialize, Deserialize)]` on *both* `Tumbler` and `Address`, and its overview explicitly states "`Tumbler`, `Address`, `Span`, `SpanSet`, `Level` derive `Serialize + Deserialize` … this requires `num-bigint` built with its `serde` feature." M1 already provides the derive *and* already flags the num‑bigint feature. The claim would mislead a builder into believing M4 cannot compile and into escalating a non‑existent cross‑module obligation. Fix: state that M4 relies on M1's already‑present `Serialize + Deserialize` on `Tumbler` (and the num‑bigint serde feature M1 already requires); delete the "serde is absent / do not compile / hard obligation on M1" language.

2. **[SHARPENING] Flag the genuine, M4‑local serde precondition the design currently omits: `im`'s `serde` feature.** `ContentStore { map: im::HashMap<…> }` derives `Serialize + Deserialize`, which requires the `im` crate built with its `serde` feature (the `im::HashMap` serde impls are feature‑gated). Unlike the phantom M1 issue, this one is real and **M4‑local** (M4 owns the `im` dependency, so it enables the feature itself). The design's serde attention was spent on the false M1 claim while missing this; it belongs alongside the already‑correctly‑flagged serde `rc` feature for `Arc<[u8]>`.

3. **[SHARPENING] Reconcile the M2→M5 seam wording "Each K.α mints from `stg.working().content()`" with M4's (correct) position.** Conflict #3 rightly concludes M4 needs no ordered map because the per‑(d, s_C) content frontier is M3's (read off M3's namespace slice, never M4 — forced by the absent M3→M4 edge and the ghost‑element decoupling). State this once explicitly against the M2 example's phrasing: the "content" frontier read during minting is M3's content sub‑allocator in the namespace slice, **not** M4's value map — so a reader cross‑referencing M2 does not infer that M4 must expose max‑under‑prefix / ordered iteration.

4. **[SHARPENING] Tighten the `s_C` / `key(…)` crate placement to the composition contract's split.** The design says both "live in the single shared base crate below the stores (`skep-kernel`, or a shared base crate)." The contract is more precise: the `s_C` constant (naming only M2 types) lives in `skep-kernel`, while `key(home, …)` (naming both `Address` and `LockKey`) lives in the shared base crate over `skep-address`+`skep-kernel`. Not load‑bearing (the three modules emit byte‑identical keys via the one `key`/`s_C` source either way), but it removes ambiguity in the crate graph.

5. **[SHARPENING] Make `FixedHasher` compile‑ready.** `ContentStore`'s field names `im::HashMap<Tumbler, Val, FixedHasher>` as if `FixedHasher` is defined; only Open decision #5 (which *specific* fixed‑seed hasher) and prose describe it. Add a one‑line `type FixedHasher = …` placeholder or note it must be a `BuildHasher + Default + Clone` the builder supplies — so the struct, its `Default`/`Clone`/`Deserialize` derives, and Open #5 are consistent.
