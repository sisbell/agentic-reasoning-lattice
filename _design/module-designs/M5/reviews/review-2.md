I reviewed M5's detailed design against the decomposition, the engine-composition contract, the source notes (ASN-0036/0058/0082/0084/0116–0119/0123/0047), and the M1–M4 interfaces. The run-list/implicit-position model is a genuinely strong choice that discharges S2/D-SEQ★/D-CTG★/D-MIN★ by construction; the `{source,new}` VERSION record with deterministic in-order replay is correct and clever; the J0/J1★/J-LV coupling at the composite boundary is faithful; upstream calls typecheck against M1–M4 as given; and the engine-plug surface (`HasM5`/`M5Rec`/`apply_m5`, `#[non_exhaustive]` variants, generic-over-`W` ops) complies with the composition contract. There is **one material gap** plus several sharpenings.

## Revision list

**1. [DEFECT] The span-set "never a fault" / "does not fault" claims are false against M1's interface for multi-document (transcluded / cross-node) content; `project`, `SHOWDELETIONS`, `FINDDOCSCONTAINING`, and `docs_containing` can fault with `LevelMismatch`.**
The design repeatedly asserts faultlessness — `project` "never a fault"; SHOWDELETIONS "both operands are now level-uniform element-level spans, so `difference_sets` does not fault"; `content_image` "consumers' set ops normalize per M1's contract." This conflates **element-level (`zeros = 3`)** with **level-compatible**. M1's `intersect`/`difference_sets`/`normalize`/`intersect_sets` require operands of equal endpoint *length* (`#start`) and return `Err(LevelMismatch)` otherwise (mirroring `hull`'s `#min P = #max P` precondition and `from_endpoints`' `#s ≠ #r ⇒ LevelMismatch`). But element addresses vary in length across documents (node/account/document fields are multi-component, so `[1,5,0,1,0,1,0,s_C,k]` and `[1,0,1,0,1,0,s_C,k]` differ in length). Transclusion (COPY) and cross-document link coverage therefore mix lengths into a single operand:
   - `content_image(d)` of a document that transcluded from another document is a mixed-length set → `SHOWDELETIONS = ever_placed(d) difference content_image(d)` faults at `difference_sets`; `FINDDOCSCONTAINING`'s `region ∩ content_image(d)` faults at `intersect_sets`.
   - `project(d, coverage)` intersects `iextent(run)` (length `#content-addr-under-d`) against coverage spans that reference other documents' content (different length) → `intersect` faults. (Note cross-length spans are **not** safely "skip as disjoint" — a length-7 span can contain a length-8 address, so naïve filtering is also wrong.)
   - `docs_containing(coverage)`'s scan over `prov_by_doc` has the same exposure.
   
   A builder following "never a fault" writes `intersect(...).unwrap()`/`difference_sets(...).expect(...)` → production panic on exactly the distributed-transclusion case that is Xanadu's point. **Fix:** specify the handling — partition each operand by endpoint length (level-class), run M1's ops per class and union the results (and for `project`, intersect only within a length-class, using the total `SpanSet::denotes` membership primitive as the fallback for genuinely cross-length containment); delete every "never a fault"/"does not fault" assertion. If single-level content is actually intended, state and *enforce* that restriction instead — but that would forbid transclusion across heterogeneous-depth documents, so it cannot be left implicit. (The internal run-list arithmetic is fine: `shift`/`==` are total, and the I-adjacency coalesce guard correctly never merges cross-length runs since `#shift(a₁,w₁)=#a₁`. The fault is purely at the M5→M6/M8 span-set seam.)

**2. [SHARPENING] Centralize the one correct Run→Span lift; don't make M7 re-derive `iextent`.** M7's MAKELINK consumes `resolve → Vec<Run>` but needs endset coverage as a `SpanSet`, and `iextent` (the *only* admissible lift, per the design's own malformed-`Span(i_start,[0,width])` warning) is M5-private. M7 must replicate `from_endpoints(i_start, shift(i_start, width))` and re-discover the level-uniformity care of the DEFECT above. Expose `resolve_coverage(&self, doc, span) -> SpanSet` (or a public `Run::iextent`) so the correct, length-disciplined lift lives in one place.

**3. [SHARPENING] Make Address-from-`shift` construction consistent.** `point` correctly shows `validate(shift(i_start.tumbler(), offset)).expect("T4-valid by construction")`, but `resolve_range` (("each within-run I-address is `M1::shift(run.i_start, offset)`")) and the `splice_in` boundary split (`Run(a,w) → Run(a,c), Run(shift(a,c), w−c)`) elide it. `Run.i_start: Address` while `shift` yields `Tumbler`, so each needs `validate(...).expect(...)`. State this once for all run synthesis.

**4. [SHARPENING] Note/guard `resolve`'s depth-2 input precondition.** `resolve` indexes `span.start().get(2)` and `span.width().get(2)`; `get` panics out-of-bounds. The global `m = 2` commitment guarantees safety today, but since `resolve` returns `Vec<Run>` (no `Result`) it cannot signal a malformed span — add a one-line precondition ("input is a depth-2 level-uniform V-span") or a defensive empty-return guard.

**5. [SHARPENING] Qualify the VERSION serialization-sharing claim.** "VERSION's fork share survives serialization as shared subtrees until divergence" / "checkpoints structurally shared" overstates `serde`: standard checkpoint serialization does not preserve cross-value `im` structural sharing, so a checkpoint writes two copies (still correct, just not smaller). Clarify that the O(1) share is an in-memory property unless a sharing-aware codec is used.
