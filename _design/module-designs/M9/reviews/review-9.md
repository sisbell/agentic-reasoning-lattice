# Review: M9 — Predicate & Coordination Layer

This design is strong in most of the places that matter — the atom dispatch table is complete and checkable against ASN-0129, the seven stated conflict resolutions are real conflicts resolved soundly, the two-transaction splits (`register_pred`, fire) are analyzed honestly against the notes' atomic reading, and the upstream calls typecheck against M2/M3/M4/M5/M7 as given. The defects below are localized, but three of them would genuinely block or mislead a builder.

**1. Revision list**

1. **[DEFECT] `classify` is view-blind but computes view-relative answers.** The stability rules (§3) are explicitly view-indexed — "M_K *in an audit-view term*" is grow-only, audit `is_K` is ST while active `is_K` is not, and FP's footprints differ per view ("Core atoms of K at view audit: `L_K`; at active: `L_K ∪ L_R`"). But `TypedTerm` carries no view (the design deliberately makes view an evaluation parameter, per PR-VIEW), and `classify(&self, t: &TypedTerm) -> Dynamics` takes none. A builder implementing the PD0 transcription has no way to decide which reading an `Atom::IsK` or `Dom::MembersDom` node is in; `certify_rule` leg (a) needs SF *at the rule's declared view*. Fix: add a `view: View` parameter to `classify` (and state that `Dynamics.footprint`/`stability`/`active_exceptions` are relative to it; `view_independent` stays view-agnostic), or annotate `TypedTerm` with a top-level view — and say which. `certify_stable` is unaffected (view-independent-only), but say so.

2. **[DEFECT] PR-DISC is silently dropped as a hypothesis, and `register_rule` itself can violate it.** The Invariants section claims PR1/PR2/PR-SIG consequences ("Reference DAG acyclic, no cycle check", "Parse/typing/certificate permanence") unconditionally, but those lemmas hold only on registration-disciplined derivations — every `L_pdef`-growing step must be `register_pred`'s deposit branch. Two concrete holes: (a) `FireAction::Marker { ty }` requires only "a cataloged Unary type" — `pdef` and `pd_stable` are cataloged Unary, so a Marker rule can deposit *unvalidated* `pdef` tuples from inside M9; `register_rule` must additionally reject the two PredLayer classes (extend `BadMarkerType` or add a variant). (b) M7's `emit` is reachable by other holders (M10 dispatches §D ops; `emit` rejects only R-class), so raw client emits into `pdef`/`pd_stable` are possible; the design must state PR-DISC as a standing assembly obligation (no writer into `pdef`/`pd_stable` other than M9's `register_pred`/`certify_stable`), and define `signature`/`evaluate_def` behavior on an undisciplined tuple (ever-registered start whose content fails to parse) — today `signature`'s `Option` return has no channel for it, and returning `None` would break the "None is transient, never memoized" rule.

3. **[DEFECT] Rule domains have no checked/expanded carrier, so the evaluator's preconditions are unestablished for them.** `Rule { pub domain: Dom }` stores the raw `Dom`, `RuleRegistry` maps `RuleId → Rule`, and §5 enumerates `[D_ρ]` "via `eval`, §2" — but §2's evaluator requires post-`Reg`-expansion input (no `ClassVar`, `count(Reg)` folded to a `Lit`), an invariant only `type_check` establishes, and only on `Term`s wrapped in `TypedTerm`. A `Filter` body containing a `Reg` quantifier (legitimate PL — PC1: "Filtered domains compose freely") is validated by the WT domain judgment but stored raw, and the natural implementation then panics at enumeration. The validation text is also ambiguous ("cataloged Concrete TypeRefs" vs "no *bare* Reg"), and a ref-bearing domain has no named rejection (`IllFormedDomain(TypeError)` wraps a `TypeError`, but "contains a `Ref`" is not a `TypeError` variant). Fix: either (i) specify that `register_rule` normalizes the domain through the same check+`Reg`-expansion pass and stores a checked form (a `TypedDom`, or `TypedTerm`s for filter bodies), or (ii) explicitly reject any `ClassVar`/`Reg` and any `Ref` inside a rule domain with named `RuleError` variants, stating the QD narrowing relative to ASN-0133's `D_ρ ∈ QD`.

4. **[SHARPENING] The "one audit seam" claim contradicts the dispatch table.** The design says the whole audit surface "rests on the one `observe`-honors-`Audit` seam," but the dispatch table routes `members(K, audit)`/`targets_of(K, x, audit)`/`M_K@audit` through M7's `members`/`targets_of` at `View::Audit` — a second audit-honoring assumption. Either rebuild the audit core-atom readings from `observe(K,&[],&[],Audit)` via V-AUD's own equations (making the claim literally true), or name both methods in the seam-dependency paragraph.

5. **[SHARPENING] Scope the `L_dom` claim to the gated sublayer.** "Every stored tuple carries a registered type (P6), so this is exactly `dom(Σ.L)`" is true of ASN-0126/0128's gated Σ but not of M7's assembled `LinkState`, which also holds MAKELINK open content links whose type slots are uncataloged content extents. The union-over-catalog implementation is the faithful ASN-0129 universe and should stand; add one sentence stating that PL's `L_dom` (and hence `Addr`-over-`L_dom` Nullify domains, the reflected residence disjunct, etc.) ranges over the typed-relation sublayer and excludes open links.

6. **[SHARPENING] Per-type BH1 filtering is already expressible on M7's given surface.** BH1's `is_filtered_J` is definitionally the membership predicate on J's own active view — i.e. `is_k(J, x)` — so the claimed v1 limitation "M7 today exposes only the aggregate `is_filtered`; a second BH1 type would need per-type filtering" is avoidable with no new M7 surface. Either implement the `K_queried` exclusion via per-type `is_k(J, ·)` (making UV correct for app-registered BH1 types), or correct the limitation's stated cause.

7. **[SHARPENING] Specify how callers mint `VarId`s and where the reserved-range exclusion is enforced.** `VarId(u32)`'s field is private and the design says the `≥ EXPANSION_NAME_BASE` reservation is "enforced structurally," but no public constructor is given and no check is named in `type_check`. State the enforcement point: a guarded `VarId::new` (rejecting the reserved range) or an explicit `type_check`/`type_check_trigger` rejection of reserved-range binders and parameters.

8. **[SHARPENING] The Q0 fixed-view "term-builder" is asserted but absent from the interface.** §Internal 6 says "M9 provides that rewrite as a separate term-builder" for reifying `quiescent_R` as a `pdef`; no signature, name, or contract appears anywhere (and per Q0, `chain`-containing default-view triggers are not fully rebuildable, so the builder would need a stated domain restriction). Either give it a signature and its restrictions, or strike the claim — the live per-rule-view detector is sufficient and correctly grounded.

The design otherwise passes the checks I ran: no M8 or M10 edge anywhere; all named upstream calls exist with the given signatures (`observe`/`emit`/`nullify`/`tip`/`reserved_type`/`coverage_class`, `Vstream::insert`/`content_count`, `value_at`, `is_registered_document`, `snapshot`/`seq`); the Unary-`pdef`, n=1-encoding, UV-ownership, content-address-supersession, expand-vs-evaluate, and registry-injection conflicts are all stated and soundly resolved; PD0/FP/UV/PR0/PR5a/Q0–Q9 are transcribed faithfully, including the ST⁺ non-compositionality trap and the honest weakening of PR1(iv) to validation-time.

VERDICT: REVISE
