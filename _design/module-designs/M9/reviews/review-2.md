Reviewing M9 against its decomposition, the upstream interfaces (M1–M5, M7), and the source notes (ASN-0128/0129/0130/0133). The design is unusually careful — the two-transaction `register_pred` soundness argument, the UV default-rewrite split with M7, the n=1 encoding collapse, and the conflict resolutions all hold up. But the PL AST has a representational hole that breaks a core ASN-0129 capability.

## Revision list

**1. [DEFECT] The PL AST cannot represent `Reg`-quantified class-variable bodies, breaking PC1/V-IDX cross-type quantification and making the type checker's stated `Reg` expansion unimplementable.** Every type position in the AST is a *concrete* `TypeKey(Endset)`: `IsK(TypeKey,_)`, `Members(TypeKey)`, `MembersDom(TypeKey)`, `ActiveSlice(TypeKey)`, `MapGet(_, TypeKey)`, etc. A `Forall{var: cvar, dom: Dom::Reg, body}` binds `cvar: VarId`, but the AST gives `cvar` **no valid syntactic position in `body`** — atoms/domains/`MapGet` take only concrete `TypeKey`, and `Term::Var` is value-sorted (Reg is "outside COD"). So the type checker's "instantiate `body` once per registered class … `M_K`, `is_K`, `L_K` with `K` a variable" (V-IDX) has nothing to substitute, and ASN-0129's stated cross-type questions (PC1: "quantifying over `Reg` expresses cross-type questions no single K's atoms can ask"; part of PL's closure per PC6) are dropped. Even the one V-IDX survivor the design names — `targets_keyed(s)[K]` under a `Reg` binder — is unrepresentable (`MapGet`'s `TypeKey` is concrete). Fix: introduce a type-position form `TypeRef = Concrete(TypeKey) | ClassVar(VarId)` accepted by the atoms/domains/`MapGet` that name a type, and have `Reg`-expansion substitute `ClassVar(cvar) → Concrete(class)` per registered class. (`Count(Dom::Reg) → Lit` is the only Reg use that survives the current AST, and it is the minor one.)

**2. [SHARPENING] `type_check` should reject `Tup`-sorted parameters in `Γ_D`.** ASN-0130's SignedTerm requires `Γ_D = ⟨x₁:C₁,…⟩` with each `Cᵢ ∈ Codom` — `Tup` is excluded (tuples are never term values). But `type_check(params: Vec<(VarId, Sort)>, …)` accepts the full `Sort` (including `Tup`). Add a check that every `Γ_D` parameter sort is in `Codom`, surfaced as a `TypeError`, so a Tup-sorted def parameter (which `evaluate_def` could never soundly bind) is rejected at registration rather than slipping into a `pdef`.

**3. [SHARPENING] Reconcile the QD-refl WT rule with the Term/Dom split.** The WT prose lists "QD-refl types an address-valued domain as a term at `℘_fin(T)`," but `Term` and `Dom` are disjoint enums and only `M_K` has an atom-term twin (`Atom::Members`); `L_dom` (`Dom::LinkDom`) and `Dom::Filter` have **no** term form, so they cannot appear as standalone set-valued *terms* (e.g. `SetEq(L_dom, …)`). The uses that matter — membership, count, emptiness, union, the `a ∈ L_dom` residence disjunct of QD-audit — are all expressible via the `Dom`-accepting formers (`Exists{x, LinkDom, AddrEq(x,a)}`, `Count(LinkDom)`, `Forall{x, D, False}`, `BigUnion`), so PL stays denotationally complete; but the design should either add a uniform `Term` reflecting an address-valued `Dom` as an `AddrSet`, or state explicitly that reflectable-domain term-uses are spelled via quantifiers/aggregates and drop the unhostable WT rule.

**4. [SHARPENING] Specify how M9 constructs its internal `LinkStore<W>`/`Vstream<W>` handles and its reserved type endsets.** The design states the `Coordinator<W>` bounds and that M9 "caches the catalog from the same `(ReservedAddrs, Vec<TypeDecl>)`," but never says M9 builds an `Arc<TypeRegistry>` (via `TypeRegistry::build`) to construct the `LinkStore<W>` that backs `emit`/`nullify`, nor how the bare calls `reserved_type(PredDef|Supersedes|…)` resolve. State that these are M9's *own* catalog accessors (not M7's snapshot-bound `LinkState::reserved_type`), with each reserved type endset computed once as `enc(&[reserved.X])` — byte-identical to M7's by construction — so the `TypeKey` equality probes against the catalog hold.

**5. [SHARPENING] The scope-body monotonicity rejection is vestigial.** All four `ScopeBody` variants (`PerEmitter/PerTarget/PerSource/PerAddress`) use `S` only positively, so "M9 rejects a non-monotone scope-body declaration (a syntactic positivity scan)" can never fire against the stated interface. Either drop the rejection claim (the four canonical bodies are monotone by construction, so Q9's global⟹scope inference holds automatically), or, if a custom `β` is intended, specify that path and what the scan actually inspects.

**6. [SHARPENING] `signature()` must memoize only the `Some` answer.** Since `sig` is defined exactly on ever-registered addresses and ever-registration is monotone, a `Some` result is permanent and cacheable forever — but a `None` (not-yet-ever-registered) is transient and must **not** be memoized, else a later registration is never observed. The prose ("on a miss … then memoizes") should make the Some-only memoization explicit.

**7. [SHARPENING] State M9's reliance on M7's `observe` honoring `View::Audit`.** `is_K(x)@audit`, `L_K`, and `L_dom` all route through `observe(K, …, Audit)` expecting the *audit* slice, but M7's interface prose describes `observe` as "over the active typed slice." The `View::Audit` parameter and ASN-0086's hist/oper selectors make M9's reading correct, but the design should name this dependency so an M7 builder who took the "active" prose literally is caught at the seam rather than silently returning active data for M9's audit reads.

**8. [SHARPENING] Consider promoting the single-`nullify` `FireAction` into v1.** The Open decision already notes it is "buildable today" (one atomic `nullify` transact, satisfying H-ATOM/H-FIN exactly as the Marker emit does) and is deferred only because a nullify rule's active-state trigger isn't SF-certifiable. Since the decomposition's "atomic fires" arguably includes retraction and uncertified rules are already admissible (with divergence monitoring), shipping `FireAction::Nullify` in v1 (the `FireError::Nullify` variant is already anticipated) would close nullify-based automation without waiting on M7's pure `stage_emit` (which only the genuinely *multi-deposit* actions require).

VERDICT: REVISE
