**Scope of this review:** M10's design against the decomposition, ASN-0134, and the seven upstream interfaces as given. I traced every dispatch-table row to its upstream signature (all ~38 check out, including argument modes, error enums, and the `*_on` snapshot twins), verified the RejectCode union covers every upstream error variant, checked the lifecycle against A1/A2/A7/G0/MIC-clause-6, and pressure-tested the two flagged upstream amendments (store-driver constructors; the type-only M10→M4 edge). Both amendments are genuine upstream holes — the handle types are unconstructible by *any* dependent as published, and M5's `insert` signature forces naming M4 types — and the design surfaces them honestly with exact signatures rather than silently inventing APIs. The zero-cross-family-composite resolution is sound (every v1 mutator maps to a single owning-store transact). One factual error against M3's semantics survives; everything else found is polish.

**1. Revision list**

1. **[DEFECT] §5 / Open build decision 7 — the `NotNextForm ⇒ Permanent` justification is factually false about M3's delegate semantics.** The design claims "M3's frontier is monotone, so the *identical* prefix never becomes next-form later," and Open decision 7 files `NotNextForm` among reclassifications "forced by upstream … monotone-frontier … invariants, not heuristic." This is wrong for the ahead-of-frontier case: `NotNextForm` fires exactly when the prefix is *fresh* but ≠ `next_in` (an already-allocated prefix yields `NotFresh` instead), i.e. the guess sits *ahead* on the account chain — and monotone advance is precisely what can make `next_in` reach it. After intervening successful delegations under the same parent, the *identical* `delegate(delegator, p, new_id)` succeeds (freshness, ancestry, top-down, and authorization all still hold for a sibling-advanced frontier). Fix: keep `Permanent` if desired, but re-justify it as a documented heuristic (like `NotArranged` — satisfiable only via other actors' intervening commits, where blind reissue-polling is bad advice and `NextAccountPrefix` re-derivation is the right recovery), delete the "never becomes next-form later" claim, and move `NotNextForm` out of the "forced, not heuristic" parenthetical (leaving `NotFresh`/`NotRegistered`, which genuinely are invariant-forced).
2. **[SHARPENING] §6 — "the atomic ω check inside create_new_document/version/fork/delegate" overstates M5's `version`.** Per M5/M3's seams, `version`'s owned-vs-cross-owner branch pre-reads `effective_owner(d_src)` off a snapshot, justified by ω-stability for an existing document — it is not an in-transaction check. The load-bearing point (M10 must not duplicate ω) is unaffected; reword to "atomic in M3's ops; a stability-justified snapshot pre-read in M5's version" so the description of the neighbor is accurate.
3. **[SHARPENING] §5 disposition table — name `DelegatorUnknown` and `NotAPrincipal` in the conservative-`Permanent` discussion.** Both are future-satisfiable (a later `delegate` can register the missing principal id) exactly like `fork`'s unknown-id `NotOwner`, which the design does discuss; today they fall through the catch-all silently. One sentence adding them to the documented conservative bucket keeps the "documented, not accidental" claim true.
4. **[SHARPENING] §5 — `TxnError::Durability(io::Error)` drops the error's diagnostic text.** `Rejection.detail` exists but `classified` always sets `None`; thread `Some(err.to_string())` for the Durability arm (and optionally `Gate`) so operators see the underlying I/O cause.
5. **[SHARPENING] §10 — the latent-composite sketch names a placeholder `M5::stage_register` that contradicts the settled eager-lazy split.** A new document's arrangement is deliberately implicit/lazy (no M5 registration step exists or should exist); a create-and-insert composite would need only a content-place step. Reword the hypothetical so a future builder doesn't infer an M5 registration primitive.
6. **[SHARPENING] §7 — state the same-op-kind/different-args `ReqId` reuse behavior.** The op-kind tag catches cross-kind reuse, but a reused `ReqId` with the *same* kind and different arguments serves the stale ack without executing. This is covered by the stated client uniqueness contract, but say so explicitly (or note payload-hashing as the upgrade path) so a builder doesn't bolt on ad-hoc argument matching.
7. **[SHARPENING] §6 — note that `bootstrap_session()` confinement is transport policy.** It mints `BOOTSTRAP_PRINCIPAL` authority ungated; the design's trust model (transport is the sole caller) covers it implicitly, but one sentence — "the transport must not expose `bootstrap_session` beyond provisioning" — makes the obligation explicit alongside the SessionId non-forgeability precondition. Similarly, a clause noting that `Codec::marshal` frames carry no correlation id (the transport envelopes the `ReqId` itself) would close the last wire-shape ambiguity in §8.
