Reviewing M10 against the upstream interfaces and ASN-0134. The design is unusually careful — the dispatch table, read/write path split, commit-before-ack derivation, idempotency gating, and the RejectCode union are all concrete and mostly typecheck against what they're handed. The signatures it calls match upstream verbatim (I checked every store call), the cross-family-composite conflict is soundly resolved to zero v1 occupants, and the ASN-0134 contracts (A7, A1/A2, A5 no-batch-fusion, V2 clause-6, G0 serializability-not-SC) are honored faithfully. But the write path rests on an unsecured upstream assumption.

## Revision list

1. **[DEFECT] The entire write path constructs store-driver handles via constructors no upstream interface publishes.** `Op::{Insert,Delete,Copy,Rearrange,Version}` call `Vstream::new(&self.kernel)`, the link writes call `LinkStore::new(&self.kernel, self.registry.clone())`, and the namespace writes (plus `editlink`) need `Namespace::new(Arc<Kernel<W>>)`. None of `Vstream::new`, `LinkStore::new`, `Namespace::new` appear in the M5/M7/M3 interfaces — which conspicuously **do** publish their other constructors (`Query::new`, `LinkQuery::new`, `Link::new`, `TypeRegistry::build`, `Run::new`, `Endset::from_spans`). The structs carry private fields, so M10 cannot struct-literal them, and no in-crate workaround exists (even the engine would need the same published constructor across the crate boundary). The design flags this ("assumed … request them"), but honesty about the gap doesn't close it: as written, every write op is unbuildable against the interfaces as given. **Resolve concretely** — either (a) get these three constructors added to the M3/M5/M7 interfaces and cite them, or (b) change `Operation::new` to receive the store-driver handles (or a factory) constructed by the binary/engine, so M10 names a *published* acquisition path. Do not leave the core write path resting on an inferred API.

2. **[SHARPENING] The parse-failure rejection is unconstructible.** The design commits to surfacing `ParseError` as `RejectCode::Malformed` (Permanent), but `Rejection` mandates `op: OpKind` and a parse failure has produced no `Op`. Since `execute` takes an already-parsed `Request`, the transport owns this response — but it has no `OpKind` to build the `Rejection`. Add an `OpKind::Unparseable` (or make `Rejection.op` an `Option`) and state explicitly that the transport constructs the parse-failure `Response::Rejected`. Otherwise the one M10-originated input-failure code can't flow through M10's own never-silent rejection model.

3. **[SHARPENING] `reject` is used but never defined.** `execute` steps (b)/(c) call `reject(op, code, disposition) -> Response`, but only `reject1(op, code) -> Rejection` and `Rejection::classified` exist. Define it: `Response::Rejected(Rejection::classified(op, code, None))` suffices for both call sites (the explicit `disposition` arg duplicates `disposition_of(code)` — `Unauthenticated→Permanent`, `Poisoned→Halt`), so drop the redundant third argument or have `reject` delegate to `classified`.

4. **[SHARPENING] `resp.clone()` (step d) silently requires `Response: Clone`, a non-trivial transitive bound.** Deriving `Clone` on `Response` requires every payload `Clone`, including M7's `Invalid` (`pub struct Invalid;`, no derives) and M6's `Deletions`/`CompareReport` (no derives shown). Since the cache only ever stores `Ack`/`AckAddr`/`AckEdit` (each carrying just `Seq`/`Address`), the cleanest fix is to clone *selectively* in `idem_put` rather than require whole-`Response` `Clone` — and state that, so a builder isn't blocked at compile time on an upstream type's missing derive.

5. **[SHARPENING] The flat `RejectCode → Disposition` table errs `Permanent` for some future-satisfiable codes.** Codes not in the explicit Reorder set default to `Permanent`, but `NotArranged` (a later INSERT can arrange the position) and `fork`'s `NotOwner` via an unknown session id (a later `delegate` can register the id) are genuinely Reorder-able. The disposition is advisory and §Open-7 already flags tuning, but call out that a flat code-keyed table cannot express op-context-dependent satisfiability and intentionally errs `Permanent` — so the imprecision is documented, not accidental.

6. **[SHARPENING] Minor pseudo-code completions.** `AtomicBool::{load,store}` omit their `Ordering` argument (§1/§5); `SessionId` minting is unspecified (an atomic counter); `Op::is_read()`/`is_write()` are used but undefined (derivable from the Op grouping, and must partition exhaustively); `SessionCtx::anon` leaves `principal`'s sentinel unstated (make `principal` an `Option` or note it is unused on the read path); and the `ReadLink`/`FollowLink` group header reads "(→ M6)" though both are M7 reads (the inline comment self-corrects, but fix the header).

VERDICT: REVISE
