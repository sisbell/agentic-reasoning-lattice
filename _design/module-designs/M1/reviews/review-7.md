## Review: M1 — Address & Span Algebra

I checked the design against the decomposition's ownership list (all eleven owned components are present and concretely specified), the three source notes (contract-by-contract for the arithmetic, span, and classification layers), the engine composition contract, and internal consistency between the interface, data model, and invariants. The algebra itself is faithful and unusually well-argued — the `subtree_of` width choice (`δ(1,#p)` vs `inc(p,0)`), the `displacement` D0–D2 gate, the field-absence⇒NO rule, and the level-gate placement all check out against the notes. Two material gaps remain, both at the seam surface rather than in the algebra.

**Revision list**

1. **[DEFECT] `SpanSet` is write-only across the seam — add read accessors.** The public interface offers `empty`/`singleton`/`union`/`normalize`/`denotes` but no way to enumerate a span-set's component spans (no `iter()`, `len()`, `is_empty()`, or slice/view accessor), and the tuple field is private. Downstream consumers cannot function without this: M7 builds its per-slot spanfilade from an endset's component spans, M8's RETRIEVEENDSETS and projection must walk them, M6/M10 must marshal a `RETRIEVEDOCVSPANSET` result span-by-span, and even reading `difference`'s ≤2-span result requires extracting members. This violates the composition contract's checklist item "readable by downstream consumers (no private-field type that crosses a seam unusably)." Add `iter()`/`len()`/`is_empty()` (and, for symmetry, a `FromIterator<Span>` or `from_vec` constructor so callers need not fold `singleton`+`union`).

2. **[DEFECT] Derived `Deserialize` is an unguarded mint path that contradicts the stated type invariants.** The design mandates `derive(Serialize, Deserialize)` on `Address` and `Span`, while simultaneously asserting "every `Address` is T4-valid; that validity is discharged at each mint site" with an enumerated closed list (`validate`, `elem_addr`, `parent`, `document_of`, `checked_inc`), and calling a zero-width `Span` "an illegal state the constructor must reject." A derived `Deserialize` is a sixth construction path that checks nothing: it can mint an `Address` whose tumbler is not T4-valid or whose stored `level` disagrees with `classify`, and a `Span` violating T12. A builder following both instructions produces an invariant hole exercised on every journal replay. Resolve it explicitly: either specify validating deserialization (deserialize raw components, route through `validate` / `Span::new`), or declare journal-boundary deserialization a trusted path with the rationale (M2 owns the journal's integrity) — the design currently says neither.

3. **[SHARPENING] `cover` deviates from S7's witness construction — align or annotate.** S7's Definition sets each unit width to `[0,…,0,1]` of length `#tᵢ` — i.e. reach `shift(t,1)` — while the design uses `from_endpoints(t, inc(t,0))`, which advances `sig(t)` instead. The two coincide exactly when `sig(t) = #t` (all T4-valid points) but over-capture past the point's subtree on trailing-zero tumblers. S7's exported postconditions (`|Σ| = |P|`, `⟦Σ⟧ ⊇ P`) still hold, so this is not a dropped contract, but the design presents it as "S7['s] unit-span cover" without noting the substitution. Either switch to `shift(t,1)` (also unifies `cover` with `subtree_of`'s construction) or state the deviation explicitly next to the existing over-capture remark.

4. **[SHARPENING] Derive `Ord`/`PartialOrd` on `Address`, delegating to the tumbler.** M3's frontier comparisons and M8's identity-ordered cursors order addresses constantly; as specified every consumer must detour through `.tumbler()`. One derive removes the friction with no semantic risk (the order is the tumbler order).

5. **[SHARPENING] Fix the do-not-port rationale in §4.** "Its add routine carried an operand-order asymmetry that discarded an argument" mischaracterizes the record: the notes present `absadd`'s prefix-from-first/suffix-from-second asymmetry as the *correct* realization of ⊕'s non-commutative semantics (TumblerAdd's three-region rule; the tail-discard is exactly TA-MTO/TA-RC), while the defects the notes actually record are the silent digit-overflow wrap in `tumbleradd` and the fatal fixed `NPLACES` length bound. As worded, a builder could be misled into treating ⊕'s spec-mandated asymmetry as the bug to avoid. Cite the recorded defects instead.

Everything else held up under scrutiny: the boundary against M3 (pure `inc` + gate predicate here, frontier/durability there) matches the decomposition and is the design's cleanest resolution; the six conflict resolutions are stated and sound; the open decisions are genuinely open in the notes rather than dodged commitments; and the `canonical_key`-vs-coverage-class-policy split is an argued refinement of the decomposition's wording, not a contradiction.

VERDICT: REVISE
