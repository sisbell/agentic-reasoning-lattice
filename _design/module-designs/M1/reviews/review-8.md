I reviewed the M1 design against the decomposition's ownership list, the ASN-0034/0045/0053 digests, and the Engine Composition Contract. Coverage of the owned capabilities is complete (order, T4 validation/classification, fields/containment, ⊕/⊖/`inc`/gate, shift, spans, span-sets, normalization, cover), the constructive definitions match the notes' contracts (I spot-checked ⊕/⊖ region rules, the D0–D2 displacement gate including the proper-prefix exclusion, `subtree_of`'s δ(1,#p) witness against S7, the merge/intersect min-max guards, the S11d dispatch table, and `parent`'s two-peel equivalence — all correct), and the boundary resolutions (allocator→M3, spanfilade→M7, coverage-class policy split) are stated and sound. I found one material flaw, in the serde recipe.

**Revision list**

1. **[DEFECT] Make `Span`'s serialization symmetric with its validating deserialization.** As specified, `Span` derives plain `Serialize` (struct-shaped: `{start, width}`) while `#[serde(try_from = "(Tumbler, Tumbler)")]` makes `Deserialize` expect a 2-tuple. `serde`'s `try_from` affects only the deserialize side, so the type cannot round-trip its own output in any self-describing format (JSON, CBOR-with-names); it only works by coincidence in positional binary formats — and the design explicitly defers the at-rest format to M2, so that coincidence cannot be assumed. Under the recipe as written, the claim "violations surface as deserialization errors at M2's replay/checkpoint-load boundary" degrades to *every* journaled span failing replay under a named-field format, on exactly the recovery path the validating-deserialize scheme was built to protect. Fix: add `into = "(Tumbler, Tumbler)"` beside the `try_from` (with `impl From<Span> for (Tumbler, Tumbler)`; `Clone` is already derived), or write matching manual impls — the same symmetric pattern the design already uses for `Address` (`into = "Tumbler", try_from = "Tumbler"`). While there: correct the preamble sentence "Serialization stays derived/plain throughout," which `Address`'s `into` attribute already contradicts, and note that `SpanSet` (whose members serialize through `Span`) inherits the fix, and that `im`'s serde feature is required alongside `num-bigint`'s.

2. **[SHARPENING] State at the `canonical_key` → M7 seam that heterogeneous-length endsets fall outside S8/S9.** Real link endsets can mix tumbler lengths (elements under a document vs. under one of its versions differ in address length), and `canonical_key` correctly returns `LevelMismatch` on such sets — S9's uniqueness is only proven within one length class. The fallibility is visible in the signature, but the seam prose ("the seam M7's coverage-class dedup key rides") reads as if one call suffices. Add one sentence telling M7 that its coverage-class policy must partition an endset by endpoint length (e.g., per-slot/per-document) and compose per-class canonical forms — and that cross-length *denotational* canonicalization is genuinely absent from the source algebra, not an M1 omission.

3. **[SHARPENING] Unify `hull`'s reach on `shift(max, 1)` instead of `inc(max, 0)`, or rename/annotate.** The stated contract (`from_endpoints(min P, inc(max P, 0))`) is correct for the ⊇-cover guarantee, but `shift(max, 1)` is total under the identical preconditions (TS4, length-preserving), is the least same-length tumbler exceeding `max`, and so yields the *tight* single-span hull — whereas `inc(max, 0)` over-captures whenever `sig(max) < #max`, the exact mis-width the design itself warns against in `subtree_of` and `cover`. Using one convention (`shift(·,1)`) everywhere is simpler and makes the name "convex hull" honest; alternatively keep `inc` and rename/document the function as a cover, not a minimal hull.

4. **[SHARPENING] Name both `LevelMismatch` conditions on `normalize` itself.** §7's `normalize` sentence says only "components are not mutually level-compatible," but S8 also requires each component span to be level-uniform (the design's own `[1,5] ⊖ [1,3,5]` example shows why the coalescing arithmetic breaks without it). The full gate is stated for `intersect_sets` and in the Invariants section; mirror that parenthetical on `normalize` so a builder doesn't implement its gate as mutual-compatibility only.

5. **[SHARPENING] Reword the "zero-sentinel span semantics" open decision.** As defined, `contains`/`intersect`/`classify_spans` are already total and fully determined on spans with all-zero endpoints — there is no unspecified M1 behavior. The genuinely open item is whether downstream consumers (M6/M8 unbounded-range queries) assign a special "unbounded" *interpretation* to sentinel endpoints. Say that explicitly, so a builder doesn't hold the algebra functions open waiting for a convention.

6. **[SHARPENING] Fix `subtree_of`'s attribution.** "(ASN-0034, the 1-position convention)" names a convention no digest states. The correct warrant is T5's contiguity (ASN-0034) for *why* a subtree is a span, plus S7's covering construction (ASN-0053) for the δ(1,#t) width witness the function reuses. The construction itself is verified in-document and needs no change.
