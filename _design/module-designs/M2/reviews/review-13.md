Reviewing M2 against the two source notes (ASN-0047, ASN-0134) and the decomposition. M2 is a foundation, so there's no upstream API to check fidelity against; the live questions are buildability, faithfulness to the notes, boundary discipline, conflict resolution, and internal consistency. The design is thorough and mostly sound — the MIC clause-mapping, the durable-before-visible ordering, the dependency-inverted `apply` fold, the two-pass recovery, and the conflict resolutions are all faithful and concrete. One load-bearing buildability defect, plus several precision sharpenings.

## Revision list

**1. [DEFECT] Correct the allocation seam to mint against `stg.working()`, not `stg.base()`, within a multi-atom content run.** The design centers committing a multi-atom content run (m × `K.α`) as one `transact` to deliver W2 (§4, Conflict #1), but every allocation example recomputes the frontier against `base()` — the *unchanging* txn-start root. Concretely: with d's content max at `[d.0.1.5]`, atom 1 does `inc(recompute_max(base))` → `[d.0.1.6]`; atom 2, reading `base()` again, still sees max `[d.0.1.5]` → `[d.0.1.6]` again. Not contiguous — *colliding*. This defeats the very invariant (W2 chain/address contiguity) the run-as-one-`transact` mechanism exists to deliver, and it is mutually inconsistent with the design's own precondition guidance: freshness (`a ∉ dom(C)`) checked against `working()` (§3) then *rejects* atom 2, so **a multi-atom INSERT can never commit** (and if a builder instead checks freshness against base, the collisions silently overwrite content in the fold and alias V-positions). Fix: each atom after the first must read the frontier off `stg.working()` (which reflects prior pushes), or M3 must expose a batch allocator returning m consecutive addresses from one `base()` read plus the count. Replace the blanket "address math against `stg.base()`" (M3 seam, M5 placement seam) with "against `stg.working()` for any allocation after the first push in the closure," and show the run pattern explicitly. This is the core INSERT path (ASN-0116), so it must be right.

**2. [SHARPENING] Drop "Txn high-water" as separate Sequencer state.** The Core-data-model Sequencer row lists "Seq high-water + Txn high-water," and §7 insists recovery "restore the Txn-id high-water ... explicitly." But `Txn(pub Seq)` *is* a transaction's first `Seq` — there is no independent counter. The next txn's `Txn` is its first `Seq` = (Seq high-water)+1, automatically beyond every committed `Txn ≤ W`, so restoring the Seq high-water to W fully restores Txn freshness. The design half-concedes this ("already carries the Txn high-water with it") then re-asserts separate restoration, inviting a builder to implement a redundant second counter — precisely the desyncing trap the first-`Seq` derivation was meant to avoid. State plainly: one counter (Seq); Txn = first Seq; recovery restores only the Seq high-water.

**3. [SHARPENING] Separate verdict-stamping from `current_seq()`.** §5 frames a verdict reported "as of `current_seq()`" as V1-retrospective, while the M9 seam correctly stamps verdicts "as of `s.seq()`." These are not interchangeable: writes can land between a `snapshot()` and a later `current_seq()`, so stamping a snapshot-computed verdict with `current_seq()` asserts it of a *later* state than it was read against — a V1 violation. State that a verdict's coordinate is always the seq of the single `Snapshot` its constituents were read off, and that `current_seq()` is only a standalone "latest committed" progress indicator, never the stamp for a snapshot-computed verdict.

**4. [SHARPENING] Specify per-segment Seq-range metadata.** Recovery "skips earlier whole segments, all ≤ S_load" and reclamation drops "whole journal segments all of whose frames have Seq ≤ S_old" — both require knowing each segment's Seq range, but the journal-framing section never says segments carry it. Specify it (name segments by first Seq, or a segment header recording `[firstSeq, lastSeq]`). Correctness is unaffected (the `Seq > S_load` fold filter still bounds replay), but the stated skip-optimization and the segment-granular reclamation floor are unbuildable without it.

**5. [SHARPENING] Tighten the Seq↔𝔼 correspondence for over-satisfied runs.** The design claims "the subsequence of Seqs carrying →_sh records is order-isomorphic to 𝔼." But a content run is m `K.α` records (m internal →_sh Seqs) that M2 over-satisfies by collapsing into one externally-observable install — i.e. M2 presents the over-satisfy 𝔼 (one step per run), against which even the →_sh subsequence is a *refinement* (m internal Seqs, one observable step), not an isomorphism. The isomorphism holds only against the finest (per-`K.α`, clause-5) 𝔼. Say which 𝔼, and note that it is the externally-observable *install* order, not the internal →_sh Seq order, that maps to the 𝔼 M2 actually presents for runs. (Build and V1 reporting are unaffected — both already key off install-Seqs.)

**6. [SHARPENING] Flag the last-committed-txn post-commit-bit-rot blind spot.** "Intact marker + failed `records_checksum` → torn tail → discard" is correct for the in-scope crash-atomicity threat (under durable-before-visible + truncate-or-poison, a torn write leaves such a marker only as a not-acked poison-tail). But it silently loses a committed, *acked* last txn if one of its records bit-rots after commit: the marker stays intact, `records_checksum` fails, W demotes to the prior marker, and the rotted txn falls "beyond W" → discarded with no `Corruption` signal. (Interior such rot is caught — it lands in `(S_load, W]` → halt — so only the *last* committed txn is exposed.) The source notes don't mandate post-commit bit-rot handling, so this isn't a fidelity gap, but the design's "never silently drop committed data" posture has this one hole; note it explicitly (in or out of scope).

VERDICT: REVISE
