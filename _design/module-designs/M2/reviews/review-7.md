Scoping note: the recommended core — `SingleApplier { durable_before_visible: true }` with per‑commit `Durability::Fsync` (or `None`) — is buildable and faithful. The dependency‑inverted `WorldState` fold, the keyed critical sections (including the stripe‑index acquisition order), snapshots/clause‑6 via the persistent root, checkpoint/`Seq > S_load` recovery, footprint‑confinement for `PerKeyMerge`, and the ASN‑0047/0134 conflict resolutions are all sound and concrete. Both defects below are confined to the **durable‑before‑visible group‑commit** path (`FsyncBatch`), which the design presents as a first‑class, recommended‑for‑throughput mechanism — so its bugs are material.

## Revision list

**1. [DEFECT] Durable‑before‑visible group commit acks before the effect is visible — an A7 violation.** §1/§3 order the leader as *barrier → raise durable watermark → install root*, and gate every **non‑leader** `transact`'s return on the watermark ("returns only after the watermark covers its `last_seq`"). Because the watermark is raised *before* the install, a non‑leader can wake and return while `root` still holds the pre‑batch state — the design even states `root.seq()` may be `< watermark`. M10 then acks the client, whose next `snapshot()` loads a root that does **not** contain the just‑acked write: a read‑your‑writes failure and a direct violation of ASN‑0134 A7. A7 requires the ack to follow the step that places the effect *in the observable order*; ASN‑0134 is durability‑agnostic, so that step is the **install**, not the durability barrier. Fix: reorder to *barrier → install → raise watermark/signal*, and gate the non‑leader return on the install, not the pre‑install watermark. (Per‑commit `Fsync` and visible‑before‑durable are unaffected — both install before returning.)

**2. [DEFECT] The group‑commit install and barrier‑failure handling run unlocked, admitting root regression and data races — and contradict the data model.** The Sequencer row promises it "serializes journal‑append **+ install**," but §3 explicitly releases the applier lock and runs the leader‑only `root.store(batch_final)` *and* the failure handling (truncate un‑acked tail + `Seq` rollback + `tip.reset_to_last_durable`) **UNLOCKED**. With per‑thread `transact` and a slow fsync, two consecutive batch leaders install concurrently and out of order — an older `batch_final` landing after a newer one regresses `root` to a stale committed state and makes `current_seq()` go backwards — and a failed batch's unlocked truncate/reset races concurrent appenders advancing the tip/file. Fix: route the install and the barrier‑failure handling through the promised serialization point (re‑acquire the applier lock or a dedicated install mutex *after* the unlocked fsync), make install monotonic/batch‑ordered (install only if `batch_final.seq > root.seq()`), and pin the zero‑step "wake‑on‑base‑identity" set to that same serialized batch resolution (so a parked idem‑hit is woken `confirmed` vs `Conflict` deterministically — the mechanism for which is otherwise left unspecified). Only the fsync itself need run unlocked.

**3. [SHARPENING] Resolve the recovery corruption‑halt inconsistency.** §7 says "correctness rests *entirely* on recovery replaying exactly `Seq > S_load`," yet also halts (`OpenError::Corruption`) on *any* CRC failure "strictly before the committed tip" — which includes `Seq ≤ S_load` frames that survived segment‑granular reclamation and that the `Seq > S_load` filter would skip. Corruption already embodied in the loaded checkpoint is irrelevant; halting on it needlessly refuses a recoverable kernel. Locate the committed tip and classify corruption only from `S_load` forward (the tip is always ≥ `S_load`), so only corruption in the genuinely‑replayed range `(S_load, tip]` is fatal.

**4. [SHARPENING] Consolidate the group‑commit protocol into one place.** The durable‑before‑visible mechanism (working tip, batch‑final capture, watermark, leader install, zero‑step wait, failure truncation/poison) is restated across the data‑model table, §1, §3, §8, Conflicts #1/#3, Invariants, and Open decisions, with the load‑bearing ordering phrased slightly differently each time — which is what let the ordering/serialization gaps in items 1–2 hide. Make §3 the single numbered source of truth and reference it elsewhere.

**5. [SHARPENING] Rename `Marker.frame_checksum`.** It checksums the txn's *record frames*, not the marker's own frame (which already carries the per‑frame `crc`). `records_checksum`/`txn_checksum` avoids inviting a builder to conflate it with the frame `crc`.

**6. [SHARPENING] Minor API/citation fixes.** `snapshot()` should specify `ArcSwap::load_full()` (owned `Arc`), not `load()` (a borrowed `Guard`), since `Snapshot` outlives the call. And the "ASN‑0134 OQ10" citation for the derived‑index divergence hazard is ASN‑0134 *decision #10* (multi‑store atomicity); there is no OQ10 in the note.

VERDICT: REVISE
