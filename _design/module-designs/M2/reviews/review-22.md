**1. Revision list**

1. `[SHARPENING]` — In §3's per-commit flow, name the failure path for a non-panicking `io::Error` from `journal.append_records` / `journal.append_marker` (e.g. ENOSPC). The flow shows an explicit error branch only on `durability.barrier()`, and `TxnError::Durability`'s doc scopes itself to barrier failure; the §3 drop-guard covers the append path only when the failure surfaces as an unwind ("a panic in `f`, in serialization, or in the append path"). Both sound routes are already fully specified — either convert the error to an unwind (guard handles it) or apply the same §1 truncate-or-poison discipline and return `Durability` — so add one sentence fixing which: e.g. "a non-unwind `io::Error` from either append follows the §1 barrier-failure discipline (durably truncate the partial tail, roll back per `BurnedSeqPolicy`, return `Durability`; poison if the truncation cannot complete durably)."

2. `[SHARPENING]` — In §7's known-limitation paragraph (post-commit bit-rot of the last committed txn), extend the narrated mechanism to cover rot of that txn's **marker frame itself**, not only a record frame. A rotted marker is no longer *intact*, so the txn is not committed, `W` demotes to the prior committed marker, and the marker's corrupt run (EOF-terminated, or landing on nothing intact) plus the txn's intact record frames all classify beyond the demoted `W` — the same silent tail-discard disposition. The heading's scope ("the last committed txn") already covers it, but the body's sentence "its marker stays intact while its `records_checksum` now fails" reads as if marker-rot were a different (caught) case; one clause naming the marker-frame flavor prevents a builder from inferring that.
