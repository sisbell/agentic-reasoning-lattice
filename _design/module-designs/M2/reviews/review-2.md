Skeptical buildability review of M2's detailed design. The core mechanism (WAL + atomic `ArcSwap` install + keyed locks + snapshot + replay) is concretely specified, the seven MIC clauses are each correctly mechanized, boundary discipline is clean (no overreach into M1/M3/M5, no dropped owned capability), and the `Seq`-refines-`𝔼` reconciliation of ASN-0134's narrow `→_sh` model with ASN-0047's fuller transition vocabulary is genuinely sound. The problems are two concurrency-correctness gaps on the scaling paths the design itself recommends, plus some phrasing that undercuts its own contracts.

## Revision list

**1. [DEFECT] Group commit under the canonical durable-before-visible ordering reads stale `base` and can commit non-serializably — the flow needs an in-memory working tip.** §1 fixes the order *append records+markers → one barrier → install roots*, and "Install stays after durability." But §3/§8 take each txn's `base ← root.load()` and claim "base == current root." Under group commit those contradict: for the 2nd-or-later txn in a batch, no install has happened yet, so `root.load()` returns the *pre-batch* state — while that txn still receives a higher `Seq`. A txn at `Seq k` must read the state as of `Seq k−1`; a batched dependent txn reads as-of-batch-start instead. Concrete break: a COPY pipelined after an INSERT into the same document, batched together, copies *without* the inserted content yet lands at a higher `Seq` than the INSERT — a torn linearization, violating M2's own serializability guarantee (and W2/H0 reasoning assumes each allocation reads the frontier its predecessor left). The register-before-allocate cases happen to be masked (stale → clean `Rejected` → retry), but read-then-write ops (COPY, REARRANGE) are not. Fix: have the applier thread an in-memory **working tip** (a `Committed<W>` advanced by each batched txn's records) that `base` is drawn from *within a batch*, publishing it to the `ArcSwap` root only after the barrier; correct "base == current root" to hold only for per-commit fsync or the first batch member. Note that the visible-before-durable variant does not have this bug (it installs before the barrier), so this defect is specific to the *recommended default* combined with the *recommended throughput mode* — i.e. likely to be hit at the first scaling step.

**2. [DEFECT] The footprint-confinement contract is stated too narrowly to be safe for merge-at-install.** The contract — the load-bearing seam that lets single-applier → per-key-concurrent migration be "transparent" — is written (in §8, Dependencies & seams, and Invariants) as "*each staged record's value and effect* must depend solely on state covered by the held keys." But merge-at-install **re-folds the already-decided records over the current root without re-running `f`**, so every read on which `f`'s decision (which records to stage, hit vs miss, reject, branch taken) depends must *also* be confined (or append-only-monotone) — otherwise a stale decision is committed at a non-serializable position and corrupts silently. ASN-0134 G1's hypothesis is "neither *reads* nor writes state the other touches"; the design's own failure-mode gloss ("a store that *reads* or writes state outside its keys ... corrupts silently") is correct, but the *contract a builder formalizes against* is the narrow record-value version, and the design explicitly tells builders to "check new store ops against it." Restate the contract to confine `f`'s entire committed-state **read set** (every value consulted to decide what to stage / reject / which branch), not only staged records' values, and align all four occurrences with the gloss.

**3. [SHARPENING] "All seven clauses free" under the single applier contradicts ASN-0134 and the design's own §5.** ASN-0134 is explicit that even under the single run-to-completion loop, clause 3 (commit-before-ack) "you must order correctly" and clause 6 is *not* free — "a recognizer that issues [reads] as separate requests drifts across indices even under the single loop (the §8 pathology needs no per-home concurrency at all)." The design's §5 in fact relies on this (its one-`Snapshot` caller contract *is* the clause-6 fix). Replace §8's "all seven clauses free" with "all but clause 6 (which still requires the §5 one-`Snapshot` threading) and the clause-3 commit-gate ordering" so the summary stops contradicting §5.

**4. [SHARPENING] Clarify that derived hints must be maintained in `apply`; `rebuild_derived` cannot stand alone.** The phrasings "index-rebuilders = `World::rebuild_derived` (and/or hint maintenance inside `apply`)" and "the spanfilade ... maintained in `apply`/`rebuild_derived`" wrongly suggest a store could maintain a hint via `rebuild_derived` only. Because `rebuild_derived` runs *once at load, before replay, never on a live commit*, a hint not folded by `apply` is stale after every live write (and after replay). State that incremental hint maintenance in `apply` is mandatory for live-query correctness, and that `rebuild_derived` exists solely to seed hints the checkpoint skip-serialized.

**5. [SHARPENING] Name the content-run case in Conflicts #1.** ASN-0134 A5 explicitly classes a *content run* (one `K.α` per atom) as a non-atomic batch, while M2 commits it as one atomic `transact`. The design handles this correctly elsewhere (over-satisfying clause 5; ASN-0134 builder decision #7) but Conflicts #1 only contrasts INSERT (composite, atomic) with `retract_stale`/rule-firing (multi-op batch, partial-visible). Adding the content run — committable either as one atomic `transact` (over-satisfaction) or as `critical_section` + separate commits (clause-5-faithful, reader-visible mid-run) — completes the composite/batch boundary and removes the apparent A5 tension.

**6. [SHARPENING] Sketch the undefined config/error types.** `KernelCfg`, `OpenError`, `CheckpointError`, and `CriticalGuard` appear in signatures but are never given fields/shape. At minimum show `KernelCfg` carrying the durability mode, checkpoint cadence, lock-table layout, and journal path that the Open-build-decisions section assumes live there.
