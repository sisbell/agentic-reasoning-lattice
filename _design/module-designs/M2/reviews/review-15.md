## Orientation

I checked the load-bearing seams and they hold. The public surface is concrete and typechecks (`Kernel<W>`, the `WorldState` fold, `transact`/`snapshot`/`Staging`, the config/error enums). All seven MIC clauses map to a named mechanism, and the three source-note conflicts are stated and soundly resolved — composite-atom-vs-batch (the content run committed as one `transact` is the OQ4 over-satisfaction ASN-0134 decision #7 explicitly blesses), single-writer-as-one-realization-of-per-home (`keys` retained as the seam), and durable-before-visible reconciling ASN-0047's visibility rule with ASN-0134's durability-orthogonality. The hardest correctness arguments survive scrutiny: the marker-as-ack with `records_checksum` correctly defends against partial page-flushes; the truncate-or-poison discipline genuinely closes the phantom-commit hole under both burned-Seq policies; the two-pass recovery's three-region corruption classification is exhaustive for the crash-atomicity threat the discipline admits, and the one gap (post-commit bit-rot of the *last* committed txn) is honestly scoped out as beyond both notes. Boundary delegation is faithful: J-couplings, store permanence, frontier/coverage math, and register-before-allocate are all correctly left to neighbors, and the `working()`-not-`base()` minting rule for multi-atom runs is exactly the subtle correctness point a build-spec must surface. I found no defects — only sharpenings.

## Revision list

1. **[SHARPENING] Specify the synchronization of the in-memory segment index.** It is shared between `transact` (append/rotate, under the applier lock) and `checkpoint` (reclamation, *claimed* non-blocking to writers, "writers run throughout"). State that the segment list/range-metadata is guarded by a **short lock distinct from the applier lock** — held only to mutate the index, with file deletions done outside it — so reclamation neither races the commit path nor blocks it. As written, a builder honoring "non-blocking to writers" must rediscover that the applier lock cannot cover reclamation; the property is achievable but the mechanism isn't named.

2. **[SHARPENING] Give the literal `Kernel<W>` struct.** The Core-data-model table names the four pieces (journal writer + segment index, `ArcSwap<Committed<W>>` root, on-disk checkpoint, `Seq` high-water + applier `Mutex`) and the prose implies a poison flag, but the struct is never written out in an otherwise signature-complete design. Showing it — and which fields live inside the applier `Mutex` vs. the separate index lock (item 1) vs. lock-free `ArcSwap` — removes the one remaining assembly ambiguity.

3. **[SHARPENING] State the truncation mechanism in the barrier-failure path.** "Truncate exactly the txn's un-acked record+marker tail" leaves the tail boundary implicit. Spell out: capture the journal file offset before appending a txn's frames, so truncation is `set_len(pre_txn_offset)` + fsync (+ dir fsync if it crossed a rotation). Trivial to infer, but worth one line given how precisely the rest of §1 is pinned.

4. **[SHARPENING] Reconcile `flush()` returning `Ok` on a poisoned kernel with `checkpoint()` returning `CheckpointError::Poisoned`.** Harmless in v1 (flush is a no-op), but the asymmetry deserves a note, because `flush()` is the design's own slot-in point for `FsyncBatch`, where it *would* perform durable work and should then surface `Poisoned` rather than a false `Ok` — flagging this now keeps the deferred mode honest.
