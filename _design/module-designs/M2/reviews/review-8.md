I reviewed M2 against its decomposition mandate (a *generic*, dependency-inverted ordering/durability/isolation kernel — semantics-blind, no address algebra, J-couplings and frontier math left to neighbors) and against ASN-0047 and ASN-0134. The interface, data model, keyed-lock discipline, snapshot/clause-6 story, recovery classification, footprint-confinement contract, and the three conflict resolutions are largely sound and well-pitched. One failure-path is specified incorrectly, and it is load-bearing.

## Revision list

**1. [DEFECT] §3 group-commit (`FsyncBatch`) barrier-failure path is unsound — it assumes the failing batch is the durable journal *tail*, which §3's own unlocked-fsync pipelining violates.** §1 says a barrier failure truncates "the txn's record+marker frames … from the journal **tail**," making `TxnError::Durability` "a **true no-op**," and §3 asserts install/failure-handling "can neither run concurrently nor reorder." But §3 runs the leader's fsync (step 3) **unlocked** while later batches append under the lock and reach their *own* steps 3–5. Three unguarded failures follow:
   - **(a) Over-truncation.** Once batch N+1 has appended seqs beyond batch N, N's frames are no longer the file suffix; step 6's `truncate` either erases N+1's frames or cannot remove N's mid-file frames at all.
   - **(b) False no-op on a durable batch.** `fsync` is whole-file: if N's barrier fails but a *later* batch's barrier **succeeds**, N's frames are already durable *and* already installed (via the working tip) *and* acked. Step 6 still truncates and wakes N's members with `Durability` ("re-invoke") — a false negative; for a same-`(d,S)` allocation the caller's retry double-deposits a **colliding address**. The success path's monotonic guard (`batch_final.seq > root.seq()`) has **no symmetric guard on the failure path** — so the "nor reorder" claim is asserted but mechanized only for installs.
   - **(c) Missing cascade.** A later batch's `base` reads N's not-yet-durable working tip, so a *genuine* rollback of N must cascade-roll-back every later batch that read it; step 6 doesn't.

   The recommended per-commit `Fsync` path is correct (barrier+install under the applier lock, no concurrent appends, failed frames are the true tail), so the bug is confined to `FsyncBatch` — but `FsyncBatch` is a first-class config whose protocol §3 bills as "the single source of truth," and the "sound failure path" invariant overclaims. **Fix, simplest first:** constrain group commit to a single FIFO flusher that fsyncs and resolves batches **strictly in order** (at most one batch between barrier-start and resolution) — a failed batch is then always the durable tail, nothing has superseded it, and truncate-tail + Seq-rollback stay valid; this keeps group commit's real win (one fsync amortized over many txns *within* a batch) and drops the unsound cross-batch overlap. If overlapping fsyncs are kept instead, step 6 must (i) first check `root.seq() ≥ last_seq` and, if so, wake members `Ok` without truncating; (ii) replace physical mid-file truncation with logical abort-markers; and (iii) cascade-roll-back later batches that read the rolled-back tip.

**2. [SHARPENING] Type and explain the `txn` field.** `LogRecord{seq,txn,bytes}` / `Marker{txn,…}` name `txn` without a type or role. Specify it (e.g. `u64`) and state its recovery purpose: recovery groups record frames by `txn` to validate `records_checksum`, which is precisely what lets validation survive a `magic`-resync that skipped a corrupt frame (file-contiguity alone can't be trusted there).

**3. [SHARPENING] Make the zero-step waiter's "base's batch" lookup concrete.** A parked zero-step op's `base` may be the tip of a *closed-but-unresolved* batch, not the current open one, so the kernel needs a seq→in-flight-batch map (or a batch handle carried on the working tip) to enroll it — "base's batch waiter set" as written underspecifies how that batch is located.

**4. [SHARPENING] Flag the CAS-only journal-order caveat.** Under `OptimisticCas` (no install lock), concurrent winners append out of `Seq` order, so §7's "fold in `Seq` order" means *group-by-marker then sort committed records by `Seq`*; under `SingleApplier`/`PerKeyMerge` appends are already Seq-ordered (linear replay). State this so a CAS builder doesn't assume file order == Seq order.

**5. [SHARPENING] Reword the m≥2 bundling claim.** "M2 deliberately does not bundle those into one transaction" is slightly off — M2 cannot bundle caller-separate operations; it offers only the per-`transact` atomic unit. A store honors A5's partial visibility by issuing an m≥2 batch as *separate* `transact`s, and *may* over-satisfy by committing it as one `transact` (A5's "atomicity must be built above the substrate" permits exactly that). M2 neither forces nor forbids the granularity.

**6. [SHARPENING] Minor ergonomics.** Derive `Copy/Clone` on `Seq` so `seq()`/`current_seq()` can return it by value as written; optionally gate `critical_section`'s availability at the type level (matching the type-level `durable_before_visible` encoding) rather than a runtime panic under `SingleApplier`.

VERDICT: REVISE
