This module is close to buildable — the WAL/commit/recovery discipline is unusually precise, the MIC clause-by-clause discharge checks out, and the three note conflicts are resolved explicitly and soundly. I found one material gap, in the recovery path's handling of the discarded tail, which contradicts the design's own Txn-uniqueness argument and would produce silent loss of acknowledged commits at a second recovery.

**1. Revision list**

1. **[DEFECT] Recovery never physically removes the discarded un-acked tail, and nothing positions the append path — the next session's Seq/Txn reuse then collides with stale tail frames still on disk.** §7 classifies frames beyond `W` as "the un-acked / torn tail → discard," but "discard" is realized only as a replay-time filter; no step truncates those frames from the journal or states where post-recovery appends land. The high-water is restored to `W`, so the next session's first transaction draws `Seq`/`Txn = W + 1` — exactly the values the stale tail frames already carry. If the builder appends at EOF (the natural reading of the pervasive "append-only" language), Pass 1's stated premise "file order == Seq order" breaks, and worse: a new transaction with `Txn = W + 1` shares its txn id with a stale tail transaction, Pass 1's by-`txn` grouping merges the two at the *next* recovery, the new — acked, committed — marker's `records_checksum` fails over the merged group, and an acknowledged commit is silently demoted (if last) or spuriously halts the kernel as `Corruption`. Overwriting from the committed-prefix end without truncating first leaves partially-overwritten stale frames that collide the same way. This is also an internal inconsistency: §1's claim that "`Seq`s are globally monotone and continue across a crash/restart, [so] no two transactions ever share a `txn`, *including across sessions*" is false as written, because §7 rolls the high-water back *below* the discarded tail's assignments. Fix: specify that `Fsync`-mode recovery, before serving any write, **durably truncates the journal to the end of the committed prefix** (truncate the straddling segment to the last committed marker's frame end, delete any wholly-later segments, fsync file and directory), and state in §1/§7 that this truncation is what makes the cross-session `Txn`-uniqueness argument and Pass 1's file-order == `Seq`-order premise true at the next recovery. (No truncation on the `Corruption`/`BadCheckpoint` halt paths — the kernel doesn't start.)

2. **[SHARPENING] State the sector-write-atomicity assumption behind "a committed marker's presence at recovery == durably-committed," or pad commit markers to sector boundaries.** A later transaction's append re-dirties the disk sector shared with the previous (acked) transaction's marker tail; a crash during that writeback on hardware without atomic sector writes can garble the already-committed marker, demoting `W` and silently discarding an acked transaction. That is the same silent-loss shape as §7's flagged post-commit-rot blind spot, but it is produced by *crash atomicity*, so §7's claim that the classification "is exhaustive for the crash-atomicity threat" holds only under an unstated atomic-sector-write assumption. State that assumption alongside the prefix-flushing-fsync one, or add marker sector-padding to the journal-framing open decisions.

3. **[SHARPENING] Specify `transact`'s panic policy for `f` and the append region.** A panic in `f`, or between `alloc_seqs` and the marker append, unwinds past the rollback: the applier lock releases (parking_lot mutexes don't poison), orphan marker-less record frames may remain in the journal, and the `Seq` high-water stays advanced — quietly voiding the "gap-free under `Rollback`" invariant claim. Recovery already handles the remnants correctly (the orphan txn has no committed marker and by-`txn` grouping isolates it), so the fix is small: a drop-guard that discards staging, rolls the high-water back, and truncates any partial append (or a declared abort-on-panic policy), plus a qualifier on the gap-free claim.

4. **[SHARPENING] Pin down what bytes `records_checksum` covers.** "Checksums the txn's record frames" leaves open payload-vs-framed-bytes and ordering; recovery recomputes it over frames regrouped by `txn` after a possible magic-resync, so writer and recovery must agree byte-for-byte. One sentence — e.g. "over the concatenated record payloads, in `Seq` order" — removes the inference.

5. **[SHARPENING] Make the `InMemory` branch explicit in §3's `transact` flow.** The one flow a builder will transcribe shows unconditional `journal.append_records` / `append_marker` / `barrier()`; under `Durability::InMemory` those three steps are skipped (Seq allocation and install still run). It's inferable from §1's mode description, but a one-line branch note in the pseudocode is where the builder needs it.

**2. Verdict**

The design is otherwise faithful: the composite-vs-batch and durable-before-visible conflicts are resolved with the right units and stated reasoning; the `Seq`/`idx(σ)` correspondence, the corrupt-run classifier arithmetic (including the marker-landing `last_seq + 1` rule and the `TolerateGap` over-halt direction), and the checkpoint/replay complementarity all check out; the composition-contract obligations (tag enum in `skep-kernel`, `key(...)` in the shared base crate, `XRec`-not-`Record`, accessor-trait reads) are met; and no owned capability from the decomposition is missing. But item 1 is a real under-specification with a silent-corruption failure mode and a contradicted in-document claim, so:

VERDICT: REVISE
