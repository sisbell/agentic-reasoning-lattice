## Orientation

M2's core — the WAL/commit/journal discipline, the `WorldState` fold inversion, the two-pass recovery with the `S_load`/`W` region split, the keyed critical section, the snapshot model, and the durable-before-visible vs visible-before-durable coupling to the concurrency mechanism — is carefully reasoned, faithful to ASN-0047 and ASN-0134, and buildable. The Seq-refines-𝔼 reconciliation of ASN-0134's coarse `→_sh` model with ASN-0047's seven primitives is sound; the three named conflict resolutions are real and correctly resolved; the boundary disclaimers (no address algebra, no J-couplings, no request lifecycle) hold. One seam, however, is described backwards.

## Revision list

**1. [DEFECT] Fix the reversed M5/M7 link-seating seam.** In *Dependencies & seams → M7 idem=⊤ emit* the design states: *"M7's seating primitive and its Record variants are published per contract (4), so **M5 seats home links by folding M7's pure body**,"* and contract (4) closes with *"so **M3/M7** must publish the pure surface."* This contradicts the decomposition, which is unambiguous on three counts: the seating API/primitive is **M5's** (M5 "owns the arrangement" and "exposes a semantics-blind link-seating API for M7"); **M7's MAKELINK is the driver** ("the link side is discharged by-construction inside M7's MAKELINK, which hands M5 an already-allocated link address through M5's arrangement API"; "seats home links via M5's arrangement API"); and the edge is **M7 → M5** with no return edge. Under contract (4)'s own mechanism, the *folded primitive* is M5's pure seating body and the *enclosing composite* is M7's MAKELINK — i.e. **M7's MAKELINK seats by folding M5's pure body**, and **M5** (with **M3**) must publish the pure surface. As written the design inverts driver, primitive ownership, the arrangement `Record` ownership, *and* the publisher, and would mislead whoever wires M5/M7 (it implies an `M5 → M7` fold, the very cycle the decomposition breaks). The content side is stated correctly (M5's placement folds M3's pure `recompute_max`/`inc`); apply the same direction to links: M7's MAKELINK folds M5's pure seating body. Correct both the M7-seam sentence and the "M3/M7 must publish" clause (→ "M3/M5").

**2. [SHARPENING] Scope the write-confinement contract to *authoritative* writes; exempt derived-hint maintenance.** §8 and Dependencies&seams(2) say a store "that … writes state outside its keys … corrupts silently under merge-at-install." Read literally this indicts the design's own spanfilade — a *global* hint that *every* emit updates (in `apply`) outside the emit's `class_key`/home keys. The resolution is correct but only implicit: the contract governs **staged (authoritative) records** (whose out-of-key deposit would collide on the re-fold); **derived-hint updates in `apply` are re-folded over `cur` in the serialized install section and are consistent regardless of which keys are held.** State this exemption explicitly so a builder maintaining a global hint isn't misled into thinking it violates the contract or trying (impossibly) to key it.

**3. [SHARPENING] Pin the segment-rotation discipline the marker-as-ack property rests on.** The v1 correctness claim "in-order append + prefix-flushing fsync make marker-presence-at-recovery == durably-committed" holds within a segment; across a rotation it requires the old segment to be durable before the new one is appended. Under per-commit `Fsync` this is satisfied **only if a txn's frames never span a segment boundary** (rotate at txn boundaries) or the old segment is fsynced on rotate. Add this to the journal-framing open decision; a builder who rotates at a fixed byte offset mid-txn breaks the property the whole no-second-watermark simplification depends on.

**4. [SHARPENING] Specify global coordination of `LockKey` space-tags.** "Callers prefix a 1-byte space tag so distinct key spaces never collide" pins the mechanism but not who guarantees *cross-store* uniqueness — two stores both choosing tag `0x01` would alias M3's `(home,subspace)` keys with M7's `class_key`s and silently over-serialize or, worse, mis-exclude. State that tags are allocated from a single central enum in the engine crate.

**5. [SHARPENING] Disambiguate "valid marker" in recovery.** §7 and the recovery invariant use "valid" for both "CRC-valid frame" and "committed (CRC-valid *and* `records_checksum`-validates)." This muddies the load-bearing claim "a durable, valid marker is by definition ≤ W": a CRC-valid marker whose `records_checksum` fails (e.g. a bit-rotted or torn-tail txn) is *not* ≤ W. Use distinct terms (e.g. "intact frame" vs "committed marker") so the W-definition and the tail/​fatal classification read cleanly.

**6. [SHARPENING] Tighten the config type-model so invalid/inert pairings are unrepresentable, not runtime-rejected.** The design makes `durable_before_visible` a flag on `SingleApplier` (so "per-key + durable-before-visible" is unrepresentable — good) but leaves three looser cases: `OptimisticCas + Fsync` is constructible and only *panics* at `open` (and the text says "rejects" *and* "PANICS" — pick one, or add `OpenError::InvalidConfig`); `BurnedSeqPolicy` is top-level yet inert except under `SingleApplier{durable_before_visible:true}`; `durable_before_visible` is ignored under `Durability::None`. Fold durability/burned-Seq into the concurrency variant where each applies (e.g. `OptimisticCas` carrying no `Durability`, `BurnedSeqPolicy` only on the durable-before-visible variant) to match the rigor already applied to `durable_before_visible`. The same "ship a runtime panic, float a type-level fix" tension recurs in `critical_section` under `SingleApplier` — resolve both the same way.

**7. [SHARPENING] Note the M9 → M5 path in the M9 seam.** "M9 calls M2 directly only for these snapshot verdicts" is accurate but reads as if snapshots + fires-via-M7 are M9's only M2-touching work; M9's predicate-definition *content* creation rides **M5's placement composite** (M9 → M5 → M2, where J0 fires for predicate-def creation). It's covered by the M5 placement seam, but one clause here would prevent the reader inferring M9 never reaches the placement path.

VERDICT: REVISE
