Reviewed against the source notes (ASN-0047, ASN-0134), the Engine Composition Contract, and the decomposition's boundary for M2. The core transact/snapshot/journal/recovery machinery is concrete and largely buildable, but three material problems remain.

**Revision list (most important first):**

1. **[DEFECT] Move the central `LockKey` space-tag enum out of the engine crate into M2's own crate (`skep-kernel`).** The `LockKey` doc comment, §Dependencies & seams ("The engine crate also owns the single central LockKey space-tag enum"), and the last Open-build-decision all place the tag enum in the **engine crate**. This contradicts the Engine Composition Contract, whose crate graph is explicit — `skep-kernel (M2, + the central Space tag enum) ← every store; no store deps` — and which warns these types must live "below every store — **never in the engine assembly crate (that would cycle)**." Every store must draw its 1-byte tag from this enum; if it lives in `skep-engine`, every store crate gains a dependency on `skep-engine`, which already depends on every store crate → a **hard compile-time cycle** (the exact failure the contract exists to prevent). Fix: M2 *defines* the tag enum in `skep-kernel` as an abstract enum of 1-byte tags — it names only `LockKey`/byte constants, no store types, so M2 stays store-agnostic — and stores reference their assigned variant. The design's rationale (one central enum ⇒ cross-store uniqueness) is correct and unchanged; only the crate is wrong. Update all three mentions.

2. **[DEFECT] Reconcile §7's disposition of a surviving failed-truncation-poison marker with §1's — they contradict.** §1 states the surviving marker is, on recovery, "if its records also check out, simply the last committed marker (recovery replays it…), or, if torn, the discarded tail." §7 instead files "the surviving frames of a barrier-failure-then-truncation-failure" *unconditionally* under "inferred max > W → un-acked/torn tail → discard … they are the tail because no successor ran." For the records-check-out case these disagree: a committed surviving marker **is** the last committed marker (= W, replayed per §1), not a beyond-W frame (discarded per §7). Taken literally, §7 discards durable committed data. Fix: rewrite §7's parenthetical to match §1 and the mechanism — a surviving poison marker whose `records_checksum` validates is the last committed marker (W = its `last_seq`), replayed as a lost-ack/indeterminate op (SAFE(b)(iii)); only a torn one is the discarded tail. "No successor ran" makes it the *last committed* marker, not a beyond-W one.

3. **[DEFECT] Wire `CheckpointPolicy` to a trigger, or demote it — `Interval(Duration)` is unbuildable as written.** `KernelCfg` commits four `CheckpointPolicy` variants in the public interface, but §6 specifies no mechanism that evaluates the policy and calls `checkpoint()`, explicitly calls cadence "an open knob," and `checkpoint()`'s doc says "cadence is the caller's policy." The public surface (kernel-driven cadence) and the internal design (caller-driven / unspecified) disagree, and `Interval` in particular has no buildable path: honoring a time interval requires a background timer whose existence, lifecycle, and interaction with the `&self checkpoint()` the design never describes. Fix: pick one. Either (a) specify M2's trigger — an on-commit counter/byte check inside `transact`'s post-install step for `EveryN`/`JournalBytes`, plus a background timer task (with shutdown coordination) for `Interval` — or (b) make checkpointing purely caller-driven, reduce `CheckpointPolicy` to `Manual` (or drop it from `KernelCfg`), and state cadence is the caller's loop over `checkpoint()`.

4. **[SHARPENING] State that `checkpoint()`/reclamation is internally serialized.** `checkpoint()` takes `&self` and deletes journal segments (reclamation below `S_old`); two concurrent calls would race on the retention set and segment deletion. Add: `checkpoint()` serializes against itself via a dedicated checkpoint mutex (distinct from the applier lock, so it stays non-blocking to writers), keeping retention/reclamation single-threaded even though the API permits concurrent calls.

5. **[SHARPENING] Split witnessed from unwitnessed batches in the "may over-satisfy A5" claim.** §Purpose and Conflicts #1 say M2 "may over-satisfy A5 by committing [a batch] as one transact." For a content run (unwitnessed interior) this is harmless and is indeed how W2 is delivered. For a link-store batch (`retract_stale`), A5 establishes the partial retractions *are* witnessed by an `Observe_K` over the active slice — committing it as one suppresses that, a real observable-behavior change, not a free over-satisfaction. Clarify the recommended default for a witnessed (link) batch is separate `transact`s, and committing-as-one is sound only where no modeled read witnesses the interior (strictly the content run).

6. **[SHARPENING] State the empty-replay boundary in §7.** When no committed marker exists above `S_load`, W is undefined by "last committed marker's `last_seq`." Add: if the scan finds no committed marker above `S_load`, `W = S_load` and Pass 2 replays nothing — fixing the implicit `W ≥ S_load` invariant.

7. **[SHARPENING] State `open()`'s InMemory path.** The design says `InMemory` has "no recovery" but never says what `open()` does. Add: under `Durability::InMemory`, `open()` ignores `journal_path` and any checkpoint and initializes the root directly from `genesis` (`S_load = 0`).

VERDICT: REVISE
