Reviewing M2 against its two source notes (ASN-0047, ASN-0134), the decomposition's boundary, and internal/seam consistency. This is a genuinely strong, careful design — the dependency-inverted `WorldState` fold, the working-tip group-commit reasoning, the phantom-commit/poison failure analysis, and the Seq-refines-𝔼 reconciliation are all sound and faithful. I found one material problem plus several polish items.

## Revision list

**1. [DEFECT] Couple the concurrency-mechanism and durability-ordering knobs — per-key merge-at-install, as specified, forces *visible-before-durable*, contradicting the "durable-before-visible is canonical" claim.** The design presents these as two orthogonal open decisions and calls durable-before-visible the canonical/general default (§3, Conflicts #3), but the enabling mechanism it gives for durable-before-visible under group commit — the working tip that defers root install past the barrier — is described *only* for the single applier and explicitly tagged "specific to the canonical durable-before-visible default" (§1). The §8 per-key flow instead draws `base` from `root.load()` and has the install section "re-fold … and **swap**, fsync batched **outside** the install section" — i.e. install-before-barrier, which *is* visible-before-durable (root-based base, no working tip, swap precedes fsync). So a builder migrating to per-key for throughput while selecting the "canonical" durable-before-visible ordering gets no mechanism for it, and following §8 literally silently enters the external-read-rollback window the design warns about only under the "optional" visible-before-durable variant — and §8 never mentions that per-key barrier failure must therefore *poison* (it cannot be a no-op once the root is installed). The "migration changes no caller's call shape" claim is true for the API but omits this durability-semantics change visible to external M10 readers. **Fix:** either (a) state that per-key merge-at-install (and CAS) entails visible-before-durable — install precedes the batched barrier, external M10-acked reads can reflect rolled-back state, barrier failure poisons — and stop listing durable-before-visible as available there; or (b) specify the deferred-install / install-section working-tip machinery needed to make per-key durable-before-visible under group commit. Then revise the two "open build decisions" (Concurrency, Durability/visibility) to record that they are coupled, not independent.

**2. [SHARPENING] Tighten the footprint-confinement statement: it is a *read-set* contract, but the monotone exception is narrower than "append-only-monotone."** The contract reads "must lie under held keys **or be append-only-monotone (e.g. `a ∈ dom(C)`)**" (§8, Dependencies & seams). The exemption holds only for reads whose *truth value* survives append — positive membership on an append-only set. A *negative* existence test (`a ∉ dom(C)`, a freshness/uniqueness probe) is not monotone-safe and must be under held keys. State this explicitly so a store author cannot read "any read of an append-only structure is exempt." Also reconcile the two phrasings — the headline says "read set," the corruption clause in contract (2) says "reads **or writes** outside its keys" — by noting writes are confined by construction (a txn's staged records touch only its held-key state and disjoint append-only entries), so the *active* obligation is on the read set.

**3. [SHARPENING] Qualify the "no atomicity for a rule firing" disclaimer and reconcile it with M9's stated "atomic fires" seam.** The Purpose section lists "a rule firing" alongside `retract_stale` as a non-atomic batch (ASN-0134 A5). But A5 makes only **m ≥ 2** fires non-atomic; an **m = 1** fire "is a single step, indivisible by A0," which M2 *does* deliver as one `transact`. M9's decomposition seam ("leans on M2 for … atomic fires") refers to exactly that single-emit per-transact atomicity. Add the `m ≥ 2` qualifier and one sentence: a single-step fire is one atomic `transact`; only multi-step fires are the A5 batches left "above the substrate." Otherwise the blanket disclaimer reads as denying a capability M2 in fact provides and a neighbor depends on.

**4. [SHARPENING] Make §6 truncation segment-granular and lean on §7's `Seq > S` filter for correctness.** §6 says "truncate every journal frame with `Seq ≤ S`," but prefix truncation on a segmented log can only drop whole sub-`S` segments; a segment straddling `S` retains some `Seq ≤ S` frames. Recovery is already correct because §7 replays *exactly* `Seq > S` (filtering any surviving `≤ S` frames), but since `apply` is non-idempotent this filter is load-bearing — say so, and reword §6's truncation as a space-reclamation optimization at segment granularity rather than an exact per-frame guarantee.

**5. [SHARPENING] Don't list gap-free `Seq` as unconditional "by construction."** The Invariants header states "Total order, gap-free monotone `Seq`," but gap-freeness depends on `BurnedSeqPolicy::Rollback`; under `TolerateGap` the invariant is monotone-only. Move "gap-free" into a policy-conditional clause (the parenthetical already notes it for Rollback). The `→_sh`-subsequence order-isomorphism to 𝔼 survives gaps, so only the gap-free half is conditional.

**6. [SHARPENING] Specify a max-latency trigger for `FsyncBatch{window}`.** A pure window-fill barrier stalls a low-traffic or single-zero-step-op batch indefinitely (the zero-step op that "waits for the barrier covering `base.seq()`" then waits on a batch that may never fill). Note that group commit needs a window *or timeout* close trigger (and `flush()` as the manual one) to bound commit-before-ack latency.

**7. [SHARPENING] State that `Snapshot<W>` is a newtype, not a bare `Arc<Committed<W>>`.** The data-model prose says "Snapshot<W> is Arc<Committed<W>>," but the public interface gives it an inherent `impl` with `seq()`/`world()`, which the orphan rule forbids on a foreign `Arc`. Make it `pub struct Snapshot<W>(Arc<Committed<W>>)`.

**8. [SHARPENING] Pin down two recovery-scan details left implicit in §7.** (a) The discriminator "position relative to the last valid marker" requires first locating that marker; specify that recovery scans to end to find the last CRC-valid, frame-checksum-validating marker, *then* classifies an earlier CRC failure as `Corruption`. (b) For the scan to skip past a corrupt record to find later markers, the frame CRC must cover the `len` field (else a corrupt length loses frame boundaries); fold "CRC covers len+payload" into the journal-framing open decision.
