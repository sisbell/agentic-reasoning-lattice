I worked through this against ASN-0047 and ASN-0134, checking the WAL/recovery story, the sequencer, the transaction/composite boundary, the keyed critical sections, and the snapshot reads — both for buildability and for faithfulness to the two notes' locked commitments. The decomposition split (M2 owns ordering/durability/isolation, never store semantics) is honored well, the seven MIC clauses are each mapped to a mechanism, and the three named conflicts are resolved soundly. But several concrete mechanisms are either self-contradictory or incorrect for a supported configuration.

## Revision list

**1. [DEFECT] Fix the contradictory CRC-failed-frame rule in recovery (§1/§7).** §7 says, in one sentence, "record frames past the last valid marker, **or a CRC-failed frame**, are a torn tail → discard + truncate," and in the very next sentence "CRC failure *inside a marked (acked) composite* … halt and report … **never silently drop it**." These are contradictory: a CRC-failed frame in the *committed prefix* is both "a CRC-failed frame" (→ discard) and "inside a marked composite" (→ halt). The discriminator the design relies on — *position relative to the last valid marker* — is never stated. As written, a builder who implements the first sentence literally silently discards corrupt **committed** data (and, since `apply` is non-idempotent and Seq-ordered, leaves a hole that produces a wrong recovered state). Restate the rule explicitly: a CRC failure (or an invalid marker) *at or after the last valid marker* is the never-acked torn tail → discard+truncate; a CRC failure *in the committed prefix, before the last valid marker* is corruption of durable acked data → `OpenError::Corruption`, halt, never drop.

**2. [DEFECT] Zero-step `transact` must not return un-barriered when its `base` is the not-yet-durable working tip (group commit).** Under the recommended single-applier **+ group commit + canonical durable-before-visible**, every `transact` draws `base ← tip.load()`, and §3's zero-step path returns `Ok((v, base.seq()))` *immediately, before the batch barrier*. A zero-step `idem=⊤` emit therefore reads its incumbent off the not-yet-durable tip, acks "Hit," and if the batch carrying that incumbent then rolls back on a barrier/crash, the client believes its tuple was deduplicated into an incumbent that no longer exists — a **lost update**. This directly contradicts the design's own Conflicts-#3 guarantee that under the canonical default "an external M10-acked read never reflects a state a crash can roll back." Reading the durable root instead is *not* a fix (it would miss the batched predecessor and double-deposit, violating clause 7). Specify that a zero-step op whose `base` is the working tip must wait for the durability barrier covering `base.seq()` before returning (it "joins" the batch's barrier even though it journals nothing); under per-commit fsync, where `base == durable root`, no wait is needed.

**3. [DEFECT] The stated multi-key acquisition order is incorrect for the `Striped` lock layout.** The invariant "Deadlock-free multi-key acquire — bytewise-sorted, deduplicated" (§4, Invariants) is correct only for the `PerKey` layout. Under `Striped{stripes}`, two *distinct* keys can hash to the *same* stripe (sorting/deduping by **key** double-acquires one non-reentrant `Mutex` → self-deadlock), and bytewise key order does not equal stripe-index order (two transactions can acquire the same two stripes in opposite orders → classic deadlock). This is reachable via the documented two-key M7 emit (`[class_key, key(home, s_L)]`) under `PerKeyMerge`/`OptimisticCas`. Restate the rule over the **resolved lock objects**: for `PerKey`, sort+dedup the keys bytewise; for `Striped`, resolve each key to its stripe index and sort+dedup the **stripe indices**. (Note the bug cannot fire under `SingleApplier`, where the table is unused.)

**4. [DEFECT] Qualify the "true no-op" durability-failure guarantee; specify poison on cleanup failure.** §1/§3 state unconditionally that a barrier failure truncates the un-acked tail and "`TxnError::Durability` is a **true no-op**; caller may safely re-invoke." But the phantom-commit fix *depends on the truncation succeeding*, and the design also rolls the Seq high-water back so the next txn **reuses** the burned Seqs. If the truncation (or its fsync) fails, the failed marker/records survive *and* a later txn writes the same Seqs → journal Seq-collision and possible phantom-commit/colliding-address corruption — the exact load-bearing hazard §1 is built to prevent. Specify that if the un-acked-tail truncation fails to durably complete, the kernel must **poison** (halt; subsequent calls fail) rather than report a safe no-op, and make the "true no-op" claim conditional on truncation success.

**5. [SHARPENING] Correct the "a →_sh record's Seq IS its idx(σ)" overstatement (Seq doc / §2).** The same comment says "A REFINEMENT … **not an identity**" and "M2's full Seq order is a finer total order," then asserts "a →_sh record's Seq **IS** its idx(σ)." Since the Seq counter also advances on `K.μ⁺/K.μ⁻/K.ρ`, a →_sh record's Seq value is *not* its `idx(σ)`. Weaken to: the →_sh subsequence is *order-isomorphic* to 𝔼, so a →_sh record's Seq *corresponds positionally* to its `idx(σ)` — it is not equal to it. (Non-load-bearing: no caller derives `idx(σ)` from `Seq`.)

**6. [SHARPENING] Reconcile optimistic-CAS "retry on change" with `f: FnOnce`.** §8 says "CAS the root, retry on change," while `TxnError::Conflict` is documented as "caller re-invokes" and `f` is `FnOnce`. Because optimistic-CAS holds no keys, a re-fold of already-staged records over a moved frontier would collide — so any internal retry would have to *re-run `f`*, which `FnOnce` forbids. State explicitly that under CAS, install-time change surfaces `Conflict` for the **caller** to re-invoke with a fresh closure (consistent with `FnOnce`); only `PerKeyMerge`, whose held keys keep the frontier fixed, may re-fold without re-running `f`.

**7. [SHARPENING] Make `critical_section`'s single-applier no-op loud.** A method that returns a guard providing *no* run-exclusion under the default `SingleApplier` (§4) is a footgun. Either `debug_assert!`/panic when called under `SingleApplier`, or document the precondition at the method (not only in prose) so a builder cannot silently get a fragmented run.

**8. [SHARPENING] Clarify the group-commit install in the §3 pseudocode.** The flow shows `root.store(tip.load())` in *every* transaction; under group commit only the batch leader installs the final tip once, post-barrier. Annotate which steps are leader-only vs per-txn so a builder doesn't install per-txn.

**9. [SHARPENING] State the `rebuild_derived` ≡ `apply`-fold consistency contract, and disambiguate "Record."** (a) Add the store obligation that `rebuild_derived`'s seeded hints must equal what folding all records ≤ S through `apply` would produce, else recovery diverges from live state. (b) The journal frame payload type `Record{seq,txn,bytes}` collides in name with the trait's `W::Record` enum (whose serialized form is `bytes`); rename one (e.g. `Frame`/`LogRecord`) to avoid confusing a builder.

VERDICT: REVISE
