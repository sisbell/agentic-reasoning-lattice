Skeptical review of M2 — Transaction, Journal & Concurrency Kernel. The core shape is sound and faithful (clean dependency inversion via `WorldState`; the persistent-root + `ArcSwap` realization correctly makes clauses 1/4/6 nearly free; MIC's seven clauses are all mapped; boundary discipline holds — it computes no addresses/frontiers/coverage, enforces no J-couplings, owns no lifecycle; Conflict 1 (composite-atomic vs A5 batches) is resolved well). But the durability/commit path, the concurrency-scaling contract, and one API have material defects.

## Revision list

**1. [DEFECT] Resolve the durability commit/recovery ordering, and make the failure path sound.** §3's canonical flow is `append → durability.commit? → root.store` (fsync-then-install, durable-before-visible), but §1/§8's *recommended* group-commit flow is `append → install → batched fsync → return` (install-then-fsync, visible-before-durable). The canonical pseudocode shows the non-recommended order, so a builder cannot tell which to build. Worse, `TxnError::Durability` ("NOT committed; treat as no-op") is unsound in two ways:
   - *Under the recommended install-then-fsync*, the txn is **already installed** when the barrier runs, so it is not a no-op and cannot be made one (readers/writers may already have built on it) — the only correct response there is to halt.
   - *Under either ordering*, the txn's record + marker frames are appended to the journal **file** before the barrier, so a later successful txn's fsync can flush a "failed" txn's marker to disk; recovery then sees a valid marker and **replays an operation reported as failed** — a phantom commit (and if it was a same-`(d,S)` allocation, the retried T2 computed the same address against a root without T1, so replay double-deposits → collision/corruption).
   
   Fix: pick one ordering as canonical and make §3 match it; specify that a txn's marker is made durable **only as the last step of its own commit** (records-fsync-then-marker-fsync, or truncate-the-failed-frames, or halt) so a durability failure leaves *no recoverable marker* and "no-op" actually holds; and note that Seqs allocated before a failed barrier are burned, which the "monotone, gap-free Seq" invariant must tolerate or roll back.

**2. [DEFECT] State the merge-at-install caller contract; retract the "changes no caller" claim.** The scaling path re-folds `stg.records` over the *current* root at install — correct only if each record's value and effect depend solely on state covered by the held `keys`, or on append-only-monotone state (e.g. `a ∈ dom(C)`, which only grows). This is exactly ASN-0134 G1's commutativity hypothesis, but the design never states it as a caller obligation; "The held keys guarantee no concurrent writer touched this txn's read-set" presents it as automatic, and Conflict-2's resolution asserts migration single-applier→merge happens "without touching any store." That is false: a store written against single-applier that reads or writes state *not* covered by its keys compiles and runs but corrupts silently under merge-at-install. (The examples happen to honor it — M3 holds `key(home,subspace)` over the frontier read, M7 holds `class_key` over the active-in-class read — which is why it works there, and why the contract must be made explicit for *new* store ops.) Fix: state the footprint-confinement obligation on `f` as a seam contract, and qualify the migration claim to "transparent *iff* every store confines its records' footprint to its held keys (modulo monotone reads)" — flagging that "build single-applier first" means stores are written *before* the discipline would otherwise bite.

**3. [DEFECT] `critical_section` provides no run-exclusion under the recommended single-applier impl.** Its stated contract — hold `keys` across separate inner `transact(&[],…)` commits so "the section already serializes," no foreign same-`(d,s_C)` allocation interleaves, readers land mid-run (clause 5 / W2) — requires the lock table to be live and respected by `transact`. But the design says "Under the single-applier impl the table is unused (the global lock subsumes every key)," and the applier lock is **released between** the section's inner transacts (it must be, or the inner transacts can't install). So a foreign `transact([key(d,s_C)],…)` — whose key is a no-op under single-applier — can commit between inner commits and fragment the run, violating W2. Fix: either scope `critical_section` to the per-key-concurrent/CAS impls (and state that single-applier supports only the one-`transact` run, i.e. clause 5's reader-visible-mid-run variant is unavailable there), or require `transact` to acquire lock-table keys even under single-applier whenever a `critical_section` may hold them — in which case the table is *not* "unused."

**4. [SHARPENING] Make the checkpoint/truncate/replay boundary exactly complementary.** "checkpoint @seq," "truncate frames `< seq`," and "replay post-checkpoint records" leave the inclusivity of `seq` ambiguous. Since `apply` is explicitly *not* required to be idempotent (a `Vector`-append record double-applies wrongly), state precisely which Seqs the checkpoint embodies and that replay covers exactly the complement — no overlap, no gap.

**5. [SHARPENING] Qualify the visible-before-durable "safe" argument and reconcile it with ASN-0047.** The prefix-closure argument covers internal causal dependence but not an external *read* acked by M10: under install-then-fsync a client can be told a read result reflecting a committed-but-not-yet-durable state that a crash rolls back. Note this, and surface the latent conflict — ASN-0047 ("make them visible only after the batch is durably committed," from its single-threaded model where visible == acked) vs ASN-0134 (durability orthogonal, not a MIC clause, visible == committed) — as an explicit resolved conflict rather than only an open knob.

**6. [SHARPENING] Tighten the "over-satisfies W2" attribution.** W2 is *chain* (address) contiguity, delivered by holding `key(d,s_C)` across the run; the *Seq*-contiguity of a one-`transact` composite is a different, stronger property. Say the held key delivers W2 and the single atomic install additionally over-satisfies it, rather than attributing W2 to Seq-contiguity.

**7. [SHARPENING] Distinguish `Seq` from ASN-0134's `idx(σ)`.** M2 assigns a `Seq` per *record* — including K.μ⁺/K.μ⁻/K.ρ steps outside ASN-0134's `→_sh = {K.σ, K.α, K.λ_sh}` vocabulary — so M2's order is a *refinement* of `𝔼`, not an identity. State this so "Seq = idx(σ)" isn't misread.

**8. [SHARPENING] Return the committed `Seq` from `transact`.** Callers reporting a *write* retrospectively (V1 — e.g. M9 reporting a fire's index) currently get only `T`; a post-hoc `current_seq()` is `≥` the write's Seq under per-key concurrency, not exact. Return the committed `last_seq` alongside `T`.

VERDICT: REVISE
