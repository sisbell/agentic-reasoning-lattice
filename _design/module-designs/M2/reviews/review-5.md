Reviewing M2 against ASN-0047, ASN-0134, and the decomposition's stated ownership/seams. The design is, on the whole, faithful and unusually careful about boundaries — it correctly stays generic over opaque keys/payloads, delegates permanence/J-couplings/frontiers to neighbors, discharges all seven MIC clauses, and resolves the three real cross-note conflicts soundly. The defects are concentrated in the recovery/failure path, where stated guarantees outrun the mechanisms given to deliver them.

## Revision list

**1. [DEFECT] Recovery fallback (`OpenError::BadCheckpoint`) contradicts §6's journal reclamation.** §6 reclaims (drops) *every* journal segment whose frames are `Seq ≤ S` for the **just-written** checkpoint `S`; but `BadCheckpoint`'s documented remedy is "fall back to an earlier one or genesis." Once reclamation has run against `checkpoint.<S>`, the frames an earlier-checkpoint replay (`> S'`) or a genesis replay (`> 0`) would need are gone — so a *corrupt newest checkpoint* in steady state is silently **unrecoverable**, while the design advertises a fallback. Fix: tie reclamation to the **oldest retained** checkpoint, not the newest — keep N checkpoints plus the journal back to the oldest one you'll fall back to, reclaiming only segments below *that* `S` — **or** delete the fallback claim and state plainly that the newest checkpoint is the sole recovery base once its covering journal is reclaimed (mandating redundant/verified checkpoint writes). Make §6's reclamation bound and the `BadCheckpoint` comment agree.

**2. [DEFECT] The "poisoned" state has no representation in the public types, and the load-bearing retryable-vs-poison distinction cannot be signaled.** The whole §1 failure narrative requires a caller (M10/M3) to distinguish "true no-op, safe to re-invoke" (`TxnError::Durability` after a *successful* un-acked-tail truncation) from "poisoned, halt, do **not** re-invoke" (truncation failed, or any visible-before-durable barrier failure). The design explicitly says poison must **not** return `Durability` — yet there is no other fitting variant, so the **poisoning call's own return value is unrepresentable**; "subsequent calls fail" names no variant; and the infallible read APIs (`snapshot`, `current_seq`) have no error channel to report poison at all. Fix: add a distinct `TxnError::Poisoned` (and `CheckpointError::Poisoned`) returned by both the poisoning call and every later write/checkpoint call, and specify `snapshot()`/`current_seq()` behavior on a poisoned kernel (per the design's own reasoning, both poison scenarios leave the in-memory root consistent, so reads may keep serving it — say so explicitly, or give them an error channel if they must fail).

**3. [DEFECT] Recovery's "scan past a bad frame to locate the committed tip" has no resync mechanism in the frame format.** §7 commits to *distinguishing* a torn tail (discard) from committed-prefix corruption (halt, "never silently drop"), which requires scanning the whole journal for the last valid marker — i.e. scanning *past* an interior bad frame to see whether a marker follows it. But `[u32 len][u32 crc][payload]` carries no resync anchor: CRC-over-`len` only *detects* a corrupt length; it does not *locate* the next frame (whose offset depended on that bad `len`). As written, a builder cannot resynchronize, so cannot tell interior corruption from a torn tail except by "stop at first CRC failure" — which silently drops committed data after an interior corruption, the exact outcome §7 forbids. Fix: add a per-frame magic/sync word (scan forward for it after a bad frame) or segment-aligned frame starts, **or** maintain a separately-durable committed-tip `Seq` so recovery knows the tip without scanning, **or** downgrade the contract to "stop at first CRC failure; interior corruption is treated as torn tail" and drop the never-silently-drop guarantee. Pick one and make the frame layout and §7 consistent.

**4. [SHARPENING] Make the invalid `concurrency × visibility` combinations unrepresentable or reject them.** `KernelCfg` exposes the two as independent fields, but the design declares them coupled (`DurableBeforeVisible` is `SingleApplier`-only; `PerKeyMerge`/`OptimisticCas` are necessarily `VisibleBeforeDurable`). No validation or error is specified, so a builder is left to silently override — which would violate a caller's durability expectation. Fold `visibility` into the `Concurrency` variant (e.g. `SingleApplier { durable_before_visible: bool }`, no such knob on the concurrent variants), or add `OpenError::InvalidConfig` and reject the invalid pairs at `open`; do not silently override.

**5. [SHARPENING] Reconcile §3's per-txn pseudocode with §1's group-commit ordering, and pin the lock discipline for the zero-step wait.** §3 shows `durability.barrier()` and `root.store()` inside the applier-locked per-txn region; under group commit the barrier runs once at batch close and only the leader installs (stated in comments/§1, but the body reads as per-txn). Spell out that under group commit the applier lock is released after appends (before the shared barrier), so the leader's fsync and a zero-step op's "await the barrier covering `base.seq()`" cannot deadlock against a held applier lock, and name the completion-signal primitive (a durable-watermark + waiters) the zero-step wait uses.

**6. [SHARPENING] State that M9's rule *fires* reach M2 through M7's gated write path, not via M9 calling `transact` directly.** The M6/M8/M9 seam ("M9 … sequences [a multi-step fire] as several `transact`s," "takes the fire's index from the `Seq` that `transact` returns") reads as M9 invoking M2 directly for writes; per the DAG, M9 calls M2 directly only for snapshot verdicts, while fires go M9 → M7 (`Emit_K`) → M2. Clarify the routing so the seam matches the `M9 → M7` edge.

**7. [SHARPENING] Specify, under merge-at-install/CAS, when a txn releases its keys.** The flow holds keys across `f`-and-install and must release them *after* the root swap (so a same-key successor's `f` reads the just-installed frontier — clause 2) but *before* the batched fsync. This is correct but only implied; making it explicit forecloses a builder releasing too early (collision) or too late (serializing through fsync).

**8. [SHARPENING] Note in §7 that recovery does not require Seq-contiguity.** Folding present records in `Seq` order tolerates a `BurnedSeqPolicy::TolerateGap` gap in the committed prefix harmlessly; only a *CRC failure* before the committed tip is corruption. One line prevents a builder from adding a contiguity check that falsely trips under `TolerateGap`.

VERDICT: REVISE
