# Review — M2: Transaction, Journal & Concurrency Kernel

The core path (single applier + per-commit `Fsync` + checkpoint/replay recovery) is soundly specified, the source-note contracts are honored at the right boundary, and the three named conflicts are resolved cleanly. The defects below are concentrated in the **group-commit optimization** (which M2 *added* beyond ASN-0047/0134 and specifies as if complete) and in the **poison/recovery corner** — places where the design's own prose/invariants contradict its mechanism.

## Revision list

**1. [DEFECT] §7's recovery claim contradicts §1's poison reasoning, leaving a phantom-commit hazard.** §1 establishes that when a barrier fails *and* the un-acked-tail truncation also fails, "the failed records+marker survive on disk" and "a surviving failed marker would still replay as a phantom commit" — which is *why* it poisons. But §7 then asserts: "a failed-barrier txn's frames were already truncated at failure time *(or the kernel poisoned)*, so no failed marker survives to replay." The parenthetical is false: poisoning halts the current process but does nothing to the on-disk frames, and a CRC-valid-but-never-acked marker is byte-indistinguishable from a committed one. A restart's normal `open()` therefore finds it as the committed tip and replays it — the exact phantom commit §1 poisons to avoid. This is the recovery contract's soundness, and it bites even per-commit `Fsync`. Note the deeper root: recovery equates "valid marker on disk" with "durably committed," but the durable/acked status is recorded nowhere, so a present-but-unacked marker is misread as committed whenever truncation can't remove it. Fix: reconcile §7 with §1 — either (a) state that a poisoned-tail journal cannot be processed by normal recovery and have `open()` detect/refuse it via a *durably-recorded* "clean up to Seq S" / clean-shutdown record that bounds the trustworthy prefix, or (b) record ack-status durably so recovery can distinguish an acked marker from a present-but-unacked one. As written the design overclaims recovery soundness for precisely the case it flagged as corrupting.

**2. [DEFECT] The group-commit leader's `root.store(tip.load())` (§3) can publish state past the durable watermark, breaking durable-before-visible.** Under `FsyncBatch` the applier lock is released after each txn's append+`tip.advance`, and the barrier+install run **unlocked** specifically so "later txns append under the lock" while the leader fsyncs. Those next-batch appends advance the single running tip, so a fresh `tip.load()` *at install time* (after the unlocked barrier) returns a `Committed` whose `seq` exceeds the batch's `last_seq` — the point the barrier covered and the watermark was raised to. Installing it makes `root.seq() > watermark`: external readers then see a not-yet-durable working-tip state. This flatly contradicts the §3 prose ("publish the batch's FINAL tip") and the §Invariants claim "external readers see only the post-barrier root, never the applier's working tip," and reintroduces the visible-before-durable window the whole ordering exists to close — *common under load*, exactly when group commit is used. Fix: the leader must **capture** the batch-final `Committed` at batch close (its `seq` == the `last_seq` it fsyncs to and raises the watermark to) and install *that* value, guaranteeing `root.seq() == watermark`; never re-`tip.load()` after the barrier.

**3. [DEFECT] The group-commit zero-step watermark-wait has no failure path — a barrier failure hangs or returns a stale verdict.** §1/§3 correctly make a zero-step op (idem-hit/nullify-hit/read) reading the not-yet-durable working tip park on the watermark until it covers `base.seq()` — but only the *success* path is specified. If the batch it read from fails its barrier and rolls back (truncate + Seq rollback), the watermark never reaches `base.seq()` (those Seqs are burned). Under `TolerateGap` the parked op hangs forever; under the default `Rollback`, a later txn reuses the burned Seqs, the watermark eventually covers `base.seq()`, and the op wakes and returns its provisional value (e.g. an idem=⊤ "Hit") computed against a state that never durably committed — a **V1 violation** (a verdict about a non-committed state) and, for the idem-hit, a **clause-7 violation** (the client is told a link exists when the deduplicated incumbent was rolled back). Fix: specify that a barrier failure wakes parked zero-step waiters to **re-evaluate** against the reset tip/current root rather than return the provisional value, and ensure a burned-then-reused `Seq` cannot satisfy a stale waiter (wake-to-retry on rollback, or have the waiter verify its `base` *identity*, not merely `watermark ≥ base.seq()`).

**4. [SHARPENING] Document that `transact` is non-reentrant and that composites compose a neighbor's pure math, not a nested `transact`.** A nested `transact` inside an `f` deadlocks (the applier lock / install serialization point is already held). The "M5 mints content addresses via M3" phrasing plus the standalone-`transact` M3 seam example invites a builder to call M3's allocation `transact` inside M5's placement closure. State that M5's content K.α reuses M3's `recompute_max`/`inc` against `stg.base()` *within* one closure, and that `transact` must never be called from within an `f`.

**5. [SHARPENING] The `OptimisticCas` realization CAS-es the whole root, so it aborts on *any* concurrent commit, not just a same-key one.** "Viable when same-key contention is rare" is wrong for the mechanism as specified (CAS on the single `ArcSwap`); it should read "viable when the **overall** commit rate is low," or the realization should be re-specified as a narrower per-key/frontier CAS (matching ASN-0134's "install if frontier unchanged") that aborts only on a same-footprint move.

**6. [SHARPENING] Pin `current_seq()` to the installed root's seq.** It should equal `snapshot().seq()`, not the in-flight Seq high-water; under group commit the high-water can name a not-yet-installed/not-yet-durable Seq no reader can observe, misleading an "as of `current_seq()`" verdict (V1).

**7. [SHARPENING] State the writer-side dual of footprint confinement.** The contract gives only the reader obligation, but the M7-emit seam's claim that the active-in-class read is "footprint-confined to the held `class_key`" silently *also* requires every writer of active-in-class — notably a same-class **nullify** — to hold `class_key`. Either state this dual or note that the uncovered emit-vs-nullify race is benign per ASN-0134 §4(ii) (valid-serialization, not a duplicate), so confining that read is sufficient-not-necessary.

**8. [SHARPENING] Define `checkpoint()`/`flush()` under `Durability::None`.** With no journal, presumably `checkpoint()` is a no-op returning `current_seq()` and `flush()` returns `Ok(())`; say so, so the MIC-faithful in-memory realization's lifecycle is fully specified.

**9. [SHARPENING] Resolve the §2 linearization-point wording against the returned coordinate.** §2 says "a →_sh record's Seq assignment is its linearization point," yet `transact` returns `last_seq` (a composite's terminal record, e.g. K.ρ, not its interior K.α). Clarify that for a multi-record composite the externally-observable coordinate is `last_seq` (the composite installs atomically; the interior →_sh Seq is internal and not separately observable).

VERDICT: REVISE
