I reviewed the M2 design against the decomposition, the Engine Composition Contract, and the ASN-0047/ASN-0134 statements, checking buildability, note-fidelity, boundaries, conflicts, altitude, and internal consistency. I found no defect-grade problems: every owned capability (journal, sequencer, transaction boundary, keyed serialization seam, snapshots, checkpoint, recovery, commit gate) is specified to implementable depth with real types; the three note conflicts are resolved explicitly and soundly; the boundary discipline matches the decomposition (J-couplings, frontier math, and the request lifecycle are correctly left to M5/M3/M10); and the recovery classifier arithmetic checks out, including the marker-landing `last_seq + 1` rule and the `TolerateGap` over-halt direction. What remains is a short list of genuine but non-load-bearing tightenings.

**1. Revision list**

1. **[SHARPENING]** In §1 (Segments), state explicitly that a segment's `lastSeq` exists only for *closed* segments (finalized at rotation; under name-by-`firstSeq` it is inferred from the successor's name), and that the final/active segment is therefore **always scanned by recovery and never range-skipped (§7) or range-reclaimed (§6)**. Both listed representations already imply this when implemented naturally, but the skip/drop rules are stated unconditionally by recorded range, and §7's cross-session `Txn`-uniqueness argument silently depends on the scan always reaching the torn tail — one sentence closes the only reading under which a stale-low live-segment range could hide the tail from truncation, or let reclamation drop the active file when `W = S_old`.

2. **[SHARPENING]** In §3 (Panic policy), state that the drop-guard is **unwind-only** (fires only when the thread is panicking) or is explicitly disarmed on the `Durability`/`Poisoned` error-return paths as well. The text says it is "disarmed at the two early returns and at install," which leaves it armed across the mid-flow error returns; a plain scope-guard would then re-run the truncate/rollback there — benign only because the `Rollback` reset is an absolute set to the last committed `last_seq` (idempotent), a property the design uses but never names.

3. **[SHARPENING]** In `open()`'s contract, require (or recommend) exclusive ownership of `journal_path` — e.g., an advisory lock file taken in `open()`. The marker-as-ack equality, tail truncation, and single-applier arguments all presume exactly one live kernel per journal; a second process running recovery (with its durable truncation) against a live appender would corrupt the journal, and the design currently leaves the single-instance assumption implicit.

4. **[SHARPENING]** In §7's known-limitation paragraph, widen "exposed only for the last committed txn" to the trailing **suffix** of committed txns: a multi-frame decay run that reaches EOF (or removes every later committed marker) demotes `W` past several acked txns and silently tail-discards them all by the same mechanism. The single-bit-rot phrasing is exact for its stated model but understates the reach of the identical disposition.

5. **[SHARPENING]** Consider carrying the evaluated-against base `Seq` in `TxnError::Rejected` (mirroring the zero-step `Ok` path's `base.seq()` return). A rejected call is one of A1's zero-step cases and A2 assigns it the one index it read; surfacing that coordinate gives M10 a V1-style retrospective referent for its typed rejections at no cost.
