# M2 — Transaction, Journal & Concurrency Kernel — Detailed Design

## Purpose & boundary

M2 is the engine's **generic transactional substrate**: it turns every state change into one atomic, totally-ordered, durable, recoverable step (or a composite committed as one), serves consistent snapshots of committed state, and serializes same-key writers — *knowing nothing about what any change means*. It is a WAL + atomic-install + keyed-serialization + snapshot engine that the stores plug into, dependency-inverted: M2 defines the fold (`WorldState::apply`), the engine implements it, and M2 only calls down through that trait. **One thing well: make the spec's single sequential, atomic-step order real and durable for a plural, concurrent world — over an opaque payload and opaque keys.**

It does **not**: compute addresses, frontiers, or coverage-classes (M1/M3/M7 supply keys and do the math — M2 has no address algebra); enforce store permanence P0–P3 or the J-couplings (the stores enforce those at their composite boundaries *through* M2, never by it — see ASN-0047); interpret record semantics; own the request lifecycle, the parse/dispatch table, or the acknowledgment-to-client (M10 — M2 keeps only the commit-gate *mechanism*); own derived hints (the stores do; M2 journals only authoritative deltas); or bundle a caller-separate *multi-step* (`m ≥ 2`) batch (`retract_stale`, a multi-step rule firing) into one atomic unit — it offers only the per-`transact` atomic unit, so a store honors A5's intended partial visibility by issuing the batch as *separate* `transact`s, and *may* over-satisfy A5 by committing it as one; M2 neither forces nor forbids the granularity (ASN-0134 A5: "atomicity must be built above the substrate"). A *single-step* (`m = 1`) fire, by contrast, **is** one atomic `transact` — indivisible by A0, exactly the "atomic fires" M9 leans on — so only `m ≥ 2` fires are the A5 batches left above the substrate.

## Public interface

The kernel is `Kernel<W>` for an engine-supplied `W: WorldState`. Keys are opaque bytes; payloads are the engine's `Record` enum (`W::Record`). All write paths return only after their commit is durable AND installed (commit-before-acknowledge).

```rust
// ---- The engine's contract to M2 (dependency-inverted) ----
pub trait WorldState: Clone + Serialize + DeserializeOwned + Send + Sync + 'static {
    type Record: Serialize + DeserializeOwned + Clone + Send + Sync + 'static;
    /// The ONE deterministic, total, side-effect-free fold step — drives both live
    /// commit and replay. Folds authoritative deltas AND maintains every derived hint
    /// incrementally; a hint NOT folded here is stale after every live write and after
    /// replay (rebuild_derived runs only at load — see below). Deterministic so replay
    /// reproduces committed state exactly; NOT required to be idempotent — recovery
    /// applies each committed record exactly once (the checkpoint embodies Seq ≤ s,
    /// replay covers Seq > s; §6/§7).
    fn apply(&self, record: &Self::Record) -> Self;
    /// Seed derived hints from authoritative state. Runs ONCE at load, BEFORE replay,
    /// and NEVER on a live commit — so it cannot keep any hint current by itself.
    /// Incremental hint maintenance MUST live in `apply` (which runs on every live
    /// commit AND every replay step); `rebuild_derived` exists solely to reconstruct
    /// hints a checkpoint skip-serialized (`#[serde(skip)]`). Default identity (hints
    /// folded by `apply` and serialized in the checkpoint); override iff hints are skipped.
    ///
    /// CONSISTENCY OBLIGATION: an override MUST seed exactly the hint state that folding
    /// every record with Seq ≤ S through `apply` would produce (S = the loaded checkpoint's
    /// seq). Recovery runs `rebuild_derived` (to seed hints for Seq ≤ S) THEN replays
    /// Seq > S through `apply`; if this seed disagrees with the `apply`-fold of the ≤ S
    /// prefix it stands in for, the recovered hint diverges from the live-maintained one
    /// and reads go wrong. The two hint-maintenance paths must produce identical hints.
    fn rebuild_derived(self) -> Self { self }
}

/// Opaque serialization key. M2 only Eq/Hash/Ord-s the bytes (Ord is bytewise, for
/// deadlock-free acquisition — NOT tumbler order). Callers prefix a 1-byte space tag
/// so distinct key spaces (e.g. (home,subspace) vs coverage-class) never collide.
pub struct LockKey(pub Vec<u8>);

#[derive(Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Hash, Debug)]
pub struct Seq(pub u64);  // M2's per-record linearization coordinate; monotone, gap-free.
                          // Copy, so seq()/current_seq() return it by value (§ergonomics).
                          // A REFINEMENT of ASN-0134's 𝔼, not an identity: every →_sh step
                          // (K.σ/K.α/K.λ_sh) gets a Seq, but so do the non-→_sh records a
                          // composite stages (K.μ⁺/K.μ⁻/K.ρ). The subsequence of Seqs carrying
                          // →_sh records is order-isomorphic to 𝔼, so a →_sh record's Seq
                          // corresponds POSITIONALLY to its idx(σ) — it is NOT equal to it (the
                          // counter has also advanced on the interleaved non-→_sh records). M2's
                          // full Seq order is a finer total order (§2). No caller derives idx(σ)
                          // from Seq.
```

**Config & errors** — the knobs the Open-build-decisions section selects; carried on `KernelCfg`.

```rust
pub struct KernelCfg {
    pub journal_path: PathBuf,        // directory for journal segments + checkpoints (Durability::None ignores it)
    pub concurrency: Concurrency,     // SingleApplier{durable_before_visible} (default true) | PerKeyMerge | OptimisticCas.
                                      //   Visibility is NOT a separate knob: it is FOLDED into this variant (§1/§8) — the
                                      //   `durable_before_visible` flag exists ONLY on SingleApplier (true = canonical,
                                      //   the default; false = opt-in throughput variant). PerKeyMerge/OptimisticCas are
                                      //   necessarily visible-before-durable and carry no such flag, so the invalid
                                      //   "concurrent + durable-before-visible" pairing is UNREPRESENTABLE.
    pub durability: Durability,       // Fsync | FsyncBatch{window,max_delay} | None
    pub burned_seq: BurnedSeqPolicy,  // Rollback (gap-free, default) | TolerateGap (monotone-only) (§1)
    pub checkpoint: CheckpointPolicy, // EveryN(u64) | Interval(Duration) | JournalBytes(u64) | Manual (§6)
    pub retain_checkpoints: usize,    // N ≥ 1 most-recent checkpoints kept; the journal is reclaimed only BELOW the
                                      //   OLDEST retained one, so BadCheckpoint can fall back to an older retained
                                      //   base. N = 1 ⇒ newest is the sole base, no fallback (§6/§7).
    pub locks: LockLayout,            // Striped{stripes} | PerKey — unused under SingleApplier (§4)
}
pub enum Concurrency { SingleApplier { durable_before_visible: bool }, PerKeyMerge, OptimisticCas }
pub enum Durability  { Fsync, FsyncBatch { window: usize, max_delay: Duration }, None }  // batch closes on
                          // window-fill OR max_delay, whichever fires first (a window-only trigger would stall a
                          // low-traffic batch — and any zero-step op waiting on its barrier — indefinitely, §1);
                          // flush() forces an immediate close. A SINGLE in-order flusher resolves batches strictly
                          // in order — one fsync amortized over the txns WITHIN a batch, no cross-batch overlap (§3).
pub enum BurnedSeqPolicy { Rollback, TolerateGap }
pub enum CheckpointPolicy { EveryN(u64), Interval(Duration), JournalBytes(u64), Manual }
pub enum LockLayout  { Striped { stripes: usize }, PerKey }

pub enum OpenError {
    Io(io::Error),
    BadCheckpoint,           // no retained checkpoint loads (each unreadable / failed its checksum) and genesis is
                             // unreachable (its covering journal reclaimed). Recovery internally falls back
                             // newest → next-older RETAINED checkpoint → genesis-while-reachable (§6/§7); this is
                             // returned only when that whole chain is exhausted.
    Corruption { at: Seq },  // CRC failure in the GENUINELY-REPLAYED range (S_load, committed tip] — durable
                             // acked data the recovered state needs is corrupt; halt, never drop. A CRC failure at
                             // Seq ≤ S_load is NOT fatal — it is skipped (already embodied in the loaded
                             // checkpoint, discarded by the Seq > S_load filter) — and one at/after the tip is the
                             // torn tail, not corruption (§7).
    PoisonedTail { trusted_through: Seq },  // a durable Poison sentinel — written when a barrier-failure
                             // truncation ITSELF failed to complete durably (§1) — bounds the trustworthy prefix
                             // at `trusted_through`. The tail beyond it MAY hold a CRC-valid-but-never-acked
                             // phantom marker that is byte-indistinguishable from a committed one (a bare marker
                             // carries no ack-status), so recovery reconstructs state through `trusted_through` and
                             // then REFUSES the tail rather than risk replaying a phantom commit. Operator
                             // intervention required (§7).
}
pub enum CheckpointError { Io(io::Error), Serialize, Poisoned }  // Poisoned: a prior barrier/truncation failure has
                             // halted the kernel (§1); no further checkpoint is taken.
```

**Lifecycle**

```rust
impl<W: WorldState> Kernel<W> {
    /// Recover (load the latest valid RETAINED checkpoint @S_load — on BadCheckpoint fall
    /// back to the next-older retained checkpoint, then to genesis while still reachable
    /// (§6/§7) → rebuild_derived → replay committed records with `Seq > S_load`) or init
    /// from `genesis` (= Σ₀, with S_load = 0). If a durable Poison sentinel is present,
    /// reconstruct through its `trusted_through` and return `PoisonedTail` (§7).
    pub fn open(cfg: KernelCfg, genesis: W) -> Result<Self, OpenError>;
    /// Persist a checkpoint embodying all records with `Seq ≤ s`, keep the most recent
    /// `retain_checkpoints` checkpoints, and reclaim journal segments lying wholly BELOW the
    /// OLDEST retained checkpoint (segment-granular — §6); recovery then replays exactly the
    /// records above whichever retained checkpoint it loads. Non-blocking to writers. Cadence
    /// is the caller's policy. Returns the checkpointed seq `s`, or `CheckpointError::Poisoned`
    /// if a prior barrier failure has halted the kernel (§1). Under `Durability::None` (no
    /// journal) it is a NO-OP returning `current_seq()` — there is nothing to persist or reclaim.
    pub fn checkpoint(&self) -> Result<Seq, CheckpointError>;
    /// Drain pending (group-commit) durability barriers; the manual group-commit close
    /// trigger; used at shutdown/checkpoint. On a POISONED kernel this is a no-op returning
    /// Ok (durability state is frozen — §1); under `Durability::None` there are no barriers to
    /// drain, so it is likewise a no-op returning `Ok(())`. A barrier failure it triggers
    /// surfaces as the precipitating io::Error here and (if it poisons) as `Poisoned` on the
    /// next transact/checkpoint.
    pub fn flush(&self) -> Result<(), io::Error>;
}
```

**Writes (transactions / composites)** — discharge clauses 1, 2, 3, 5, 7.

```rust
impl<W: WorldState> Kernel<W> {
    /// Hold `keys` for the txn's duration, run `f` against a consistent state, and —
    /// iff `f` returns Ok with ≥1 staged record — commit them atomically & durably
    /// under one commit marker, INSTALL the root, then return (A7). Returns `(T, Seq)`:
    /// the closure's value and the committed `last_seq` — a write's V1 retrospective
    /// coordinate, exact even under per-key concurrency (unlike a post-hoc `current_seq()`).
    /// `f` returning Err → clean typed rejection, nothing committed, no dangling state.
    /// `f` returning Ok with zero records → zero-step op (A1: read-only / idem-hit /
    /// nullify-hit), no commit; the returned Seq is then `base.seq()` — the committed index
    /// the op evaluated against (V1). UNDER DURABLE-BEFORE-VISIBLE GROUP COMMIT a zero-step
    /// op whose `base` is the not-yet-durable working tip first locates that tip's IN-FLIGHT
    /// BATCH via the batch handle the working tip carries (§3) — which may be a closed-but-
    /// resolving batch, not the currently-forming one — enrolls in THAT batch's waiter set,
    /// and WAITS to be resolved at the batch's serialized resolution (§3), woken once that
    /// base is durable+installed — before returning: it journals nothing, but must not
    /// acknowledge a value read off a state a batch rollback could erase (e.g. an idem-hit
    /// deduplicated against a still in-flight batched incumbent — §1/§3). If that base is
    /// instead ROLLED BACK by a barrier failure, the op is woken to retry and returns
    /// `TxnError::Conflict` (caller re-invokes), NEVER its provisional value (§3). Under
    /// per-commit fsync `base` is already durable, so no wait.
    ///
    /// NON-REENTRANT: `f` MUST NOT call `transact`/`critical_section` (or any kernel write
    /// path) — the applier lock / install serialization point is held, so a nested write
    /// DEADLOCKS. A composite composes neighbors' PURE math (e.g. M3's `recompute_max`/`inc`
    /// against `stg.base()`) inside ONE closure, never a transaction-within-a-transaction (§3).
    pub fn transact<T, E>(
        &self,
        keys: &[LockKey],
        f: impl FnOnce(&mut Staging<W>) -> Result<T, E>,
    ) -> Result<(T, Seq), TxnError<E>>;
}

pub struct Staging<W: WorldState> { /* base, working, records */ }
impl<W: WorldState> Staging<W> {
    pub fn base(&self) -> &W;            // Σ — the read snapshot at txn start (the applier's working tip; §3)
    pub fn working(&self) -> &W;         // Σᵢ — base folded with records so far (intra-composite checks)
    pub fn push(&mut self, r: W::Record); // fold into working, append to the txn's records
}

pub enum TxnError<E> {
    Rejected(E),            // f's typed precondition failure — surfaced verbatim to M10
    Durability(io::Error),  // durable-before-visible (SingleApplier{durable_before_visible:true}) ONLY: a barrier
                            // failed BEFORE install AND the txn's (or its batch's) un-acked tail was durably
                            // truncated, so nothing was installed and no failed marker survives → a TRUE no-op;
                            // caller may safely re-invoke. The single in-order flusher keeps the failing batch the
                            // journal tail, so this truncate-tail no-op is sound for a batch exactly as for a single
                            // commit (§3). If the truncation ITSELF fails to complete durably the kernel POISONS
                            // and the call returns `Poisoned` INSTEAD (a surviving failed marker + the reused burned
                            // Seqs would corrupt — §1). Under visible-before-durable — the
                            // SingleApplier{durable_before_visible:false} variant AND the necessary ordering of
                            // PerKeyMerge/OptimisticCas (§8) — a barrier failure instead returns `Poisoned`
                            // (the txn is already installed and cannot be unwound), so this is never returned there.
    Conflict,               // the caller must re-make the staged decision with a FRESH closure (f is FnOnce, so
                            // the kernel cannot re-evaluate internally). Two sources:
                            //   (1) optimistic-CAS impl — the root moved between read and install, so the staged
                            //       records can be neither re-folded (they would collide on the moved frontier)
                            //       nor reproduced without re-running f;
                            //   (2) a group-commit ZERO-STEP op under SingleApplier{durable_before_visible:true}
                            //       (idem-hit/nullify-hit/read decided against the not-yet-durable working tip)
                            //       whose `base` batch was ROLLED BACK at its serialized resolution (§3) — the
                            //       provisional value was decided against a now-erased state and acking it would
                            //       violate V1 / clause 7, so the op is woken to retry.
                            // Never under per-key merge-install, whose held keys pin the frontier so it re-folds the
                            // staged records WITHOUT re-running f, and whose installed root is a real committed
                            // state no rollback erases.
    Poisoned,               // the kernel was halted by a prior UNRECOVERABLE barrier/truncation failure (§1):
                            // a surviving failed marker (durable-before-visible, truncation failed) or an
                            // already-installed-but-not-durable root (visible-before-durable) makes further
                            // writing unsafe. Returned by the poisoning call ITSELF (in place of Durability)
                            // and by every later transact; reads (snapshot/current_seq) keep serving the last
                            // consistent root.
}
```

## Core data model

The **only durable, authoritative state M2 owns is the journal.** Everything in memory is a recoverable fold of it (Lampson: the log is the truth; in-memory structures are hints). Within the recovered `World`, the *store-level* distinction between authoritative slices (C, L, E, M, R) and derived hints (spanfilade, reverse indexes) belongs to M4/M5/M7 — to M2 the whole `World` is one fold.

| Structure | Shape | Authority | Why this shape |
|---|---|---|---|
| **Journal** | append-only file(s) of magic-anchored, CRC-framed records + per-txn commit markers, every frame `txn`-tagged (so recovery groups a transaction's records to validate its marker's checksum even after a `magic`-resync skips a corrupt frame — §1/§7) (+ a durable poison sentinel written only in §1's failed-truncation corner) | **authoritative, durable** | record-of-record; replay reconstructs everything; append-only makes immutability of committed steps free (ASN-0047 P0/P1/P2 at the log level); the per-frame magic word anchors recovery resync (§1/§7); the poison sentinel bounds the trustworthy prefix when a failed-barrier truncation cannot itself complete (§1/§7) |
| **Root** | `arc_swap::ArcSwap<Committed<W>>`, `Committed { seq: Seq, world: W }` | recoverable materialization | lock-free reads; **atomic install = atomic, indivisible step (A0/A4)**; persistent `W` (im) ⇒ snapshot & install are O(1) and snapshots never tear |
| **Working tip** | `Committed<W>` + its in-flight **batch handle**, held by the applier across a group-commit batch | volatile (internal to the applier; never externally visible; rebuilt fresh on recovery) | lets a batched txn read its predecessors' (same-batch) not-yet-published records (correct dependent reads); the leader captures it at batch close and the batch's final state reaches **Root** via the leader's serialized, **monotonic** install *after* the barrier (§3) — never a fresh post-barrier `tip.load()`; the batch handle lets a parked zero-step op enroll in the specific (possibly closed-but-resolving) batch its `base` belongs to (§3). The single in-order flusher (§3) keeps the batch under barrier the journal tail. **single-applier `durable_before_visible:true` only; per-key/CAS install before the barrier and need no tip (§8)** |
| **Durable watermark** | monotone `Seq` "max committed-durable-and-installed" + waiters (a condvar) | volatile (rebuilt at recovery as the committed tip's `last_seq`) | the **post-install** completion signal: at a group-commit batch's serialized resolution the leader installs the root and *then* raises this watermark to the batch `last_seq`, *then* wakes parked `transact`s and zero-step ops once it covers their `last_seq`/`base.seq()` (§3) — so a woken waiter's effect is already in `root` (A7). On a batch rollback the affected waiters are instead woken to retry (zero-step ops → `Conflict`) |
| **Checkpoint** | serialized `W` @ `Seq` on disk (temp→fsync→rename), most recent `retain_checkpoints` kept | recoverable cache (a prefix-fold) | bounds replay time; optional; the oldest retained one is the journal-reclamation floor and the `BadCheckpoint` fallback base (§6) |
| **Lock table** | striped `Vec<parking_lot::Mutex<()>>` *or* `DashMap<LockKey, …>` | volatile (locks don't outlive a crash; recovery is single-threaded) | the keyed critical section (clauses 2/5/7) |
| **Sequencer** | `Seq` high-water + the install serialization point (a `Mutex` or actor mailbox) | volatile, recovered as `max committed Seq` | assigns the total order; **serializes journal-append + install** (under group commit the leader re-acquires this point after its unlocked fsync to install — §3; `current_seq()` reports the installed *root*'s seq, not this in-flight high-water — §5) |
| **Flush slot** | a single FIFO flush handle: at most one batch occupies it, from barrier-start to resolution | volatile (rebuilt empty on recovery) | the in-order flusher (§3): while a batch holds the slot no later frame is appended above it, so the batch under barrier is always the journal tail — the precondition for sound truncate-tail on barrier failure |

`W` is the engine's composition of all store slices, each an `im` persistent collection (`OrdMap` for address-keyed stores — gives prefix-range scans free — `HashMap`/`Vector` elsewhere). `W: Clone` is O(1) (Arc bumps); `W::apply` returns a structurally-shared successor touching only changed paths. This is the ASN-0134-recommended persistent-immutable representation: the root's identity *is* the version coordinate, making clauses 1/4/6 nearly free.

`Snapshot<W>` is the newtype `Snapshot<W>(Arc<Committed<W>>)` (not a bare `Arc`, so it can carry the inherent `seq()`/`world()` the orphan rule would forbid on `Arc` — §Public interface) — a cheap, pinned, consistent view carrying its own `seq` (so verdicts can be reported as retrospective statements about `Σ_r`, V1).

## Internal design

### 1. The journal & WAL discipline

**Frames.** `[u32 magic][u32 len][u32 crc][payload]`, where the fixed `magic` sync word anchors frame starts for recovery resynchronization (§7) and `crc` covers **both the `len` field and the `payload`** (so a corrupt length is *detected* rather than silently mis-delimiting the following frame). After a CRC failure the recovery scan (§7) seeks forward for the next `magic`, takes that as a candidate frame start, and accepts it only if its `crc` validates over its framed `len`+payload — a `magic` that occurs by coincidence inside a payload fails this CRC check and the scan continues to the next. Payload is one of `LogRecord{ seq: Seq, txn: Txn, bytes }` (where `bytes` is the serialized `W::Record` — the frame struct is named `LogRecord` so it does not collide with the trait's `W::Record` enum), `Marker{ txn: Txn, last_seq: Seq, records_checksum }` (`records_checksum` checksums the txn's *record frames* — distinct from the marker's own per-frame `crc`), or the rare `Poison{ trusted_through: Seq }` sentinel (below). Here **`Txn(pub u64)` is a per-kernel-monotone transaction id**, assigned when `transact` begins staging and tagging every frame of one transaction. **Frames are matched to their marker by `txn`, not by file position:** recovery groups a transaction's record frames by their `txn` to validate that transaction's `records_checksum` — which is precisely what lets validation survive a `magic`-resync that skipped a corrupt frame, since file-contiguity ("the frames between the previous marker and this one") can no longer be trusted once a frame has been skipped (§7). **The marker is the recovery contract** (ASN-0047): a txn is committed iff its marker is *durable* and its `records_checksum` validates over the txn's records; record frames past the last valid marker are a torn tail — discarded and truncated.

**Canonical commit ordering: durable-before-visible.** A txn commits in this order — *append records → append marker (terminal frame) → durability barrier → install the root → return `(v, last_seq)`* — the detailed batched realization (working tip, single in-order flusher, leader-serialized install, post-install watermark) specified authoritatively in §3. Two properties this buys, both load-bearing for sound failure handling:

- **The marker is made durable only as the last step of its *own* commit.** A txn is committed exactly when *its own* marker reaches disk; nothing else may promote it. This closes the **phantom-commit hole**: were the marker merely *appended* before the barrier and left in the file, a later txn's fsync could flush a failed txn's marker, and recovery would replay an operation reported as failed — and, for a same-`(d,S)` allocation, the retried successor (computed against a root without the failed txn) would double-deposit a *colliding* address. The fix is to **truncate the un-acked tail on barrier failure** (below). Under group commit, the single in-order flusher (§3) keeps the failing *batch* the journal tail and lets no later batch's barrier run before it resolves, so no later fsync can flush its frames — truncate-tail removes them before any other fsync runs.
- **Barrier failure is a true no-op — *conditional on the un-acked-tail truncation succeeding*.** If the durability barrier fails, the txn's (under group commit, the *batch*'s) record+marker frames are truncated (durably) from the journal tail and the root is *not* installed — so no durable marker survives (recovery omits it) and no in-memory state reflects it. `transact` returns `TxnError::Durability` and the caller may safely re-invoke. The Seqs the txn had been assigned are **burned**; the serializer rolls the `Seq` high-water back to the last committed marker's `last_seq` before releasing, preserving the gap-free invariant. (The alternative — *tolerate* the gap, relaxing the invariant to monotone-only — is an open knob.) **This no-op guarantee is load-bearing on two things: that the failing batch is the journal tail, and that the truncation *itself* completes durably.** The first is delivered by the in-order flusher (§3) — no later frame is appended above a batch under barrier, and no later batch resolves before it — so truncate-tail removes exactly the failing batch's frames, with no over-truncation of a successor, no false no-op against a successor whose own fsync happened to flush this batch (none has run), and no cascade (no later batch read this batch's tip — none has formed). The second is what the Seq-rollback rests on: it hands the burned Seqs to the *next* txn to reuse, so if the truncation (or its fsync) fails, two things go wrong at once: the failed records+marker survive on disk (a later fsync can flush them and recovery replays a reported-failed op — the very phantom-commit hole this ordering exists to close), *and* a later txn writes the *same* burned Seqs (a journal Seq-collision, and for a same-`(d,S)` allocation a colliding address). Both are the exact corruption the durable-before-visible ordering is built to prevent. Therefore: **if the un-acked-tail truncation fails to durably complete, the kernel must poison (halt; subsequent calls fail), and the poisoning `transact` returns `TxnError::Poisoned`, *not* `TxnError::Durability` as a safe no-op.** (The poison applies regardless of burned-Seq policy: even under `TolerateGap`, where the next txn does not reuse the burned Seqs, a surviving failed marker would still replay as a phantom commit.) **And because that surviving failed marker is, on disk, byte-indistinguishable from a committed one — a bare marker records no ack-status — in-memory poison alone does not save the *next* `open()` from replaying it as a phantom commit (the recovery hole reconciled in §7).** So poisoning here additionally **durably writes a `Poison{ trusted_through }` sentinel** — `trusted_through` = the last genuinely-committed marker's `last_seq`, below the failed tail — which a subsequent `open()` honors by reconstructing state through `trusted_through` and then **refusing the untrustworthy tail** (`OpenError::PoisonedTail`), rather than adopting the phantom marker as its committed tip (§7). If even the sentinel cannot be made durable (the same disk failure that blocked the truncation), the condition is unrecoverable without operator intervention — the kernel stays poisoned in-memory and refuses further writes, the best it can do.

**Group commit (the throughput realization of the canonical order).** `FsyncBatch{window, max_delay}` amortizes one fsync over the txns *within* a batch (not across batches), closing the batch on whichever of *window-fill* or *max_delay* fires first — a window-only trigger would stall a low-traffic batch (and any zero-step op waiting on its barrier, §3) indefinitely, so the timeout is mandatory; `flush()` forces an immediate close. A **single in-order flusher** resolves batches strictly in order: at most one batch sits between barrier-start and resolution, and no frame for a later batch is appended above the batch under barrier until it resolves — so the batch under barrier is always the journal tail (this is exactly what keeps the barrier-failure truncate-tail sound; §3). Because install must stay *after* durability, no `ArcSwap` root update happens until the batch's barrier — yet a batched txn must still read the state its predecessor left *within the same batch*: a COPY pipelined after an INSERT into the same document must see the inserted content, and an allocation must read the frontier its predecessor advanced (H0). The applier therefore threads an **in-memory working tip** — a `Committed<W>` it advances with each batched txn's staged records — and draws each batched txn's `base` from that tip rather than from `root.load()`. The working tip is internal to the applier, carries the in-flight batch's handle (so a parked zero-step op enrolls in the specific batch its base belongs to — §3), and is never externally visible. **The full leader-serialized commit protocol — batch-final capture, the flush-slot claim, the single fsync (applier lock released, flush slot held), the re-serialized *monotonic* install, the *post-install* watermark raise, the waiter-wake, and the zero-step watermark wait — is the single source of truth in §3;** the barrier-failure handling (truncate-tail + Seq-rollback, or poison + `Poison` sentinel) is exactly the canonical-ordering bullets above, performed under §3's re-acquired serialization point and sound because the in-order flusher keeps the failing batch the journal tail. (The dependent-*write* hazard — a batched dependent txn reading a stale pre-batch root yet landing at a higher `Seq` — is specific to *this* durable-before-visible default combined with group commit, and the working tip is its fix; the zero-step watermark wait is its read-side companion. Because a later batch never forms until the current one resolves, cross-*batch* dependent reads see the resolved root, not the tip.)

**Only authoritative deltas are journaled.** Derived hints are *never* journaled — they are reconstructed by `apply` during replay (mandatory incremental maintenance — §6/§7), and seeded once at load by `rebuild_derived` if the checkpoint skip-serialized them. This is the structural answer to ASN-0134's divergence hazard (decision #10, multi-store atomicity): one logical step is exactly one journal record driving one `apply`, so there is nothing to diverge.

`Durability::{ Fsync, FsyncBatch{window, max_delay}, None }`. `None` is the fully in-memory realization — **MIC-faithful** (ASN-0134 is silent on durability), no journal, no recovery, atomicity/isolation intact.

**Optional variant: visible-before-durable (install-then-fsync).** This is the `SingleApplier { durable_before_visible: false }` ordering (and, necessarily, the only ordering available to the concurrent realizations of §8): install the root *before* the batched barrier, returning only once durable. This is a throughput choice (install latency off the fsync's critical path), justified for *internal* causal dependence by prefix-closure: anything causally dependent on txn T is journaled after T, so "R durable ⟹ T durable," and a reader/writer that acts on a not-yet-durable T either commits (making T durable by prefix) or leaves no persistent effect. **But the install is already visible when the barrier runs, so its failure cannot be a no-op** — readers/writers may already have built on it; the only sound response is to **poison the kernel** (halt; subsequent calls fail), the call returning `TxnError::Poisoned`, not `TxnError::Durability`. And prefix-closure does *not* cover an **external read acked by M10**: a client can be told a read result reflecting a committed-but-not-yet-durable state that a crash then rolls back (the resolved ASN-0047/0134 conflict — see *Conflicts resolved*). Choose this variant only when that external-read window is acceptable. (Because it installs the root *before* the barrier, each txn's `base ← root.load()` already reflects its predecessors even under group commit — so this variant needs **no working tip**, **no flush-slot gating** of next-batch appends, and hence neither the batch-final capture nor the zero-step watermark-wait of the canonical ordering; a barrier failure poisons rather than truncates, so it has no truncate-tail precondition to protect. The working-tip + in-order-flusher mechanism is specific to durable-before-visible under group commit, which is a **single-applier** ordering. The per-key-concurrent and CAS realizations (§8) likewise install before the barrier and so are *themselves necessarily* visible-before-durable — they too need no working tip, and choosing them for throughput adopts this external-read-rollback window not as an option but as a consequence.)

### 2. Sequencer & the linearization point

Each committed record receives the next `Seq` from a monotone counter, assigned inside the serialization point so the order is gap-free and a composite's records are **Seq-contiguous** (no foreign record interleaves a composite). Under `SingleApplier`/`PerKeyMerge` this serialization point is also the journal-append point, so **file order == `Seq` order**; under `OptimisticCas` the point is the winning CAS, so a composite's Seqs are still assigned as one block (Seq-contiguous) but committed *frames* of distinct txns may land in the file out of `Seq` order (§7/§8). **`Seq` refines ASN-0134's `idx(σ)`, it is not identical to it:** every `→_sh` step (`K.σ`/`K.α`/`K.λ_sh`) receives a `Seq`, but so do the non-`→_sh` records a composite stages (`K.μ⁺`/`K.μ⁻`/`K.ρ`); the subsequence of `Seq`s carrying `→_sh` records is order-isomorphic to `𝔼`, so a `→_sh` record's `Seq` *corresponds positionally* to its `idx(σ)` — it is **not equal** to it (the counter has also advanced on the interleaved non-`→_sh` records), while M2's full `Seq` order is a finer total order; no caller derives `idx(σ)` from `Seq`.

A `→_sh` record's `Seq` assignment is its linearization point (A2); one `transact` = one operation = one linearization point (single-step op) or one contiguous composite boundary. **The interior `Seq` and the externally-observable coordinate must be kept apart.** For a *single-record* op the returned `Seq` is that record's own `Seq` and is its linearization point — directly observable. For a *multi-record composite*, the interior `→_sh` record's `Seq` (e.g. the K.α inside an INSERT) is **M2-internal and not separately observable**: the composite installs atomically at one boundary, so A2's "entire effect is one transition" maps to that single atomic install, never to the interior step. The coordinate `transact` returns is therefore the composite's terminal `last_seq` (the K.ρ, say) — the one boundary at which the whole composite becomes visible — and that, not the interior K.α `Seq`, is the V1 referent a caller reports against. M2 fixes both; M10 merely chooses to call `transact` once per operation. Seq-contiguity is a property of M2's *internal* order; it is *not* what delivers W2 chain contiguity — that comes from holding `key(d,s_C)` across the run (§4).

### 3. The transaction / composite boundary

`transact(keys, f)` — recommended single-applier flow, canonical durable-before-visible:

```
acquire keys in resolved-lock order            // clauses 2/5/7; §4 (no-op under SingleApplier)
  (PerKey: bytewise KEYS; Striped: STRIPE INDICES — §4)
lock the applier (single global serializer)
  (FsyncBatch: a txn that would APPEND a frame waits while the single flush slot is occupied by
   a batch in [barrier-start, resolution]; appends never land above a batch under barrier, so
   that batch stays the journal tail — §1. A zero-step op does NOT append and is NOT gated.)
base ← tip.load()                              // working tip: == root for per-commit fsync, a batch's
                                               //   FIRST member, or the first member after a resolution;
                                               //   == predecessors' fold within a FORMING batch (§1)
stg  ← Staging::new(base)
match f(&mut stg) {                            // store logic; f MUST NOT call transact/critical_section (#NR — deadlock)
    Err(e)             → release applier lock; return Rejected(e)        // clean rejection; nothing journaled
    Ok(v) if stg empty →                       // zero-step (A1); V1 referent = base.seq()
        if base is a not-yet-durable working tip (durable-before-visible group commit):
            locate base's IN-FLIGHT BATCH via the batch handle the working tip carries  // §3 / data model
              (may be a CLOSED-BUT-RESOLVING batch, not the currently-forming one)
            enroll in THAT batch's waiter set keyed on the batch handle                  // stable across resolution
            release applier lock; park until that batch is RESOLVED (proto step 5/6):
                resolved committed (durable + installed) → return Ok((v, base.seq()))
                base batch ROLLED BACK                   → return Conflict   // value decided vs now-erased state;
                                                                            //   f is FnOnce ⇒ caller re-invokes
                poisoned                                 → return Poisoned
        else:                                  // per-commit fsync, or base already durable
            release applier lock; return Ok((v, base.seq()))
    Ok(v) ⇒
        seqs ← alloc_seqs(stg.records.len())                       // linearization (burned+rolled back on failure)
        journal.append_records(txn, seqs, stg.records)            // PER-TXN, under applier lock
        journal.append_marker(txn, last_seq, records_checksum)    // PER-TXN — commit marker, terminal frame
        tip.advance(Committed{ last_seq, stg.working }, batch)    // PER-TXN — advance the working tip (proto step 1)

        if Durability == Fsync:                // PER-COMMIT — barrier + install INLINE, lock held (single core):
            durability.barrier()
                on Err → if truncate(seqs) durable: rollback_seq_hi; release; return Durability   // TRUE no-op
                         else: write Poison{trusted_through}; poison; release; return Poisoned
            root.store(Committed{ last_seq, stg.working })        // ATOMIC INSTALL, AFTER durability
            release applier lock; return Ok((v, last_seq))        // commit-before-acknowledge (A7)

        // FsyncBatch — append + advance done above (step 1); this txn now follows the single-in-order-flusher
        //   group-commit protocol (steps 2–6 below). A non-leader parks and returns when the leader resolves the
        //   batch; the leader claims the flush slot + captures batch_final under the lock (2), fsyncs with the lock
        //   released but the slot held (3), re-acquires the serialization point (4), installs MONOTONICALLY →
        //   raises the watermark → wakes waiters → frees the slot (5), or truncates-tail/rolls back/poisons (6).
}
```

**Group-commit commit protocol (durable-before-visible) — single in-order flusher, the single source of truth for the ordering.** Under `FsyncBatch`, the per-txn `barrier`+`install` shown above for per-commit fsync is replaced by this leader-serialized batch protocol; every other section refers *here* for the ordering:

1. **Append + advance, under the applier lock.** Each batched txn, in turn under the applier lock, appends its record+marker frames and advances the working tip (carrying the forming batch's handle), joining the currently-forming batch. A **non-leader** then enrolls in the batch's waiter set, releases the lock, and parks (step 5/6 wakes it).
2. **Close + capture + claim the flush slot, under the lock.** The txn that closes the batch (window-fill / `max_delay`) is the **leader**; *still holding the applier lock* it captures `batch_final ← tip.load()` (seq == its own `last_seq` == the batch `last_seq`) and **claims the single FIFO flush slot** — from this barrier-start until the batch resolves, the flusher admits no other batch and step 1's append-gate admits no append above this batch, so the batch under barrier *is and stays the journal tail*. Then it releases the applier lock.
3. **Barrier — applier lock released, flush slot held.** The leader issues one `durability.barrier()` covering every batched txn's frames. The applier lock is free — so snapshot reads proceed and a zero-step op may read this (closed, resolving) batch's tip and enroll in it (located via the batch handle the tip carries) — but the held flush slot gates every subsequent-batch append, so no later frame is written above the batch under barrier, and strict FIFO admits exactly one batch to the slot. This is the deliberate **drop of cross-batch fsync overlap**: group commit amortizes one fsync over the txns *within* a batch and does **not** overlap a batch's fsync with the next batch's appends. (If fsync-concurrent throughput is wanted, the per-key realization — which installs before the barrier and *poisons* rather than truncates on failure, so needs no journal tail to protect — is the path, not cross-batch overlap; §8.)
4. **Re-acquire the serialization point.** After the fsync the leader re-acquires the applier lock (the §Core-data-model sequencer's *install* point) — so install, watermark, waiter-wake, and the barrier-failure handling are all serialized; installs and failure handling from different batches can neither run concurrently nor reorder (strict FIFO already orders the *batches*; this serializes their *resolution steps*), nor race the appenders that advance the tip/file.
5. **On barrier success: install → raise watermark → wake → free slot.** Install `batch_final` **iff `batch_final.seq > root.seq()`** (**monotonic** — retained as cheap insurance, though strict-FIFO resolution already guarantees in-order, never-regressing installs, so the guard never trips; this is also what keeps `current_seq()` monotone, §5); *then* raise the durable watermark to the batch `last_seq`; *then* wake the batch's members (→ `Ok`) and its zero-step waiters (→ `confirmed`); *then* free the flush slot (releasing the gate, so the next batch may begin forming). Because the watermark is raised *after* install (both under this serialized point), any woken waiter's effect is already in `root` — the read-your-writes A7 requires, which a pre-install watermark would violate.
6. **On barrier failure: truncate-tail/rollback/wake, under the lock.** The failing batch is the journal tail (step 2/3 gated every later append) and no later batch has resolved or been made durable (strict FIFO — no later barrier has run), so truncate-tail + Seq-rollback are sound with **no over-truncation** (no successor's frames sit above it), **no false no-op** (no later whole-file fsync flushed this batch — none ran), and **no cascade** (no later batch read this batch's tip — none has formed). If `journal.truncate` of the batch's un-acked frames completes durably: roll the `Seq` high-water back to the last committed marker, reset the tip to the last durable state, wake the batch's members (→ `Durability`, a true no-op) and its zero-step waiters (→ `Conflict`, never acking a value off the erased state), free the slot. If that truncation itself fails to complete durably: durably write `Poison{ trusted_through = last committed last_seq }`, poison the kernel, wake all (→ `Poisoned`) — the surviving failed marker plus reused burned Seqs would otherwise corrupt (§1/§7). Release the lock.

The leader returns only after step 5/6 — i.e. post-install — commit-before-acknowledge (A7); non-leaders and zero-step waiters return when the leader wakes them at step 5/6, deterministically `confirmed` vs `Conflict` (the wake-on-batch-handle set is resolved at this one serialized point, not by racing the watermark). Only step 3 runs with the applier lock released — but the held flush slot means no subsequent batch appends above the one under barrier, so the failing batch is always the durable tail and both resolution paths run strictly in order.

**Composites are one closure, not nested transactions.** A composite (M5's placement = K.α + K.μ⁺ + K.ρ) is a *single* `transact` whose `f` stages each step's record and, where a step needs a neighbor's address math, calls that neighbor's **pure** function against `stg.base()`/`stg.working()` — e.g. M5's content K.α reuses M3's `recompute_max`/`inc` body directly, *inside this one closure*. It must **never** invoke a neighbor's allocation `transact` from within `f`: `transact` is non-reentrant (the applier lock / install serialization is held), so a nested call deadlocks. The standalone seam examples (Dependencies & seams) show a *bare* allocation as its own `transact`; when that allocation is one step of a larger composite, the caller lifts its *pure* body into the composite's closure, not the transaction.

**Lock discipline (group commit).** Under per-commit `Fsync` the barrier and install sit *inside* the applier-locked region (single applier, single core — nothing to gain by releasing). Under `FsyncBatch`, **only the leader's fsync (protocol step 3) runs with the applier lock released**, and even then the held flush slot gates every subsequent-batch append; the applier lock is released after a txn's appends + `tip.advance` (the leader having first captured `batch_final` and claimed the flush slot under the lock, step 2), and the leader **re-acquires** the serialization point (step 4) to perform install + watermark-raise + waiter-wake + slot-free (step 5) or the truncate-tail/rollback/reset + waiter-wake + slot-free (step 6). This is what lets (a) the leader's fsync proceed while later txns' zero-step reads enroll, while (b) keeping every install/rollback serialized through the one point the Sequencer row promises *and* keeping the batch under barrier the journal tail — so two leaders can never install or fail out of order, and a failed batch's truncate-tail/tip-reset never races a concurrent appender or a later batch's resolution. The durable watermark is the post-install completion signal: a monotone "max-`Seq`-known-durable-and-installed" the leader raises *after* install, with waiting `transact`s and zero-step ops parked on a condvar until it covers their `last_seq`/`base.seq()` — or, on a batch rollback, woken to *retry* (zero-step ops return `Conflict`, §1). Because the lock is dropped *before* any waiter parks and *before* the unlocked fsync, a waiter can never block the very barrier it awaits — no deadlock.

`Staging.working` (= `base` folded with staged records, cheap over persistent `W`) is what lets the store check **intra-composite preconditions** at intermediate states (ASN-0047's "observable intermediate states," e.g. S3★ referential integrity after K.α but before K.μ⁺). Those intermediates are visible only to the executing closure — **never to external readers**, who see only the single atomic install. The J-couplings the closure may check at the boundary (`base`→`working`) are M5's to assert; M2 never does.

The barrier shown is the canonical per-txn durable-before-visible commit; group commit amortizes it across a batch (intra-batch only) and publishes the batch's captured final state *after* its barrier, via the leader's re-serialized monotonic install (steps 4–5). Either way **install follows durability**, so `TxnError::Durability` is a sound true no-op — *provided the un-acked-tail truncation completes durably; if it does not, the kernel poisons (returning `Poisoned`, and writing the `Poison` sentinel for recovery) rather than no-ops* (§1). The optional visible-before-durable variant (§1) — and, necessarily, the per-key-concurrent and CAS realizations (§8) — move the install above the barrier and convert a barrier failure into a kernel poison (`Poisoned`).

### 4. Keyed critical sections

One mechanism serves clauses 2, 5, 7; the key is always caller-supplied bytes. `transact` acquires `keys` before taking its snapshot and holds them through the root install (the precise release point under the concurrent realizations — after install, before the batched fsync — is pinned in §8), so **read-decide-deposit is atomic for those keys** — exactly what clause 7's idem dedup needs (the dedup-read of the global active set and the deposit are one action under the coverage-class key; cf. G2) and what clause 2 needs (frontier-read-and-deposit under the `(home,subspace)` key — M3 does the `inc(max,·)` math; M2 only locks).

**Acquisition is deadlock-free by acquiring the *resolved lock objects* in a canonical order — and that order is layout-dependent.** Under `LockLayout::PerKey` (one mutex per distinct key) sort + dedup the **keys** bytewise. Under `LockLayout::Striped{stripes}` sort + dedup is over the **stripe indices**, not the keys: resolve each key to its stripe index *first*, then sort and dedup *those*. Sorting/deduping by key under `Striped` is wrong on two counts — two *distinct* keys may hash to one stripe (a key-dedup would then double-acquire one non-reentrant `Mutex` → self-deadlock), and bytewise key order ≠ stripe-index order (two txns could acquire the same two stripes in opposite orders → classic deadlock). This is reachable via the documented two-key M7 emit (`[class_key, key(home, s_L)]`) under `PerKeyMerge`/`OptimisticCas`, so the stripe-index ordering is mandatory there. The bug cannot fire under `SingleApplier { .. }`, where the table is unused.

**Run contiguity (W2) is delivered by the held key, not by Seq order.** Staging a multi-atom content run inside one `transact([key(d,s_C)], …)` holds `key(d,s_C)` across every atom, so no foreign `s_C`-allocation to `d` interleaves between the run's first and last atom — *that* is W2 (chain/address contiguity). The single atomic install then *additionally* makes the run atomic-to-readers, over-satisfying clause 5 (no reader lands mid-run at all). Seq-contiguity (§2) is a distinct, internal property and is not the source of W2.

`critical_section` is the rarer guard that holds `keys` across *separate* inner commits — the modeled clause-5 path where readers *may* land mid-run. **It is available only under the per-key-concurrent and CAS realizations**, where the lock table is live and `transact` honors keys. Under the single applier the lock table is **unused** (the global applier lock subsumes every key, and is released between the section's inner commits), so a foreign `transact([key(d,s_C)], …)` — whose key is a no-op there — could commit between the inner commits and fragment the run; the guard would therefore provide **no run-exclusion under the single applier**. So that a builder cannot silently get a fragmented run, **`critical_section` panics when called under `SingleApplier { .. }`** rather than handing back a do-nothing guard. A single-applier run must instead be **one `transact([keys], …)`** (atomic, satisfying clause 5 by over-satisfaction); the reader-visible-mid-run flavor of clause 5 is simply unavailable under the single applier, whose runs are atomic.

Lock table: striped `Vec<Mutex>` (bounded memory, possible false contention) or per-key map (no false contention, needs entry GC) — an open decision that *also* sets the acquisition order above (`Striped` → order by stripe index; `PerKey` → order by key). Under the single-applier impl the table is unused; under per-key concurrency it is live and also backs `critical_section`. The `transact`/`snapshot` API is identical across realizations, so moving single-applier → per-key concurrency changes no caller's *call shape* — though it does newly *bind* the footprint-confinement contract on `f` (§8 / Dependencies & seams).

### 5. Snapshot reads

`snapshot()` is one lock-free `ArcSwap::load_full` — an *owned* `Arc<Committed<W>>` (not `load`'s borrowed `Guard`, since the returned `Snapshot` outlives the call) — wrapped in the `Snapshot<W>` newtype. It is **infallible and stays available even on a poisoned kernel** — both poison paths (§1) leave the in-memory root a consistent committed state — so reads keep serving while writes/checkpoints fail with `Poisoned`. Per-call single-state (clause 4 / A3 / V0) is by construction. A multi-read verdict reads all `p` constituents off **one** `Snapshot` → clause 6 / V2 for free (persistent state dissolves the "global" cost ASN-0134 flags). This is the seam contract on M6/M8/M9: thread one `Snapshot` through every constituent of a verdict; do not issue them as separate `snapshot()` calls (the §8 pathology).

`current_seq()` returns this **same installed root's seq** (== `snapshot().seq()`), **never the sequencer's in-flight Seq high-water** — which under group commit can name a not-yet-installed / not-yet-durable Seq no reader can observe. Because group-commit install is serialized and **monotonic** (the single in-order flusher resolves batches strictly in order, so installs never regress; the `batch_final.seq > root.seq()` guard, §3, is cheap insurance over that), this coordinate never regresses. A verdict reported "as of `current_seq()`" is therefore a retrospective statement about a real committed `Σ_r` (V1); were it pinned to the high-water, the verdict could name a state no `snapshot()` will ever return. (A write reports its own coordinate from the `last_seq` that `transact` returns — exact even under per-key concurrency — rather than from a post-hoc `current_seq()`.)

### 6. Checkpoint & truncation

Non-blocking: grab a `Snapshot` `Committed{ seq: S, world }` (lock-free) — `world` is the fold of **exactly the records with `Seq ≤ S`**, and `S` is always a committed marker boundary (installs are atomic at commit). Serialize `world()` (authoritative; hints may `#[serde(skip)]`) to `checkpoint.tmp`, fsync, atomic-rename to `checkpoint.<S>`, fsync dir.

**Retention & reclamation.** The kernel keeps the most recent `retain_checkpoints` (N ≥ 1) checkpoints; let `S_old` be the seq of the **oldest** retained one. Reclaim journal space only by **dropping whole journal segments all of whose frames have `Seq ≤ S_old`** — *segment-granular* truncation, not an exact per-frame guarantee: a segment that *straddles* `S_old` is kept whole, so some `Seq ≤ S_old` frames may survive on disk. **Tying reclamation to the *oldest* retained checkpoint (not the just-written `S`) is what makes `BadCheckpoint`'s fallback real** — the journal back to `S_old` survives, so a corrupt newest checkpoint falls back to an older retained one (or to genesis only while nothing below it has yet been reclaimed) and replays from there (§7); with `N = 1`, `S_old = S`, the newest checkpoint is the **sole** recovery base, there is no fallback, and the write should be made redundant/verified. Truncation is therefore a space-reclamation optimization, **not** a correctness mechanism; correctness rests entirely on recovery (§7) replaying, from whichever checkpoint @`S_load` it loads, **exactly `Seq > S_load`** — its `Seq > S_load` filter discards any surviving `≤ S_load` frames *regardless of their integrity* (a corrupt `≤ S_load` frame is irrelevant — its effect is already in the loaded `world`). Each checkpoint @X thus *embodies* `Seq ≤ X`, and recovery from it replays *exactly the complement* `Seq > X` — no overlap, no gap. This complementarity, enforced by that filter over a coarse segment-granular truncation, is essential because `apply` is **not** idempotent (a `Vector`-append record double-applies wrongly): every committed record must be folded into the recovered state exactly once. Writers run throughout — the snapshot's Arc keeps the checkpointed version alive while live installs advance the root. Crash mid-checkpoint leaves an ignored `.tmp` and an unreclaimed journal: always safe (the next recovery just replays more, the filter still bounding it to `Seq > S_load`). Cadence (every-N / time / size), **retention `N`**, and representation (full-World vs per-store/incremental) are open knobs.

Under `Durability::None` there is no journal: `checkpoint()` is a no-op returning `current_seq()` (nothing to persist or reclaim), and the in-memory realization simply has no recovery story to bound.

### 7. Recovery

`open`: load the latest valid **retained** checkpoint `checkpoint.<S_load>` (on `OpenError::BadCheckpoint` fall back to the next-older *retained* checkpoint, then to `genesis` with `S_load = 0` only while nothing below it has been reclaimed — §6; the whole chain exhausted ⟹ surface `BadCheckpoint`), call **`rebuild_derived`** (seeds, from authoritative state, the hints the checkpoint skip-serialized; `apply` then keeps them current across replay — and a store's `rebuild_derived` override **must** seed exactly the `apply`-fold of the `Seq ≤ S_load` prefix it stands in for, or the recovered hint diverges from the live-maintained one, a trait contract — §Public interface, §Dependencies & seams), then replay the committed journal records, **filtering to `Seq > S_load`** (skipping any `Seq ≤ S_load` frames that survived §6's segment-granular space reclamation) and folding them via `apply` in `Seq` order — exactly the complement of what the loaded checkpoint embodies (§6), no record applied twice or skipped. The `Seq > S_load` filter is load-bearing precisely because `apply` is non-idempotent: a surviving `≤ S_load` frame, replayed, would double-apply.

**Journal order vs `Seq` order is realization-dependent.** Under `SingleApplier` and `PerKeyMerge` every append occurs under the install serialization point, so file order == `Seq` order and replay is a linear scan. Under `OptimisticCas` there is no such point — concurrent winners append committed frames out of `Seq` order — so recovery must **not** assume file order == `Seq` order: it groups frames by `txn`, keeps only transactions whose commit-marker is durable and whose `records_checksum` validates, and folds their records **sorted by `Seq`**. The fold is `Seq`-ordered in every realization; only the journal scan differs (linear vs group-and-sort).

A txn is committed iff its marker is durable and validates (§1). Recovery **first scans the journal to locate the last frame that is a CRC-valid `Marker` whose `records_checksum` validates over its txn's records — the *committed tip*** — and only then classifies failures by position. **Records are matched to their marker by `txn`, not by file position:** a `magic`-resync that skips a corrupt frame breaks file-contiguity, so a transaction's records can no longer be identified as "the frames between the previous marker and this one"; recovery instead groups frames by their `txn` id (§1) to validate a marker's `records_checksum` — a transaction missing a (corrupt, skipped) record then *fails* its checksum and is classified by position rather than silently mis-grouped. **Locating the tip requires scanning *past* any earlier bad frame, and the per-frame `magic` sync word (§1) is what makes that possible:** on a CRC failure recovery cannot trust the framed `len` to find the next frame (the offset depended on the corrupt length), so it **seeks forward byte-by-byte for the next `magic`**, takes that as a candidate frame start, and accepts it only if its `crc` validates over its `len`+payload — a coincidental `magic` inside a payload fails this check and the scan continues. This is what lets the scan resynchronize to later frames and markers after interior damage, so it can tell a torn tail from committed-prefix corruption.

**Two boundaries — `S_load` and the committed tip — partition the journal into three regions, and a CRC failure is classified by which it falls in.** Recovery need only consider the journal from `S_load` forward: it begins at the first segment containing a `Seq > S_load` (earlier whole segments, all `≤ S_load`, are skipped outright), and a corrupt run's `Seq` range is bounded above by the `Seq` of the next valid frame it resyncs to (via the `magic` word).

- **`Seq ≤ S_load`** (a frame surviving §6's segment-granular reclamation in a straddling segment, identified when the resync's next-valid `Seq` places the whole corrupt run at or below `S_load`): **harmless** — the `Seq > S_load` filter skips it and the checkpoint already embodies its effect; recovery resyncs past it and continues. Halting here would needlessly refuse a recoverable kernel.
- **`(S_load, committed tip]`** (a corrupt run reaching above `S_load` and below the tip): **corruption of durable acked data the recovered state needs** → halt and report (`OpenError::Corruption{ at }`); never silently drop it, because a silent discard would leave a `Seq` hole in the genuinely-replayed range that — `apply` being non-idempotent and `Seq`-ordered — recovers a *wrong* state.
- **at or after the committed tip** (a CRC/marker failure with no valid marker following the corrupt run): the never-acked **torn tail** → discard + truncate. It was never acked, so loss is correct, and in the **normal** failure path a barrier-failed batch's record+marker frames were already truncated at failure time (the in-order flusher having kept them the tail), so no failed marker survives to be misread as the tip.

This classification resolves the apparent tension between "correctness rests entirely on recovery replaying exactly `Seq > S_load`" and the corruption halt: only corruption *inside the replayed range* `(S_load, tip]` is fatal; corruption already embodied in the loaded checkpoint is irrelevant. The bound on the corrupt run's `Seq` (from the surrounding valid frames) is what lets recovery tell the regions apart, so a genuinely-replayed corrupt frame is never silently skipped.

**The one exception — the poison corner of §1 — is why recovery cannot equate "valid marker on disk" with "durably acked" unaided.** When a barrier failure's un-acked-tail truncation *itself* fails to complete durably, a CRC-valid-but-never-acked marker **does** survive on disk, byte-indistinguishable from a committed one; naive tip-location would adopt it and replay the very phantom commit §1 poisons to avoid (in-memory poison halts the current process but does nothing to the on-disk frames, and a bare marker carries no ack-status to consult). The reconciliation is the durable **`Poison{ trusted_through }` sentinel** §1 writes before halting: recovery scans for it *first*, and if present takes `trusted_through` — the last genuinely-acked marker's `last_seq` — as the authoritative cap, reconstructs state through it (replaying `S_load < Seq ≤ trusted_through`), and then **refuses the tail beyond it**, surfacing `OpenError::PoisonedTail{ trusted_through }` for operator intervention rather than processing the untrustworthy phantom. The sentinel is the positively-recorded boundary that the bare marker's "durable ⟹ acked" inference fails to supply in exactly this corner; in every other case truncation guarantees no un-acked marker survives, so "last valid marker = committed tip" needs no such record. (Where the disk failure is so severe the sentinel itself could not be made durable, the kernel stays poisoned in-memory and the condition is unrecoverable without operator intervention — §1.)

**Recovery requires no `Seq`-contiguity in the replayed range.** It folds the surviving `S_load < Seq` records **in `Seq` order** (group-and-sort under CAS, linear scan otherwise); under `BurnedSeqPolicy::TolerateGap` that range may legitimately contain burned-Seq gaps, and those fold harmlessly (each *present* record applied exactly once, in order). A builder must **not** add a contiguity check that would falsely trip on such a gap — the only journal defect that is corruption is a **CRC failure in `(S_load, committed tip]`**, never a merely missing `Seq`. `apply` determinism guarantees a clean replay reproduces the exact committed state (A6: every journal prefix up to a marker is a canonical reachable state). Recovery is single-threaded — the volatile lock table, durable watermark, `Seq` high-water, and empty flush slot are rebuilt fresh (the high-water and watermark as the committed tip's `last_seq`).

### 8. Concurrency realizations — the fault line

The `transact`/`snapshot` API is invariant across these; only internal locking — and, as a coupled consequence, the durability-ordering — changes.

- **Single applier (recommended first; ASN-0047's choice).** `f` runs under the global applier lock. With per-commit fsync (or for a group-commit batch's *first* member) `base == current root`; under group commit `base` is the applier's **working tip** (§1/§3), so a later batch member reads its predecessors' staged records, and the single in-order flusher gates next-batch appends so the batch under barrier stays the journal tail. The lock table is unused (keys are no-ops). This makes clauses **1, 2, 4, 5, 7 free**, leaving **clause 6** — which still needs the §5 one-`Snapshot` threading, since the §8 read-drift pathology arises even here, with no per-home concurrency — and the **clause-3** commit-gate ordering to be handled explicitly. Group commit (§1/§3) amortizes one fsync over the txns *within* a batch for throughput, with the single-in-order-flusher monotonic install of §3; it does not overlap a batch's fsync with the next batch's appends. Its `durable_before_visible` flag (default `true`) selects the canonical durable-before-visible ordering (install after the barrier, via the working tip + flush slot, the leader installing the captured batch-final state); set `false` for the opt-in visible-before-durable throughput variant (which needs neither working tip nor flush-slot gating — install precedes the barrier). **This is the *only* realization that can be durable-before-visible** — the concurrent variants below install *before* the barrier and carry no such flag. Bounded by one core. *Because `f` always sees the live tip here, a store written against the single applier may freely read state outside its `keys` — which is exactly why the footprint contract below does not bite until migration.*

- **Per-key concurrent with merge-at-install (scaling path; what ASN-0134 G1 blesses).** `f` runs outside the install lock holding only its `keys`; at commit, a short global install section assigns Seqs (in `Seq` order, so file order == `Seq` order — §7), re-folds `stg.records` over the *current* root **without re-running `f`**, journals, and **swaps the root** — the batched fsync then following *outside* the install section, with the txn returning only after the durable watermark covers its `last_seq` (A7). It **holds its `keys` across `f`-and-install and releases them immediately after the root swap** — *after* install (so a same-key successor's `f` reads the just-installed frontier, clause 2) but *before* the batched fsync (so writers never serialize through durability). Because the swap precedes the barrier, this realization is **necessarily visible-before-durable** (§1): it uses *no working tip* and *no flush-slot gating* and so needs neither the batch-final capture nor the zero-step watermark-wait; in the window between a txn's install and its barrier an external M10-acked **reader** can reflect that committed-but-not-yet-durable state, which a crash rolls back; and a barrier failure **poisons** the kernel (the root is already installed and cannot be unwound), returning `TxnError::Poisoned` rather than a no-op `Durability` — there is no journal tail to truncate, so it tolerates fsync overlap that the durable-before-visible ordering cannot. Durable-before-visible is **not** available here — it is the single-applier ordering (§1/§3) — so the concurrency and durability-ordering decisions are **coupled**: adopting per-key for throughput adopts visible-before-durable semantics. This re-fold is conflict-free **only under a caller obligation** — *footprint confinement*: `f`'s **entire committed-state read set** — every value it consults to decide *what to stage, whether to reject, or which branch to take*, not merely the values it writes into staged records — must lie under state the txn's held `keys` cover, or be **monotone-safe**. Monotone-safety is *narrower* than "any read of an append-only structure": a *positive* membership test on an append-only set (`a ∈ dom(C)`, whose truth survives every append) is exempt, but a *negative* existence/freshness test (`a ∉ dom(C)`, a uniqueness probe) is **not** — a concurrent append can falsify it — and must be under held keys. The contract is on the *read set* because merge-at-install re-folds the already-decided records over the current root **without re-running `f`**: any unconfined read means a stale *decision* (which records, hit vs miss, reject, branch) commits at a non-serializable position. (A txn's *writes* are confined to held-key state by construction — staged records mutate only that state and append fresh, disjoint entries — but this carries a **writer-side dual** that is *not* automatic: any committed-state slice some `f` *reads* under a key K must be *written* only by txns that also hold K. The clause-7 active-in-class membership is the live case — a same-class **nullify** mutates it, so a nullify must hold `class_key` too. For emit-vs-nullify *specifically* the dual is sufficient-not-necessary — that race is benign per ASN-0134 §4(ii), a valid serialization and never a duplicate — but the dual holds generally, for any less-benign read-vs-write race. So the active obligation has two halves: confine each `f`'s read set to its keys, and hold the covering key when writing read-shared state.) This is ASN-0134 G1's full commutativity hypothesis — neither *reads* nor writes state another txn touches — raised here to a **seam contract** (Dependencies & seams). Under it, the held keys guarantee no concurrent writer touched this txn's read-set (G1 commute) and the re-fold reproduces `f`'s decision. **Persistent state alone gives neither the write-concurrency nor the confinement:** root-install still contends (the held keys, not persistence, give concurrency), and a store that *reads* (unconfined) or writes state *outside* its keys compiles and runs correctly under the single applier but **corrupts silently** under merge-at-install. The example seams honor the contract (M3 holds `key(home,subspace)` across the frontier read; M7 holds `class_key` across the active-in-class read *and* on nullify), which is why those migrate cleanly; *new* store ops must be checked against it — and since "build single-applier first" authors stores *before* the discipline would otherwise bite, the contract must be stated up front.

- **Optimistic frontier-CAS (optional).** No held locks; read fresh, compute, and attempt to CAS the root. The CAS *is* the install, so this realization is likewise **necessarily visible-before-durable** (the barrier follows the successful CAS; a barrier failure after a won CAS **poisons**, returning `TxnError::Poisoned`, the root being already installed) — coupled to visible-before-durable semantics, never durable-before-visible. Seqs are assigned at the winning CAS (the realization's only serialization point), so a composite's Seqs are still a contiguous block but committed *frames* of distinct winners land in the journal **out of `Seq` order**; recovery must therefore not assume file order == `Seq` order — it groups frames by `txn`, keeps only durably-committed transactions, and folds their records sorted by `Seq` (§7). **Because the CAS is on the *single `ArcSwap` root*, it aborts on *any* concurrent commit — not merely a same-key one — so it is viable only when the *overall commit rate is low*, not merely when same-key contention is rare.** (To abort only on a same-*footprint* move — ASN-0134's "install if frontier unchanged" — re-specify it as a narrower per-key/per-frontier CAS that compares only the read-set's slice rather than the whole root; that restores the "rare same-key contention" regime, at the cost of a finer compare-and-swap.) Because it holds no keys there is nothing to release. With the frontier unpinned it may move under it between read and install — and crucially it **cannot internally retry**: re-folding the already-staged records over the moved frontier would collide, and re-running `f` is forbidden (`f: FnOnce`). So an install-time root change surfaces `TxnError::Conflict` for the **caller** to re-invoke with a *fresh* closure. (This is one of the two `Conflict` sources; contrast `PerKeyMerge`, whose held keys pin the frontier so it re-folds the already-staged records at install *without* re-running `f`.) Same footprint-confinement obligation (the full read set, with the same positive-vs-negative monotone caveat) as merge-at-install. Viable when the overall commit rate is low; retry termination is open (ASN-0134 OQ1/OQ3).

`critical_section` is available only under the latter two realizations (§4); the single applier offers only the one-`transact` run (and `critical_section` **panics** there).

## Invariants & contracts

**By construction** (falls out of the data model above):
- **Total order, monotone `Seq`, refining `𝔼` — gap-free *only* under `BurnedSeqPolicy::Rollback`** — counter under the serializer (ASN-0134 A1/A2, SequentialTransitionAxiom; ASN-0047 same). A `→_sh` record's `Seq` *corresponds positionally* to its `idx(σ)` (the `→_sh` subsequence is order-isomorphic to `𝔼`) but is **not equal** to it — non-`→_sh` records also carry `Seq`s — so M2's order is a *refinement* of `𝔼`, not an identity (§2). The order-isomorphism to `𝔼` survives gaps, so the *refinement* is **unconditional**; only **gap-freeness** is policy-conditional — it holds under `Rollback`'s Seq-rollback on durability failure (§1) and relaxes to **monotone-only** under `TolerateGap`. For a single-record op the returned `Seq` is observable; for a multi-record composite the interior `→_sh` `Seq` is internal and the *observable* coordinate is the terminal `last_seq` (§2). File order == `Seq` order under `SingleApplier`/`PerKeyMerge`; under `OptimisticCas` only the *fold* is `Seq`-ordered (§7).
- **No torn read / per-call single-state** — immutable `Committed<W>` + atomic `ArcSwap` install + lock-free `load_full` (A0/A3/A4/V0, MIC-4). Under group commit, external readers see only the installed root, published by the leader's **serialized, monotonic** install *after* the barrier (§3) — never the applier's working tip and never a not-yet-durable state — so every observed root is durable and `current_seq()` (that installed root's seq, not the in-flight high-water — §5) never regresses (the single in-order flusher resolves batches in order; the install guard is insurance over that).
- **Reads available under poison** — both poison paths leave the in-memory root a consistent committed state (durable-before-visible: root never installed = last durable state; visible-before-durable: root is a real committed `Σ_k`), so `snapshot`/`current_seq` keep serving it and never fail; only write (`transact`) and `checkpoint` paths return `Poisoned` (§Public interface, §5).
- **Multi-read verdict single-state** — one `Snapshot` threaded through all reads (V2, MIC-6; caller contract, made trivial by persistent root).
- **Composite Seq-contiguity** — a composite's Seqs assigned as a unit; an *internal-order* property only — W2 chain contiguity comes from the held `key(d,s_C)`, not from this (§2/§4).
- **Append-only journal; a committed frame (one whose marker is durable) is immutable; every prefix-to-a-marker is a replayable canonical state** — magic-anchored, `txn`-tagged append-only file + terminal per-txn marker + `apply` determinism (ASN-0047 journaling; ASN-0134 A6).

**By active enforcement** (M2 must guard, named where):
- **Same-key serialization** — keyed critical section §4 / single applier §8 (ASN-0134 H2, MIC-2; M3 builds frontier H0 atop it).
- **Commit-before-acknowledge** — `transact` returns only post-durable+install; under group commit a non-leader is woken by the leader's serialized resolution *after* the install (§3 step 5), so a returning write's effect is already in `root`. A zero-step op reading off a not-yet-durable working tip likewise locates its in-flight batch (via the working tip's batch handle) and waits to be resolved at that batch's serialized resolution before returning, and on a barrier-failure rollback of that base is woken to **retry** (returns `Conflict`), never acking a value off erased state §1/§3 (A7, MIC-3).
- **Composite atomicity (none-or-all to readers)** — single atomic install §3 + commit-marker recovery discard §7 (ASN-0047).
- **Durability before ack, with a sound failure path** — canonical durable-before-visible (`SingleApplier { durable_before_visible: true }`): append records+marker → barrier → install → raise watermark → return; under group commit the **single in-order flusher** has the leader claim the flush slot and capture `batch_final` under the lock, fsync with the lock released **but the slot held** (so no later batch appends above it and no later barrier runs before it resolves), then re-acquire the serialization point to install **monotonically** (no root regression / `current_seq()` backslide) and raise the watermark before waking waiters (§3). Because the failing batch is always the journal tail, a barrier failure truncates exactly the batch's un-acked frames and rolls the `Seq` high-water back — **no over-truncation, no false no-op, no cascade** — so `TxnError::Durability` is a **true no-op** and no failed marker can be promoted by a later fsync — *but only if that truncation itself completes durably; if it does not, the kernel **poisons** (the poisoning call returning `TxnError::Poisoned`, not `Durability`) **and durably writes a `Poison{ trusted_through }` sentinel so the next `open()` refuses the surviving failed marker's tail (`OpenError::PoisonedTail`) instead of replaying it as a phantom commit**_, since a surviving failed marker plus the reused burned Seqs would corrupt §1/§3/§7 (ASN-0047). The visible-before-durable ordering — the optional `durable_before_visible: false` single-applier variant **and the necessary ordering of the per-key-concurrent and CAS realizations (§8)** — instead **poisons** on barrier failure (returning `Poisoned`, the root being already installed) and exposes a not-yet-durable state to an external M10-acked read (resolved conflict — see *Conflicts resolved*).
- **Recovery faithfulness** — load the latest valid *retained* checkpoint (falling back to an older retained one or genesis on `BadCheckpoint`, §6/§7); resynchronize past interior bad frames via the per-frame `magic` word, grouping a transaction's records by `txn` (not file position) to validate its `records_checksum` and locate the **committed tip** (§1/§7); replay committed records **filtered to `Seq > S_load`** (skipping any `≤ S_load` frames surviving §6's segment-granular reclamation), folded in `Seq` order (a linear scan under `SingleApplier`/`PerKeyMerge`; group-by-`txn`-and-sort-by-`Seq` under `OptimisticCas`, whose file order ≠ `Seq` order — §7) **without requiring Seq-contiguity** (a `TolerateGap` gap folds harmlessly); a CRC/marker failure *at or after* the committed tip is the never-acked torn tail (discard + truncate — in the normal path a failed-barrier batch already truncated its frames as the tail, so no marker survives); one in the genuinely-replayed range **`(S_load, committed tip]`** is corruption of durable acked data (halt, `OpenError::Corruption` — never drop); one at `Seq ≤ S_load` is **harmless** (the `Seq > S_load` filter skips it; the checkpoint already embodies it — never fatal). The **poison corner** (§1: a failed-batch truncation that itself failed) is the sole case where a never-acked marker DOES survive on disk, byte-indistinguishable from a committed one; recovery handles it not by re-deriving an ack-status the bare marker lacks but by honoring the durable `Poison{ trusted_through }` sentinel §1 wrote — reconstructing through `trusted_through` and **refusing the tail** (`OpenError::PoisonedTail`) §6/§7 (A6; ASN-0047).
- **Deadlock-free multi-key acquire** — acquire the *resolved lock objects* in a canonical layout-dependent order: keys sorted + deduped bytewise under `PerKey`, **stripe indices** sorted + deduped under `Striped` (a key-order acquire would self-deadlock or deadlock under striping) §4.
- **idem=⊤ dedup atomicity** — read-decide-deposit under the coverage-class key = one `transact` §4 (I1a/I4/G2, MIC-7).
- **Run contiguity** — a run as one `transact([key(d,s_C)], …)`: the held key delivers W2 chain contiguity, the single atomic install over-satisfies clause 5; or — *concurrent impls only* — `critical_section` held across separate deposits §4 (W2, MIC-5).
- **Live derived-hint correctness** — incremental hint maintenance is folded by `apply` on every commit and every replay step; `rebuild_derived` only seeds skip-serialized hints at load (§1/§7). A store that maintains a hint via `rebuild_derived` alone leaves it stale after every live write — so hint folding in `apply` is mandatory; and a store that *does* override `rebuild_derived` must seed exactly the `apply`-fold of the `Seq ≤ S_load` prefix, else the recovered hint diverges from the live one (§7).

**Explicitly *not* M2's** (passes through M2, enforced by neighbors):
- store permanence P0–P3/L12 and the J-couplings J0/J1★ (stores' `apply`+API; M5's composite boundary — ASN-0047);
- frontier/address and coverage-class computation (M3, M1/M7);
- register-before-allocate ordering (a store precondition checked against the snapshot, then a clean `Rejected` if unmet);
- the request lifecycle and ack-to-client (M10);
- **multi-*step* (`m ≥ 2`) batch atomicity** — M2 offers only the per-`transact` atomic unit; a store honors A5's intended partial visibility by issuing the batch as *separate* `transact`s, and *may* over-satisfy A5 by committing it as one (A5: "atomicity must be built above the substrate"); M2 neither forces nor forbids the granularity. A single-step `m = 1` fire **is** one atomic `transact`;
- durability *as a requirement* (not a MIC clause — `Durability::None` is faithful);
- **footprint confinement of `f`** — a *caller* obligation under merge-at-install/CAS: `f`'s entire committed-state **read set** — every value consulted to decide what to stage, whether to reject, or which branch to take, not just the staged records' values — must lie under its held `keys` or be **monotone-safe** (a *positive* membership test on an append-only set, e.g. `a ∈ dom(C)`; a *negative* existence/freshness test like `a ∉ dom(C)` is **not** monotone-safe and must be keyed). Writes are confined to held-key state by construction, but with a **writer-side dual** — state read by another `f` under key K must be written only while holding K (the clause-7 nullify holds `class_key`; benign-race exception per ASN-0134 §4(ii)) — so the obligation has two halves: a confined read set and key-holding writers of read-shared state (§8). M2 *relies* on both for the conflict-free re-fold but **cannot itself check** them; violated, they corrupt silently under concurrency. Enforced by the stores, by contract, not by M2's mechanism.

## Dependencies & seams

**Upstream: none.** M2 is a foundation (it carries no edge to M1 — keys and payloads are opaque, ordering of keys is plain bytewise, not tumbler order). Its only dependencies are crates: `im`, `arc_swap`, `serde`, `parking_lot`/`dashmap`, a CRC32C lib.

**Composition seam (dependency-inverted).** The engine crate defines `World` (composing all store slices) and `Record` (the enum union of every store's record-types), implements `WorldState` for `World` by dispatching `apply` to the owning store's logic, and instantiates `Kernel<World>`. "Stores register record-types" = contribute `Record` variants + `apply` arms; "index-rebuilders" = **mandatory** incremental hint maintenance inside `apply` (it runs on every live commit and every replay step — a hint not folded here is stale after every write), plus, optionally, `World::rebuild_derived` to seed hints the checkpoint skip-serialized (it runs once at load, before replay, never on a live commit, so it cannot keep a hint current on its own — and whatever it seeds must equal the `apply`-fold of the `Seq ≤ S_load` prefix it stands in for, §7). Three hard contracts on store code:

**(1)** stage only authoritative deltas, maintain hints incrementally in `apply`, and **never journal a hint**.

**(2)** under the per-key-concurrent/CAS realizations, **footprint confinement** — `f`'s entire committed-state **read set** (every value consulted to decide what to stage, whether to reject, or which branch to take — not only the staged records' values) must lie under the state the txn's `keys` cover, or be **monotone-safe**. Monotone-safety is *narrower* than "append-only": a *positive* membership test on an append-only set (`a ∈ dom(C)`) is exempt because its truth survives every append, but a *negative* existence/freshness probe (`a ∉ dom(C)`) is **not** — a concurrent append falsifies it — and must be under held keys. This read contract carries a **writer-side dual** that is *not* automatic: a txn's *writes* are confined to held-key state by construction (its staged records mutate only that state and append fresh, disjoint entries), **but** any committed-state slice some `f` *reads* under a key K must be *written* only by txns that also hold K. The clause-7 active-in-class membership is the live case — a same-class **nullify** mutates it, so a nullify must hold `class_key` too. (For emit-vs-nullify *specifically* the dual is sufficient-not-necessary: that race is benign per ASN-0134 §4(ii) — a valid serialization, never a duplicate — so confining only the emit's read still suffices for clause-7 no-duplicate. The dual matters wherever a read-vs-write race is *not* so benign.) So the active obligation has two halves: confine each `f`'s read set to its keys, and hold the covering key when writing state another `f` reads. Because merge-at-install re-folds the decided records without re-running `f`, an unconfined read means a stale decision (which records, hit vs miss, reject, branch) commits at a non-serializable position. A store honoring (2) migrates single-applier → concurrent transparently; one whose *read set* escapes its keys, or that writes read-shared state without the covering key, is correct under the single applier but corrupts silently under merge-at-install. M2 cannot check (2); it is the store's contract.

**(3)** if a store overrides `rebuild_derived` to reconstruct a skip-serialized hint, that override must seed exactly what folding the `Seq ≤ S_load` prefix through `apply` would produce — so the load-time seed and the live `apply`-fold can never disagree (§7); M2 cannot check this either.

**Downstream seams (what neighbors code against):**
- **M3 allocation** (frontier under H0): `let (addr, _seq) = kernel.transact(&[key(home, subspace)], |stg| { let φ = recompute_max_under(stg.base(), home, subspace); let addr = inc(φ); stg.push(Record::Alloc{addr, …}); Ok(addr) })?`. M3 supplies the key bytes (1-byte space tag + tumbler bytes) and does all address math; M2 only locks + commits. The frontier read is confined to `key(home,subspace)`, satisfying footprint confinement (it is the only committed-state read `f`'s decision depends on). This standalone form is for a *bare* allocation; when allocation is one step of a larger composite (M5's placement), the caller does **not** invoke this `transact` from inside its own closure (that would deadlock — §3) but reuses the *pure* `recompute_max_under`/`inc` body directly against `stg.base()`.
- **M5 placement composite** (INSERT/COPY/VERSION): one `transact([key(d, s_C)], …)` staging K.α + K.μ⁺ + K.ρ, returning `(_, last_seq)`; M5 checks S3★ on `stg.working()` and the J-couplings at the boundary; M2 commits atomically. M5's content `K.α` mints its address by reusing M3's **pure** `recompute_max`/`inc` math against `stg.base()` *inside this one closure* — it does **not** nest a call to M3's allocation `transact` (a nested `transact` deadlocks on the held applier/install serialization — §3); the composite is one closure composing neighbors' pure functions, never a transaction-within-a-transaction. CREATENEWDOCUMENT (M3) is one `transact` registering the entity (returning its `Seq`) — it does *not* materialize an arrangement (M5 keeps that lazy).
- **M7 idem=⊤ emit**: `transact(&[class_key, key(home, s_L)], |stg| { if m7_active_in_class(stg.base(), class).is_some() { Ok(Hit) } else { let ℓ = inc(…); stg.push(Record::LinkEmit{ℓ, tuple}); Ok(Deposited(ℓ)) } })` → `(outcome, seq)`. The class_key serializes same-class emits (clause 7); the alloc key serializes same-home allocation (clause 2); the active-in-class read the hit/miss decision turns on is confined to the held `class_key` (footprint-confined) — and, by the writer-side dual, a same-class **nullify** must *also* hold `class_key` so that read serializes (the emit-vs-nullify race it leaves uncovered is benign per ASN-0134 §4(ii), so this is sufficient-not-necessary, but M7 holds `class_key` on nullify regardless). Nullify hit-branch = a `transact` that stages nothing (zero-step), returning `(Hit, base.seq())` — and, under durable-before-visible group commit, first locating its base's in-flight batch via the working tip's batch handle and waiting to be resolved at that batch's serialized resolution, **returning `TxnError::Conflict` for re-invoke if that base is instead rolled back by a barrier failure (§1/§3)**. The spanfilade is M7's hint, maintained incrementally in `apply` (mandatory — never journaled) and seeded by `rebuild_derived` only if the checkpoint skip-serialized it — that seed obligated to equal the `apply`-fold of the `Seq ≤ S_load` prefix (§7).
- **M6/M8/M9 readers & verdicts**: `let s = kernel.snapshot();` then read every constituent off `s` (clause 6). M9 reports quiescence as "as of `s.seq()`" (V1 retrospective). M9 calls M2 **directly only for these snapshot verdicts**; its reactive rule *fires* do **not** call `transact` — they go through **M7's gated write path** (`Emit_K` → M2), per the `M9 → M7` edge. A *single-step* (`m = 1`) fire is exactly one atomic `transact` *inside M7's emit* (the "atomic fires" M9 leans on), and M9 obtains the fire's index from the `Seq` **M7 returns** (exact even under per-key concurrency, unlike a post-hoc `current_seq()`, which names only the installed root — §5); a *multi-step* (`m ≥ 2`) fire is an A5 batch M9 drives as several such M7 emits, sequenced above the substrate.
- **M10**: opens/commits each operation's transaction via `transact`, receiving `(result, last_seq)`; acknowledges to the external client only after it returns (commit-before-ack), may report `last_seq`, surfaces `TxnError::Rejected(E)` as a typed rejection (never a silent skip), re-invokes a fresh closure on `TxnError::Conflict`, and treats `TxnError::Poisoned` as a halt condition (do not re-invoke). On startup, `OpenError::PoisonedTail`/`Corruption`/`BadCheckpoint` are operator-intervention conditions, not retried automatically. (An operation still returns only once *its own* effect is durable and installed in every realization; but under the visible-before-durable realizations — `durable_before_visible: false`, per-key, CAS, §8 — a **reader** can be acked reflecting *another* op's installed-but-not-yet-durable effect, which a crash may roll back. The single applier's durable-before-visible default closes even that window — §1/§3/Conflicts #3.)

## Conflicts resolved

**1. Composite atomicity (ASN-0047) vs "batches are not atomic" (ASN-0134 A5).** The two speak of different units. M2's atomic unit is the **transaction** (one `transact`) — externally none-or-all. ASN-0047's "observable intermediate states" of a composite are precisely `Staging.working`, visible *only to the executing closure* for intra-composite precondition checks, never to external readers. ASN-0134's "batches not atomic" refers to a sequence of *separate* operations (`retract_stale`, a multi-step (`m ≥ 2`) rule firing) whose partial visibility is intended (a single-step `m = 1` fire is one atomic `transact` — §Purpose). **M2 cannot bundle caller-separate operations** — it offers only the per-`transact` atomic unit; a store honors A5's intended partial visibility by issuing an `m ≥ 2` batch as *separate* `transact`s, and *may* over-satisfy A5 by committing it as one `transact` (A5's "atomicity must be built above the substrate" permits exactly that). M2 neither forces nor forbids the granularity. The **content run** (one `K.α` per atom) is the boundary case ASN-0134 A5 explicitly classes as a non-atomic batch — and M2 may commit it *either* way, the builder's call (ASN-0134 decision #7): as **one atomic `transact([key(d,s_C)], …)`** (the held key delivers W2, the single install over-satisfies clause 5 — no reader lands mid-run), or, when reader-visible mid-run partial visibility is wanted, as **`critical_section` + separate per-atom commits** (clause-5-faithful, available only under the concurrent realizations — it panics under the single applier — §4). So: M2 delivers transaction (composite) atomicity; multi-transaction batch atomicity is the caller's, "above the substrate"; and the content run sits on the seam, committable either as one atomic unit (over-satisfaction) or as a held-key sequence of commits (faithful clause 5).

**2. Single global writer (ASN-0047) vs per-home serialization suffices (ASN-0134 G1).** The **contract** is the weaker one — per-key serialization (clause 2). The recommended **first implementation** is a single applier (ASN-0047), which over-satisfies it. Because `transact(keys, …)` is identical for both, the migration single-applier → per-key-concurrent (merge-at-install) changes no caller's *call shape* — but it is transparent **iff every store confines its entire committed-state read set — every value `f` consults to decide what to stage, whether to reject, or which branch to take, not just its staged records' values — to its held keys** (modulo monotone-safe reads — *positive* append-only membership only, not negative existence probes; §8) **and holds the covering key whenever it writes state another `f` reads** (the writer-side dual — e.g. a nullify holding `class_key`; §8/Dependencies). This is ASN-0134 G1's full commutativity hypothesis (neither reads nor writes shared state) raised to a seam contract. A store written against the single applier that reads or writes state *outside* its keys compiles and runs correctly there but corrupts silently under merge-at-install; and because "build single-applier first" authors stores *before* this discipline would otherwise bite, the contract must be stated up front. ASN-0047's single-writer is one conservative realization of ASN-0134's contract, not a competing requirement.

**3. Visible-after-durable (ASN-0047) vs durability-orthogonal (ASN-0134).** ASN-0047 says make a composite visible only after its batch is durably committed — natural in its single-threaded model, where *visible* == *acked*. ASN-0134 treats durability as orthogonal (not a MIC clause; `Durability::None` is faithful) and takes *visible* == *committed*. M2 resolves this by making **durable-before-visible the canonical ordering of the single applier** — the recommended first implementation, the `SingleApplier { durable_before_visible: true }` default (§1/§3): install follows the marker barrier (under group commit a **single in-order flusher** has the leader capture the batch-final state, claim the flush slot, fsync with the lock released but the slot held — so no later batch appends above it or resolves before it — then re-acquire the serialization point to install it **monotonically** and raise the watermark *before* waking waiters — §3), so every installed root is durable, an external M10-acked read never reflects a state a crash can roll back, and a woken write's effect is already in `root` (the read-your-writes A7 requires) — *including a zero-step idem-hit, which under group commit locates its base's in-flight batch via the working tip's batch handle and waits to be resolved at that batch's serialized resolution before acking, and is woken to retry rather than ack on a rollback* (§1/§3) — and `TxnError::Durability` is a sound true no-op *so long as the un-acked-tail truncation completes durably* (which is well-defined because the in-order flusher keeps the failing batch the journal tail, with no over-truncation/false-no-op/cascade) *; if it does not, the kernel poisons (returning `TxnError::Poisoned`) and writes a `Poison` sentinel so recovery refuses the surviving failed marker* (§1/§7). The **visible-before-durable** ordering (install-then-fsync) takes ASN-0134's weaker stance: prefix-closure keeps it safe for *internal* causal dependence, but an external read acked during the not-yet-durable window can be rolled back by a crash, and a barrier failure must **poison** the kernel (returning `Poisoned`) rather than no-op (the install is already visible) — having no journal tail to truncate, it tolerates the fsync overlap durable-before-visible forbids. This ordering is the `SingleApplier { durable_before_visible: false }` opt-in throughput variant *and the necessary, non-optional ordering of the per-key-concurrent and CAS scaling realizations* (§8) — whose install-before-barrier shape leaves no room for durable-before-visible. **So the concurrency-mechanism and durability-ordering decisions are coupled, not independent, and M2 makes the invalid pairing *unrepresentable*:** `durable_before_visible` is a flag **only** on `Concurrency::SingleApplier`, and `PerKeyMerge`/`OptimisticCas` carry none — there is no "concurrent + durable-before-visible" config to mis-set or silently override (§Public interface). Durable-before-visible requires the single applier; choosing per-key/CAS for throughput adopts visible-before-durable, and with it the external-M10-read-rollback window and poison-on-barrier-failure. The migration single-applier → per-key changes no caller's *call shape*, but it **does** change this externally-visible durability semantics — the one thing "API-invariant" does not cover. The conflict is thus resolved by canon (ASN-0047) for the single applier, with the ASN-0134 reading the mandatory semantics of the scaling path.

**Boundary clarifications (territory that *looks* like M2's but is a neighbor's, resolved by the decomposition's dependency inversion):** the frontier discipline ASN-0134 reasons about (H0) is M3's *allocator*; M2 owns only its *serialization*. The request/response path and pipelining-vs-sequential client model (G0) are re-homed to M10; M2 keeps only the commit-gate mechanism. Neither is a conflict — both are M2 honoring its seam by *not* doing the neighbor's job.

## Open build decisions

- **Concurrency mechanism** — single applier (`SingleApplier { durable_before_visible }`, recommended first, flag default `true`) → per-key concurrent with merge-at-install (scaling path; binds the footprint-confinement read-set contract and its writer-side dual) → optimistic-CAS (only under measured low **overall commit rate** — the whole-root `ArcSwap` CAS aborts on *any* concurrent commit, not just same-key; a per-frontier CAS would narrow it to same-footprint — §8; `Conflict` is caller-re-invoke-with-a-fresh-closure since `f` is `FnOnce`; concurrent winners append out of `Seq` order, so recovery group-by-`txn`-and-sorts-by-`Seq` — §7; retry termination unresolved, OQ1/OQ3). Pick by throughput need; the API doesn't change — **but this is *not* independent of the durability-ordering decision below: `durable_before_visible` is a flag *only* on `SingleApplier`; `PerKeyMerge`/`OptimisticCas` are necessarily visible-before-durable and carry no such flag (§1/§8), so "concurrent + durable-before-visible" is unrepresentable rather than silently overridden.**
- **Durability/visibility ordering** (a flag on the single applier, **unrepresentable** for the concurrent variants) — **durable-before-visible (`SingleApplier { durable_before_visible: true }`, canonical: append records+marker → barrier → install → raise watermark; under group commit `base` is drawn from the applier's working tip, and the **single in-order flusher** has the leader capture the batch-final state, claim the flush slot, fsync with the lock released but the slot held, then re-acquire the serialization point to install it **monotonically** and signal — never a fresh post-barrier `tip.load()`, §3; a `Durability` failure is a sound no-op via truncate-tail + Seq rollback because the failing batch is always the journal tail *iff that truncation completes durably — else poison, returning `Poisoned`, plus a `Poison` sentinel for recovery, §1/§7*)** vs visible-before-durable (`SingleApplier { durable_before_visible: false }`, install-then-batched-fsync; needs no working tip, no flush-slot gating, no batch-final capture, no zero-step wait; prefix-closure keeps internal dependence safe, but an external M10-acked read can reflect a rolled-back state, and a barrier failure must **poison** (return `Poisoned`) rather than no-op — §1, Conflicts #3) — the latter also the **forced** ordering under `PerKeyMerge`/`OptimisticCas`. Group commit amortizes the barrier under either; under durable-before-visible it is **intra-batch only** (one fsync over a batch's txns; no cross-batch fsync overlap — that overlap would break truncate-tail), so **if fsync-concurrent throughput is needed the per-key realization is the path** (it installs before the barrier and *poisons* rather than truncates on failure, so has no journal tail to protect — §8).
- **Burned-Seq policy on durability failure** — roll the `Seq` high-water back to the last committed marker (keeps the order gap-free; recommended) vs tolerate the gap (relaxes the invariant to monotone-only; recovery tolerates the gap, §7) (§1). Either way, a *failed* truncation of the burned frames forces a kernel **poison** (`Poisoned`) and a `Poison` sentinel, not a no-op (the surviving failed marker would replay as a phantom commit) — §1/§7.
- **Durability mode** — `Fsync` per commit vs `FsyncBatch{window, max_delay}` (group commit via a **single in-order flusher** — one fsync amortized over the txns *within* a batch, batches resolved strictly in order with no cross-batch fsync overlap so the failing batch is always the journal tail; the batch closes on window-fill *or* `max_delay`, whichever fires first — a window-only trigger would stall a low-traffic batch and any zero-step op waiting on its barrier indefinitely; `flush()` is the manual close) vs `None` (in-memory, MIC-faithful, for tests/embedding; `checkpoint()` then a no-op returning `current_seq()`, `flush()` a no-op `Ok` — §6/§Public interface).
- **Checkpoint cadence, retention & representation** — every-N-commits / time / journal-size; **`retain_checkpoints` (N ≥ 1)** most-recent checkpoints kept, journal reclaimed only below the **oldest** retained one so `BadCheckpoint` can fall back to an older retained base (N = 1 ⇒ newest is the sole base, no fallback, so verify/duplicate the write) — §6; full-`World` serialize vs per-store/incremental; serialize hints vs `#[serde(skip)]` + `rebuild_derived` (checkpoint size vs recovery recompute — and an overriding `rebuild_derived` must match the `apply`-fold of `Seq ≤ S_load`, §7). The recovery-time-vs-overhead knob ASN-0047/0134 leave open. (The `≤ S_load` / `> S_load` checkpoint-vs-replay boundary against the *loaded* checkpoint is *fixed*, not a knob — §6/§7; journal truncation is segment-granular space reclamation, never a correctness mechanism — recovery's `Seq > S_load` filter handles any `≤ S_load` frames a straddling segment leaves behind, and corruption among them is non-fatal, §7.)
- **Lock-table layout** — striped `Vec<Mutex>` (bounded, false contention) vs per-key `DashMap` (no false contention, entry GC). *This choice also sets the multi-key acquisition order: `Striped` acquires in stripe-index order, `PerKey` in bytewise-key order (§4).*
- **Journal framing** — CRC algorithm (the frame `crc` covering **both `len` and payload**) **plus a fixed per-frame `magic` sync word** so the recovery scan can resynchronize past an interior bad frame to find later markers and tell a torn tail from committed-prefix corruption (§1/§7); the per-frame **`txn` id (a `u64`)** that groups a transaction's frames so its `records_checksum` validates after a `magic`-resync skipped a corrupt frame (file-contiguity untrustworthy there — §1/§7); the marker's `records_checksum` over the txn's record frames (distinct from the frame `crc`); the rare `Poison{ trusted_through }` sentinel framing (§1/§7); segment rotation, max frame size, fsync-of-dir on rotate.
- **Whether to build `critical_section` at all** — default to issuing every run as one `transact` (atomic, delivers W2 via the held key, over-satisfies clause 5); build the held-across-commits guard only if a run is genuinely too large to commit atomically or needs intended mid-run reader visibility — and only under the per-key-concurrent/CAS realizations, since under the single applier it provides no run-exclusion and therefore **panics** (§3/§4). *Optionally gate its availability at the type level — a concurrency-mode type parameter on `Kernel` so single-applier callers cannot name the method — matching how `durable_before_visible`'s placement makes the invalid concurrent pairing unrepresentable; the runtime panic is the baseline specified here.*
- **Record/key encoding** — `Record` (the trait's `W::Record`) as one serde enum (recommended for a single binary, compile-time dispatch) vs a runtime type-id registry of boxed appliers; `LockKey` as `Vec<u8>` vs `SmallVec`/`Box<[u8]>` vs a fixed-width digest.
