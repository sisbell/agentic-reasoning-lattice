## Revision list

**1. [DEFECT] M5 responsibility prose: COMPARE does not join M and R.** The text reads "the read-side observers that join the two — SHOWDELETIONS, COMPARE (M6) — require a single consistent (M, R) snapshot." ASN-0122 is explicit that COMPARE "reads neither content values, the link store, the entity set, **provenance**, nor any other document's arrangement" (X5) — it is correspondence by *address equality* over arrangements alone, and "never opens the content store." COMPARE requires a consistent *multi-document M* snapshot (ASN-0122's "one consistent snapshot spanning all documents named"), **not** an (M, R) snapshot. The operation that actually joins M and R alongside SHOWDELETIONS is **FINDDOCSCONTAINING** (ASN-0124: `finddocs(resolve(Q,Σ),Σ)` reads R for the candidate set and current M for the present-tense filter, at one Σ) — which is exactly what the Open-partition prose correctly lists ("SHOWDELETIONS, FINDDOCSCONTAINING"). Fix: in the M5 (M,R)-co-location justification, replace COMPARE with FINDDOCSCONTAINING (or SHOWDELETIONS alone), and note COMPARE's snapshot need is multi-document M. The boundary (R in M5, COMPARE in M6) survives — but the justification is built on a false dependency claim.

**2. [SHARPENING] M2 seam over-attributes the J-couplings (borders on a defect).** "The three-layer permanence discipline and the J-couplings (content-allocation ⇒ placement ⇒ provenance) ... are enforced by the stores (M4/M5/M7)." Permanence is roughly store-wide (and actually spans M3 too, for the entity set E's append-only-ness, which the list omits). But the J-couplings are **M5-only** — they bind content allocation to placement and provenance, which co-occur only in M5's INSERT/COPY composite. ASN-0047 is explicit that "Link allocation (K.λ) has no such coupling" (orphan links are valid). Listing M4 (a passive value store) and M7 (uncoupled link allocation) as J-coupling enforcers risks a builder coupling link allocation to placement/provenance — exactly the orphan-link violation ASN-0047 forbids. Narrow the J-coupling attribution to M5; keep permanence as the store-wide (M3/M4/M5/M7) discipline.

**3. [SHARPENING] M7/M8: Observe (M7) and findlinks (M8) are near-duplicate matchers over one index.** Observe(K, F, G) ≈ findlinks(home=*, F, G, K) over the active view — both are AND-of-ORs coverage compositions over M7's spanfilade. The producer correctly flags this as the softest seam and correctly places the shared *index* in M7 to break the would-be M7↔M8 cycle. But the *combination engine* is then implemented twice (Observe's in M7, findlinks's in M8). Consider factoring the per-slot-match-plus-AND-of-ORs combiner into M7 (alongside the index it owns), leaving M8 as pure discovery presentation (windowing/cursors/count/pagination/projection/RETRIEVEENDSETS) over M7's matcher. Sound either way; this removes the conceptual overlap.

**4. [SHARPENING] M2's "generic over caller-supplied keys" and "depends on M1" are in tension.** The seam says the keyed critical section takes keys "supplied by the calling store, never computed here," and records are dispatched to caller-registered rebuilders — i.e., M2 needs only key *equality* and opaque payloads, not M1's algebra. Yet M2→M1 is justified by "the (home,subspace) contention unit and step keys are address structure." Either M2 is genuinely generic over opaque keys (drop M2→M1, making M2 a second independent foundation alongside M1 — a cleaner story) or its interface is M1-typed (keep the edge, drop the "generic / never computed here" framing). Resolve the inconsistency; it doesn't threaten acyclicity but it muddies whether M2 is a foundation.

**5. [SHARPENING] M5 should name the referential-integrity / subspace-alignment / non-transclusion gates.** ASN-0036's "referential-integrity gate" and "subspace-alignment precondition," ASN-0047's S3★ (content→C, link→L routing at placement), and ASN-0043's hand-up of the non-transclusion guard are all M5 placement preconditions, currently folded implicitly into "subspace confinement & contiguity maintenance." Name them — they're distinct active-enforcement obligations (S3★ is the one stopping a content V-position from binding a link address), and a builder reading "subspace confinement" alone could miss the referential-integrity-at-placement check.

**6. [SHARPENING] M8 seam describes only V→I, but project needs I→V.** M8's seam says it "resolves content regions to I-addresses via M5's image/resolve" — that's the V→I direction (findlinks_V). But `project` (ASN-0098), a core M8 component, goes coverage(I-addresses)→V-positions, the I→V direction (the within-document reverse of M(d), ASN-0082 OQ1). Note that M8 reads M5's arrangement in *both* directions (or via an inverse-arrangement hint, which if materialized lives in M5). The capability is assigned (project ∈ M8); only the seam wording undersells it.

**7. [SHARPENING] On the producer's flagged boundary calls — I largely endorse them.** M4/M5 split (Istream/Vstream spine): keep. R in M5 (write-locality + single (M,R) snapshot for SHOWDELETIONS/FINDDOCSCONTAINING): keep — the J-coupling forces the R-append into the same composite as the M-edit, so co-location is right. M9 bundling and M2-as-module: keep. M3 ownership-fold (vs an Authority module): defensible — delegation *is* a baptism and a principal prefix *is* a baptized address, so the coupling is real; the Lampson policy/mechanism argument is the live alternative but not a wrong choice. M5 (~10 ASNs) and M7 (~9 ASNs) sit at the upper size bound but are cohesive — all of M5's editing operations share the POOM + displacement core, and M7's store/types/index/primitives are one "own the link store" responsibility; splitting either would create a fat thin-interface seam for little gain. None of these is a wrong choice; none is a defect.

[SHARPENING] Minor naming/prose fixes.** (a) M1 should explicitly list tumbler *decomposition* `(parent, depth, ordinal)` — ASN-0040 forces it and M3's counter-registry depends on it (currently subsumed under "field parser"). (b) M4's "kind-from-address" is a pure subspace projection and belongs to M1 (or note M4 delegates to it); the final two-store model (C/L disjoint) leaves M4 holding homogeneous bytes with no kind to recover. (c) M4's seam under-lists consumers — M9 also reads M4 (value-at) for predicate-def read-back. (d) The Open-partition remark "SHOWORIGIN is pure M1 projection" is loose: only the *pointwise* projector is M1; the SHOWORIGIN *operation* with its I-span/V-span resolvers reads state and is correctly in M6. (e) The Overview's "the one append-only structure that is authoritative history rather than a hint being R" reads as if R were the only authoritative append-only structure — the content/link/entity journals are too; clarify that R is the one *derived-looking relation* that's authoritative (non-recomputable from current M), distinguishing it from recomputable hints, not from the primary stores.
