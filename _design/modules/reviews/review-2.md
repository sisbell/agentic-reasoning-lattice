Reviewing the manifest against the corpus. The decomposition is broadly sound — 9 coherent modules, an acyclic DAG, the two near-cycles (M5↔M7 link-seating, M3↔M5 registration) correctly broken by direction, and the content/link J-coupling asymmetry correctly reflected in M7-bundles-MAKELINK but M4-doesn't-bundle-content-creation. The problems are localized.

## Revision list

**1. [DEFECT] M9 owns predicate-definition *creation* but is missing the M5 edge that placement requires.** ASN-0130 stores predicate definitions as immutable **content** runs (M4), and M9's registration surface *writes* them. But ASN-0047's J0/J1★ couples content allocation to placement + provenance in one composite ("an allocated-but-unplaced content address would indicate corruption") — there is no raw content-append that bypasses M5's composite boundary, and that boundary is where M5, not M4, lives. M9's declared `M9 → M4` covers *reading* a def by address (M4 value-at) but not *creating* one: a builder following `M9 → M4` directly will write def-bytes into M4 with no placement, producing orphan content that violates a load-bearing foundation invariant. **Add `M9 → M5`** and route def-content creation through M5's placement composite (the def's identity stays its content start-address; the V-position is incidental J0 satisfaction) — or, if def-content is meant to be genuinely unplaced, state that exemption explicitly and acknowledge it relaxes ASN-0047 J0 (a claim the corpus does not currently support). Edge is acyclic (M5 < M9).

**2. [DEFECT] `M4 → M3` is spurious, and M4 over-claims content allocation (K.α).** M4 is a passive byte store; it never mints. Content minting is M3's frontier allocator, and because content allocation is J0-coupled it is invoked *inside M5's INSERT/COPY composite* — exactly as M5's own seam says ("mints content addresses via M3, writes bytes via M4"). So `M5 → M3` (mint) and `M5 → M4` (store); M4 calls nothing in M3, and addresses reach it as parameters, not via a call. The tell is the contrast with M7: `M7 → M3` is justified because M7 contains a minter (MAKELINK); M4 contains none, so `M4 → M3` is unjustified. **Set `M4 → M1, M2` only**, and re-scope M4's ASN-0093 attribution from "K.α content allocation" to the *storage* half of K.α (the mint is M3, orchestrated by M5). This also resolves the latent double-claim of content minting between M4 (source + edge) and M5 (seam). (If you intend M4 to defensively gate stores on baptized addresses, say so — that's a check, not "receives addresses from M3.")

**3. [SHARPENING] The link-coverage index (spanfilade) is in M8, but ASN-0086 wants it backing M7's Observe — surface the constraint or co-locate.** Observe (the authoritative typed-relation read, M7, consumed by M9's PL) matches by from/to/type coverage, and ASN-0086 explicitly names the spanfilade as its index. With the spanfilade in M8, a source-faithful builder backing Observe with it creates an `M7 → M8` cycle. The decomposition is buildable *only* because Observe can be served within M7 (type-keyed slice + per-tuple coverage-check — ASN-0086's scan/slice fallback), but that is an unstated load-bearing constraint and it forecloses ASN-0086's recommended indexed Observe on the hot PL-polling path. Either (a) move the link-coverage index into M7 — the store it indexes — so Observe and M8's discovery share one index (M8 reaches it via the existing `M8 → M7`), or (b) state that M7's Observe is M7-internal (type-slice) and the M8 spanfilade is discovery-exclusive. This is the sharp form of your flagged "softest seam."

**4. [SHARPENING] Provenance R in M5 cuts against the decomposition's own "separate permanent record from mutable presentation."** R is permanent, append-only, *non-recomputable* authoritative history; M5 is the mutable-presentation module. Co-locating R with its writers is defensible (state with its mutator), but it leaves the largest module owning two permanence classes. Either reframe M5's responsibility to bracket R explicitly as "authoritative history, co-located for write-locality," or lift R + its read family into the "Provenance & Attribution" module you flagged. Relatedly, the overview's "keep every derived index as a recomputable hint" must be read to *exclude* R (M5 correctly marks it authoritative) — tighten the prose so R isn't swept under "every index is a hint."

**5. [SHARPENING] M2's "per-coverage-class serialization" leaks link semantics into the kernel.** M2's stated principle is "owns ordering/durability/isolation, never store semantics," yet its components list per-*coverage-class* dedup serialization (a link-typing concept from ASN-0086/0128). Reframe: M2 provides a *generic keyed critical section*; M7 supplies the coverage-class key (computed via M1). Keeps the kernel store-agnostic and consistent with your dependency-inversion seam.

**6. [SHARPENING] Ownership (M3) bundles policy with allocation mechanism.** Folding owns/ω/delegation/fork into M3 is defensible (delegation *is* baptism; principals label the registry), but it mixes mechanism (allocation) with policy (authority), and the session/access consumer is external (out of corpus). You flagged this; it's sound either way — keep the Authority-module split noted as the live alternative.

**7. [SHARPENING] Minor source/seam tidy-ups.** (a) M4's ASN-0036 parenthetical lists "run-decomposition on demand," which is an *arrangement* capability (ASN-0058, owned by M5), not the content store's — trim it. (b) M3's seam says "M5 … distinguishes registered-empty from unallocated," but the ⟨⟩-vs-fail *query* distinction belongs to M6's queries (via `M6 → M3`); M5 only checks "is d registered?" for edit preconditions — attribute the distinction to M6. (c) "MVCC" in M2's components is one realization of "snapshot reads"; harmless, but it's a slight mechanism leak at boundary altitude.
