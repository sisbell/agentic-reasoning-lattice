Reviewing against the corpus. Every ASN is assigned to some module and I find no orphaned capability at the note level — the stack is complete. The kernel/feature split, the Istream/Vstream spine, and the hints-over-journal discipline are sound, and the DAG is acyclic. The problems are concentrated in two seams: document-registration access and the M7/M8 link boundary.

## Revision list

**1. [DEFECT] Add `M6 → M3` (the document-registration / "is d allocated?" gate).** Five M6 operations require a registry-membership test that M6's declared dependencies (M1, M2, M4, M5) cannot answer:
- RETRIEVEDOCVSPANSET (ASN-0113) must distinguish *allocated-empty* → `⟨⟩` from *unallocated* → fail — the note is explicit this is "a membership test … against the document registry," and that the two states must stay distinguishable.
- RETRIEVEDOCVSPAN gates on `d` allocated; RETRIEVEV requires `d ∈ dom(Σ.M)`; SHOWORIGIN_V's admissibility checks "source document allocated"; COMPARE requires "each named document exists."

That membership lives in M3's entity registry (M3's own seam hands "is allocated?" to *every* operation), and **M9 already takes exactly this edge for `is_doc`** — so M6's omission is an internal inconsistency, not a deliberate choice. As written, M6 cannot make the registered-empty/unregistered distinction; the only fallback available to it (read it off M5's arrangement domain) silently conflates the two — the precise bug ASN-0113 warns against. Fix: add `M6 → M3`, or state in M5's seam that resolution fails-on-unregistered (then `M6 → M5` suffices) and update M6's description accordingly.

**2. [DEFECT] Resolve Observe's ownership — it is an M8 component but ASN-0086 (its only source) is attributed to M7.** M8 lists "findlinks (four-set match) & Observe," yet ASN-0086 is in M7's sources, not M8's, and the producer's own open question calls Observe "M7-declared." M8 thus claims a component no M8 source supports. Pick one: keep Observe in M7 (the by-pattern read of the typed-relation surface) and strike it from M8's components; or split-source ASN-0086 (Emit/Nullify/slices/retraction → M7; Observe → M8, consistent with "indexed pattern queries execute in M8"). Either is fine — the current state contradicts itself.

**3. [SHARPENING] Place typed-reverse-lookup (ASN-0128 BH3) execution explicitly in M8.** Its backing index is the spanfilade (owned by M8), but ASN-0128 is sourced only to M7 and BH3 is left unplaced; M7's component list names only "determinate-walk." A builder reading "behaviors live in M7" and executing BH3 there needs M8's spanfilade → `M7 → M8`, cycling against `M8 → M7`. The producer's stated principle ("indexed query execution in M8") already resolves this — make it explicit: M7 owns the behavior *declarations* and the forward behaviors (determinate-walk over forward adjacency, read-filter, age); reverse-lookup *execution* is M8.

**4. [SHARPENING] State that CREATENEWDOCUMENT (M3) must not eagerly materialize the M5 arrangement.** ASN-0103 recommends eagerly building `M(d)=∅`. But M3 → {M1, M2} only — it cannot write M5's store — so the empty arrangement must be implicit/lazy (a registered doc with no M5 entry resolves to ∅, M5 distinguishing registered-empty from unregistered via `M5 → M3`). A builder following ASN-0103's eager recommendation would write M5 from M3 and create an `M3 → M5` cycle. Surface this constraint and its divergence from the source note. (This is the write-side companion of defect #1: document registration lives in M3, the maps in M5.)

**5. [SHARPENING] M2's ASN-0047 attribution over-claims store semantics.** M2 sources "composite executor" and "three-layer permanence discipline" from 0047, but the J-couplings (content-alloc ⇒ placement ⇒ provenance) are enforced by M5's INSERT/COPY at their composite boundary, and the existential/historical append-only discipline is enforced per-store (M4/M5/M7). M2 should own only the *mechanisms* (journal, linearization, composite boundary, commit-marker durability, snapshots) and "never store semantics" — as its own seam says. Reword so the couplings/invariants sit with the stores that enforce them through M2's boundary.

**6. [SHARPENING] M5 co-owns two permanence layers.** M5 is billed as "the only layer where destructive change lives," yet it also owns provenance R, which is *historical/append-only* (P2), never destructive. Co-locating R with its writers is defensible (the component already marks it "authoritative" — good), but the "only destructive layer" framing is loose; note that R is permanent history, not part of the mutable presentation.

**7. [SHARPENING] M8's responsibility says "follow"; FOLLOWLINK is in M7.** ASN-0114's FOLLOWLINK (recorded-endset read by address, no resolution) is correctly placed in M7. Change M8's "project/follow/count/paginate" to "project/resolve/count/paginate" so it doesn't read as claiming FOLLOWLINK.

**Producer's flagged open questions — my read (no change required):** keep M4/M5 split (the Istream/Vstream immutability boundary is the architectural spine and earns module-visibility); keep ownership folded into M3 (a separate ownership table is exactly the divergence trap the corpus repeatedly warns against — folding is the Lampson-correct "don't duplicate authoritative state" call); M9-as-one is fine. The provenance-module split is worth it only if R's query family grows. The M3 element-frontier allocator stays acyclic so long as its frontier counters are hints over M2's journal (not derived from M4/M7 stores) — which the manifest's stated "hints over an append-only journal" principle already implies.
