Below is a revision list. The digest is, on the whole, accurate, well-grounded, and unusually actionable — its fork O(1)-share-vs-O(n)-provenance observation, the "R is authoritative history, not a recomputable hint" point, and the content-only recovery contract (J0/J1★ for content, never for links) are exactly the subtleties a builder needs. The items below are improvements, ordered most-important first.

---

**1. Design commitments (link-subspace bullet): "the reference implementation … tombstones link positions" is wrong, self-contradicting, and misframes the divergence.** The note's own Open Questions section states the opposite explicitly: the implementation keeps a *gap-free POOM* and *compacts-and-renumbers* surviving V-positions on interior deletion, and adds parenthetically that "this is a question about the contraction *operation*, **not about tombstoning**." So (a) the implementation does not tombstone the arrangement, and (b) the note's gaplessness strengthening *agrees with* the implementation's gap-free POOM for the suffix deletions K.μ⁻ actually models — it does not "diverge here." The digest's own *Decisions* item gets this right ("compacting-and-renumbering surviving positions"), directly contradicting this commitment. Fix: delete "tombstones link positions"; state the real divergence — the note's K.μ⁻ models suffix-removal only, while the implementation additionally performs interior compaction/renumber, which the note leaves open. Keep the accurate half (D-CTG★/D-MIN★ drop ASN-0036's link-subspace tombstoning *exemption*).

**2. Guarantees: the within-document link-uniqueness asymmetry (CL-UNIQ) is missing.** The digest nails the *cross-document* asymmetry (content transcludable anywhere; a link only in its home doc) but omits the *within-document* one: content may occupy many V-positions in one document (S5), but a link occupies **exactly one** — K.μ⁺_L's precondition `ℓ ∉ ran(M(d))`, invariant CL-UNIQ (M(d)|dom_L is injective). This is an active precondition a builder must enforce at link placement (reject re-arranging an already-placed link), not just an invariant. Add it alongside "Link ownership."

**3. How it fits: the "ASN-0134" reference is ungrounded.** "the consistency/isolation model (ASN-0134)" names a specific artifact that appears nowhere in the note or the evidence answers. Either cite its source or generalize to "a downstream consistency/isolation model," hooking it to the note's *actual* open questions on concurrency and composite-boundary scoping rather than a fabricated number.

**4. Implementation approaches (fork): surface the note's headline J4 distinction — fork preserves V-position multiplicity, it does not deduplicate.** J4 is *characterized* by the φ-bijection (order- and multiplicity-preserving); range-equality is only a derived consequence, and the note spends an entire worked example proving a "deduplicating range copy" silently drops duplicate I-addresses and undercounts contents. The digest's "share the source's content-subspace map" is correct by construction but never states the trap. Add it as an explicit guarantee/warning (copy the V-position→I-address *map*, never the *range*), tied to the origin-identity commitment — a builder choosing a set/range representation could otherwise collapse transcluded duplicates and get fork wrong.

**5. Surface V-position depth as a real builder degree of freedom.** The note makes subspace depth `m_S ≥ 2` a caller-chosen parameter at first insertion, fixed thereafter, and *re-pinned from scratch* after full subspace clearance (the m_S(d) / ValidFirstInsertionPosition machinery). The digest only touches this inside the fork `m_new ≠ m_old` aside. State it as a standalone constraint/decision: any arrangement representation must let the caller choose insertion depth ≥ 2 and re-pin after a subspace empties.

**6. Tighten "immutable entries of E" and "freely/fully mutable M."** E is a set with no values, so "value-immutability of … E" is vacuous — say "membership-only growth (P1)." And M is not "freely mutable": every mutation must preserve D-SEQ★/S3★/CL-OWN/CL-UNIQ at each atomic step. The note's "Fully mutable" means "admits all three mutation modes (extend/contract/reorder)," not "unconstrained" — say that, so the builder doesn't read it as license to skip the per-state invariants.

**7. Drop or qualify the language/repo-specific anchors.** "the `im` crate's ordered map" presumes Rust (the note is language-agnostic), and "this repo's links.jsonl pattern" is a local reference not verifiable from the note or evidence. Keep the structural recommendations (persistent ordered map; append-only journal + replay); cut the unverifiable anchors. Also "snapshot isolation for free" overstates — persistent maps give cheap *historical snapshots*, not the concurrency-control isolation level.

**8. Provenance approach: "Green's spanfilade is exactly this" overstates.** The spanfilade indexes both link endpoints (LINKFROM/TO/THREESPAN) and content provenance (DOCISPAN); R maps only to the DOCISPAN content-provenance role. Keep the apt "write-only reverse index, never trimmed" analogy; drop "exactly."

**9. (Minor) Note K.μ~'s firing precondition.** Reorder fires only when M(d)|dom_C takes ≥ 2 *distinct values* — under transclusion (S5), `|dom_C| ≥ 2` is not sufficient. Worth one clause so a builder treats a single-address/constant-valued arrangement as a no-op rather than a transition.
