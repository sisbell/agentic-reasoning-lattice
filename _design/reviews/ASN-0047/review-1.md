Reviewing the digest against ASN‑0047 and the verified evidence. It's a strong, well-disciplined digest — the Lampson hint-vs-authoritative reasoning is mostly excellent (especially identifying R as the one genuinely-authoritative non-hint, and turning the J-couplings into a recovery contract). But several link-structure claims misread the note, one load-bearing state is omitted, and a couple of approach claims overstate. Revision list, most-important first.

---

**1. Add the orphan-link commitment, and scope the recovery contract to content — the note's content/link coupling asymmetry is missing and the proposed recovery would corrupt valid state.**
The digest states "Allocation requires placement requires provenance (J0/J1★/J1'★)" and the recovery approach says "an allocated-but-unplaced address (J0 violation) or an unrecorded placement (J1★ violation) signals a torn composite to discard." That holds **only for content**. The note is explicit that link allocation (K.λ) has *no* J0-analog: an allocated-but-unplaced link is an *orphan link* — a valid, intentional endpoint (owner's right to withdraw, LM 2/29; deleted-but-permanent links, LM 4/9), and J‑LV makes link placements neither trigger nor witness provenance. So a recovery routine that discards any "allocated-but-unplaced address" would throw away legitimate orphan links, and one that flags "unrecorded placement" would mis-flag every normal K.μ⁺_L. Do W: add the asymmetry to Design commitments (content allocation is coupled to placement+provenance; link allocation is coupled to *neither* — orphans are an intentional valid endpoint), and explicitly scope the J0/J1★ recovery checks to content allocations/placements.

**2. Decisions / Guarantees — the empty-endset policy is inverted, and the note's real open question is dropped.** The digest frames "admit an empty type-endset" as an open builder choice and cites Green accepting it. But the note's **L3 requires the type endset (Θ/e₃) to be non-empty** — it's a maintained invariant, not a decision; Green's acceptance of empty Θ *violates* it. Meanwhile the note's *actual* open question is whether to admit empty **from/to** endsets (`e₁ ∪ e₂ ≠ ∅` — type-only links / one-sided links, LM 4/48), which the digest never mentions. The "phantom link discoverable on some paths but not others" evidence the digest cites is the empty-**F/G** case, not empty-Θ. Do W: list L3 (type endset non-empty) under Guarantees to uphold (noting Green is non-compliant), and replace the empty-type-endset "decision" with the note's from/to-emptiness open question.

**3. "What must be built" / Decisions — link arity is mis-stated as fixed-at-three.** The digest says the link store holds "a fixed triple of endsets" and "Arity is fixed at three (F, G, Θ)." The note's `Link` type is **N ≥ 3**, with the F/G/Θ triple as the *StandardTriple convention* "applied in worked examples only, not as a structural restriction." Fixed-arity-3 is grounded in evidence (Q6, the implementation) — so it's not fabricated — but the digest presents the *implementation's* answer as the *note's* commitment, silently resolving a real note-vs-evidence divergence. Do W: state the note commits to arity ≥ 3 (triple = StandardTriple convention); note the reference implementation fixes 3; present fixed-vs-variable arity as the builder choice rather than asserting it's fixed.

**4. Implementation approaches (Arrangements) — "fork is an O(1) structural copy" elides the mandatory O(n) provenance.** Fork is J4 = K.δ + K.μ⁺ + **K.ρ**, and J1★ forces a provenance entry `(a, d_new)` for every distinct transcluded content address — all of which are content-subspace-range-new for a fresh document. So fork is O(1) for the arrangement M but **O(n) in provenance writes**, hence O(n) overall; the digest's own "allocation⇒placement⇒provenance" commitment implies this. Do W: keep the O(1)-share insight for M but state the unavoidable O(n) provenance cost. (Minor adjunct: structural sharing realizes only the equal-depth fork m_new = m_old; the note's depth-rebasing freedom m_new ≠ m_old in J4 is not a pure structural share.)

**5. Implementation approaches (Arrangements) — "every previous arrangement remains reconstructable" is over-attributed to persistent-M.** The note routes Nelson's reconstructability through **R** (containment-*ever* — ordering is *not* retained) and through **versioning** (fork yields a separate, persistent document), not through retaining a single document's past M states. R cannot reconstruct a past arrangement's order. Persistent-M snapshot isolation is a fine *optional* enhancement that gives strictly *more* than the note requires — don't pin it to "precisely Nelson's reconstructability," which risks implying the spec mandates retaining M snapshots (it does not) or that R captures ordering (it doesn't).

**6. "What must be built" (allocator) — "sub-allocator per document/account/node" risks implying materialized allocator records.** The evidence is emphatic (Q2 and the stateless-allocator answers): Green materializes *no* per-entity allocator state — the address tree *is* the allocator, and version-allocator state appears only at first `docreatenewversion`. Your approach section gets this right ("stateless… no per-document allocator record"), but the "what must be built" bullet reads as four kinds of state to build. Do W: mark these sub-allocators as *logical* address-chains (the note's A_C/A_L/A_v/A_doc/A_account), not records to materialize.
