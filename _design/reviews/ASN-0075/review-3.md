## Revision list

**1. "Design commitments" → "Classification is at I-address-set granularity": relabel "Forced" — it is a deliberate scoping *choice*, not a forced consequence.**
This is the one place the digest miscategorizes (and the reviewer's first duty). The note frames set-granularity as a decision: it classifies on `ran(M(d))`, discarding the V-position multiplicity that `M` *itself* carries (the note writes `|{v : M(d)(v)=a}| > 1`), and explicitly *"scope[s] out"* per-occurrence show-deletions as a Vstream concern "needing finer state." The digest's own prose ("the note deliberately scopes that finer operation out") contradicts its "Forced" label. The masking-location analysis (it lives in the `ran(M(d))` read, not in `R`) is correct — keep it — but don't let "an occurrence-aware `R` wouldn't help" stand in for "forced." Fix: relabel as a **scoping decision** (rationale: transclusion multiplicity, ASN-0058/0036, makes set-granularity coherent), and surface the builder consequence the note implies — extending to per-occurrence deletion needs *new historical occurrence state*: it is not in `R` (no occurrence record) and not recoverable from current `M` (which carries only *current* multiplicity, not what it was).

**2. "Implementation approaches" → "Output representation": the green-`sporgl` analogy misreads the evidence.**
The digest claims green's `sporgl` "carries its `sporgladdress` even though that is structurally derivable." Per Q18 + Q20, `sporgladdress` is the *placing/holding* document, which for transcluded content is **not** derivable from the I-address — only `origin(a)` (the prefix) is. So green carries a *non-derivable holder* field; it is not an example of denormalizing a derivable one, and the analogy actually cuts against the point. Fix: correct or drop it. The digest's own recommendation — enrich with `origin(a)`, derivable per S7/D-ORIG — is sound; keep it. Also resolve the latent ambiguity in "origin-document": it means `origin(a)`, not the deleted-from operand. Note that the *deleted-from* document is already encoded by *which half* an address lands in (positional), so the only non-positional enrichment worth carrying is `origin(a)`.

**3. "Implementation approaches" → "Current arrangement range": the `ran(M(d))` materialization is not a self-correcting "hint."**
A stale cached range-set yields a *wrong* `CURRENT` (hence wrong DELETED/NEVER_INCLUDED), not a recoverable miss — so it is a derived view that must be **invalidated on every `M(d)` edit**, not merely "recomputed on a miss" (a stale entry is a cache *hit*, so miss-recompute never fires). Under the recommended persistent-DS snapshot this is automatic, but the digest offers a mutable-cache alternative ("cache the range-set and keep `M` authoritative; recompute on a miss") that, taken literally, builds the staleness bug. Fix: in the cache alternative say "invalidate on composite commit," and reserve "hint" for the `R`-index (which genuinely is recomputable-from-the-authoritative-log).

**4. "Implementation approaches" → "Snapshot and concurrency": keep the analysis, soften the framing.**
The hazard analysis is excellent — `R`-ahead-of-`M` fabricates a phantom DELETED on the *legitimate* row, which is exactly why D-WIT cannot catch it, while `M`-ahead is benign — keep it as written. But: (a) the note lists the consistency model as an **open question** (and a separate foundation concern), so present this as the *minimal sufficient* condition for this read, not "the right answer to the concurrency open question." (b) "Snapshot isolation" overstates — the operation never writes, so it needs a *consistent joint `(M,R)` snapshot* (MVCC-style read), not full SI. (c) State up front that "always reads a boundary" *requires composite-granular atomic commit*, not merely any immutable-root swap — the whole point is that elementary-step swaps would expose the torn read.

(minor) "What must be built" → item 2:** "This, not point membership, is what the operation *actually consumes*" overstates — the *spec* is defined on point membership `(a,d)∈R`; the *efficient implementation* consumes the projection `{a:(a,d)∈R}`. Soften to "what an efficient implementation reads."

**6. (minor) Edge cases dropped.** The note enumerates `d_A=d_B`, both-arrangements-empty, and asymmetric-population; the digest omits them. They all fall out of the proposed algebra (`d_A=d_B` ⇒ both halves `∅`, since `(Rproj(d)∩ran(M(d)))\ran(M(d))=∅`). Add one line confirming the set algebra subsumes the note's edge cases, rather than leaving a builder to re-derive that it does.
