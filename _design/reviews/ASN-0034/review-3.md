This digest is strong: accurate against the note, well-grounded (every source-level claim — the leading-zero alias, the NPLACES widening, `absadd`'s operand-order loss, the missing-`.0.` bug — traces to the note; no invented routine names), at design altitude throughout, and committal where the note supports a position. The defects below are mostly sharpenings; one is a real gap.

## Revision list

**1. [Require active enforcement: Allocator discipline / Guarantees: Global uniqueness] The discipline statement drops the zero-count gate on child-spawning, which makes "trust internal producers" latently unsound and mis-attributes T4-validity to admission.**
The digest renders T10a as "siblings by `inc(·,0)`, children by one `inc(·,k∈{1,2})`" and tells the builder to "validate at admission only / trust internal producers." But the note's discipline (TA5a, folded into the T10a claim as a precondition "checked before each spawn") gates *which* child mode is admissible on the current address's zero-count: `inc(·,1)` preserves T4 only when `zeros(t)≤3`, `inc(·,2)` only when `zeros(t)≤2`, and `inc(·,k≥3)` always violates T4 (adjacent separators → empty field). Concretely: you may version (k=1) at any level through element, but you may descend a level (k=2) only from a node/user/document address, never from an element. An allocator that spawns children without this guard silently emits T4-invalid addresses; because the arithmetic deliberately never re-validates, the violation propagates and breaks level-determination — on which GlobalUniqueness Case 3 rests. So "trust internal producers" holds *only if* the producer enforces the `zeros(t)` bounds — state that as an allocator obligation. Relatedly, fix the framing in "Global uniqueness — free given… T4 level-determination *at admission*" and "admission validation is part of the uniqueness story": for the system's own allocations, T4-validity comes from *discipline-internal preservation from a valid root* (T10a.4/TA5a), not from admission. Admission validation secures T4-validity for *externally-introduced* addresses — which is exactly where the T6/T7 containment queries need it. Separate the two paths.

**2. [What must be built / Implementation approaches: Ordinal-only shift] The shift is reduced to its API; the guarantees that make it safe to build element-stream maintenance on (TS1–TS5) are dropped.**
The strip/shift/reattach contract and the TA7a no-op pitfall are captured well, but the digest never states what the ordinal shift *guarantees*: order preservation (TS1), injectivity (TS2), additive composition (TS3), strict increase (TS4), amount-monotonicity (TS5). Order-preservation and injectivity are load-bearing — they are what let a builder use shifts to maintain a sorted element stream and keep addresses distinct under shift (the note's table ties them to exactly these uses). Add a line: the ordinal shift is an order-preserving, injective, additively-composing strict advance (inherited from ⊕), so I-stream/V-enfilade advancement is safe to build on it.

**3. [Implementation approaches: Durability and recovery] Sharpen *why* skip-ahead is safe — it rests on domain-exclusivity, not on "T9 makes gaps permanent."**
The batch-reservation recommendation and the "never hand out an address twice / over-shoot harmless, under-shoot fatal" framing are exactly right. But "T9 makes gaps permanent and legitimate" under-grounds the safety and brushes against the note's own prose that "no gaps arise within a single allocator's sibling stream" under strict `inc(·,0)`. The precise reason skip-ahead is safe: each skipped slot lies in that allocator's *exclusive* domain (no other allocator can ever produce it — domain-disjointness under GlobalUniqueness) and the counter never regresses, so the slot is permanently unallocatable — functionally a ghost element (claimed, forever empty). Tie the safety to exclusivity + monotonicity, and note that skipped slots are ghosts, so the frontier still correctly bounds the (ghost-inclusive) allocated set.

**4. [Decisions for the builder: Frontier durability] The note's actual durability open question — global-history vs. per-session — isn't weighed.**
The digest recommends a global journal-of-record and frames *cadence* as the open decision, but the note's open question is specifically whether counter durability must be a "global-history property or only a per-session property." Since the architecture is already per-domain allocators, a weaker per-session model (each session durably claims a per-domain block, recovers by skipping unused tails, needs no single global log) is a real alternative to one global journal. Surface it as the other horn of the note's question so the builder picks global-history vs. per-session deliberately rather than defaulting to a global log.

**5. [Minor surfacings] Two small pins.** The root allocator's base is not arbitrary — Nelson fixes the server field to begin with `1` (all servers descend from it); worth one line under "What must be built / per-domain allocators" since it pins the root base. And "action point" is named a primitive in the approaches but not listed under "What must be built," where it belongs as the shared kernel of ⊕/⊖/`inc`/shift/span-length.

**Solid as-is** (no change): the literal-sequence representation choice and its bug-class-deletion argument; the GlobalUniqueness decomposition (non-nesting→T10, nesting→level-determination/length-separation); the child-spawn-activation durability catch (journal the new prefix *before* handing out any child address, or it can be re-spawned and its base reused after a crash); the forced-vs-deliberate call on T4-flatness (correctly *not* marked forced — T2 permits intrinsic hierarchy-aware primitives); and the temporal-vs-structural-order gotcha.
