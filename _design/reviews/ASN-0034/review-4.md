The digest is unusually strong — it correctly handles length separation, the `k∈{1,2}` allocation gate, T4 preservation, the durability invariant, content/allocation decoupling, the zero-sentinel distinction, and ordinal-only shift, and its forced-vs-deliberate tagging is accurate. But it has one material error in the arithmetic kernel, plus two tightenings.

## Revision list

**1. [DEFECT] — "What must be built" / "The arithmetic": `inc` does *not* act at the action point; it acts at `sig(t)`, the *last* significant position — the opposite end of the tumbler.** The digest defines the action point as "a displacement's first nonzero component" and then lists `inc` among its users three times ("shared kernel of ⊕, ⊖, `inc`…", "…all organized around it", "Implement ⊕/⊖/`inc` … (action point…)"). But `inc` takes no displacement: `inc(t,0)` modifies `sig(t) = max{i : tᵢ ≠ 0}` (TA5-SIG, TA5(c)), which for a valid address is the *last* component `#t` (TA5-SigValid), whereas the action point of a valid address is position 1. A builder following the digest would increment the wrong component — `inc(1.0.3.0.2.0.1.5, 0)` must advance position 8 to `…6`, not position 1. Fix: (a) add `sig(t)` (last-significant-position) to "what must be built" — it is the distinct named primitive `inc(·,0)` requires (the note treats it separately as TA5-SIG), and the digest currently omits it entirely; (b) drop `inc` from the action-point family, keeping the action point as the kernel of **⊕, the ordinal shift, and the span-length convention only**. Optionally note that `⊖` is governed by the zero-padded divergence (zpd), which coincides with the displacement's action point only in the well-behaved partial-inverse case — so it too is not cleanly "action point."

**2. [SHARPENING] — "Allocation — partition first" / durability: child-spawning operates on a *specific parent slot*, not "the frontier."** The digest writes `inc(frontier, 1)` / `inc(frontier, 2)` and "each `(frontier, k')` spawn at most once." But the discipline spawns a child from *any* parent sibling `t` via `inc(t, k')`, and the at-most-once constraint is per `(t, k')` (claim statement: "Each `(t, k')` pair … yields at most one child-spawning event"). Taken literally, `inc(frontier, …)` would only permit subdividing the latest sibling — you could not version an older document. Replace "frontier" with "the parent address being subdivided" in the two child-spawn modes and in the spawn-record durability discussion.

**3. [SHARPENING] — "version (k=1)" terminology is too document-specific.** `k=1` is *same-type subdivision*, which is "versioning" only at the document level; at the node level it forks a sub-server and at the user level a sub-account (the note reserves "version" for the document field). "you may version (k=1) at any level through element" reads as document-versioning applied to elements/nodes. Generalize the label (e.g. "same-type subdivision — a version, at document level") so the structural claim (k=1 valid at all levels) isn't conflated with document semantics.

Genuinely solid and worth stating: the durability section (never-hand-out-twice; over-shoot harmless because the slot stays in the allocator's exclusive domain; under-shoot fatal; child-*activation* is itself durable state that must be journaled before any child address is handed out) is the best part and is fully grounded. The observation that T5 contiguity holds for *any* prefix without T4 validation, and the zero-sentinel-is-a-valid-span-endpoint-but-rejected-as-an-address distinction, are both correct and load-bearing catches.

VERDICT: REVISE
