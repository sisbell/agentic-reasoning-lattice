## Revision list

**1. [DEFECT] — Implementation approaches → C, "Common case fast, rare case correct": the filter cost model is wrong.** The bullet says the filter is "nearly free" on growing (deletion-free) histories and that "the filter's total cost is proportional to the over-approximation, which is bounded to 'documents that have deleted queried material.'" This is factually false. A *monotone, write-only* index cannot distinguish live candidates from stale ones — that is the entire reason it needs a filter — so the filter must run an I→V probe on **every** candidate the index returns. Its total cost is proportional to the candidate count `|finddocs_R|` (≈ live answer + ghosts), **not** to the ghost residue. A deletion-free query for a widely-shared passage returns thousands of *live* containers and probes every one — the opposite of "nearly free," and not "bounded to documents that have deleted." (This cost model is the digest's own addition; the note only says the filter is "a lookup, not a re-search.") Fix: state that filter cost is proportional to the over-approximated answer set (every candidate gets one cheap I→V lookup, not a re-search); deletion *inflates* that set with ghost probes (wasted work) on top of the unavoidable confirming probe per live container. Reserve "nearly free" for the *per-probe* cost, not the total.

**2. [SHARPENING] — Result assembly: "(ASN-0127 territory)" mis-points position-recovery.** ASN-0127 is the content-region *link* query; recovering "where within a returned document" is a per-document **I→V lookup** — the *same machinery as the soundness filter* — and its attribution-bearing form (documents paired with positions) is the note's **open question 3**, not yet specified anywhere. Retarget the pointer: "a per-document I→V query (the same probe the soundness filter runs; an attribution-bearing variant is open question 3) — not ASN-0127's link query."

**3. [SHARPENING] — "soundness" is overloaded across two sections.** In "How it fits," J1'★ is glossed "soundness — no fabricated entry" (the *historical index's* no-fabrication); in approach C, "soundness (no ghosts)" is FD-SOUND (the *live* operation's present-witness property the filter provides). These are different properties of different objects. Reserve "soundness" for the live no-ghosts property and call J1'★'s contribution "no-fabrication," so a builder doesn't read "J1'★ gives soundness" as "the index gives me FD-SOUND."

**4. [SHARPENING] — How it fits: "containment-bounds-provenance invariant" reads backwards.** P4★ is `Contains_C ⊆ R` — provenance bounds containment, not the reverse. The following gloss ("bounds the live answer within that historical one, FD-SUPER") is correct, so this is only naming, but rename to "the containment-within-provenance bound (P4★: `Contains_C ⊆ R`)" to remove the wrong-direction reading.

**5. [SHARPENING] — Surface FD-UDIST as an optimization lever.** The digest captures the OR-primitive/AND-derived structure but not that `finddocs(I₁∪I₂) = finddocs(I₁)∪finddocs(I₂)` (FD-UDIST) lets a multi-fragment query be **decomposed per fragment and unioned** — i.e., parallelized — which is exactly how the index does per-span lookups. Worth one line under approaches or builder decisions.

**6. [SHARPENING] — Within-query consistency could note the boundary requirement.** The "single consistent snapshot" point is right, but the coupling invariants (P4★/FD-SUPER) hold only at *composite boundaries*, not interior states (the note's open question 1). One line — "apply composites atomically so a query never observes an interior state where these invariants need not hold" — closes the gap, and is the natural design given in-memory persistent-value state.
