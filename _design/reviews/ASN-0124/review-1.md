Reviewed against the note, its claim statements, and the Q11–Q20 evidence. The digest is strong: its spec/implementation separation is disciplined, the three-way scan/live-index/monotone-index analysis is sound and correctly recommends the monotone-index-plus-filter, every Green source-level claim (write-only spanfilade, type-tagged origin dimension, I-keyed stability, FOLLOWLINK's I→V filter, the paired recording discipline) is grounded in the evidence, and the "provenance relation *is* the historical index, justified by economy" synthesis is a genuine insight faithful to FD-WITNESS. Altitude is well judged throughout — architecture terms (POOM, spanfilade, enfilade, I→V probe), never signatures. The defects below are corrections and sharpenings, not structural.

**Revision list (most important first):**

1. **"Guarantees to uphold → Hold by construction": drop the "given a correctly-keyed index" qualifier, and re-state positional-edit stability as unconditional.** As written, the header conditions the entire by-construction list on an implementation choice — but every guarantee in it (subject-matter permanence from P0, poison-immunity from FD-GROUND, identity-keying, locality/non-impedance from FD-LOCAL, flat reach from FD-CHAIN, origin-neutrality from FD-NEUT) is a spec-level property of the address model and the comprehension that holds for *any* faithful implementation, including approach A's scan, which has no index at all. The qualifier contradicts the digest's own clean spec/impl separation — its chief virtue. Worse, the positional-edit-stability bullet says it holds "*provided the index carries no V-coordinate*… by construction of the representation." But FD-FRESH proves the *answer* is invariant under insertion because the membership criterion has no V-position term — true for the scan, with no index and no representation choice. The no-V-coordinate keying is what makes *maintaining* that invariance free (no per-edit index update), i.e. a cost property, not the source of the guarantee. Fix: header reads "from the address model and the comprehension"; the positional-edit bullet states the answer's invariance as unconditional (FD-FRESH) and confines "key by I-address" to *cost-free maintenance* (which it already argues correctly under "Index structure").

2. **"Decisions for the builder → 'Any-portion' boundary semantics": this is a fidelity requirement, not a free decision.** The digest says "whether single-point boundary contact counts as containment (green deliberately admits it). Pick it and document it." But FD-PART fixes the semantics exactly: a single shared address suffices *and is all that is ever required* — no more, no less. Once material is resolved to an I-address set, membership is exact set-intersection non-emptiness; an interval encoding's overlap predicate is therefore *constrained* to equal address-set intersection, not free to choose. Under-counting (excluding a genuinely shared address) breaks FD-PART/completeness; over-counting (admitting interval adjacency that shares no address) breaks soundness. Presenting this as discretionary could license a builder to pick a "stricter" boundary and silently under-report. Fix: reframe as "make the interval encoding's overlap test exactly address-set intersection (FD-PART)"; Green's 12/20/84 boundary change was that fidelity correction (loosening the test so a single shared I-address registers), not a policy knob.

3. **"Implementation approaches → C": the green relation is stated backwards.** "This is precisely the udanax-green spanfilade strategy — minus the filter" reads as C = green − filter, but C is *defined* as "monotone index **+ present-tense filter**" two paragraphs up; green is the one without the filter. Fix: "Green implements C's index but omits the filter — green is C minus the filter (equivalently, C is green's write-only index plus the present-tense check green never runs)." The surrounding sentences already mean this; only this line inverts it.

4. **Surface FD-VERS (version-fork membership duplication) — currently missing.** The note dedicates a lemma and a worked-illustration beat to it, and Q20 confirms the mechanism: a J4 fork makes the new version an *immediate* co-member for every shared address, the two memberships then diverging under independent editing. The digest's "flat transclusion reach" guarantee covers FD-CHAIN but not this. It matters on two counts a builder needs: (a) behavior — forking auto-populates the new version into containment results for shared material; (b) recording obligation — fork is a content-placement path the completeness discipline must cover, and it is *non-obvious* as one (whole-document copy onto a fresh identity, allocating no new addresses). The digest's generic "every path that gives a document content must record" won't flag fork unless fork is named. Add FD-VERS to the by-construction guarantees and name the fork among placement routes under "Completeness" (Q20: green writes whole-extent DOCISPAN entries at fork time).

5. **Surface the authority/access-control gap as a builder-relevant fact.** The digest folds "no authority parameter" into the completeness commitment and stops there, but the consequence is load-bearing and security-relevant: as specified, FINDDOCSCONTAINING is a globally-complete membership oracle over *every account and node* (FD-COMPLETE), and Q20 confirms Green applies no BERT and no access check to queried or returned documents. So the operation is a containment-disclosure surface; any authorization must be layered externally as a post-filter (the search itself cannot scope by authority — Q12 makes a document-scope filter a hard error), and the precise contract is a note open question. A builder reading the digest should not assume access control is handled. Add a short note under "Decisions for the builder" or the distribution/enforcement discussion.

6. **"Resolving regions": anchor the cache-vs-re-resolve decision on FD-V's same-Σ requirement.** FD-V is `finddocs(resolve(Q,Σ), Σ)` — both phases at one Σ. A faithful two-phase implementation must execute resolve and find against a consistent state snapshot; a naive split (resolve, then find after edits land) silently computes a hybrid. The digest's "one-shot vs cached resolved set" is good but discusses caching *across* queries without stating the *within*-query consistency obligation. Make it explicit, and name the cached-set option as exactly the well-defined hybrid `finddocs(resolve(Q,Σ₀), Σ_now)` — legitimate (not a consistency bug) because P0/FD-NONMONO keep the resolved material grounded forever — so "find more like this, stably" is a deliberate choice to resolve at an earlier state, distinct from a torn read.

7. **Surface the two region-resolution properties that justify the input shape.** The digest treats the input as a vspec-set throughout (correct) but omits the note's reasons. (a) *FD-ASKER*: resolution is transclusion-transparent — pointing through any copy resolves to the same I-addresses as pointing through the origin; this is the asker-side reading of "regardless of where the native copies are located" and tells a builder the query works against any copy. (b) *FD-CONVEX*: the input must allow *multiple* regions, not one span, because a single contiguous span is order-convex and drags in connective material — so fragment-exact and co-occurrence queries are expressible only with a multi-region set. Add a line to the region-resolver bullet under "What must be built."

8. **Minor wording, "What must be built" / "Implementation approaches": "resolved material is a span-set" overstates.** FD-RES resolves to a bare I-address *set* (with structure flattened); a span-set is one *representation* of that set, the one Green and the interval-lookup recommendation rely on. The practical conclusion (interval/range-overlap lookup) is right; just phrase it as "the resolved address set is naturally a union of intervals, so it wants range-overlap lookup," not as a spec property.

Items 1–3 are accuracy defects, 4 is a missing load-bearing guarantee, 5 a missing builder-relevant fact; 6–8 are sharpenings.
