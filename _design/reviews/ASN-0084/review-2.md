## Revision list

**1. "Design commitments / Conventional" + "Implementation approaches": surface that depth‑2 is load‑bearing for the implicit‑position model, not a throwaway scoping point.** The digest files "Fixing `m_1 = 2`" as merely conventional ("a builder may honor only depth 2 and still be complete") and never connects it to its own headline recommendation. But depth‑2 *is* the connection: the note's identification of singleton tumblers `[k]` with naturals `k`, plus D‑SEQ giving `V_1(d) = {[S,1..N]}`, is exactly what collapses a text V‑position to a single integer ordinal — which is the precondition for the prefix‑sum/sequence/rope model the digest recommends. State this explicitly, and note the consequence: the note's out‑of‑scope `m_1 > 2` case (multi‑component ordinals, no flat `1..N` range) would not admit the clean prefix‑sum representation without rework. This both repairs the undersell and ties two of the digest's own sections together. (The Green evidence — text hardcoded at depth 2, `findisatoinsertmolecule` — confirms depth‑2 is the real-world reality, strengthening "you only need depth 2," so lean on it.)

**2. "Canonicalization (merge)": the run‑count claim is sound but loose and over‑confidently silent that it extends an open question.** The bound is correct, so don't cut it — tighten and attribute it. The exact operation‑local bound is `|Δ canonical runs| ≤ n` (the cut count, i.e. ≤ 4): Phase‑1 splits add at most `n` runs; new merges occur *only* at the ≤ `n` region seams, with no cascade because R‑COMM keeps each region's interior canonical under translation — so `Δ = (#splits) − (#seam-merges)` with both terms in `[0,n]`. Replace "≤ +4 from splits … ±O(cuts)" with this, and fix "check O(cuts) seam pairs (≤ ~8)": the seams are ≤ `n` (3 pivot / 4 swap), not ~8. Critically, flag that this is a *derived* operation-local result that goes **beyond** the note — the note lists the general run‑count characterization as an explicit open question — so a builder doesn't read it as something the note proved.

**3. "What must be built": "per‑document, per‑subspace arrangement map" states per‑subspace as a requirement, but the digest itself later treats it as a choice.** The note requires a per‑*document* arrangement plus confinement‑as‑a‑property; "Subspace confinement" and "Decisions for the builder" (correctly) frame per‑subspace *storage* as one option vs. unified‑and‑filter. Resolve the internal inconsistency: say "per‑document arrangement map" in the requirements list and defer the per‑subspace storage decision to the confinement discussion, so the requirement isn't read as foreclosing the unified-and-filter option.

**4. "The arrangement map": the Rust/`im::Vector`/RRB‑vector instantiation is the one altitude lean — keep it as illustration, not commitment.** It's already flagged "one worked instantiation," so this is minor, but the actual recommendation should remain the abstract contract ("persistent ordered sequence with O(log n) split/concat + structural sharing"); make explicit that the crate/data-structure name is an example a builder can swap, not a design output of 0084.
