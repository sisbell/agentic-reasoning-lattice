Below is the revision list, ordered most-important-first. The digest is strong, dense, and largely accurate — most of these are real, not manufactured. I flag the genuinely solid sections at the end.

## Revision list

**1. "Atomicity, journaling, recovery" (Snapshot/recovery) + "Provenance recorder" — the recovery design is unsound for the historical provenance index it commits to; it silently breaks P2.** The digest correctly establishes that historical provenance (Σ.R, P2) is **not** recomputable from current arrangements (live containment ⊆ Σ.R, P4★). It then commits the reverse index to that *historical* reading ("append-only, no delete path… the note commits to the historical reading"). But the recovery recommendation — "omit it from snapshots and rebuild from arrangements + journal provenance on load, so it can never drift" — is paired with "snapshot to bound replay" (a bounded/truncated journal). These are mutually inconsistent: an address referenced and then *deleted before the latest snapshot* is absent from snapshotted arrangements **and** from the post-snapshot journal tail, so the rebuilt index loses (a, d) — exactly the pair P2 says is permanent. The "+ arrangements" phrasing is the tell (arrangements yield only live containment). **Do:** treat the accumulated Σ.R / historical index as **authoritative snapshot state** (snapshot it alongside arrangements, don't omit it), *or* commit explicitly to full provenance-journal retention (giving up bounded replay for provenance) — and delete the "rebuild from arrangements … can never drift" claim. State that *only* a live-containment index is a recomputable hint safe to omit-and-rebuild.

**2. "Arrangement representation" — the (2)-vs-(3) tradeoff the Pick agonizes over is not real, because persistence is orthogonal to relative-offset addressing.** The digest frames rep (2) [free snapshots, O(trailing-runs) splice] against rep (3) [O(log n) splice, but "udanax's mutable enfilade cannot give snapshots"], then hedges the default behind a benchmark. But "enfilade ⟹ mutable ⟹ no snapshots" is a false inference: a **persistent displacement-offset enfilade** (path-copy the cut path, share the rest; offsets are relative so descendants are untouched) gives O(log n) splice **and** free pre-state snapshots **and** O(span count) storage — and the 2-D I→V query as a bonus — dominating both (2) and mutable-(3) on exactly the axes the Pick weighs, at the cost only of implementation complexity. **Do:** add the persistent enfilade as a fourth option (or recast (3) as "mutable vs persistent"), and de-hedge the recommendation accordingly — the displacing-case-shift benchmark that currently gates the default largely dissolves. (Also drop the weak aside that rep (1)'s O(trailing) shift "is acceptable since the working substrate rebuilds in memory on load" — in-memory reload doesn't make runtime shifts cheaper; the "documents are modest" gate is what carries that recommendation.)

**3. "What must be built" / "Guarantees to uphold" — the operation's stated precondition (content-residence) and its scope limit (content-only) are missing.** The note's `enabled(COPY)` includes content-residence — *every* active position lands in `s_C` — and this is load-bearing: without it resolution can read `dom(L)` and placement then binds a link address into a content position, violating S3★ referential integrity. The digest enforces span well-formedness/binding at the API edge but never lists subspace-residence as a guard. Relatedly, the digest nowhere states that COPY-as-specified is **content-only**: placing a *link* by reference is the note's open question 5, unspecified. **Do:** add content-residence to the preconditions the resolver/placement must enforce, and state plainly that link-transclusion is out of scope (note OQ5) so a builder doesn't assume COPY generalizes to `s_L`.

**4. "Placement → Run-coalescing on placement" — "no correctness risk; default on" overstates a deliberate divergence from the only proven implementation.** The argument (I-contiguity ⟹ same origin by M16a, so coalescing is origin-safe and M14-invisible) is sound *for every guarantee the note states* — that part is right and well-made. But the digest is recommending dropping a guard (homedoc-equality) that udanax-green *keeps*, on the strength of a model (the note's `origin`) that doesn't include the immediate-source distinction udanax retains. The note's own open question 4 (the correspondence relation) is exactly where finer-than-origin tracking might be needed. **Do:** reframe as an optimization, not a free win: soften "no correctness risk" → "no risk to any guarantee the note *states*"; note that I-contiguity coalesces strictly more than udanax and erases the immediate-source (homedoc) distinction; and consider defaulting to udanax's homedoc-guarded behavior unless run-count is a *measured* problem. (Minor, fold in: the rep-(2) parenthetical says `isanextensionnd` widens "for a same-origin … run" — udanax's actual guard is *homedoc*-equality + `reach==origin`, not origin-equality; say so.)

**5. Minor wording — "Cross-origin material never merges … *k* sources preserves *k* distinct homes."** *k* sources can share an origin, so the count of distinct homes can be < *k*; the note's invariant is the origin **multiset** (with multiplicity). The digest says "the origin multiset carries verbatim" one clause later, so just tighten the earlier phrasing to "*k* sources preserve their origin multiset (≤ *k* distinct homes, counted with multiplicity)."
