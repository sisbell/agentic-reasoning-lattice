## Revision list (most important first)

**1. "How it fits → Sits at": the append claim is conflated and could mislead a builder into a real bug.** The digest says "append needs the reach… the next write VSA is `stream ⊕ width`," then contrasts with version creation, which "does *not* build on this operation… because the bounding box bridges subspaces." This asymmetry is incoherent: if the bounding-box reach is wrong for version creation *because it bridges into link space*, it is equally wrong for **content** append into a mixed document — `stream ⊕ width` there lands in *link* space, not at the content end. The evidence shows Green uses *different* primitives precisely for this reason: content append goes through `findvsatoappend` (text-subspace reach, not via this op — Q15), while *link* append goes through `findnextlinkvsa`, which legitimately uses `stream ⊕ width` because a new link sits past the document max in link space (Q16, Q1), with a floor at the link minimum for a doc that has no links yet. Fix: state that it is **link append** that builds on the bounding-box reach (and why that is sound); content append into a mixed doc and version creation both need the *content-only* extent, which is exactly why version creation uses a separate content-only primitive. As written, the contrast invites a builder to write content at a link-space address.

**2. Design commitments: the V9 composition-*insensitivity* half is missing — only rearrangement invariance is surfaced.** Commitment 4 gives "permuting what sits where… returns the identical span" (rearrangement), but the note's V9 develops the more surprising consequence at length: in a *mixed* document, a composition change that keeps content present (adding/removing content positions) **does not move the reported span** because it does not move an extreme — only clearing content or moving the max does. This is a caller-facing commitment with teeth ("I added text to my mixed document; why is the bounding span unchanged?"). Add it: the span tracks only `(min, max)`, so in the cross-subspace regime it is a coarse bound that ignores mid-document content edits — distinct from, and more surprising than, rearrangement invariance.

**3. "Decisions → Tumbler in-memory form": the justification "component-vectors suffice *because the depth policy fixes scale*" is mis-reasoned.** Component-vectors suffice because the note's abstract model is purely positional — it uses leading-zero integer vectors with no exponent at all (including the depth-3 cases like `[1,2,0]`), independent of any depth policy. The depth policy is an *orthogonal* simplification: it fixes vector *length* (enabling fixed-size vectors and plain lexicographic comparison), not "scale." The conclusion (component-vectors suffice; reach for mantissa+exponent only for Green wire-compat) is right, but decouple the two so a builder doesn't think depth divergence forces mantissa+exponent — it forces only variable-length vectors plus the prefix-comparison convention.

**4. Approach 1: the `im` crate reference presumes Rust, which the note does not establish.** Generalize to a language-neutral "persistent/immutable balanced ordered map (B-tree or HAMT)." Same caution applies (more mildly, since it is hedged) to the `links.jsonl`-style journal in Approach 3 — fine as a conditional mapping, but it presumes a substrate the note doesn't fix.

**5. (Optional, low value) Discriminator exposure: "exact cover" silently drops the occupied-depth qualifier.** V5's "Exact" means "no *occupied-depth* position outside `O(d)`," not `⟦σ_d⟧ = O(d)` — even exact covers strictly contain deeper non-V tumblers like `origin_d.0`. This is below builder altitude (no caller enumerates non-V-positions), so include only a half-line if you want the discriminator's precise meaning pinned for callers; otherwise leave as is.
