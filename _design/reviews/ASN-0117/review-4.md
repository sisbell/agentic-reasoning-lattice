**Revision list**

1. **[DEFECT] Design commitments §"Two layers, one touched": the gloss of the provenance relation `R` is a misread.** The digest describes `R` as "recording, for each content address, the document it first entered through" — i.e., a single-origin function. This conflicts with the note's own `Contains_C(Σ') ⊆ Σ'.R` (P4★) read against its transclusion example, where one I-address (`a_3`) is arranged by both `d` and `d'`. If `Contains_C` is the (multi-document) content-containment relation and `R ⊇ Contains_C`, then `R` cannot be one-document-per-address; the note's "provenance *coverage*" (P7a) points the same way. Restate `R` as the provenance/coverage relation recording *which documents have introduced/arranged each content address* (verify the exact ASN-0047 semantics). It is non-load-bearing for DELETE itself (which frames `R`), but this is the *shared* state model — INSERT/COPY write `R` — so the wrong mental model has reach beyond this note.

2. **[SHARPENING] Approach §1: "Green realizes the shift entry-by-entry" undersells, and mildly self-contradicts, the cited mechanism.** Because the intersection-finder is stubbed to return the root, Green's `tumblersub` runs on root's *direct children's* displacements — for any document past height 1 those are subtrees, so the shift is subtree-coarse, not per-leaf. That sits in tension with the digest's own adjacent claim that Green "never makes the O(log N) descent." Both pieces are individually grounded (the KB synthesis does loosely say "entries"; the code shows root's children), so it isn't false — but reconcile it: Green *already* shifts subtree displacements wholesale (a crude version of the very subtree-shift the persistent ideal formalizes); what it lacks is the descent-to-locate and the persistence, not the subtree granularity. As written it slightly overstates the gap between Green and the recommended representation.

3. **[SHARPENING] Approach §5: "out-of-bounds span into silent corruption" conflates two distinct Q4 cases.** Per the evidence, a span *entirely* before the run is a silent **no-op** (no crums in range / exponent guard fires), whereas a span *straddling* the document's start is the one that shifts in-range survivors by the full out-of-range width into negative/unreachable positions. The unifying lesson — both are acknowledged as success regardless — is the real point and survives intact, so the build instruction (validate containment before mutating; never ack before durable) is unaffected; just don't imply *every* out-of-extent span corrupts.
