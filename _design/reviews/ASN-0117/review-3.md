Overall this is a strong, well-grounded digest. It is unusually disciplined about separating *what Green does* from *what to build* — the stubbed intersection-finder, in-place mutation, the *accidental* (exponent-guard) subspace isolation, ack-before-work, and the delete-all re-insertion crash are all used as cautionary evidence, not copied as design. The by-construction-vs-active-enforcement split in **Guarantees** and the count-and-last-witness ruling in **Decisions** are the best parts; leave them. The items below are mostly accuracy/consistency and completeness.

---

**1. "What must be built" → precondition validator: "boundary-aligned endpoints" is mis-stated as a validation and contradicts Approach §7.** In the note's abstract whole-position model, endpoints are *inherently* boundary-aligned (you can only delete whole `q_k`), so there is nothing to validate — the real precondition obligations are positive width, matching depth, **`p` is an existing arranged position**, and containment. At the implementation level (a run-coalescing representation), an endpoint interior to a multi-unit run is **split** (Approach §7, `slicecbcpm` on a strictly-interior cut), *not rejected*. As written, the validator reads as if a non-boundary-aligned endpoint is a reject condition, which directly conflicts with §7. Fix: drop "boundary-aligned endpoints" from the validator's reject-list; state the validator's job as "positive width, matching depth, `p` arranged, containment," and note that boundary-alignment is automatic abstractly and achieved by splitting (cross-ref §7) in a coalescing impl.

**2. Make the text-subspace-only scope explicit.** The note's precondition fixes `S = subspace(p) = s_C` — the specified DELETE is *text deletion only*. The digest implies this ("only its text-subspace part") but never states the scope boundary, so a builder could try to use DELETE to remove a link. Add one line in **Design commitments** (and "What this is"): the spec'd operation is text-subspace deletion; removing a link from a document's link subspace is an analogous-but-separate operation not covered here. This is a real scope fact a builder needs.

**3. The state model omits the entity set (`E`) and provenance relation (`R`) that DEL-CFRAME frames.** **Design commitments** ("Two layers, one touched") lists content store, link store, arrangement — but the note's extended state also carries `Σ.E` and `Σ.R`, and DEL-CFRAME explicitly fixes `Σ'.E = Σ.E ∧ Σ'.R = Σ.R` (DELETE adds no content ⇒ no range-new addresses ⇒ no provenance entry, J0/J1★/J1'★ all vacuous). A substrate builder needs to know both exist and that DELETE frames them. Add them to the state enumeration and to **Guarantees** as frame obligations (low-action, but real). 

**4. Approach §7 cross-reference is wrong.** "In a run-coalescing representation (the enfilade of **approach 2**)…" — the enfilade is Approach **§1**'s second realization; Approach §2 is the content-store frame. Trivial but unambiguous; fix to "Approach §1."

**5. Approach §3 / "How it fits": state the discovery-index invariant crisply, and don't conflate it with the link-discoverability wp.** The note poses OQ3 as the *invariant* relating a content→document index to the arrangement; the digest gives the strategy (superset + post-filter, grounded in Q16) but never states the invariant. Say it plainly: `live-arrangement(d) ⊆ index-claims(d)`, index monotone/append-only — that is what licenses "post-filter on read." Separately, the digest says the wp "drives targeted index cleanup," but the wp governs **link** discoverability (`find_links`), whereas the content→document index (`find_documents`) staleness is driven by `A_del^{excl}` *directly* (addresses leaving `d`'s range). Both rest on `A_del^{excl}`, but they are different indexes; tighten the wording so the builder knows the wp's extra last-witness layer is the *link*-index refinement. Worth noting the digest is here resolving a note-open-question via evidence — flag it as such (as the digest already does for totalization).

**6. Approach §4: retained-root version cost is O(changed-nodes), which is O(suffix) for the absolute-key map — not "O(delta)."** "keep the old root as a version handle … at O(delta) memory" is misleading for the recommended default: a front delete in the absolute-key persistent map re-keys the suffix (§1's own analysis), so each retained root path-copies O(suffix) unshared nodes. Only the relative-displacement tree (split/adjust-root/join) gives true O(log N) per-version delta; the journal sidesteps the issue entirely (backtrack by replay, no retained roots). Sharpen so a builder doesn't pair retained roots with the absolute-key map expecting cheap versioning — for the absolute map, use the journal for backtrack.

**7. Altitude nit, Approach §1:** drop the specific library type (`im::OrdMap`) and name the structure family ("a persistent ordered map"). A concrete type is a code detail; the rest of the digest holds design altitude well, so this is the lone slip.

**8. (Optional) Trim the overlap between "Implementation approaches" and "Decisions for the builder."** Position-representation, totalization, discovery-index, and backtrack each appear in both. The "Decisions" framing (explicit choice + recommended default) earns its place, but the restated analysis could cross-reference §1–§7 rather than re-derive — a tightening, not a defect.
