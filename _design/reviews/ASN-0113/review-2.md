This is a strong, well-grounded digest — the guarantees taxonomy (hold-by-construction / inherited / actively-enforced) is the right organizing move, and the arranged-not-homed warning is exactly the nugget a builder needs. The items below are the improvements worth making, real defects first.

## Revision list

**1. Design commitments + Implementation approaches: "degrades to a bounding box" is wrong for the recommended default, and it masks a worse failure mode.** The commitment bullet says "if contiguity were relaxed, the single span degrades to a bounding box that overshoots interior gaps." That is the behavior of a *max−min* span (Option 4 / Green), **not** of the *count-based* W2 span that Options 1/2 — your default — synthesize. The count-based span is `([S,1,…,1], δ(n_S, m_S))`: under a gap, e.g. `V_S = {[S,1],[S,3]}`, it reaches only `[S,3]` and covers `{[S,1],[S,2]}` — it *omits* the real `[S,3]` and *invents* `[S,2]`. That is a silently wrong, mis-located span, not a conservative overshoot. Fix: state that the count-based extent (W2) is exact **only** under D-CTG★ and, unlike a bounding box, does not degrade gracefully — it fails silently. This strengthens, not weakens, the "trust-plus-debug-assert" call (the failure mode is wrong answers, not over-reporting). Also surface the note's **Open Question 1** here: the digest lists OQ2–5 in "Decisions for the builder" but drops OQ1, treating contiguity purely as an implementation tactic. OQ1 has a *contract* dimension the digest never resolves — if D-CTG★ is ever relaxed, must the operation emit a faithful fragmented span-set or a single bounding span? "Trust + debug assert" presumes contiguity holds; it does not answer what the operation *promises* when it doesn't.

**2. Implementation approaches, Option 4: misattributes a clean free-ride to Green; the evidence (Q14) says Green could *not* just read it.** Option 4 says "(Green's case…) the extent is already computed; just read it." Q14 is explicit that Green reads the root aggregate only for the **link** subspace (masking `mantissa[1]`); for **text** in a mixed document it runs a separate traversal (`maxtextwid`) precisely *because* the root's *combined* bounding box does not decompose per-subspace. Your own Assembly section already concedes this ("a root-field read for links, a separate tree traversal for text"), so Option 4 contradicts it. Fix: clean free-riding requires a **per-subspace** aggregate; a **combined** whole-document aggregate (Green's) is at best a *partial* free-ride — one subspace by digit-masking, the other by traversal. A builder modeling their aggregate on Green expecting "just read it" will be surprised.

**3. Guarantees to uphold (W9/W11): the attribution is imprecise — disjointness does rest on a convention fact.** The digest says two-kinds-only *and* disjointness "rest not on the numbering convention but on S3★-aux." Two different bases are being conflated. Per the note, **W9** (no third subspace) rests on S3★-aux (exhaustiveness); **W11** (the two members don't overlap) rests on **SC-NEQ**, `s_C ≠ s_L`, which the note calls "the 1 ≠ 2 of the convention." So disjointness *does* depend on the convention — specifically on the two labels being **distinct**. What is dispensable is only the *specific values* 1 and 2, not their distinctness, and S3★-aux gives exhaustiveness, not disjointness. The builder lesson ("enforce subspace confinement at write admission") is correct and unaffected — but state the bases separately: S3★-aux → no third member; distinctness of the labels → the two members are disjoint.

**4. Recovery: "links.jsonl append-only-journal pattern" is an ungrounded specific.** This filename appears twice as "the pattern" but is in neither the note nor the evidence answers, and carries no citation. The underlying advice — append-only arrangement journal + replay on load, registration journaled separately — is sound and well-grounded (Q1). Either cite where `links.jsonl` comes from or generalize to "an append-only arrangement journal"; don't present a specific artifact as established.

**5. Implementation approaches, Option 1: "the start is fixed by convention" contradicts your own (correct) structural-depth point.** You carefully establish that working depth `m_S` is *structural, not conventional*, then say the start is "fixed by convention, so you never even need to find a minimum." The start `[S,1,…,1]` is fixed by the **D-MIN★ invariant** (the minimum is canonical), and its depth `m_S` must still be read off an occupied key — which the aggregator already does. Reword to "fixed by D-MIN★" (or "by invariant"), and keep the true operational point intact: you skip a minimum-scan, but you still read `m_S`.

**6. How it fits / W14: make the "absent member = count 0" reading rule explicit for the comparison consumer.** The digest keeps kind self-describing (start's first component = `S`) but never states the other half of W14 that a version/document comparator actually needs: an *absent* subspace member must be read as `n_S = 0`. Without it, a consumer comparing a links-bearing document against a text-only one has no rule for the missing member. State it: read kind from each member's start, and treat any kind absent from the report as extent 0.

**7. What must be built / allocation gate: surface W19's clean cardinality partition rather than "otherwise → emit members."** The three-way dispatch folds the one- and two-member cases into "otherwise." W19 gives the sharper, testable statement: result cardinality is a total function of the two emptiness bits given allocation — both-empty → `⟨⟩`, exactly-one-empty → 1 member, neither-empty → 2 members; unallocated → fail. Stating it this way makes the dispatch's full case matrix (and its test obligations) obvious.
