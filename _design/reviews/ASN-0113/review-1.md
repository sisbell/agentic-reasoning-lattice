**1. Implementation approaches — Options 3/4 conflate the *count* with Green's *bounding-box extent*, and omit the contiguity caveat that the rest of the digest insists on.** Option 3 says to maintain `(n_{s_C}, n_{s_L}, …)` — counts — then calls this "exactly udanax-green's proven approach … `setwispnd` propagates a bounding-box aggregate." But a count `|V_S(d)|` and a bounding-box extent are different objects; per the evidence (Q11, Q13), Green's `setwispnd` aggregate *overshoots interior gaps* and is therefore the extent, not the count. They coincide *only under D-CTG★* — the note itself says the count is boundary-recoverable "only because the subspace is contiguous." This matters for the build, not just for precision: Options 1/2 compute `|V_S(d)|` by counting actual keys (faithful even if a gap appears), whereas Options 3/4 read an extent that equals the count only while contiguity holds — the *same* invariant the digest elsewhere says this operation "cannot self-certify," and which Green's own `acceptablevsa` stub did **not** enforce (Q18/Q20). So the recommendation "reach for Option 4 if your arrangement already carries the aggregate" silently inherits a contiguity-trust that compute-on-read does not. Fix: state that the maintained/free-ridden aggregate is a bounding-box extent whose last component equals `n_S` only under D-CTG★; that a literal count-hint (robust) is *not* what Green maintains; and that Options 3/4 therefore import the same contiguity dependence as W4, while Options 1/2 stay faithful to the count under a write-path gap.

**2. Design commitments — "the common working depth of 2" is mislabeled as merely conventional; it is a per-subspace structural value, and the note explicitly exercises `m_S = 3`.** Listing depth-2 alongside `s_C=1`/`s_L=2` reads as "you may assume depth 2." But S8-depth fixes `m_S ≥ 2` as the common depth *within* a subspace, and the note's depth-3 worked instance exists precisely to show that prefix-confinement (T5) is non-vacuous when an interior position genuinely exists — i.e., depth is variable and the synthesizer must handle the general case. This also contradicts the digest's own later text ("special-case the depth-2 common path … micro-optimization" and "How `m_S` is obtained"), both of which presuppose `m_S` is not fixed. Fix: drop depth-2 from the "conventional" list; state that `m_S` is a per-subspace value `≥ 2` the synthesizer reads, that the general start is `[S,1,…,1]` of depth `m_S`, and that depth-2 (canonical prefix collapsing to `[S,1]`) is the common/minimal case, not an assumption.
