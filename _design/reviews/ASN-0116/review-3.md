## Revision list

1. **Implementation approaches → "unifying move" tradeoff (also Decisions, "store the allocated start"): the digest contradicts itself, calling the stored start both "*required*, not a nicety" and "a Lampson hint."** These are mutually exclusive — a hint is by definition recomputable; "required" means authoritative and non-recomputable. Under the digest's own scheme (an append-only journal of *all* edit operations replayed through a deterministic query-and-increment allocator) the start *is* recomputable: replaying prior ops rebuilds the content store, the max-query returns the original value, and the increment reproduces the original address. The digest's own phrase "makes replay a *verification*" confirms recomputability (there must be something to verify against). **Fix:** demote "required" to "a strongly recommended defensive hint" — its real value is decoupling the on-disk format from allocator internals and guarding against allocator drift, not enabling replay. Add the one case where it *does* become required: if the journal omits other address-consuming operations (e.g., link-creation, which the evidence shows also draws from the allocator) or the allocator isn't deterministic.

2. **Implementation approaches → "unifying move" / Approaches 1 & 5: the granfilade↔permascroll relationship is over-specified beyond what the evidence supports.** The digest asserts "the granfilade … layered over the **permascroll**, the append-only log the granfilade indexes; the two are distinct layers, not interchangeable." The evidence shows content living *directly* in granfilade GRANTEXT crums (`typegranbottomcruminfo` holds `textstring`, written by `insertseq`), and uses "permascroll" loosely for that same content path — not as a separate log the granfilade indexes. The *terms* are grounded Green structure; the specific "log + index, two distinct layers" relationship is neither in the note nor clearly in the evidence. **Fix:** soften to the grounded claim — the granfilade is Green's append-only content store realizing `C` — and drop or explicitly hedge the "separate indexed permascroll log" framing. The advice (persist directly, no replay) doesn't depend on it.

3. **What must be built → precondition checker, and Design commitments: the precondition that the document must already exist is missing.** The note's INSERT precondition opens with `d ∈ dom(M) = E_doc` ("the document is an allocated entity"), and F-ENT states INSERT registers no entity — i.e., INSERT is *not* document-creation; a separate operation allocates the document. The digest's precondition checker lists subspace, depth, slot-position, and length `N` but omits the existence gate, which should be the first check. **Fix:** add "document `d` must already be allocated (`d ∈ E_doc`); INSERT creates no entity" to both the precondition checker and the commitments. While there, note the depth-fixing subtlety the digest currently flattens to "matching depth": the *first* insertion into an empty subspace fixes the subspace depth `m`, and every later insertion must match it.

4. **Decisions for the builder → "Do you coalesce adjacent runs?": surface that forward-coalescing is provably unnecessary.** The digest gives the backward-merge condition (share origin ∧ I-adjacent) correctly but leaves a builder to wonder whether to also check the right neighbor. The note devotes a full paragraph (IP1 discussion) to proving the inserted block can *never* I-merge forward with the shifted suffix "in any reachable state" — `shift(a, n)` always lies beyond the post-allocation frontier, so it can't equal the suffix head's address. **Fix:** state explicitly "coalesce backward only; forward-merge with the shifted suffix is provably impossible and need not be checked." This is a concrete simplification of the coalescing logic, not a sharpening of theory.

5. **Implementation approaches → Approach 4 / Decisions → discoverability: the tight-endset design lever (IP6c) is omitted.** The digest's discoverability discussion correctly surfaces ghost references → cache invalidation, but the note offers an alternative the digest doesn't mention: IP6(c) shows that if endsets are *tight* at creation (no forward/ghost references), then `LP19a` gives `A_new ∩ coverage(e) = ∅`, so an insert never adds witnesses and discoverability is preserved *unconditionally* — eliminating the ghost-driven invalidation problem entirely. **Fix:** add tight-endset discipline at link-creation as a genuine builder lever in the discoverability decision: enforce tightness (simpler discoverability, no ghost-driven cache invalidation) vs. permit ghost references per L4/L9 (more flexible — pre-creating links to future content — at the cost of insert-time witness/cache handling).

6. **Design commitments → fusion paragraph: strengthen the "implementation may fuse the two steps" claim with the evidence.** It currently rests only on the note's "the rewrite is not itself one of these atomics." The evidence directly supports fusion: Green realizes the displacement as essentially one pass (`makegappm` shifts existing entries' V-displacements in place, then `insertcbcnd` adds the new piece) — it does *not* perform a literal contraction-then-extension. **Fix:** cite that the proven implementation already fuses the K.μ⁻/K.μ⁺ pair, so fusion is not just permitted in principle but is the demonstrated path.
