This is a strong, well-grounded digest: the core reading of the note is correct (references move / content is fixed; rigid uniform shift; subspace+document isolation; text-dense/link-sparse inherited from ASN-0036; insertion general-depth, contraction depth-2 text), the Green grounding is careful (permascroll, POOM, spanfilade, the NPLACES/version-chain evidence, Gregory's "suspicious shift" comment are all used correctly and at structural altitude — no invented function names), and the central design insight ("sequence-for-text turns the note's preservation lemmas into by-construction facts; a map/tree turns them into obligations") is genuinely valuable. The defects below are in the refinements and design inferences, not the spine.

**Revision list (most important first):**

1. **Design commitments §8 / "Shift/contraction at depth 2": stop calling contraction's *text-only* restriction a "proof boundary."** The digest bundles two restrictions ("depth-2 text spans") and labels the whole thing "a proof boundary, not a hard design limit." Only the **depth-2 ceiling** is a proof boundary — the note's Open Questions explicitly ask whether D-SEP/D-DP generalize to depth > 1 ordinals. **Text-only is structural, not a provability gap:** contraction's job is to *close a gap and restore contiguity*, and D-CTG/D-SEQ/D-MIN exist only for text (V_2 is deliberately sparse). There is no gap to close in the link subspace — DELETE there is just remove-and-tombstone, no shift. Extending contraction to links isn't a matter of more proof; it would contradict the sparsity exemption and gratuitously renumber stable link endpoints. Split the two: depth-2 = proof boundary (matches Green); text-only = intrinsic. This also sharpens the insertion/contraction asymmetry (insertion is defined on *any* subspace S ≥ 1, contraction only on S = 1) that is currently only implicit across commitments 5 and 8.

2. **Design commitments §6 and "Atomicity and recovery": separate content permanence from version history — the digest conflates them, twice.** "Append-only content … yields historical versions for free" and "version history and the permanence guarantee fall out of the same mechanism" attribute version history to the *content* side. But the note's permanence guarantee (D-I: `Σ'.C = Σ.C`) only says content is never destroyed. To read a *past document version* you need the past *arrangement* M(d) — and D-DOM explicitly discards it (post-contraction domain is `L ∪ Q₃`; the X mappings are gone). So version history requires **retaining superseded arrangement roots** (the digest's own snapshot idea), which is an arrangement-side choice, not a content-side freebie. Fix: keep "content permanence — forced by D-I, free from the append-only Istream" as one guarantee, and attribute version history to retained/structurally-shared arrangement roots as a separate (sound) design choice.

3. **Design commitments §7 / Guarantees / "Decisions for the builder → Span maintenance": scope width-invariance to within-region spans; the straddle case breaks "move its start alone."** I3-S/D-S prove rigid shift only for a span lying *entirely within* the shifted region ("Both endpoints of a within-subspace span shift by the same displacement"). A selection that **straddles** the edit point does not move rigidly: an insertion inside it widens it, a deletion inside it shrinks it. The unqualified "A stored selection survives an edit by moving its start alone" will mislead a builder doing the common case (typing inside a selection). State the scope and note that straddling spans change width and need separate handling.

4. **Design commitments §1: "D-I is stronger still" than I3-C is wrong — they express the same content-store invariant.** I3-C is `dom(C')=dom(C)` with values unchanged, which *is* `Σ'.C = Σ.C`. The note's registry calls D-I "strictly stronger than **S0**" (which only gives `dom(C) ⊆ dom(C')`), not stronger than I3-C. Drop "stronger still"; both INSERT and DELETE pin exact content-store equality.

5. **"What must be built → Contract" and "Decisions for the builder": surface the operation preconditions a builder must enforce.** Contraction carries a **containment** precondition (`p₂ + w₂ − 1 ≤ N` — the delete range must lie within the current text); the digest never says DELETE must validate its range against current bounds. Add it. (Secondarily, general-depth insertion carries a **depth-compatibility** precondition — `#p` must equal the existing depth in subspace S; automatic at the recommended depth-2 build, but worth a line in the Depth decision for anyone building general-depth INSERT.)

6. **"Atomicity and recovery": "replay rebuilds the arrangement exactly" from an `INSERT p,n / DELETE p,w` log is incomplete.** DELETE replays from `(p,w)` alone, but INSERT's *gap-fill* — which I-addresses get bound into the opened slots — is not determined by `(p,n)`; reconstructing the post-fill V→I bindings needs the content-append/fill record too. The "Journal granularity" decision already hints at "operation log vs content-append log vs both"; make the atomicity claim consistent with it (operation log rebuilds the *shift*; the *bindings* need the fill/content log).

7. **Implementation approaches → Option 1: state the link-side cost.** A "sparse ordered map keyed by ordinal" pays **O(k) re-keying on a mid-ordinal link INSERT** (every key ≥ p must increment) — the same cost problem flagged for Option 3, just confined to the link subspace. This is what actually grounds the advice "move to Option 2 if link edits get hot," so say it (and note it's moot if link creation is append-mostly).

8. **Design commitments §3: "contiguous suffix" overclaims.** The shifted region is a *suffix* in the subspace's order, but it is contiguous only in text; for links it is sparse. The body ("Every position at/beyond the edit point in the affected subspace") is correct — just drop "contiguous" from the header so it doesn't blur the very text/link distinction the note is careful about.

9. **"The content store (Istream)": verify the repo self-reference.** "this repo's own `links.jsonl`/`paths.json`-recovered-by-replay pattern" is a checkable claim about *this* repo (not Green, so not a grounding defect per se), but if `paths.json`/replay-recovery isn't actually how this repo works it's a misleading analogy. Confirm or drop.

Solid as-is — no change needed: the three-representation analysis with the "pick" and unify-or-split note; the I-address-anchoring + spanfilade answer to the external-reference open question; the placement of full tumbler arithmetic on the I-side (correctly grounded in the NPLACES/version-chain evidence); and the shift-sub-op vs. full-INSERT/DELETE decomposition in "How it fits."
