This is a strong digest — accurately read, well-grounded in the note and the depth-2 evidence, disciplined about not inventing Green source-level claims, and carrying a genuinely useful organizing thesis (the sequence representation turns most preservation lemmas into by-construction facts). The improvements below are mostly about one muddled justification, one under-budgeted component, and several scoping refinements.

**1. Design commitments → commitment 8 ("Contraction is text-only…"): the *justification* is unsound on both stated grounds (the conclusion is fine — fix the reasoning).** "It would contradict the sparsity exemption" is wrong: the exemption *permits* sparsity, it does not *forbid* density, so compacting V_2 on delete contradicts nothing — a compacted link subspace is still a validly sparse-allowed subspace. "Gratuitously renumber stable link endpoints" is also undercut twice: the note's *own* link-insertion example renumbers link V-positions ([2,1]→[2,2], [2,2]→[2,3], …), so link endpoints are not stable as V-positions under link edits to begin with; and the digest's own external-reference section recommends anchoring durable references to I-addresses, which makes any V-position renumbering harmless. Replace both with the note's actual stated reason: contraction is defined and proven only for S=1 because its machinery consumes the text-only contiguity preconditions (D-SEQ/D-CTG/D-MIN) — links are contiguity-exempt, so there is no gap to close and contraction has no job there. Then present "link DELETE = remove-and-tombstone" explicitly as the digest's *recommended design* (tombstone is cheaper and the exemption permits it), not as something the note states — the note never defines link deletion at all.

**2. Implementation approaches → "External references / staleness": the design answer leans on an I→V reverse lookup it never names or budgets.** "Re-resolved through its I-address after an edit" requires recovering a *current V-position from an I-address within a document* — the reverse of M(d). The **spanfilade** the digest cites is the *cross-document* I→referrers index; it stays valid passively precisely because it is keyed on the immovable I-address, but it does not answer "where does this content now sit in document d." Add the within-document reverse lookup as a required capability — for a forward-only sequence it is a scan or a maintained reverse index; the POOM/enfilade can serve it directly — and list it in "What must be built," since the note raises this exact need as Open Question 1. Also flag the disambiguation hole: if M(d) is non-injective (within-document transclusion → one I-address at several V-positions), the I-anchor alone cannot identify which occurrence the external reference meant.

**3. Design commitments → commitment 8 / Decisions → Depth: make the depth-2 ceiling's *reason* concrete.** The digest justifies depth-2 mostly by "the Open Questions ask whether it generalizes" plus a passing "inverse-law math is still open." The note's third Open Question states the actual obstruction: at ordinal depth > 1, TA4's zero-prefix precondition collides with S8a's componentwise positivity at the intermediate components 2..m−1, so the projection round-trip `(ord(p)⊕w_ord)⊖w_ord = ord(p)` that D-SEP/D-DP rest on has no inverse law to lean on. Surface this collision — it is what makes depth-2 a *genuine* boundary rather than mere unwritten proof, and it is the load-bearing fact a builder needs to weigh "invest in general depth now."

**4. Implementation approaches → "The content store" / tumbler arithmetic: scope the "arithmetic lives on the I side" claim.** The note never does arithmetic on I-addresses (they are opaque values that ride along), so "the full tumbler arithmetic lives here, on the I side" is an *inference about the surrounding content-allocation layer* — grounded in the evidence that I-addresses are deep version chains (NPLACES 11→16), so say that rather than presenting it as established by this note. And reconcile it with the digest's own commitment that INSERT is general-depth: at depth > 2 a V-position shift is genuine multi-story tumbler addition, so "trivial at depth-2 V-positions" is a property of the *chosen depth-2 build target*, not of V-positions in general. The "narrow seam for depth > 2" is exactly where V-side arithmetic returns.

**5. Design commitments → commitment 1, parenthetical: S0 is undersold.** The gloss "the foundation's one-sided S0 (`dom(C) ⊆ dom(C')`)" drops S0's value-preservation conjunct — S0 is "dom(C) ⊆ dom(C') *and* Σ'.C(a)=Σ.C(a) on dom(C)." What D-I/I3-C add over S0 is only the reverse inclusion dom(C') ⊆ dom(C); state it that way. (The substantive point — D-I and I3-C are equal strength, both stronger than S0 — is correct and a good catch worth keeping.)

**6. Implementation approaches → Option 1: the `im`-crate reference dips below design altitude.** "rope / RRB-vector with O(log n) split/concat" is the right design-level description; naming a specific Rust library presumes a language and reads as implementation. Drop to the structure name, or mark it explicitly as just an illustrative existing implementation.

**7. Guarantees → Width preservation / Decisions → Span maintenance: state the ordinal-level precondition.** I3-S and D-S hold only for *ordinal-level* spans — width acting at the deepest component (actionPoint(ℓ)=#ℓ). It is automatic at the depth-2 target (any width [0,c] acts at position 2), so it doesn't bite now, but a builder generalizing depth or storing structurally "wide" spans needs to know width-preservation-under-shift is conditioned on it. One clause suffices.

Genuinely solid and needing no change: "What this is"; commitments 1–7; the by-construction-vs-obligation thesis in Guarantees; the straddling-span caveat (correctly scopes I3-S/D-S to within-region selections); and the Atomicity/recovery section — the observation that DELETE is fully `(p,w)` but INSERT's gap-fill is *not* determined by `(p,n)` and so needs the content-append record is exactly the right load-bearing distinction.
