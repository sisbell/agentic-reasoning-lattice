## Revision list (most important first)

**1. "What must be built" / "Implementation approaches §2 (link index)": surface the index-candidate vs Match gap (the ghost-slot finding).** The digest treats "port the spanfilade" as yielding `Match`, but the spanfilade returns links by I-address overlap — *candidates* — not the note's discoverability `Match`. Per evidence Q20/Q15, Green resolves a link's endsets to V (the I→V reachability check) only at follow-time, *after* windowing, so a literal port fills window slots with orphaned/ghost links that resolve to empty endsets — the reader gets fewer than N *resolvable* results, and exhaustion reflects index membership, not `Match`. This is in scope for a delivery contract. Add a builder consideration: realizing the note's discoverability semantics requires filtering each candidate by current reachability at window-build time (so N counts resolvable matchers); clarify that the spanfilade is the matching/ordering *index*, while `findlinks_V` (= image-resolution + index lookup + reachability) is the discoverability layer above it. The digest currently doesn't address whether the recommended port realizes `Match` exactly.

**2. "Implementation approaches §2": the matched-slot "slides up → can skip a live link" is the wrong direction.** A key that slides *up* (least matched endpoint orphans out, position → higher I-address) moves a link toward the tail: a below-cursor link re-ascends *above* the cursor → **re-delivery (duplicate)**, never a skip; a tail link merely lands later, still reachable. A **skip** requires the key to slide *down* (a tail link falls below the cursor), which happens when a *lower* matched address **enters** the image (LP9 arrangement extension, or resurrection of a lower endpoint), not when the least one leaves. Fix: state both directions — orphaning slides up → duplicate; extension/resurrection slides down → skip; both are clause-1 violations on a mutating set — or, if keeping the orphaning mechanism, change the consequence to "re-deliver an already-seen link." The conclusion (matched-slot order is frozen-set-only) is correct; only the mechanism→consequence link is mislabeled, in a digest otherwise scrupulous about skip-vs-duplicate direction.

**3. "Implementation approaches §5 (exhaustion signaling)": "With a permanent key the empty window is unambiguous" drops a qualifier that §1A and the Guarantees section correctly supply.** §1A's own insight is that the empty-vs-exhaustion ambiguity is a *resume-mechanism* property, not just a key property: Green has a computable address key yet still goes dark because it resumes by exact-match scan. §5 contradicts that by attributing unambiguity to the permanent key alone. Fix: "With a permanent key **and key-cut resume**, the empty window is unambiguous," aligning §5 with §1A and the "Cursor survives orphaning" guarantee (which gets it right).

**4. "Implementation approaches §1B": "merge of ordered streams" silently assumes the multi-endpoint intersection preserves the enumeration order.** Evidence Q11 explicitly flags Green's intersection ordering (`intersectlinksets`) as unresolved. Order-preservation is load-bearing: if the from∩to∩type combine doesn't preserve the key order, W0's unique listing and W4's partition break. Add it as a builder obligation: the intersection/merge must re-establish the total enumeration order (automatic if each stream is sorted on the same key; for content keys the merge must key on the `(boundary, address)` composite).

**5. "Implementation approaches §1 recommendation" vs "Key/index coupling": reconcile them.** The §1 recommendation "(B) when index order matches your key" reads as if (B) can be free, but the coupling paragraph establishes that *no* correct (permanent) key is the spanfilade's native (matched-slot) order — so (B) on a permanent key always presupposes a purpose-built derived/address-ordered index, and the native order supports a fast (B) only against a *frozen* set. Pull that caveat into the §1 recommendation so a reader of §1 alone isn't misled about (B)'s cost.
