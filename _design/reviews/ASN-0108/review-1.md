Reviewing the digest against ASN-0108, its formal claims, and the verified evidence. The digest is strong and well-structured; the most valuable corrections cluster around the *resume mechanism* and the *grounding precision* of the udanax-green evidence notes. Ordered most-important first.

---

**1. Implementation approaches §1(A) + "Guarantees: Cursor survives orphaning" + "What must be built: Cursor evaluation" — the digest's resume mechanism is self-contradictory, and approach (A) as described forfeits W8.** Approach (A) relays Green's resume literally — "linear-scan to the cursor, truncate" — and calls it "obviously correct." But the verified evidence (Q12, Q17) is emphatic that this *exact-match* scan returns an empty batch with count 0 **when the cursor link has orphaned out of the re-materialized list**, which is *indistinguishable from exhaustion* — the very ambiguity the note (W8) and the digest pin on the *position* key alone. So (A) is not "obviously correct": with an address (identity) cursor it still goes dark on a deleted cursor, because the failure lives in the *resume mechanism*, not the key (Q12: "a stale-cursor invalidation that would be impossible if the cursor were a pure address boundary into the index"). The digest's own "What must be built … robustly, even after the cursor link has left the matching set" and its guarantee "Cursor survives orphaning — by construction for permanent keys" are therefore both undelivered by (A). Fix: state plainly that W8 requires resume by **key-cut / successor search** — deliver the ≺-least matchers whose key is *strictly greater than* the cursor's key — never an exact-match scan for the cursor link. Correct "by construction for permanent keys" to: cursor survival needs a computable key *and* a key-cut resume; Green has the former but not the latter, which is exactly why its address cursor still suffers the ambiguity. Give the per-key mechanism: address key → "first matcher with address > c" (cursor need not be present); content-composite key → re-derive the cursor's content boundary from its immutable endset (L12/LP13, available post-orphaning) and successor-search by (boundary, address). This is the same mechanism the digest's own decision #5 (fattened token carrying the cached key) already presupposes — so either amend (A) to do the cut, or it contradicts #5 and the W8 guarantee.

**2. Implementation approaches §3 (evidence note) + §2 (index) — two specifics are contradicted by the evidence; the (boundary, address) composite is a requirement to impose, not Green behavior to inherit.** The evidence note's core point — Green orders by the matched endpoint's *permanent content I-address*, not a V-position — is correct and well-grounded (it rightly resolves the contested Q11 material against the dedicated Q1 consultations). Two riders are wrong: **(a)** "link-ISA dedup as the de-facto tiebreaker … not a traversal accident." The evidence (Q1 tie-break; Q1 onlinklist) shows link-ISA is used for *dedup* (each distinct link once), while the order *among distinct links sharing a content boundary* is set by enfilade traversal/insertion order, with **no link-address tiebreak** — it *is* a traversal artifact. So the `(boundary, address)` composite that W0/W1 demand for a clean, value-functional injective key is a design obligation the builder must add, not something Green realizes; say so. **(b)** "least-covered-tumbler reading" / §2's "gives the least-covered-tumbler ordering for free": Green keys on the *matched slot's* content address — query-dependent, "not a function of the immutable link value" — which the note explicitly distinguishes from the a-priori-fixed-slice least-covered key. The recommended index `(endset-slot, content I-address) → link` realizes Green's *matched-slot* order, not the a-priori key; either commit to a derived `link → least-covered-tumbler-of-designated-slice` index, or relabel the recommendation as the matched-slot order (adequate for windowing a fixed query, but not the note's clean key).

**3. Design commitments §3 — the discoverability (live-view) reading is the load-bearing *adopted* choice, not merely "inherited."** The note opens by *adopting* the discoverability reading "rather than the monotone, historical fixed-`I` findlinks … store-membership reading," and that adoption is precisely what makes Match non-monotone and forces the whole orphaning/resurrection apparatus (W7, W8-orphan-survival, W9b inflow, W9c). The digest's "Forced by the discoverability reading inherited from ASN-0127" understates this. Surface it as the pivotal fork with a *named* monotone alternative — and note that the alternative would obviate half the machinery (no orphaning → cursor trivially survives, no resurrection inflow). A builder should know this is a choosable semantics, not a fixed inheritance.

**4. Guarantees: Termination — the "trap to actively guard" is aimed at the wrong trap for the recommended build.** The digest says termination "requires finite cumulative tail inflow *plus* cut-point preservation (a still-matching delivered link re-ascending … loops forever — W9c). … this is the trap to actively guard." But under the recommended *permanent* keys, cut-point preservation is free (state-stable) and the W9c re-delivery loop **cannot occur** (W9b: a permanent key returns a resurrected link *below* the advancing cursor). So W9c is a reason to *reject the position key*, not a guard you implement. Reframe: with a permanent key the only non-termination is *legitimate* unbounded cumulative inflow (correct behavior — new matchers keep arriving), which needs no guarding; the W9c re-ascension loop is the position key's failure mode, not the recommended build's.

**5. Minor.** (a) Approach (B) under-specifies that the index walk must be *restricted to the query's current image* — the I-addresses the query region resolves to via the consulted POOM (`findlinks_V = findlinks(image(W,d_q,Σ),Σ)`); a bare spanfilade walk is not Match, and this restriction is where orphaning enters (image shrinks when content leaves `d_q`). One clause fixes it, and it also corrects any impression that (B) walks the global index. (b) The repo-specific build references — `im`, `links.jsonl`, "this repo's own substrate pattern," recovery-by-journal-replay — are grounded in neither the note nor the evidence (the note is silent on index durability); keep them but mark them as the author's recommendation pending verification against the actual repo, so they aren't read as established. (c) Tiny: "Forced" on statelessness is really forced *given* the crash/reconnect/concurrent-reader goals the note names — one qualifying clause.

**Solid, and worth saying so:** the forced-vs-conventional taxonomy in Design commitments is mostly excellent; the W2 offset-vs-identity weakest-precondition argument and the W9 short-window / exact-multiple treatment are crisp and accurate; the hint-cache (C) is held to the right Lampson discipline (droppable, never authoritative); and "Decisions for the builder," cleanly separated from the note's spec-level open questions, is genuinely actionable. The corrections above are about *resume mechanism* and *grounding precision*, not about the digest's overall shape, which is sound.
