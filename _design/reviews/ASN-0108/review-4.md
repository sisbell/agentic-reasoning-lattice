## Revision list

**1. [DEFECT] — "Implementation approaches" §2 ("A candidate index is not Match"): the claim that the spanfilade over‑includes `Match` and must be narrowed by a per‑candidate reachability post‑filter "at window‑build time" is a misread, and the recommended filter would under‑deliver `Match`** — contradicting both the note ("windowing takes `Match` as given and … delivers it") and the digest's *own* approach (B).

- Under the discoverability reading, `Match = findlinks_V = findlinks(image(W, d_q, Σ))`, and the image is the query region's *current, reachability‑resolved* V→I map — Green builds it through the consulted document's POOM as **stage 1 of the search, before windowing** (Q15/Q20). Restricting the index lookup to that image yields *exactly* `Match`: a link overlapping the image has a matched endpoint in `ran(M(d_q))`, hence is reachable/non‑orphaned, hence in `Match` (and conversely). There is no separate "per‑candidate reachability" step and none is needed; orphaning manifests as the image *shrinking* (matched content leaving the region), automatically dropping the link (= W7). This is exactly what approach (B) says correctly ("restrict the walk to the query's current image … a bare global index walk is not Match … the image shrinks when matched content leaves the region") — §2 contradicts it.
- The Q20 "ghost" the digest wants to filter is a link that **is** in `Match` (its matched endpoint overlaps the reachable image) but whose *non‑matched* endpoint(s) are orphaned, so that *following* it for display yields empty endsets. That is a follow/display artifact on a separate operation, downstream of windowing; the link genuinely matches the query that found it. Filtering it makes windows carry fewer than `Match`, miscounts N, and mis‑signals exhaustion. The supporting sentence "Green runs the I→V reachability check only at follow‑time, after windowing" is also false: the *query‑side* V→I (the reachable image) runs *before* windowing; the follow‑time I→V is a *different*, display‑only conversion of the link's own endset.
- **Fix:** rewrite §2 to (a) state that restricting the lookup to the current reachability‑resolved image yields *exactly* `Match`, with no per‑candidate post‑filter, consistent with (B); (b) keep the one valid kernel — the *raw/append‑only* spanfilade is not `Match`, so you must search the current image, not walk the index globally; (c) move the ghost point to follow/display ("a delivered, genuinely‑matching link may show empty *non‑matched* endsets when followed"), explicitly **not** a window‑build‑time filter, and drop "exhaustion of the index, not of Match" / "N counts resolvable matchers."

**2. [SHARPENING] — Design commitments, W2 bullet:** "silently broken by any insertion or orphaning between calls" is imprecise — only changes *at or below the cut* falsify the frozen‑prefix count (an above‑cut insertion/orphaning leaves the at‑or‑below count, and the weakest precondition, intact; the note says "below the cut"). Tighten to "any insertion or orphaning **at or below the cut**." The commitment (identity over offset) is unaffected.

**3. [SHARPENING] — §3 evidence rider / tie‑break:** the digest correctly establishes that Green's `onlinklist` uses link‑ISA only for *dedup*, with ties resolving to enfilade traversal order (no address tiebreak). Make explicit that this **corrects the source note**, which asserts "the link's permanent address is the de facto low‑order key, not a traversal accident." Saying so sharpens *why* the `(boundary, address)` composite is a real builder obligation (W0/W1 injectivity, W3 determinism) rather than free Green behavior — the digest's conclusion is already right; only the attribution could be louder.
