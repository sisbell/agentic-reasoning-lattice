Reviewed against ASN-0058, its claim set, and the two evidence answers. The digest is accurate on the algebra itself (no M-property misattributions, the M3/M8/M12 readings are right, the bidimensional-adjacency-suffices argument is correctly grounded in M14a+M16). The defects are concentrated in the implementation-approach reasoning and in two missing contracts. Most-important first.

---

**1. "Implementation approaches → The store": the enfilade's cost is misjustified, and the ordered-map Pick hides an edit-time cliff it routes work into.**
The digest says the 2-D enfilade "earns its complexity only when you also need I-indexed queries (within a single document)." That misidentifies why the enfilade exists. The enfilade's cumulative displacement/width per dimension — the very "cumulative-sum mechanics" the digest itself cites two paragraphs later — primarily buys **O(log n) bulk address-shifting on insert/delete**: shift a whole downstream region by adjusting one ancestor's displacement. A V-keyed ordered map with *absolute* V-start tumbler keys (what the digest recommends) re-keys and re-creates **every downstream block** on a mid-document insert, so edits are O(n) and the touted "cheap versioning via structural sharing" collapses (an edit near the document start shares almost nothing with the predecessor version). The digest explicitly names the operation layer (insert/delete/copy) as this store's consumer, so a store recommendation cannot ignore that cost. Fix: state that the ordered-map Pick is right *for this note's read/split/merge/resolve surface* (split/merge/resolve don't shift downstream), but that the enfilade is warranted as soon as edits arrive — its justification is edit-time bulk shift, with within-document I-indexing only a secondary benefit. (Reads-as-pure/snapshot-consistent is fine and unaffected; the problem is the write/versioning claim and the enfilade rationale.)

**2. "Design commitments / Guarantees": origin traceability and cross-origin non-merge are presented as unconditional "by construction," but M16a carries a standing input contract the digest never surfaces.**
M16a's origin invariance is proved *under the precondition that the content store C conforms to T10a* (every `a ∈ dom(C)` is T4-valid, `zeros(a)=3`, element I-addresses extend the document prefix). The digest lists S3 (referential integrity) as an upstream input contract — correctly — but files origin-as-prefix and M16/M16a/M16b purely under "by construction, not by enforcement / from tumbler-prefix arithmetic." That omits that the cross-origin guarantee holds *only because* the upstream allocator forms element addresses by extending document prefixes. Evidence Q5 is directly on point: this prefix structure holds in Green because of how `tumblerincrement` builds element ISAs, but T10a "discipline" does **not** propagate for free — it must actually hold at element allocation. Fix: add "content store allocates element I-addresses as document-prefix extensions (T4-valid, `zeros=3`)" to the input-contract list alongside S3; note that M16/M16a/M16b are guaranteed by construction *given that contract*, and break under a content store that allocates I-addresses without prefix structure.

**3. "Implementation approaches → Persistence/recovery": the `links.jsonl + paths.json` citation is ungrounded.**
"Follow this repo's own substrate: an append-only journal of arrangement writes (the `links.jsonl + paths.json` model...)" names specific artifacts that appear in neither the note nor the evidence nor documented Green structure, and presents them as a model the POOM persistence should follow. That is exactly the kind of unverifiable specific to flag — and it risks transplanting an unrelated substrate (those files may store spec documents/links, not a per-document V→I arrangement). The surrounding recommendation (append-only journal, replay, periodic canonical snapshots, permascroll/granfilade for content) is sound and well-grounded; drop the `links.jsonl/paths.json` reference or replace it with a real citation.

**4. "Design commitments → A unique, history-free normal form": "independent of edit order" is wrong as stated, and the digest contradicts it later.**
The canonical decomposition is determined by `M(d)`, and `M(d)` depends on edit order — insert/delete/copy do not commute. M12 gives **merge-order** independence on a *fixed* arrangement, not edit-order independence. The digest's own persistence section gets this exactly right ("M12's order-independence governs *merge* order on a fixed arrangement, not the order of journal *edits*"), which makes the commitment-section phrasing a self-inconsistency. Fix: change "independent of edit order" to "independent of merge order / of which equivalent decomposition you start from."

**5. "Design commitments → Width is a single count": "store the count once" is a chosen representation smuggled into the forced list.**
M0 forces the *coupling* (`|V(β)| = |I(β)| = n` — conceptually one width), not single-storage. Green stores two width tumblers held equal by immutability (the digest itself records this), and the digest's own "Decisions for the builder" lists "scalar count vs. dual per-dimension tumblers" as an open builder decision. Listing "store the count once" under commitments "forced on all downstream design" overreaches. Fix: the forced commitment is the equal-cardinality coupling; move "store once" into approaches as the recommended (not forced) representation.

**6. "Implementation approaches → Multi-subspace layout": the per-subspace-trees recommendation under-weights why the one verified implementation unified them.**
The digest defaults to per-subspace trees for a fresh build "unless you need atomic edits spanning subspaces." But evidence Q1 shows that exact need is not a rare exception — link creation, a *core* Xanadu operation, writes from/to/three endpoints into one link POOM and also writes the link-ref subspace of the document POOM, and Green's unified tree (with the two-blade knife for isolation) exists precisely to make those cross-subspace writes atomic in one structure. As framed, the digest makes the unusual case the default and the dominant case the exception. Fix: surface that the "unless" caveat is the actual driver behind the verified design, so the builder weights cross-subspace atomicity (i.e., whether they're building links) before defaulting to per-subspace trees.

**7. "Implementation approaches → Merge/canonicalize": "O(1) per edit" for eager local coalesce is glib.**
The coalescing *check* is local (the touched point's neighbors), but only after the edit's own O(log n) locate, and the claim's correctness depends on the pre-edit decomposition already being canonical (so new adjacencies can appear only at the edit boundary). State it as "O(1) additional coalescing beyond the edit's locate, given the decomposition was canonical before the edit" — and note this reasoning lives in the out-of-scope edit layer.

---

Net: the M-algebra commitments, the C0 "resolve input reduces to (start, scalar count)" insight, the bidim-adjacency-suffices + origin-prefix short-circuit, the edit-order-vs-merge-order distinction in persistence, and the M3 truth-vs-hint nuance are all genuinely sharp — leave them. The work is in items 1–2 (a misjustified store Pick and a missing upstream contract) and the smaller accuracy/grounding fixes above.
