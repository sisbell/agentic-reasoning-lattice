## Revision list

**1. Multi-subspace layout (Implementation approaches + the matching Decision): the headline recommendation rests on an ungrounded motivation, and the example partly contradicts it.** The claim "Green unified the tree *precisely to make those cross-subspace writes atomic in one structure*" asserts a *motivation* that neither the note (which marks subspace layout "merely conventional") nor evidence Q1 supports — Q1 confirms the unified tree, the leading-digit convention, the knife isolation, and that the document POOM coexists text (1.x)/link-ref (2.x)/type-endpoint (3.x) subspaces, but says nothing about *why* Green unified or that atomicity drove it. Worse, the digest's own (accurate) example undercuts the conclusion: link creation writes the three endpoints into the *link* POOM and the link-reference into the *document* POOM — two separate trees — so a unified *document* tree cannot make "those cross-subspace writes" atomic; the only genuine one-tree multi-subspace write is the link POOM's three endpoints. Fix: drop the asserted atomicity rationale; ground the default in the verified facts (document POOM coexists three subspaces; link POOM holds three endpoint subspaces; Green isolates with the knife). Keep the "are you building links?" heuristic — links *do* force multiple subspaces into play — but present cross-subspace *atomicity* as a builder hypothesis, not Green's established reason.

**2. Resolution approach silently assumes a canonical store, contradicting the co-offered lazy option.** "Clip the first and last blocks to the span boundary on the output" yields C1a's unique maximally-merged slice *only* when the store is already canonical (eager mode). Under the digest's own "lazy global coalesce on snapshot/resolve" option, the scanned slice can contain V- and I-adjacent blocks, so clip-alone returns a non-canonical, over-split run sequence — more runs than C1a/C2 require. The lazy bullet does say resolution "canonicalizes its slice anyway, per C1a," so the digest contains the right fact but the Resolution paragraph understates it. Fix: state that resolve produces the canonical slice (C1a) = clip **+ coalesce**, with clip-alone being the eager-mode specialization; tie this explicitly to the canonicalization-timing decision so a lazy-mode builder doesn't ship clip-only resolution.

**3. The store "Pick" leaves the real build-order call implicit.** The digest scopes the V-keyed-index recommendation to "this note's surface," yet its own "How it fits → Hands to" identifies the edit layer (insert/delete/copy) as the immediate adjacent consumer — and says the V-keyed index goes O(n) the moment edits arrive. Recommending a store the digest itself calls edit-inadequate, for a note that exists to support edits, risks throwaway work. Fix: surface the build-once-vs-simplest-now judgment — a builder serving any edit workload should likely build the enfilade up front; the V-keyed index is the right pick only if read/split/merge/resolve is genuinely the terminal scope.

**4. Two loose M15 citations (Persistence, Resolution).** (a) "Composite resolution is per-document and independent (M15)" — references in a sequence may name the *same* document (the note explicitly permits it), where M15 (d₁≠d₂) does not apply; the parallelism actually comes from resolution being a *pure read*, with M15 covering only the distinct-document case. (b) "insert/delete/copy do not commute (cf. M15's byte deletion)" — M15's byte-deletion quote is about cross-document independence, not within-document edit ordering; the non-commutativity point stands on its own. Retarget (a) to read-purity + per-reference independence; drop the citation in (b).

**5. Guarantees: name decomposition validity (B1 ∧ B2 ∧ B3) as the store's standing invariant.** It is currently scattered — B1+B2 folded into S2-functionality, B3 left implicit in "operations preserve consistency." This is the one invariant the store must hold at all times and that every operation (split/merge/edit) must re-establish. Add it explicitly as the core by-construction guarantee, with M6f/M7f as the preservation argument.

**6. "What must be built" lists a "subspace-scoped V-range selector" that isn't a separate component.** Single-subspace confinement is guaranteed by well-formedness (C0a: every `t ∈ ⟦σ⟧` has `t₁ = u₁`), not something the builder selects or enforces. Fold it into Resolve as a property ("resolve operates on a single-subspace span, guaranteed by C0a — no cross-subspace selection logic needed") rather than a build target.

**7. Surface the split↔merge exact-inverse duality (M9/M10).** The note calls this "the algebraic core of the permutation model"; the digest captures its consequences (M8 boundary loss, M12 confluent canonicalization) but never states the duality itself. Add one line: split and merge are exact inverses given the cut point/boundary — which is *why* canonicalization is lossless on pairs and confluent, and why M8's forgotten boundary is the only thing the round trip cannot restore.
