A capable digest — it scopes cleanly (store + split + merge + canonicalize + resolve, edits deferred), and several approach calls are genuinely sharp. But it has two real soundness problems and a couple of mischaracterized tradeoffs. Revision list, most-important first.

**1. Design commitments, item 1 — "the POOM is a *hint*… not authoritative state" overreaches M3; split the forced fact from the design choice.** M3 forces only *representation-independence of the decomposition*: any two block sets denoting the same (V, I) pairs are interchangeable, so you may freely normalize/re-represent the boundaries. It does **not** make the POOM non-authoritative. The arrangement `M(d)` — the actual (V, I) pairs — is authoritative, and absent a separately-designated durable form it lives *in* the POOM; lose the POOM with no journal and you've lost `M(d)`. "Hint status" for the live tree is real only *given* the digest's own later choice to make an on-disk canonical set + journal the truth — a builder decision, not a forced consequence. Fix: state the forced part as "the *choice of block boundaries* is free (M3); the *mapping information* is authoritative wherever it is stored," and relocate "live tree is a derived hint" out of "forced" into the persistence design, where it is contingent on designating journal+snapshot as truth.

**2. Implementation approaches → Persistence: "replay is robust to ordering" is unsound — it misapplies M12.** M12's order-independence is about *merge order on a fixed arrangement* — canonicalizing a given `M(d)` reaches the same normal form regardless of merge order. It says nothing about the order of *journal entries*. If the journal records arrangement edits (insert/delete/copy — the operation layer this digest itself defers), those edits do not commute (the note's own M15 cites byte deletion); replaying them in a different order yields a *different* `M(d)`, and canonicalizing afterward merely normalizes two different arrangements to two different forms. "Because canonicalization is order-independent, replay is robust to ordering" is a non-sequitur, and false for any journal with deletes/overwrites. Fix: drop the order-robustness claim (or restrict it explicitly to a commuting, per-position idempotent log and say so); justify partial-tail robustness by append-only + atomic records, not by M12. "Canonicalize after replay" stays — that part is fine.

**3. Implementation approaches → Width: "[dual per-dimension tumblers] invites drift" contradicts the note.** The note states Green's separate V-width/I-width tumblers are "maintained by immutability — no subsequent operation writes to an existing crum's width fields," so they precisely do *not* drift. The scalar recommendation is right, but for the right reason: it stores the count **once** (no redundant second copy to keep equal) and avoids the 2-D cumulative-sum machinery — not because dual storage drifts. Fix: replace "invites drift" with "stores the count redundantly"; note that immutability, not single-storage, is what keeps Green's dual form coupled.

**4. Implementation approaches → The store: "one enfilade serves both directions at once" conflates the per-document POOM with the cross-document spanfilade.** A 2-D (I×V) POOM enfilade answers I- and V-queries *within one document*. But "back-following" (find every document/V-position referencing a given content I-address) is a *cross-document* index — the spanfilade, which the note (M8) describes as coalescing I-spans *across* source documents and which the digest itself elsewhere calls "a sibling structure keyed by I." A single per-document enfilade does not deliver global back-references. Fix: separate the claims — building the POOM as a 2-D enfilade buys *within-document* I-indexed queries; the spanfilade is a distinct cross-document structure. Don't imply one enfilade covers both.

**5. Implementation approaches → The store: naming the `im` crate dips below design altitude.** "Realized over the `im` crate's structurally-shared map" names a library where a design digest should name the *property*. The design content — a persistent, structurally-shared ordered map so each document *version* shares nodes with its predecessor (cheap versioning, lock-free snapshot readers) — is exactly right and worth keeping. Fix: state the property and drop the crate name (or mark it as one instance). (`links.jsonl`/`paths.json` is already framed as "this repo's substrate," so that one is acceptable.)

**6. (Sharpening) Width / Decisions: surface that V-start and I-start may sit at *different* tumbler depths — that is *why* one scalar width works.** OrdinalShiftBase shifts each tumbler "at its own depth," and the note observes Green encodes "the same integer count at different hierarchical depths" (`#v` need not equal `#a`). That is the load-bearing reason a single scalar `n` advances both `v+k` and `a+k` correctly. The digest asserts "coupling is free" without this. Stating it strengthens the scalar pick and lets you surface the note's Open Question 4 (whether any depth-*relationship* is constrained) as a real builder-facing unknown.

**7. (Sharpening) Resolve: a well-formed content reference is necessarily an *ordinal* displacement (C0).** C0 forces the span's displacement to action-point = depth `m`, so a content reference reduces to `(start u, scalar count ℓₘ)` at depth `m` — the same (start, scalar-count) shape as a block, reinforcing the scalar worldview. The digest says only "level-uniform V-span"; add that the resolve input is effectively (position, count-at-depth-`m`), not an arbitrary span.

**Minor:** "How it fits" should keep the note's caveat that merge↔S3 is *only* S3's adjacent-only sub-case (M7 forbids the overlap general S3 admits); and commitment 5 should say *every* block is single-origin (M16b), not only canonical ones.

**Solid — leave alone:** The merge/canonicalize approach is the strongest section: consecutive-only merging (from no-overlap), a single confluent coalescing pass (M12), and the observation that the bidimensional I-adjacency test *already* subsumes both cross-origin (M16) and shared-I-extent (M14a) exclusions — with origin-prefix compare as a verified-cheap pre-filter (evidence Q5) — is accurate and well-grounded. "Guarantees to uphold" (by-construction vs. active-enforcement) and "Decisions for the builder" are sharp and correct, and resolution-as-pure-read with clip-on-output is the right call.
