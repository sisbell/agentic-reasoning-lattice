## Revision list

1. **Implementation approaches → effective-owner cache: the "never over-claims" reassurance is directionally wrong for authorization** `[SHARPENING]`. The claim "a stale hit can only under-resolve to an ancestor, the cache never over-claims" is true as a statement about a *resolver hint* (it never invents a longer match), but in this subsystem under-resolution-to-an-ancestor is precisely the privilege-escalation direction — it re-grants authority to a parent that *irrevocably delegated the subdomain away* (O8), which is the exact divergence the note exists to prevent. Reframe: the cache is a resolver hint that must be revalidated against the registry before it feeds any authorization decision; it is never an authorization shortcut, and its failure mode (returning the ancestor) is the unsafe one, not a "conservative" one.

2. **Implementation approaches → resolver/cache: leverage O6 (StructuralProvenance) — ω depends only on the account field** `[SHARPENING]`. The note proves `acct(a) = acct(b) ⟹ ω(a) = ω(b)` (O6): document/element fields are irrelevant to ownership. The digest caches per *address* (`address → owner`) and matches on full "tumbler components," leaving this lever on the table. Add: the resolver need only inspect/match against `acct(a)` (node+user), and the cache should key on `acct(a)`, not the full address — every address sharing an account field has one owner, so this strictly coarsens the cache (higher hit rate, far smaller) at no correctness cost. This is a note-supported simplification, not an invention.

3. **Implementation approaches → delegation gate: state that the gate *conditions* — not just the write — must be evaluated at the serialization point** `[SHARPENING]`. The digest correctly makes the journal append the serialization point and stresses baptize+register atomicity, but "≤1 principal per transition for free" covers only the *count*. Freshness (v) and authorization (ii) are TOCTOU-sensitive: two concurrent delegations that each pass the gate against a pre-append snapshot can both target the same fresh slot (→ O1b violation) or be invalidated by each other's top-down-order. Make explicit that condition evaluation must happen at/under the serialization point, not in a separate "check then append" phase.

4. **Subdivision/Decisions: tighten "authorize writes within its own undelegated subtree by containment alone"** `[SHARPENING]`. As written this overstates — containment authorizes only (a) *fresh allocations* under one's own prefix (where the next-slot allocator structurally lands outside every sub-delegate, so O5 holds by construction) and (b) *leaf* principals with no sub-delegates. A principal that has sub-delegated must still consult `ω` even within its own prefix, because containment cannot distinguish a delegated sub-position from an undelegated one — which is exactly the `owns([1], [1,0,2,0,3]) = TRUE` but `ω = π_A` case the next sentence gives. Bind the qualifier to the claim so the two sentences don't read as in tension.

5. **What must be built → Bootstrap (O14): add the missing O14.9 clause** `[SHARPENING]`. The bootstrap checklist lists eight of O14's conditions but omits O14.9 — `Σ₀.B` must itself be a well-formed ASN-0040-reachable registry. It's inherited from the ASN-0040 lean, but it's a real seeding precondition; name it so the bootstrap isn't built on an ad-hoc registry snapshot.
