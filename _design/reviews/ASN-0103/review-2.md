This is a strong, unusually well-grounded digest: the forced/conventional distinctions are accurate, the version-exclusion analysis is faithful to the note's load-bearing argument, and almost every Green claim traces cleanly to the evidence answers. The improvements below are real but mostly sharpenings of a sound piece; only the first three touch genuine defects.

## Revision list

1. **Implementation approaches → "Stateless recompute" bullet: drop or qualify "naturally correct after a crash."** The bullet sells statelessness as crash-correct ("it is naturally correct after a crash because the registry … is the authority"). This overstates and contradicts both the evidence and the digest's own durability section: Q20 shows Green's *stateless* mechanism is explicitly **not** crash-safe — address-find and index-insert are separate steps, so a crash between them hands out an id that was never recorded and can be re-minted ("monotonicity there is a property of normal execution, not a crash-safe invariant"). Fix: statelessness only buys you *no counter drift and no counter-recovery logic*; crash-correctness still depends on the registry insert being a durable, atomic commit reached before the id is returned (cross-reference the durability section). Do not let a reader conclude that recomputing-from-registry is crash-safe by itself.

2. **Entity registry and durability: tighten the attribution to Green.** "Use an append-only journal of baptism events, recovered by replay on load — the discipline udanax-green follows…" over-attributes. The evidence supports only that Green makes *allocation immediate insertion into the index* (commit = insertion) and that this is demonstrably crash-*un*safe at the find/insert boundary (Q20); it shows an in-memory enfilade backed by disk blocks, not a journal-and-replay-on-load. Fix: credit Green with the commit-by-insertion discipline **and** the worked example of its crash hole, and present journal-append-as-commit + replay-on-recovery as *your* fix for that hole, not as Green's mechanism. (Same crash-safety theme as item 1; the two should read consistently.)

3. **Add a missing builder consideration: creation is non-idempotent.** The digest never confronts a direct consequence of two of its own locks — "identity is the address (no value-based identity)" plus "stores nothing." CREATENEWDOCUMENT has no idempotency key; each call baptises a fresh address. Under at-least-once delivery, a lost response → client retry → an orphan duplicate empty document (harmless because empties can't dangle, but unintended, and reclamation is open per Q4). The "Commit point" decision covers *server* durability but not *client-facing* exactly-once semantics. Add a builder decision: where idempotency lives (e.g., a client-supplied request key at the session layer), noting the operation itself **cannot** be made idempotent without the value-based identity the note forbids — a clean Lampson tradeoff to surface explicitly.

4. **Subspace activation: reconcile "two sub-allocators" (note) with "three subspaces" (Green).** "What must be built" correctly says **content and link** subspaces (matching the note's CND.subAlloc: A_C(d), A_L(d) — exactly two), but the implementation section silently expands to **three** — "content, link, and type subspaces (1.x / 2.x / 3.x)." The type subspace (3.x) is a Green realization detail (Q14); the note's single link sub-allocator A_L(d) is realized by Green's link **and** type subspaces together. State this, so a builder doesn't mistake "three subspaces" for a spec commitment — and so the digest isn't internally inconsistent (two in one section, three in another).

5. **Decisions for the builder → Create-and-open coupling: fix which operation has the combined path.** "The green reference keeps them separate except for one combined copy-mode path" is imprecise. Per Q17, Green's combined create+open path is `open` with `BERTMODECOPY`, which creates a new **version** and registers it; for CREATENEWDOCUMENT specifically there is **no** combined path — bare document creation never opens, and even the internal open inside `docreatenewversion` is an implementation detail that authorizes the content copy, not a grant to the caller. Clarify that bare document creation in Green is always create-only.

6. **Implementation approaches → mark "persistent (structurally-shared) data structures" / "concurrent reads" as your recommendation, not Green's.** Green mutates the granfilade in place (`insertseq` rewrites `cwid` up to the root, Q19), and the note leaves concurrency open (Q2). Persistent structures are a fine clean-slate choice, but presenting them — and the "serving reads concurrently with the write" benefit — without flagging that they (a) diverge from Green's mutate-in-place mechanism and (b) presuppose a concurrency posture the note hasn't fixed could mislead a builder porting Green. Tie the concurrent-read benefit explicitly to the open serialization decision you already list.

Minor: the cost claim "bounded prefix-scan plus one index insert … (logarithmic in registry size)" is defensible — the granfilade is a balanced, B-tree-like tree (split/recombine/levelpush in the evidence), so the rightmost-descent max-query and the insert are O(log n) — but neither note nor evidence asserts a complexity bound, and the word "scan" understates that `findpreviousisagr` is a point-max descent, not a linear sweep. Either ground "logarithmic" in the balanced-tree structure or soften "scan."
