**1. Conformance-suite bullet ("What must be built") — the worked example is sold as a ready acceptance vector, but it tests none of the riskiest things this digest tells the builder to build, and the coverage claim is factually off.**
The bullet says the note's worked example is "a conformance suite ... Use it directly as the acceptance vector for the store, allocator, and index." It is a strong *invariant*-conformance vector on one static state plus a six-step extension — but it exercises none of the build targets you enumerate: it never restarts/replays (so **recovery** is untested); it always mints under an existing `d`, checking L1a only on the holds-case and never the reject-case (so the **home-existence gate** you call "real and must be enforced here" is untested); every link it builds carries a non-empty type (so **empty-type rejection at the create boundary**, your decision 6, is untested); and it has no concurrency. A builder who "uses it directly" will ship exactly the parts most likely to be wrong, untested. Reframe: keep it as the invariant-conformance vector, then explicitly require the acceptance tests it does *not* supply — a journal round-trip (create → restart → replay → identical store/index), allocation refused under an unregistered home, an empty/absent type specset rejected at create, and concurrent same-home allocation never reissuing an ordinal.
Also fix the precision error in the same bullet: **"L7 … is the only property omitted" is false.** **L12b (HomeDocumentPersistence)** is never exercised by the worked example either — it holds there only trivially because `Σ.M` is constant across all six steps. Since your own Guarantees table lists "No orphaned links (L12b)" as a guarantee to uphold, say plainly that this vector leaves L12b untested, and that L7 and L12b are the omissions.

**2. Forced-commitments list — "independently … removable" contradicts "immutable and append-only" on its face.** Two bullets above, you commit (forced) that "no entry is ever changed or removed"; this bullet then commits (forced) that same-valued links are "independently owned and removable." Read as hard constraints — which is what a forced list is for — these conflict, and "removable" invites a delete path the model forbids (and that "What must be built" / the Permanence guarantee both explicitly prohibit). You resolve this correctly, but only much later in the persistence approach. Move the gloss to the commitment: use the note's third adjective — "independently owned and independently **targetable**" (grounded in L13, no deletion implication) — and footnote that the note's word "removable" means object-identity independence, not a removal operation, of which there is none.

**3. Search index + decision 6 — higher-arity *search* (slots 4+) is silently dropped though L3 cites it.** L3 quotes Nelson on "n-sets supported in link storage **and search**," and the model admits arity > 3; your search-index bullet and arity decision address only storage arity and the three standard slots. Add a line: the note commits to *storing* N ≥ 3 endsets, but neither it nor Green specifies *searching* slots beyond 3; build the index for the three standard slots and treat higher-slot search as explicitly deferred, so a builder neither over-builds speculative slot-4 indexing nor is surprised that the model's "search" aspiration is unimplemented.
