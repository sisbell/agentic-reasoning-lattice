This is a strong, evidence-disciplined digest: it gets the big commitments right (identity-by-address, dual-primitive, non-transcludability), its approaches are sound (the append-only-journal/snapshot-as-hint framing is textbook Lampson), and it carefully separates *build* decisions from the note's *spec* open questions. The findings below are mostly sharpenings, with a few real accuracy/completeness gaps.

## Revision list

**1. Forced commitments / Decision 6 — state L3's non-empty-type conjunct as a forced commitment.** The forced-commitments list renders L3 as "≥3 endsets" but silently drops `e₃ ≠ ∅`. That conjunct is the *actual conformance boundary* between the model and the implementation — evidence Q5 shows `docreatelink` stores a two-endset/empty-type link whenever the client sends an empty type specset. Add to the forced list: *every conforming link carries a non-empty type endset (≥1 classifying address); the store rejects an empty/absent type slot at create.* Decision 6 already scopes the gate correctly (slot 3 only; from/to may be empty per L9/L7) — but the commitment should not live only inside a build decision.

**2. Forced commitments + "content-addressing" approach — fix the content/link contrast (accuracy).** The digest twice frames link identity as "the inverse of content-addressing" and says content-addressing "is correct for content." The note does not support content being value/hash-addressed: ASN-0036 content is *allocation-addressed*, append-only, and may hold duplicate values at distinct addresses. The note's own L14 table already gives the real axis of contrast — **transcludable vs non-transcludable** (and opaque-bytes vs structured-endsets) — which the digest states correctly elsewhere. Keep the operative warning (don't key the link store by a hash of the endset value — L11b forbids enforced injectivity; the allocator assigns identity), but drop the implication that this system content-addresses content, since the correct contrast is already in hand.

**3. "What must be built" / link search — specify count and stable pagination (completeness).** The note explicitly names a five-operation FEBE set including `FINDNUMOFLINKSFROMTOTHREE` (count) and `FINDNEXTNLINKSFROMTOTHREE` (paginate). The digest acknowledges the family but never translates count/paginate into *index* requirements — its index spec covers only find-overlap + identity-intersect. Even though the operations live upstream, the index built here must support efficient match cardinality and a stable result ordering + cursor. Surface these (the L5 evidence — Green returns endsets in I-address order — gives the natural ordering basis).

**4. "Implementation approaches: physical layout" — soften "self-describing address as the single source of truth" (grounding).** This recommendation presumes the content layer keeps *all* content in `s_C` — which the note lists as an **open spec question, not an invariant** — and it inverts Green, where the `infotype` tag (`istextcrum`/`islinkcrum`) is the authoritative runtime discriminator. State that the address reliably identifies *links* (L0), but that using it as the *sole* content/link discriminator additionally depends on global content `s_C`-residence; until that contract is fixed, keep the leaf-type tag authoritative (as Green does) or gate the recommendation explicitly on the `s_C` contract the digest already flags.

**5. "Implementation approaches: link search — In Rust this is an interval map…" — drop the language-specific specificity (altitude).** Neither the note nor the project context fixes a target language; naming Rust (and a concrete map type) is an unsupported drift below design altitude. Keep the design-level guidance (per-slot range/interval index; immutable/shared snapshots for cheap checkpoints); remove "In Rust."

*Sharpenings:*

**6. Usefulness — point the builder at the worked example as a conformance vector.** The note ships a fully-grounded single-link state plus a six-step extension that exercises every L-invariant non-vacuously (non-injectivity, link-to-link, arity-4, type discrimination, multi-span coverage-equality). That is directly usable as the acceptance/conformance suite for the store, allocator, and index — a concrete builder asset the digest currently omits.

**7. Allocator approach — lead with the simpler default.** The digest recommends the cached high-water hint ("I'd pick this") up front, while elsewhere it rightly says "add the index when scale demands it." For consistency, present *stateless query-and-increment* (the verified Green approach; the store **is** the counter, no duplicate state to drift) as the default, and the per-home high-water hint as the scale-driven optimization once the bounded max-under-prefix query proves hot.

**8. "Forced commitments" — StateExtension is a definition, not an invariant.** "The whole-state StateExtension relation is the journaling discipline stated as an invariant" mislabels it: `⊒` is a *relation/definition* the lemmas use; the per-transition append-only invariants are L12/L12a (links), with S0/S1 and document monotonicity for the other stores. Minor wording fix.

**9. "Conventional" list vs Decision 6 — reconcile "fixes arity at 3."** The conventional list says the reference implementation "fixes 3," which decision 6 then contradicts (Green can emit a two-endset link). Say the reference *API* takes three specsets but can store fewer when the type specset is empty — so the digest doesn't assert and retract the same fact.

Sections that are genuinely solid and need no change: the type-matching/hierarchy/ghost-type treatment, the extensional-vs-coverage two-equality distinction, "do not reify allocation events," and the disciplined separation of build decisions from the note's spec-level open questions.
