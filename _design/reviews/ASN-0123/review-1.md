Skeptic's review of the ASN‑0123 digest. It's a strong, well-grounded digest; the issues below are the most valuable improvements, real defects first.

---

**1. Design commitments → "The composite is the atomic unit. [forced]" (and Guarantees → "Global uniqueness … no cross-node coordination needed"): both treat composite-level serialization as settled, which the note explicitly leaves open.** The note's atomicity remark is emphatic that the foundations do *not* make the composite a unit — at the interior state (v allocated, `M(v)=∅`) "nothing in the foundation forbids another composite from beginning," and "what serialization concurrent forks require is among the open questions" (OQ4). What is forced is only the *boundary invariant*: the terminal boundary carries v together with its snapshot and provenance (couplings initial-to-final), so no *completed* VERSION returns a torn version. Interior states are reachable; Green's non-observability of them is an *implementation* property (single-threaded run-to-completion, evidence Q8), not a spec guarantee — so the gloss "must never be externally observable; only interior states show that" overstates. Relabel: boundary-carries-full-effect = [forced]; composite-as-indivisible-unit / concurrent-fork serialization = implementation obligation + OQ4. Same correction for "global uniqueness needs no coordination": it holds across *prefix-disjoint* namespaces, but two concurrent forks of *one source* compute the same frontier `c_{hwm+1}` and collide unless the allocation step is serialized (the abstract model assumes this via SequentialTransitionAxiom; Green supplies it by single-threading). That serialization is exactly the concurrency policy the digest's own "Decisions for the builder" demands — resolve the internal contradiction.

**2. Design commitments → "ancestry is read by truncation; rank by the final component" omits the VD discipline that makes it sound — a load-bearing commitment.** The note proves the address encodes *allocation lineage* unconditionally but warns (V5a, VD, [LM 4/29]) that decoding it as *derivation/rank* is sound only if version namespaces are populated by forks alone — and it names a live counter-client: ASN-0047's J4 allocates into `A_v(d_src)`, and "any discipline-conforming K.δ may take the frontier," so one interleaved non-VERSION allocation gives the k-th fork a rank > k. This is OQ1. A builder who implements VERSION and later adds *any* other operation that can allocate into a version namespace silently corrupts rank/ancestry decoding. Add the commitment ("address-encoded ancestry/rank decode correctly only under VD — nothing but forks may allocate into a version namespace") and the corresponding builder decision ("enforce VD, or accept rank = allocation order ≠ fork order").

**3. Implementation approaches → Provenance recording: drop the claim that the address→document reverse index "makes link carry-through … computable."** Per V10, carry-through to a given version is computed from `ran(M(v))=A` and the (unchanged) link store via LP12 — R never enters, and the note stresses "zero per-link work … a consequence of the address algebra, not a migration," which the digest *itself* restates correctly under "How it fits." The reverse index (= Green's spanfilade / FINDDOCSCONTAINING, evidence Q12/Q17) is what makes *version correspondence* and *cross-owner version discovery* (V9w, V7's downward limit) computable — not carry-through. Rewrite the clause to attribute the reverse index to correspondence/cross-owner discovery only, removing the contradiction with the digest's own "zero per-link work."

**4. What must be built → Ownership resolver (and the contract generally): surface P-tier's domain restriction.** P-tier (`ω(d_src)=π ∨ zeros(pfx(π))=1`) is part of the contract: the cross-owner branch is defined *only* for an account-tier forker, because a node-tier non-owner commands no document-producing namespace and forking a foreign doc would require minting both an account and a document — outside VERSION's single-identity domain. The digest's "the forker's account, for cross-owner" silently assumes this. State it: cross-owner forks require an account-tier forker; a node-tier principal forking a document it doesn't own is out of domain (reject or route elsewhere). This is also the hook for Green deviation 4's FEBE mis-anchoring bug — correct cross-owner placement depends on honoring P-tier.

**5. Implementation approaches → Registry / Arrangement-snapshot C: state the implementation-substrate assumption rather than presenting "the `im` target" / `OrdMap` / the `links.jsonl`/`paths.json` pattern as established.** Nothing in the note or evidence establishes a Rust/persistent-immutable-structure target; the structural-sharing default (C) and the single-`OrdMap` registry are *sound only on* such a substrate (on a mutable B-tree, C's "snapshot-for-free via copy-on-write" does not hold). The digest already hedges C with "[recommended for `im`]," so make the premise explicit once ("assuming a persistent-immutable-structure engine") and keep the recommendations contingent on it, instead of treating the target as given.

**6. What must be built → Provenance recorder: "adds exactly the dual rows {(a, v)}" mislabels what the fork writes.** The fork writes only the *version-side* rows `{(a, v) : a ∈ A}`; the source-side rows `{(a, d_src)}` already exist (P4★ at the boundary). The "dual" provenance (V9w) is the *coexistence* of both, not two rows the fork creates. Reword to "adds the version-side rows `{(a, v)}`, which together with the pre-existing source rows form the dual witness (V9w)."

---

**Solid — leave as-is:** the origin-addressed-not-content-addressed caution under "How it fits" (catches precisely the value-identity/dedup trap the spec forbids); the treatment of Green deviation 4 as a security boundary with client account as untrusted input; the hold-by-construction vs active-enforcement split; and arrangement-snapshot C's per-subspace-map framing, which enforces the V2/V2b content/link boundary structurally.
