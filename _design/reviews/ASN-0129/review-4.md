# Revision list

**1. [DEFECT] — "What must be built" / "Evaluator" / "Guarantees": PC2a's third aggregation operator `max_{T1}`/`min_{T1}` and the "ordinal extrema, scoped" commitment are missing entirely.** The digest names only `count` and `⋃`-folds ("reserve full materialization for `count` and the union folds"); `max_{T1}`/`min_{T1}` appear nowhere ("max"/"extrema"/"latest"/"ordinal" are all absent). This drops one of the *two* commitments the note says ride on PC2a. Two consequences a builder gets wrong: (a) the evaluator must implement the extrema folds — single-pass, `⊥`-at-empty, composing through PC2's binder guard — or it cannot evaluate terms that use them; (b) the per-home scoping is a real semantic gotcha the note flags — `max_{T1}` over link addresses recovers emission order *only within one home's chain* (ordinal-time doctrine, BH4); cross-home T1 comparison is well-defined but temporally meaningless, so any "latest" built from it is per-home-scoped. Add the extrema operators to the buildable aggregates and the per-home-scope caveat to the commitments/guarantees.

**2. [DEFECT] — "What must be built → Base read adapters": "`count(elems(chain(t)))` reads the walk length" is false at view `default`.** The note limits this equation to active/audit: at `default`, `chain` returns the UV-rewritten sequence, *strictly shorter* than the walk whenever a traversed element is filtered (the traversal is unchanged; only the returned sequence shrinks). State it as: `count(elems(chain(t)))` is the *returned-sequence* length — the full walk length at active/audit, the shorter filtered length at default. (`elems` is count-faithful at every view; it is only the "= walk length" identification that is view-restricted — and the note makes a point of this, since it drives the default-view footprint increment in FP.)

**3. The digest's instance-wise rule already handles it correctly; add a clause surfacing the route so a builder/protocol-author knows cross-`Reg` BH3 data is queryable.

**4. [SHARPENING] — "Dynamics analyzer" / "How it fits": PD2 is compressed to "frame-stability falls out of footprint plus the step frames."** That is the right analyzer *mechanism*, but the note's three *named* active-view non-interference exceptions are the practical gotchas it tells you to "name … or be surprised by": retraction (`[R]` shrinks any active slice), BH4 same-home deposits of any type (advance `age`), and `targets_keyed` (reads every BH3-attached Binary slice). The ingredients are scattered across the digest (BH4 home-wide footprint, `targets_keyed` cross-type, active = audit − nullified); consolidate them as the explicit PD2 non-interference rule a protocol author reads off the analyzer's output.

[SHARPENING] — "Evaluator"/"Vocabulary": make PC6's converse rationale explicit.** `Observe_K`'s pattern query *is* a QD filter over V-TUP per-tuple coverage tests (a per-tuple conjunction — "this one active tuple's F covers x and its G covers y₁,y₂"). The digest builds V-TUP and treats `Observe_K` as a primitive adapter but omits the load-bearing "why."
