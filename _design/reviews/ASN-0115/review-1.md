This is a strong, well-grounded digest: the forced/chosen split is accurate, the "don't hash-address content — it violates origin identity (S4)" catch is exactly the soundness check this review exists to surface, the "bounded scan, not set-intersection against an effectively-infinite point set" insight is the right common-case-fast hint, and the "enforce ordinal-level at the gate, stricter than the reference" recommendation correctly turns the note's Confinement lemma against the Green read-path footgun (Q19/Q1). The "by construction vs. active enforcement" framing of the guarantees is genuinely useful. The defects below are mostly under-argument and misgrounding, not misreadings of the note's commitments.

**Revision list, most-important-first:**

1. **"Implementation approaches" (Byte-opacity/coalescing) and "Decisions for the builder" (run granularity / wire segmentation): "coalescing is a representation choice invisible to the contract" is asserted, not argued, and it buries a load-bearing commitment the note devotes a whole corollary to — *span width is a tumbler boundary, not a count*; delivered quantity for a spec = |act|, and (evidence Q14) delivered bytes ≠ sum of V-widths.** Add width-is-not-a-count as a named commitment. Then *justify* the invisibility claim instead of stating it: coalescing contiguous (V, address) runs is contract-safe only because R5 leaves intra-run boundaries implicit and R6's terminal-overrun keeps every gap at a run's *end*, never interior — so the gap is the segment boundary. That same argument exposes the constraint the digest currently presents as a free choice: you must **never coalesce across a gap**, and because byte-length cannot reveal how many positions a run covers (width≠count), a caller's R6 gap-diff depends on segments staying gap-aligned. Surface that constraint where you list "wire segmentation" as open.

2. **"Guarantees to uphold" (the one legitimate failure): "the named document must be *allocated/open*" conflates a forced note precondition with a Green-only gate.** The note's sole document precondition is `d ∈ dom(Σ.M)` (allocation); it does not model "open" — that is Green's session/BERT check (evidence Q15/Q17/Q20). Stating "allocated/open" as the contract's sanctioned failure promotes an implementation gate to a guarantee. Fix: the note-forced failure is *non-allocation*; the open/access check is an additional Green gate outside the note's model — keep it where you already correctly have it (the "placement of the access/open check" builder decision) and don't fold it into the contract.

3. **"Implementation approaches" (Content store): the repo-substrate grounding is misgrounded.** This is the spec-*authoring* repo; `links.jsonl`/`paths.json` and the "bitten this substrate before" concurrency history belong to the note/review tooling (cf. the memory's fleet double-close note), not a docuverse content store. "This maps directly onto this repo's working substrate" overstates an analogy and could send a builder hunting for reusable infrastructure that is not the target system. Fix: present append-only-journal + replay-rebuilt-index as a general technique well-suited to permanence-by-construction (which is the real point, grounded in R11 + Q20); drop "maps directly onto this repo's substrate" and the file names unless you can cite a content-store use of them; if you keep the atomic-write caution, frame it as a general concurrency hazard, not this system's bug history.

4. **"Implementation approaches" (Arrangement representation): `im::OrdMap` is a code-level reference — lift to altitude.** Replace "an `im::OrdMap` keyed by tumbler" with "a persistent ordered map keyed by tumbler (HAMT or balanced tree with structural sharing)" so the recommendation names the load-bearing properties (bounded range scan; O(1) structurally-shared version fork) rather than a specific library type.

5. **(Sharpening) "Design commitments" / "What co-delivery does": surface that genuine transclusion is content-only (R8's vacuous link sub-case).** "No deduplication" is stated generically; add the note's structural result that distinct link positions can *never* share an address (CL-OWN + CL-UNIQ), so the never-dedup rule's transclusion case only ever arises for content, and the lone link multiplicity is one position named by two overlapping specs (which legitimately delivers the same reference twice). A builder otherwise wonders whether link-transclusion needs handling; it cannot occur.

6. **(Sharpening) "Implementation approaches" (Repeatability): note R7 is a sufficiency, not a biconditional.** Equal arrangement restriction ⟹ identical delivery, but identical delivery does *not* imply unchanged arrangement — S4 permits rebinding to a distinct, equal-valued address, leaving the bytes identical while the restriction changed. Builder consequence to add to the snapshot-pin recommendation: a delivery cache must be keyed on the consulted arrangement *value*, never inferred from or invalidated by output byte-identity.

7. **(Sharpening) "What must be built" (request gate): one line that an odd subspace start (`s₁ ∉ {s_C, s_L}`) is harmless, not a special case.** The note shows such a spec delivers nothing (the unused subspace is empty at every reachable state, so `act = ∅` falls out), so the gate need not reject it — saving a builder a needless validation branch.
