This is a strong digest. Before the revision list, the things it gets right and that I therefore won't belabor: the permanent‑stored / live‑recomputed split is the correct spine and is drawn cleanly; the forced‑vs‑conventional labels are accurate throughout (I checked each — tightness and the subspace‑partition convention are correctly the only "conventional" ones); no proposed approach actually *violates* an ASN‑0098 commitment (the dense‑V‑position one relaxes ASN‑0047 shape, not this note's laws, and says so); the green grounding is careful and evidence‑backed with no fabricated source‑level claims; the reverse‑index keying analysis (coverage‑keyed + filter‑live, never home‑scoped) and the insertion‑model decision are genuinely useful and correctly grounded; and LP20's image‑vs‑projection distinction is handled correctly where most digests would blur it.

The improvements, most important first:

**1. Arrangement+edits / Decision #5 — narrow the "no requirement of LP9–LP21" claim and reconcile it with the digest's own contraction description.** The digest says relaxing D‑CTG★/D‑SEQ★ for dense V‑positions is "a tradeoff against *other* ASN‑0047 reasoning, not against this note, since that contiguity is … no requirement of LP9–LP21." That is true for LP9/LP10/LP11/LP20/LP21 (their proofs use only E1/E2, subset+agreement, the bijection, and coverage) — but **false for LP12a, LP12b, LP19, LP19a, which are all in this note and are formulated over the D‑SEQ★/canonical structure**: LP12a's retention set `R` *is* the per‑subspace D‑SEQ★ prefix union, LP12b's parameters are subspace prefix counts, and LP19/a concern canonical spans against contiguous emission. So the dense model — which the digest *recommends* ("I'd take dense/stable V‑positions") — reshapes `R` away from a prefix, which directly contradicts the same section's "contraction = remove a D‑SEQ prefix's complement," and means the pre‑edit survival check (LP12a, the wp the digest tells the builder to implement) must be **re‑expressed** over the new arrangement shape, not inherited verbatim. The core identity `project(Σ′) = project(Σ) ∩ R` does survive for any `R`, so the fix is precision: scope the contiguity‑free claim to LP9–LP11/LP20/LP21, and state explicitly that LP12a/LP12b/LP19 are phrased over the contiguous/canonical shape and require re‑derivation under dense V‑positions.

**2. Projection approach — the inverse arrangement index is multi‑valued, and the digest models it as if it weren't.** It says "model `M(d)` as a persistent ordered map V→I" (correct — `M(d)` is a function) and "keep an I→V index." But within a single document one I‑address can sit at multiple V‑positions (the POOM is a multimap — evidence Q3, SS‑POOM‑MULTIMAP; and the note's `project` returns a set that may hold several `v` mapping to one covered address, which LP20's image then collapses). A builder who implements the inverse as a plain map silently drops projected positions. Fix: state that the I→V index must be a multimap and that projection can return several V‑positions per coverage address.

**3. Projection approach — the LP‑Fin justification for the inverse index is imprecise on both its precondition and what it actually buys.** Two problems with "LP‑Fin guarantees only finitely many allocated addresses fall in any canonical span's reach, so you … filter the (finite) arrangement": (a) LP‑Fin requires the span start `s ∈ F` (substrate‑emittable) — true for tight/allocated‑rooted spans, not for arbitrary endsets; state the precondition. (b) Termination of the interval query comes from `ran(M(d))` being finite (always true), not from LP‑Fin; LP‑Fin's real contribution is bounding the *per‑span result size* to `n` for `F`‑rooted canonical spans, which is what makes the lookup cheap rather than merely terminating — attribute it correctly. While there, fix the half‑step: "intersect coverage's intervals with the document's I‑range" yields the *reached I‑addresses* (LP20's image); recovering the projection (V‑positions) needs a final I→V lookup through the (multimap, per #2) index.

**4. "What must be built" / discoverability — surface that the existential runs over *all* slots, including the always‑non‑empty type endset.** The test "does any slot's projection through a document hit" is correct, but the digest never notes that the existential in `discoverable_from` ranges over every slot `1..|L(a)|`, and L3 forces slot 3 (type) non‑empty. Consequence: a link is discoverable from *any* document that arranges its type endset's coverage, so a coverage‑keyed reverse index returns links by type‑coverage too, and "this delete will break N links here" counts type‑slot reach. Surface this so the builder decides whether reverse‑discovery and the survival count should weight, isolate, or exclude the type slot.

**5. Discoverability+reverse index — make the index's query model explicit and wire the survival check to it.** "A reverse index from content I‑address to link addresses" reads as a point map, but coverage is a *dense interval set*; the index must be a spatial/interval index over coverage spans supporting **stabbing** (I‑address → covering links) and **overlap** (a removed range → reaching links) queries — which is precisely what green's spanfilade is. Separately, the pre‑edit survival check is listed as its own capability but never connected to this index; in practice it enumerates candidate links by overlap‑querying the to‑be‑removed positions. Wire them together.

**6. Guarantees / subspace integrity — surface the mechanism under LP12b, not just its sensitivity.** The digest cites LP12b for "projection is sensitive to the subspace partition of a deletion." The design‑relevant fact behind it (LP‑Fin Corollary) is that a canonical content‑subspace span's coverage is *subspace‑pure* — disjoint from the link store. That is what justifies indexing content‑reaching and link‑reaching discovery separately, and what explains why emptying the content subspace orphans a content‑canonical link from that document *regardless* of retained link positions. Stating the mechanism converts a sensitivity warning into actionable index structure.

**7. (Minor) Design commitment #7 — the "never move it" list is incomplete.** "allocation, link‑allocation, document‑registration, and provenance‑recording (LP6–LP8, LP14)" omits K.δ in the Node and Account cases, which the note explicitly classifies as non‑displacing under the same arrangement‑fixing template. The *displacement* catalog is complete; the non‑displacement list isn't. Add Node/Account.
