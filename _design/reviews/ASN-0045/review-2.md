## Revision list

**1. Implementation approaches (sum-type bullet) — the "name-free core" passage misattributes the note's circularity argument.** The digest says T4c "is a separable derived fact used only for reporting, and reading *exclusivity* off it would be circular." The note's circularity warning is not about exclusivity — it is about *membership*: in the **at-least-one** step it warns against reading `zeros(t) ∈ {0,1,2,3}` off T4c's "bijection on {0,1,2,3}," because the bijection *presupposes* that membership. The **at-most-one/exclusivity** step rests on a different point — `zeros` is single-valued and 0,1,2,3 are distinct numerals, and the note says T4c's *injectivity* "does no work here" (unnecessary, not circular). Fix the attachment: circularity belongs to the membership step; for exclusivity say T4c's injectivity is *not needed* because the zero-count is single-valued and the numerals are distinct.

**2. Implementation approaches — repo-infrastructure claims are ungrounded and one is load-bearing for an argument.** "Append-only journal," "paths.json-style registry," "the oracle pipeline can emit the classifier directly from the Dafny spec," and "don't reach for `im`" appear in neither the note nor the evidence. They are plausibly real repo context, but the admission-gate recommendation is justified *by* the journal/registry substrate ("addresses are the keys into the append-only journal and the paths.json-style registry"). The recommendation (validate once, at the boundary) stands on general principle regardless — so either attach a pointer that grounds the substrate or soften it, so an unverified detail isn't carrying a sound conclusion. Same for the Dafny/oracle-pipeline suggestion: keep it, but mark it as contingent on that toolchain existing.

**3. Implementation approaches (On Green's encoding) — sharpen the interop consequence of the double-zero terminator.** The digest correctly says "borrow structure, not bytes," but stops short of the load-bearing instruction. The evidence shows Green's account terminator is a *double* zero (`defaultaccount` = `1.1.0.1` array-padded, scanned by `tumbleraccounteq`), which is exactly the adjacent-zero pattern T4-valid *forbids*. State the resolution: Green's double-zero is an array end-marker, not a logical separator, so Green's *logical* tumblers (e.g. `1.1.0.1`, one separator) **are** T4-valid — but raw Green arrays must be **decoded before** running the T4-valid scan, or the terminator reads as a forbidden adjacent-zero and valid addresses get rejected. That is the concrete builder hazard.

**4. Implementation approaches (parse-once option) — "validity becomes 'parse succeeded'" is only true for a *validating* parser.** A naive split-on-zeros does not catch leading/trailing/adjacent zeros (these surface as *empty* fields) or over-depth (>4 fields). Add: parse-success equals T4-valid only if the parser rejects empty fields and caps at four; otherwise a builder gets a parser that silently admits invalid shapes while `populated-count − 1 = zeros` quietly overflows on the five-field counter-example.

**5. Decisions for the builder (What Invalid carries) — note that failure reasons co-occur.** The four counter-example rows make good diagnostic categories, but they are not mutually exclusive: `[0]` violates leading *and* trailing; `[0,0]` violates leading, trailing, *and* adjacent. So "report the reason" is itself a decision — first-failure vs. full set — which the current text glosses. Surface it.

**6. How it fits (Leans on ASN-0034) — "the ℕ-ordering facts under Partition are inherited, not re-proved here" understates what ASN-0045 does.** The ℕ *axioms* (NAT-order/discrete/addcompat) are inherited; the `0 ≤ n ≤ 3 ∧ n ∈ ℕ ⟹ n ∈ {0,1,2,3}` *enumeration* is derived in ASN-0045 (it is the heart of at-least-one, and the note labors over it precisely to avoid the circular shortcut). Reword so "inherited" attaches to the axioms, not to the enumeration result.

**7. Guarantees to uphold (Level stability) — flag it as contingent, not inherited.** It is listed flatly alongside Partition and Off-Domain Vacuity, but the note says nothing about address mutability; stability follows *only* from the implementation decision to make addresses immutable. The digest half-acknowledges this ("Were addresses mutable, you'd demote it"), but should mark the guarantee itself as conditional on that choice rather than as a note-level property.

**8. Decisions for the builder (degenerate empty tumbler) — defer to the note's own totality claim rather than guessing.** The note asserts T4-valid is total on T (well-formed for any `t : T`), so the empty-tumbler answer is *already fixed* at T0/T4 — the builder should adopt that resolution, not independently pick "presumably Invalid." Add the prior question: does T0's carrier even admit the empty sequence? If not, the case is moot; if so, the `t₁ ≠ 0` / `t_{#t} ≠ 0` clauses have no element to test and the resolution must come from T4's definition, not the classifier.
