# Revision list

**1. [SHARPENING] Implementation approaches → Certification: "three distinct reasons" undercounts PR5a's four checks.** The note runs `(0)` predicate-sort, `(i)` active-target, `(ii)` well-posedness, `(iii)` ST⁺. The digest's approach enumerates only 0/ii/iii (non-predicate, ill-posed, unknown) and gives remediations for two of them — omitting check `(i)` (de-registered target → "re-register first"), which the note treats as load-bearing (parallel to PR0(iv): "new endorsements are not issued against withdrawn registrations"). The build list *does* carry "active target," so nothing is missing from the digest as a whole, but the diagnostic framing should name the fourth refusal and its remediation, or rephrase to "three term-property reasons *plus* the active-target precondition," so a builder's diagnostic/remediation surface is complete.

**2. [SHARPENING] Guarantees → Structural-reads-only vs Implementation approaches → Resolution/expansion: reconcile the two.** The guarantee is phrased for the materialize-then-evaluate model ("*the* pure term handed to ⟦·⟧ carries no references") and warns that "a builder who defers reference resolution into the evaluator silently breaks it" — while the *recommended* approach is DAG-recursive evaluation with no materialized flat term. These are consistent but the connection is never drawn, and DAG-recursion is exactly what a careless builder would implement as the forbidden deferral. Add a line: under DAG-recursion, reference-node handling stays in the evaluate *operation* (which reads content to resolve referents, exactly as `resolve`/`expand` are licensed to), and ⟦·⟧ is invoked only on reference-free PL constructs with referent *values* already substituted — so structural-reads-only holds; the forbidden move is making ⟦·⟧ *itself* resolve references.

**3. [SHARPENING] Guarantees → Acyclicity: grounds the DAG in the wrong condition relative to the note.** The digest attributes acyclicity to "the typing gate's ever-registration condition" (iii); the note's PR2(a)/(b) and the formal-claims extraction both argue it via the *active*-registration condition (iv). Ever-registration genuinely *does* suffice for the strict deposit-order (at D's earliest deposit, each referent is in `L_pdef` at the pre-state, hence deposited strictly earlier; self-reference fails at first registration because D's start is not yet ever-registered) — so the claim is true and arguably the cleaner ground, since the DAG is a fact about *ever-registered* definitions. But the phrasing "references can only name already-(ever-)registered definitions" understates the actual registration constraint: new references must name *actively*-registered definitions (iv), not merely ever-registered ones. Note the divergence from the note's proof and keep the stronger (active) constraint visible.

**4. [SHARPENING] Implementation approaches → Certification: make ST⁺'s per-instantiation semantics explicit.** The digest conveys the parameter-reading *mechanism* (bound constant, aggregate-threshold extension) but not what the certificate *asserts*: ⊤-stability for *every* `Γ_D`-instantiation of `expand(a)` — the note's "once true at a reachable Σ for given `args`, true at every →_sh*-successor for the *same* `args`." This is what lets a single certificate bind at every `evaluate` call whatever arguments the caller passes; state it.

**5. [SHARPENING] Implementation approaches → Certification / What must be built: mark the universal lint as snapshot-relative.** The note is emphatic that the lint's verdict "carries no standing guarantee" — a later registration or `pd_stable` retraction can falsify it. The digest covers this in principle under "single-coherent-pre-state reads," but the lint specifically should be flagged as a *retrospective, point-in-time* check (sound only about the one committed state its reads pin to), not a standing invariant, so a builder doesn't treat a passing lint as durable.

**6. [SHARPENING] Two minor items.** (a) Add to **What must be built** an explicit step "register the two designated classes — `pdef` Multi, `pd_stable` Unary, both idem=⊤, behaviors=∅, surface-sealed, with pairwise non-collision checks" — currently present only in the commitments and "How it fits," absent from the build list. (b) In the "if you must cache" sub-point, the de-Bruijn/locally-nameless + hash-consing representation (for *interning* the cached form) and the monotonic-counter fresh-name scheme (for a *named* representation) are alternative representations presented somewhat entangled; separate them — a name-free form doesn't need fresh names, a named form doesn't get interning.
