This is a strong, unusually actionable digest — the fan‑out diagnosis and the surgical fix (replace the lockstep merge with a real join, reuse the enumeration wholesale) is its centerpiece and is precisely grounded in the evidence (Q15/Q16 + Deficiency 1). Below are the improvements worth applying, real defects first.

---

**1. "Design commitments": R3 (deterministic presentation) is binding, but the digest demotes it to a downstream "guarantee" and overstates presentation freedom.** X12 lists R1, R2, **and R3** as binding postconditions; only R4 (the specific canonical form) is non‑binding. The digest says "Both soundness and completeness are binding… Forced (R1+R2)" and "Denotation is fixed; presentation is free. Conformance is denotational." That elides R3: *report* conformance is denotational (R1+R2), but a conforming *implementation* must additionally emit its report as a deterministic function of the inputs. Read literally, "presentation is free" licenses nondeterministic pair ordering — which violates R3. Fix: make the binding set R1+R2+**R3**; recast "presentation is free" as "presentation **granularity and packing** are free (R4), but the implementation must fix **one deterministic** presentation (R3, binding)." This also reconciles the commitment with your own (correct) "Determinism — enforced" guarantee.

**2. The exact semantic contract of a single pair (X10) is missing — and the note makes it one of three core deliverables.** The note opens by naming what must be delivered, the second being "what an ordered pair of spans is, and exactly what a reader may conclude from one." X10 pins it: a pair asserts its two spans realize the *same address sequence* (hence same value sequence), *in the same order*, and **"asserts nothing else — nothing about neighbouring positions, nothing about how the sharing arose, nothing about any other state component."** The digest delivers the positive (certification) but never states this *bound*. It is load‑bearing for the very consumers you hand the report to (diff/merge views, transclusion‑provenance displays): without it they may over‑read a pair as implying contiguity, provenance, or neighbor‑correspondence. Add the bound to "Guarantees" or the "How it fits" handoff, and note it is *why* the minimal record (doc, start)×2 + width suffices — there are deliberately no provenance/neighbor fields.

**3. "Implementation approaches → Matching": the interval‑join default's rationale conflates the (shared, proven) resolver with the (broken) matcher.** You justify the default as "the proven structure with the one corrected step… keep the reference's efficient interval intersection **and bounded traversal**." But bounded traversal — the sub‑range walk, the real locality dividend (Q17) — lives in the **resolver** and is mandatory for *either* matcher; the hash‑join also resolves only the window. The interval *intersection* is the only matcher‑specific piece of the interval‑join, and it is optional sugar, not the load‑bearing part — the proven, reusable thing the evidence vouches for is the bounded‑traversal resolution + restriction that *faithfully enumerates fan‑out*; the pairing on top is exactly the broken step. So the matcher choice (interval‑intersection vs. hash‑multimap) is a pure post‑resolution join decision, independent of bounded traversal, and by "prefer the simple thing" the hash join is the natural greenfield default. Fix: separate the resolver decision (bounded traversal — required, shared by both) from the matcher decision, and re‑justify the default on the *real* tradeoff (interval = block‑preservation / less presenter coalescing; hash = simplest, obviously fan‑out‑complete) rather than on "keeping bounded traversal."

**4. "Design commitments": "Restricting to the content subspace… Forced (X9)" mis‑cites what X9 proves.** X9 proves the restriction is *lossless* (link instances carry no cross‑position/cross‑document/cross‑operand correspondence), not that it is *forced*. The forcing is X12's precondition. Tighten to: "lossless by X9, made binding by X12's precondition." Minor, but the citation currently attributes forcedness to the wrong claim.

**5. "What must be built / Guarantees": surface X4c as the clipper's contract.** Window‑exactness is stated as an outcome, but X4c — the sharper fact that clipping a maximal run to a *single‑span* window yields **at most one contiguous pair**, not a fragmented set — is not surfaced. It bounds the clipper's output (one block in, one block out) and confirms that refragmentation arises *only* from rearrangement (X7), never from clipping. Worth one line so the builder doesn't conflate the two.

**6. "Implementation approaches → Snapshot": "one snapshot per document named" should say one consistent Σ.** corr is evaluated at a *single* Σ (X5 reads `res_Σ|P` and `res_Σ|Q` at the same Σ); resolving two named documents at different states yields a relation valid at no single Σ and breaks determinism (R3). State that all named documents must be resolved against **one consistent snapshot** — which the persistent‑reference approach gives for free, but an explicit‑lock approach must arrange explicitly.

**7. Two minor precision fixes.** (a) "What this is": "span‑pairs that resolve to the same stored content" reads as value‑equality in the *first* sentence, undercutting the address‑not‑value commitment two lines later — say "the same stored occurrence / content address." (b) "Resolving a region": the Rust/`im` target is assumed, not established by the note; if it is the project's stack this is fine, otherwise present the persistent ordered map as one option rather than the named target.
