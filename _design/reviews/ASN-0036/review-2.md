This digest is accurate on the note — the forced/deferred split is correctly drawn, no guarantee is misstated, and its Green claims (`levelpull` disabled, height floors, `isanextensionnd`, `acceptablevsa` stub, the two-blade knife) are all grounded in the evidence rather than fabricated. So the real work is in tightening the implementation approaches, where most of the design content lives.

## Revision list

**1. "The arrangement — run representation" and "Contiguity and subspace alignment" give contradictory data-structure advice; unify them.** The arrangement section recommends "an ordered map keyed by V-start" (absolute V-keys). The contiguity section then says absolute/explicit tumbler keys force `O(n)` renumbering on insert and recommends implicit positions instead. "Keyed by V-start" *is* the thing the later section warns against — and since the evidence shows both text (`1.x`) and links (`2.x`) are append-contiguous, there is no established subspace where absolute V-keys are even motivated. **Do this:** make the single recommendation a run-list with *implicit* V-positions (each run carries `(I-start, length)`; a run's V-start is the prefix sum of preceding run lengths), held in a balanced tree carrying subtree length-sums — `O(log #runs)` positional lookup *and* `O(log #runs)` splice with no renumber. This is the central "what to build" decision; right now a builder following the arrangement section literally builds the `O(n)`-insert structure the digest elsewhere tells them to avoid.

**2. "Decisions for the builder" / "The content store": surface the Val-heterogeneity decision (the note's open question 1), which the evidence answers directly.** The digest treats `Val` as fully opaque and never raises whether the store holds uniform text or heterogeneous content. The note explicitly asks this, and the evidence settles the Green answer: text content *and* link objects both live in the store as **untyped tumblers** — the type distinction is carried by the V-position's *subspace*, not by the value. **Do this:** add a builder decision and a one-line commitment: content values are heterogeneous and stored without runtime type tags; type lives in the V-subspace, not in `Val`. This also reinforces why the content store can stay value-oblivious (S4).

**3. "The arrangement…": "queries are representation-independent" is overbroad as stated.** It is true for *content/positional* queries (what I-address is at `v`) but false for *structural* queries that expose run/span count or boundaries — the same arrangement has different run counts in non-canonical form, which is exactly the evidence's `span_count: 1` vs. fragmented observation. As written, a builder could expose "number of spans" and be surprised it is representation-dependent. **Do this:** scope the claim — the representation-independence *contract* constrains which queries you may offer; positional/content reads are safe, but any query over run structure must canonicalize-on-demand first (consistent with your "recompute, don't store" line).

**4. "Design commitments / Forced": "runs break exactly at transclusion boundaries" is too narrow and contradicts your own implementation section.** A run breaks at *any* I-address lockstep discontinuity — wherever consecutive V-positions map to non-consecutive I-addresses — of which a transclusion/native boundary is one instance (and reordering or non-adjacent fragments from the *same* source also break a run). Your implementation section already states the correct criterion (`isanextensionnd`: I-contiguous *and* same-origin). **Do this:** restate the commitment as "runs break at I-address discontinuities (lockstep breaks)" and let the transclusion boundary be the worked example, so the commitments and implementation sections agree on what storage must actually detect.

**5. "What must be built" / "Decisions for the builder": name ValidInsertionPosition as a strand-level deliverable.** The note *defines* the valid insertion positions (the `N+1` slots: any existing position `1..N` plus exactly one append slot; for an empty subspace, exactly `[1,…,1]` at chosen depth `m`). The digest folds this into "splice" and never names it. The recommended implicit-sequence representation honors it for free, but a builder who keeps explicit keys must enforce "insert only at `1..n+1`, never open a gap" — that's the INSERT precondition the strand hands down and the thing that makes contiguity-preservation tractable. **Do this:** list a "valid-insertion-position check" component and note it is automatic under the implicit representation, a required guard otherwise.

**6. "Design commitments / Forced": tighten the grounding of the no-sharing-cap commitment.** S5 is a *consistency* theorem — it shows S0–S3 *permit* unbounded sharing — not a constraint that "downstream design cannot violate" (an implementation could add a cap and still satisfy S0–S3). The genuinely *forced* commitment (never cap sharing, never require injectivity) is grounded in Nelson's quoted "indefinitely / recursive and unlimited" transclusion requirement, which S5 shows is consistent with the formal core. **Do this:** re-attribute — the forcing comes from Nelson's requirement; cite S5 as the licence that this is consistent, not as the constraint itself.

**7. Minor — "The content store": qualify "no write-write conflict handling," and mark the repo-tooling analogies as analogies.** Logically there is no write-write conflict (immutable values + unique addresses mean no address is written twice), but a builder still must serialize *physical* journal appends or use per-writer logs that merge — which is precisely this repo's own `links.worker-N.jsonl`-buffer-then-flush pattern, born from concurrent-write pain. Say so. Separately, the `links.jsonl`/`paths.json` references are the *spec-authoring pipeline's* files, not components of the Xanadu engine being specced; keep them as clearly-labeled "this pattern is proven here too" analogies so a builder doesn't mistake `paths.json` for part of the design.
