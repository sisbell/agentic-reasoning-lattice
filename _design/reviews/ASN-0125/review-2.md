## Revision list

**1. Implementation approaches → "The supersession claim reuses the link store": fix the subtype over-claim (accuracy + grounding).** The digest says coverage-class storage "is exactly what lets independently-minted subtypes be recognized across clients." That states a *necessary* condition as if it were *sufficient*, and it asserts as settled exactly what the note flags as open. Q19 is explicit that "all clients using the new type must agree on the same I-addresses" — cross-client recognition requires a *coordinated* root, not independence — and OQ9 asks precisely "what closure guarantee must observation provide … so that independently minted refinements remain jointly recognizable." Rewrite to: coverage-class storage (not an enum) is *required* for any cross-client recognizability; subtypes minted under a single **agreed** root stay jointly queryable by one rooted span (L10); but whether **independently-minted** refinements remain jointly recognizable rests on an unresolved closure guarantee (OQ9). Then add OQ9 to the "scope the substrate leaves open" list in Decisions for the builder. (Keep the core point — coverage, never enum, as the stored kind — it is correct and well-grounded.)

**2. Implementation approaches → "Link store & allocation": make the allocation watermark explicit and name the Q12 hazard.** "The next address is the home chain's current max + one flat sibling" is loose exactly where the evidence documents a concrete bug. Per Q12, computing the next position from the *current listing extent* (Green's `findnextlinkvsa`) reuses positions after a de-list, whereas the append-only I-address allocator never does. State plainly: the allocation max must be taken over the **append-only allocation record (the journal), never the current listing/arrangement** — de-listing shrinks the listing but must never lower the allocation watermark — with Q12 as the named cautionary case. The digest is *correct* (the guarantee section names the obligation, and "recomputable by scanning the journal" picks the right source); the implementation instruction just needs to foreclose the documented mistake it currently invites.

**3. Guarantees to uphold: add chain connectivity (EL15) as a distinct guarantee.** The digest dissolves EL15 into "record permanence" + the in/out queries, but EL15(c) is a load-bearing builder fact in its own right: the historical component is traversable edge-by-edge in **both directions from any member, with no privileged entry point** — an entire edit lineage is reconstructable from any node by single arrangement-free observations. State it, paired with EL15(d)'s explicit non-guarantees (completeness of unasserted hops; operative integrity of demoted hops), which the digest already covers under "Record completeness."

**4. Currency build item (EL14e): say *why* `current(y)` can return a dead link.** The digest correctly requires each member to carry "its own activity status" and lets the reader "drop members whose own link is retracted," but never states the mechanism that forces this: `succ_o`'s only activity filter is on the *claim's* address, never on the endpoint links (Df-CUR/EL14e), so a successor can be a current sink and simultaneously be `Nullify`'d as an endpoint. Add one line — `current` answers "which readings are supersession-sinks," not "which readings are live"; every member is resolvable (EL9(1)) but may be inactive — so a builder doesn't assume `current` members are active.

**5. Open scope: surface OQ3 alongside the meta-claims item.** The digest surfaces the three most builder-facing open questions (OQ1 third-party retraction authority, OQ4 meta-claim stratification, OQ7 wholesale-vs-span-level edits). A builder enabling meta-operations also needs OQ3: a *retraction* tuple is an addressable link, so `assert_sup`/`editlink` can target it, and what superseding a retraction must guarantee — given R6a fixes nullification permanently — is open. Add it beside OQ4. (OQ2/OQ5/OQ6/OQ8 are more theoretical and fine to leave.)

**6. Decisions for the builder: make the edit gesture's *bundling* an explicit decision.** EL9 commits that "supersede and retire" is *available but never implied.* The digest captures re-listing the successor but not the symmetric retirement of the original. Fold into one decision: whether the "edit" gesture also re-lists the successor and/or **retires the original** (`Nullify`/de-list). Both are separate, separately-attributed acts; bundling either *silently* would violate the "superseding moves none of the three axes" commitment. Note too that de-listing a *non-tail* original is not surgical — per EL9(2), `K.μ⁻` retains only a prefix, so it drops the whole suffix and re-seats survivors — so a "replace in the listing" gesture costs more than one operation.
