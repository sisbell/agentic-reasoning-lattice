The items below are real but mostly modest; the worst is one backwards analogy.

**1. "Decisions for the builder" → Gate-failure signaling: the Green analogy is backwards.** The digest justifies the silent-no-op option with "the Green-like option — Green silently accepts even an empty-from link." Green silently *stores* the malformed link and returns success (evidence Q1: "a link with an empty from-set can be created, and the backend accepts it without error"); a gate-failing `→_sh` emit silently stores *nothing* (no image). These are opposite dispositions. Green is the model for *not having a gate* — which in this framework is the note's own unregistered-type / empty-registry configs, where a would-be emit simply has no image — not for silently rejecting on a gate that exists. The error-vs-silent-drop decision and its rationale (how far callers should lean on the gate as a validation service) are sound; keep them, but cut or correct the Green attribution so a builder doesn't conclude that a silent no-op reproduces Green's behavior. It produces the opposite of Green's behavior.

**2. "Implementation approaches" → gated emit choke point: drop the ungrounded repo filenames.** The append-only-journal-recovered-by-replay approach is well-grounded (Green's permanent I-space link orgls + write-only spanfilade; evidence Q1/INV-SPANF-WRITE-ONLY). But the parenthetical "(the `links.jsonl` + `paths.json` pattern; ... the proven approach this repo already uses)" names specific artifacts that appear in neither the note nor the evidence and carry no citation — false precision the reviewer cannot check. Genericize to "an append-only link-emission journal recovered by replay," or explicitly mark the filenames as an illustrative local instance rather than an established fact.

**3. Commitments / "Address allocation": "concurrency-free" overcredits the registry; surface the frontier as the emit-path serialization point.** The digest calls the immutable registry the keystone that makes the gate "decidable, stateless, and concurrency-free," then separately recommends a "per-home frontier counter" — and never connects them. The shape lookup is concurrency-free; the *emit* is not. FrontierUnification + L-ContiguousPrefix require every deposit to land at *the* single frontier slot and advance it by one, so concurrent same-home emits must serialize on that frontier — the very counter the digest proposes is the contention point, and a builder who reads "concurrency-free" and implements the counter without ordering will get frontier collisions that violate the contiguous-prefix invariant. Concurrency is beyond the note's sequential model, but since the digest raised concurrency-freedom as a benefit it owns the follow-through: state plainly that the per-home frontier, not the registry, is where same-home emits serialize.

**4. "Sterilization containment": the containment guard isn't as local as stated.** "Reject … a to-coverage that reaches past the filled region into the home's frontier. The frontier and the to-coverage's reach are both already computed" assumes the sterilized chain is the *retractor's own* home. But RangeSterilization fixes `d` independently of where the retraction is homed: a retraction homed at `d_retr` can carry a to-span pointing under a *different* document `d`'s link subspace and sterilize `d`'s chain. So the guard must test the to-coverage against the *target's* home-chain frontier — which is cheaply the same as `a_emit`'s frontier only in the canonical same-home wrapper case, not in general. Clarify this, or scope the guard's "cheap/already-computed" claim to the same-home wrapper.

**5. "Implementation approaches" → canonical-key index: make the precondition load-bearing and add the query-side obligation.** The reduction `coverage([k]) = coverage([k']) ⟺ k = k'` (correctly distinguished from prefix-containment) holds *only* for unit-depth singleton representatives. The digest hedges with "if your convention is unit-depth singletons" but doesn't make the failure mode explicit: a single non-singleton (or non-unit-depth) representative silently breaks exact-tumbler equality, and the *emitted* type slot being matched must be canonicalized the same way — a non-singleton `K` with the same coverage as a stored `[k]` will not be found by exact-tumbler lookup. State that the index is valid only if the C0 validator *enforces* the singleton convention and the lookup canonicalizes the query; otherwise fall back to the coverage-equality scan.
