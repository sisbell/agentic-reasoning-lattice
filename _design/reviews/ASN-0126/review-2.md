Reviewed against the note, the formal claims, and the evidence. The digest is accurate on the load-bearing commitments (`|F|=1`, arity-3, shapes-classify-registrations, registry immutability, effect-identity, no-residence-check) and its evidence use is faithful — `putvspaninlist`, `findnextlinkvsa`, the no-coalescing claim, and `tumbleradd`'s `s ⊕ ℓ > s` are all grounded in the answers, not fabricated. The defects are below.

**Revision list (most-important first):**

1. **"What must be built / A registry" and "Decisions / Σ_init authoring": surface the construction-time C0 *well-formedness* validation — it is currently absent.** The digest cites C0 only for finiteness ("the bound from C0") and treats the registry as given-well-formed. But C0 also requires (a) coverage-class keys *unique* (no two declared types `~`-equal), (b) every representative in `T_admissible` (non-empty endset), (c) shape values in `{Unary, Binary, Multi}`. (a) is load-bearing and *non-syntactic*: two declarations with syntactically different representative endsets can be coverage-equal, and a list-of-(representative, shape) registry (which the digest's "linear scan over stored representatives" implies) would then hold both — making `shape(K)` a *relation, not a function*, silently breaking the keystone the digest rightly emphasizes. Add: at `Σ_init` construction, validate C0 by running coverage-equality among the *declared* keys to reject `~`-collisions, reject empty/inadmissible representatives, and reject bad shape values — a construction-time well-formedness gate distinct from and prior to the runtime emit gate.

2. **"Sterilization containment": the worst case ("sterilize outright" / up-set) is a *gap-2* phenomenon, not gap-1 — fix the causal attribution and state gap-2's future-slot effect.** The digest pins sterilization on "the cost of gap 1 (a non-unit, range to-span)." But a chain-level range span has finite width and can only poison a *finite block*; the *up-set* (every future deposit to the home born nullified, irreversibly) requires a to-span at an interior node *above* the chain — e.g. a **unit-depth** wrapper aimed at the ghost link-subspace root `d.0.s_L`, whose coverage `{t : g ≼ t}` is the whole subtree and hence the entire chain tail. That is gap 2 (P-tgt failure), gap-1 closed — and it is exactly the note's "ghost-root call" realizing the corollary's up-set. The digest states gap-2's effect on *resident* links ("you sterilize that node's entire subspace") but omits its effect on *future* frontier slots, which is the most severe sterilization. Consequence: "unit-depth alone avoids sterilization" is *false*; P-tgt is load-bearing for sterilization, not only single-tuple-scope. Fix the attribution to "to-coverage reaches the frontier via two independent routes — a range to-span at the chain level (finite block) or any to-span at an interior node above the chain (up-set)." Your containment-check phrasing ("a to-coverage that reaches… into the frontier") is already correctly gap-agnostic; only the explanation needs repair.

3. **"Implementation approaches / canonical-key index": "coverage equality collapses to prefix equality on the tumbler `k`" is imprecise and invites a wrong implementation.** For unit-depth singletons `coverage([k]) = coverage([k']) ⟺ k = k'` — exact tumbler **equality**, not prefix-containment. A builder reading "prefix equality" could implement longest-prefix / prefix-match lookup, which would wrongly conflate `[k]` with `[k.1]` (genuinely distinct coverage classes). Say: coverage-class identity reduces to exact tumbler equality; key an ordered map by the full tumbler and match exactly for O(log n). (Conclusion and structure choice are fine; only the matching predicate is mis-described.)

4. **"How it fits / Faithful to Green, at the grain": the fidelity discussion omits the sharpest Green-contrast.** It notes the range grain and the discoverability-effect difference, but the evidence is explicit that Green's retraction is *unattributed* — `DELETEVSPAN` carries no from-set, and `CREATELINK` even accepts an empty from-set silently. This framework *mandates* a from-set (empty-from has no gated image). That is a deliberate **departure** from Green, not a fidelity. Add a sentence so the "faithful to Green" claim is not read more broadly than "at the grain."

5. **"Implementation approaches / Nullification index": tighten the nullified definition and the emit-time recipe.** (a) "an address is nullified iff some retraction tuple's to-coverage contains it" drops the *residence* conjunct — the note is explicit that a covered-but-ghost address is **not** nullified ("A ghost target is not itself nullified"); `nullified = resident (∈ A_rel) ∧ covered`. Operationally harmless (you only ever filter resident addresses) but state it correctly, since the note makes a point of it. (b) The emit-time born-nullified check is described only via C3 (pre-existing retraction covers `a_emit`); a retraction *self-emit* at `a = a_emit` is born nullified by **C2** (the new tuple covering its own address), which a pre-existing-dead-set consultation cannot catch. Note that the per-emit hint update must also test the new retraction's own coverage, or defer to query-time recompute (which catches both C2 and C3). The digest knows C2 in "Two outcomes"; the operational recipe should not silently narrow to C3.

6. **"Decisions for the builder": add the gate-failure signaling decision.** The note defines a gate-failing emit as having "no `→_sh` image" (a relational non-step); the digest renders this as "no state change" but never says how the substrate *signals* the failure — error vs silent no-op. This is a real builder choice with a Green contrast worth flagging (Green silently *accepts* empty-from, so a silent no-op is the Green-like option; a returned error is the stricter contract). Surface it alongside the other builder decisions.

7. **"Implementation approaches / Registry storage": minor altitude slip — drop the crate/type names.** "do not use the `im` crate's persistent maps… an `Arc`-shared immutable map" descends into specific Rust library/type names. The design point is correct and worth keeping (a write-once table gains nothing from a persistent/structurally-shared map and needs no locking or MVCC); state it without `im`/`Arc`.
