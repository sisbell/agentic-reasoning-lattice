**1. Implementation approaches → Endset packaging: the merged-span recommendation conflates V-contiguity with I-chain-adjacency and drops the cross-origin case.** The digest says "emit one span per contiguous resolved run as it falls out of the range scan … with no extra adjacency bookkeeping … you never merge across a gap because the scan only sees active positions." Two errors. (i) Canonical-span merging is over *I-chain-adjacent* addresses (`a_{k+1} = inc(a_k,0)`), not V-scan order. A single fully-active V-span can resolve to several non-chain-adjacent I-runs when it covers content transcluded from multiple origins — the note's **M16 CrossOriginMergeImpossibility** — which cannot be one canonical span and must be split at the I-discontinuity; the active-position filter does nothing about this (it only removes V-gaps). (ii) "No extra adjacency bookkeeping" is false for the resolver you recommend (the plain V→I ordered map): grouping resolved I-addresses into mergeable runs requires testing the sig-valid sibling step between consecutive I-addresses. Only the enfilade you set aside does that grouping for free (one region per contiguous I-run, per Q13). **Do:** package by maximal *I-chain-adjacent* resolved runs — break at every I-discontinuity (cross-origin included), never extend onto the unallocated frontier — or default to the reference decomposition (one unit span per address), which the digest already offers and which is immune to all of this.

**2. Design commitments → "Merely conventional": the from/to slot-role binding is forced, not conventional.** The list files "which of the two non-type slots a user reads as 'from'" under conventional. ML5 commits the opposite: the order *fixes* the roles and `(F,G,Θ) ≠ (G,F,Θ)` is "a stable, recoverable distinction" — slot 1 is the from-side, and the builder must preserve that order. Calling it conventional invites storing endsets in arbitrary slot order, breaking ML5's recoverability. **Do:** replace the item with the two things that *are* conventional — the *semantic meaning* of from/to per case (Nelson: "what 'from' and 'to' mean depend on the specific case"), and, for a one-sided link, *which* slot to leave empty (both `(∅,e₂,e₃)` and `(e₁,∅,e₃)` legal).

**3. Guarantees to uphold: the Frame (ML10) is missing — surface "linking into a region modifies nothing of that region."** The Guarantees list omits ML10. This is load-bearing: MAKELINK creates no content/entity/provenance and edits *only* the home's link-subspace; in particular, linking into B's content changes nothing of B. With ML4 this is what actually enables annotation of published, un-owned content — and it forbids the conventional-hyperlink reflex of writing a back-reference into the *target* to make the link findable (discovery is via the content-identity index, never by mutating the target). The digest only alludes to it ("the home seating is the one in-place arrangement edit"). **Do:** list the Frame as an enforced-by-construction guarantee with the no-target-mutation consequence spelled out.

**4. Implementation approaches → Discovery: the structure-choice criterion is wrong; the note's discovery is never a span-overlap query.** The digest hedges "a range/interval structure if you must answer span-overlap queries; an ordered map on exact addresses if point lookups suffice." Per ML9's own reduction (Fact (a): `coverage(eᵢ) ∩ store = ρ`; the covering surplus is non-store by LP-Fin; arrangement ranges are store addresses by S3★), the discovery test is exactly the exact-set intersection `ρ(R_i,Σ) ∩ ran(Σ.M(d'))`. A querying document's arrangement can *never* reach a proper descendant of a resolved root, so every match is at the root itself — you never face a span-overlap query. **Do:** state it definitely — key by `ρ`, answer by point-membership; interval-vs-exact is a compactness tradeoff, not the query-capability tradeoff the wording implies.

**5. Design commitments → "the discovery index is a hint" is a recommended realization, not a locked commitment.** It sits among commitments "downstream design cannot violate."
