## Revision list

1. **"Implementation approaches → Endset resolution" / "What must be built → Endset resolver": surface the depth-mismatch hazard, because the note admits depth-mismatched specs as in-scope and the digest's recommended "proven" path inherits the bug.** The digest tells the builder the resolver "must tolerate… depth-mismatched specs" and recommends possibly inheriting an enfilade (Green's POOM, called "the proven approach"). But it cites only Green's *happy-path* behavior (Q1, second batch: "I-widths trace exactly allocated content"). The note explicitly admits specs whose depth differs from the arrangement ("A spec whose depth differs from the arrangement's is admitted… ρ resolves exactly those"), and the evidence (Q1, first batch) documents that Green's interval-clipping V→I (`permute`/`context2span`) *mishandles* exactly this in-scope input class: shallower specs emit over-broad capture with no precision clip; deeper specs silently discard the sub-unit position and produce **zero-width (→ `qerror`) or negative-width (→ silently corrupt) I-spans.** Add a caution: implement ρ as the note defines it — **enumerate active positions in the interval and take their images** (which the ordered-map range scan already does, and which is *why* it is safe on depth mismatch) — never as arithmetic interval-to-interval clipping. This converts a one-line "tolerate" into the guidance that actually avoids the documented failure.

2. **"Guarantees to uphold → Permanence": relocate the guarantee from MAKELINK-local to vocabulary-wide, because survivability depends on it.** "by construction, if you simply never expose a delete or rewrite" reads as a MAKELINK choice. ML7 is explicit that it holds because *the entire transition vocabulary* contains no operation that removes or rewrites a link. State it as a system invariant: no operation anywhere may delete or rewrite a link value, and a builder who later adds any link-edit/delete operation breaks not just ML7 but ML8/EndsetSurvivability (the survivability payoff rests on the recorded I-addresses never being rewritten). This matters precisely because the same digest sells survivability as "the one thing you cannot get wrong."

3. **"Implementation approaches → Identity allocation": the high-water-mark formula needs its first-emission base case.** "the next address is `max(existing links homed at d) + 1`" is only the subsequent-emission branch; for a link-virgin home the homed set is empty and `max(∅)+1` is undefined — the address is the first emission `[d.0.s_L.1]` (Green: `docISA.0.2.1`, Q11). State both branches. The digest already relies on the first-vs-subsequent distinction in its (excellent) contracted-home discussion, so this is an internal-consistency fix.

4. **"Implementation approaches → Endset resolution": drop or spell out the unexplained `im` token.** "an `im` balanced-tree map" introduces an undefined reference that grounds in neither the note nor the evidence. The actionable content is "persistent ordered map keyed by V-position, answered by range scan" — say that and cut `im`, or expand it if it denotes a specific structure you intend.

5. *(Optional, minor)* **"Implementation approaches → Discovery" / "What must be built": acknowledge eager-at-write index maintenance as the proven instance.** Framing index maintenance as living "in the discovery subsystem" is faithful to the note's stance (index = derived hint), but Green's proven realization updates the spanfilade *inline within link creation* (Q14/Q20) — a legitimate eager view-maintenance co-located with the write. The digest's "eager or lazy" technically covers it; a half-sentence noting that eager-at-write is fine and is what Green does would keep a builder from reading "separate subsystem" as "must not touch the index at write time."
