Overall this is a strong, well-grounded digest — the `I0a → minimal-antichain dedup key` extraction is exactly right and genuinely useful, the "almost nothing here is authoritative state; recover by replay" framing is the correct Lampson read of the note, and the evidence is deployed accurately (no persistent timestamps → ordinal time; single-pass link queries → no closure; range-valued substrate; tested cycles/fan-out). The defects below are concentrated in two implementation approaches and a few load-bearing omissions.

**Revision list, most-important first:**

1. **Implementation approaches / Decisions — "per-home serialization is sound because ordering is home-local" is wrong for idempotent dedup.** The note makes cross-home de-duplication a *commitment*: I0's identity is `(coverage(F), coverage(G))` within `[K]` and "home document is outside it," and I1 states "cross-home de-duplication is deliberate." I4's serializing authority must therefore order two same-`(F,G,K)`-different-home calls so the loser, "evaluated against the winner's post-state, finds the now-active tuple." Under per-home sharding those two calls land in different shards, both miss, and both deposit — **two active tuples in one I0-class across homes, violating I1a (ActiveIdemUniqueness)**. Home-locality holds for *frontier allocation* and for *staleness denomination*, not for dedup. Fix: keep the recommendation that frontier allocation/journaling/non-idem emits may shard per home, but state plainly that the idem-⊤ dedup check-and-deposit must be a single globally-atomic critical section (a global dedup index). Note this also contradicts the digest's own parenthetical in "What must be built" that multiple dedup matches arise "only off the disciplined path" — under per-home sharding they arise *on* the surface.

2. **Implementation approaches / Decisions — "omit the born-nullified check entirely on surface-only" overstates DR.** DR only makes **C3** (a *pre-existing* retraction covering the fresh address) vacuous on surface-disciplined derivations. The note's DR statement is explicit that born-nullified survives: "a tuple is born nullified only through **C2's self-nullification**." A wrapper **self-emit** retraction (P-tgt's `a = a_emit(Σ, d_retr)` disjunct) self-nullifies and lands born-nullified on the surface. Moreover, in a replay-derived design there is no standalone "born-nullified check" to omit — born-nullified-ness falls out of `A_K = L_K \ nullified`, which you compute regardless of path. Fix: state the true simplification — on surface-only, no *non-R* deposit is ever born-nullified (C2 free via `K ≁ R`, C3 vacuous via DR), so the active view of non-R types never loses a just-deposited tuple to a pre-existing retraction; the one residual surface case (wrapper self-emit retraction) is handled by the standard `nullified` derivation, needing no special machinery. Do not imply self-emit retractions land active.

3. **What must be built (behavior surfaces) — missing the load-bearing builder note that filter × behavior-surface interaction is undefined (OQ1).** The note pins read-filter's rewrite to `members`/`targets_of` only and leaves *deliberately uncommitted* whether filtering rewrites `sources_to` (BH3) or a `chain`/`tip` walk through a filtered mid-chain element (BH2) — and stresses that since `retired` and `supersedes` both ship, "the BH1 × BH2 case is the canonical lifecycle scenario, not a corner." A builder implementing those surfaces must know to ship the active-view reading and treat dominance as an explicit, deferred policy. Add this to the behavior-surfaces build item.

4. **Design commitments — R's Binary shape and the gate-confinement rationale are absent, and the nullification approach is under-justified without them.** S3 makes R's Binary shape a *deliberate choice* among ASN-0126's four `[R]` configurations: Binary is the one where retraction is expressible *and* the gate confines **every** R-tuple — wrapper-routed or raw-bypass — to a single-span to-endset (ASN-0126's P6). This is exactly what bounds off-surface raw retractions to a *single* (possibly range-valued) span rather than a multi-subtree set, which is why the digest's "prefix-trie for unit-depth, spanfilade for range-valued off-surface" index suffices. Surface this commitment (R is Binary; the gate confines all R-tuples to single-span to-coverage) and tie it to the nullification index.

5. **Guarantees / Implementation approaches — "surface discipline" conflates three distinct note notions, and the idem-uniqueness condition is stated as necessary-only.** The note keeps apart (a) *K-surface-emitted* (I1a, per-type — the actual hypothesis for idem uniqueness), (b) *surface-disciplined / SD* (`[R]`-specific — the hypothesis for C3-vacuity / no sterilization), and (c) a surface-only deployment (implies both). The digest collapses these into "surface discipline." Consequently "at most one active tuple per coverage class … holds by construction iff every store-growing step goes through the surface" is necessary but **not sufficient** — it also requires sequential ordering of the dedup check (see item 1). Fix: name the two disciplines separately, attribute uniqueness to K-surface-emitted-*plus*-serialized-dedup and no-sterilization to SD, and stop implying surface-routing alone delivers uniqueness.

6. **Implementation approaches (registry) — "settling the note's open attribution question" overclaims, and the udanax precedent is shakier than stated.** Choosing bootstrap-document type storage yields provenance as a *side benefit*; it does not *settle* spec-level OQ4 (whether substrate types should carry explicit `provenance.import`), which the note deliberately left open. Soften to "offers a provenance answer relevant to OQ4." Also note the evidence here is mixed: Q8's code exploration finds the backend treats all links identically and locates the named-type constants in the Python client, disputing the "bootstrap type registry in the store" reading the note cites — so "proven in udanax-green" should be "the precedent the note cites (per the KB synthesis)."

7. **Decisions for the builder — "derive vs index, chosen independently per query family" is false for idem dedup.** The dedup index for idem-⊤ types is necessarily a global synchronization point (item 1), so it is *not* independent of the concurrency-granularity decision. Couple these two bullets: choosing to index dedup commits you to global atomic check-insert for idem types.

8. **Minor completeness (worth one line each):** the view selector defaults to `default` and is carried by *only* `members`/`targets_of` (a builder needs the surface inventory); the escape-hatch asymmetry (filtering is reversible via the `active` selector, nullification is irreversible and only resurfaced in the audit view); `is_in_chain` is enumeration-derived, not a membership predicate (so an extension of a chain element does not satisfy it); and the surface's partiality is *rejection* (undefined, no step, no address), an explicit choice over a total-with-error-value surface. None is load-bearing alone, but the first two sharpen the views/selector story the digest currently leaves vague.

The remaining sections — the seven design commitments, the "what must be built" inventory, dedup-key/nullification/age-staleness/storage-generality approaches, and the dependency map in "How it fits" — are accurate and at the right altitude; no change needed beyond the items above.
