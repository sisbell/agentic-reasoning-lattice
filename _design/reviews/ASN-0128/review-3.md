This is a strong, unusually well-grounded digest. It correctly separates note-cited precedent from evidence-verified behavior (the bootstrap registry, replay-vs-snapshot recovery, symmetric-vs-asymmetric link matching), and several of its sharpest moves are exactly right: the I0a minimal-antichain dedup key, the "shard dedup by coverage-class, never by home" analysis, the C3-vs-C2 born-nullified precision, the two-condition statement of idem-uniqueness, and the `nullified`-reads-audit vs `is_filtered`-reads-active distinction. I found no accuracy error. The improvements below are completeness gaps, a few consequences left implicit, and one altitude slip.

**1. "What must be built" / emit surface — state the F=1 / arity-3 envelope and stop calling the source a "set."** The prose "accept `(home, source-address-set, target-address-set)`" is signature-faithful but misleading: the shape gate enforces `|F| = 1` for *every* admitted call across all three shapes, so the source is always a single address — only G's cardinality varies (Unary `G = ∅`, Binary `|G| = 1`, Multi finite). This is the implicit precondition that makes your own dedup key (`source-address`, minimal-target-antichain) sound; a builder who reads "set" and admits multi-span sources breaks that key. Fix the prose, and echo the note's deferred-scope boundary *"Extensions beyond F=1 and N=3"* (the whole layer is fixed at this envelope; loosening is a future note) alongside the three "doesn't cover" items you already carry. Also note the two considered-but-deferred behaviors (cascade-with, single-source-restriction) so the catalog reads as four-committed-of-a-growing-set rather than four-total.

**2. "State representation" — drop the "im crate" reference (altitude slip).** Naming a specific Rust library presumes a language the spec doesn't commit to and is the one code-level detail in an otherwise altitude-clean digest. Say "persistent / structurally-shared immutable structures" and let the builder choose. Minor, but it's the clear blemish.

**3. Design commitments / "Attribution" — surface the consequence of proposer-exclusion under idem=⊤, and the R-from-fill escape, as an app-type design decision.** The digest lists proposer/source-app/home as outside I0 but treats cross-home dedup only as a *concurrency-correctness* concern. The load-bearing consequence for type designers is left implicit: under idem=⊤ on a non-R type, identical assertions from *different proposers* collapse to the first (the second emit is a no-op returning the first's address), so per-author claims do not accumulate. This bites a shipped type — `supersedes` is idem=⊤ with `F = old-version` (not the proposer), so two parties asserting the same old→new edge collapse to one record, which sits in slight tension with the note's own "supersession claims are owned links that accumulate." State the escape the note demonstrates for R and generalizes: to preserve who-asserted-what, fold the author into F (R's per-document from-fill makes `coverage(F)` document-specific, so cross-document retractions are *not* I0-equal) or register idem=⊥. idem=⊤ is identity-of-assertion, not identity-of-claimant.

**4. "Age-staleness" / retraction reasoning — add the per-document retraction-identity case split that underwrites `retract_stale`'s "harmless" claim.** The digest says a batch "cannot sterilize" because targets are existing link addresses, but doesn't surface why re-retracting an already-nullified target is safe: R's I0 identity is (retracting-document, target-coverage), so re-retracting the same target *from the same document* is an idempotent hit (dedups to the existing tuple), while retracting an already-nullified target *from a different document* — or after the prior retraction was itself nullified — is not I0-equal and deposits a fresh, redundant-but-harmless retraction. This is the note's own case split (S3, BH4) and is what makes the batch's net postcondition hold under interleaving; a builder reasoning about retraction idempotence needs it.

**5. S2 — generalize the slot-direction point from `supersedes` to a builder rule (L7).** The digest treats old→new as a one-off convention. The note's reason (L7: directional interpretation belongs to the *type*, not the structure — the substrate's F→G carries no inherent direction) is a general obligation: any directional Binary type, shipped or app-registered, must pin its slot convention as part of its registration contract, or two conforming implementations walk it opposite ways. Surface it as a rule for whoever registers walkable/directional relations, not as `supersedes` trivia.

**6. I6 / emit surface — make the read-back caveat explicit as an API contract.** The digest notes the suppressed decomposition "is never stored," but the caller-facing form is sharper: on an idem=⊤ hit the returned address bears the *incumbent's* `(F', G')`, so a caller that emits and then reads the address back expecting its own span decomposition is wrong — the only guarantee is coverage-equality (I6's POST is coverage-typed, not value-typed). State it: emit `[a, a.x]`, and the store may report `[a]` at the returned address.

**7. Minor — bootstrap-registry refinement and Approaches/Decisions overlap.** (a) The bootstrap skepticism is good and correctly sided with Q8's code exploration, but "largely a synthesis artifact" undersells what's real: the *client-side* type-reference-into-the-bootstrap-doc convention does exist in Green (QUOTE_TYPE/MARGIN_TYPE as client VSpecs); what's absent is any *backend* type-registry enforcement. Tighten to "a client-side convention with no backend enforcement," so the builder knows the R1-isolation that approach requires is the digest's invention, not inherited. (b) "Implementation approaches" and "Decisions for the builder" restate the same five forks (registry location, concurrency granularity, dedup key, durability, state representation); make "Decisions" a pure cross-referenced checklist to cut the duplication.
