**1. "How it fits" — the `findlinks_V` wiring is a misread; correct it and re-open the question it closes.**
The digest says FTT "Sits behind ASN-0127's V-spec front-end (`findlinks_V`): a V-region request is first resolved through the arrangement … then handed to **this query**." The note's Notation section says the opposite in plain terms: "*the second phase of `findlinks_V` (F-V) remains the foundation's bare `findlinks`, not the present operation.*" So `findlinks_V` wraps F-FIND (slot-agnostic, unfiltered), **not** `findlinks_FTT`; the two are parallel queries (V-level wrapping bare-findlinks vs. the I-level FTT), not stacked. Worse, the note flags the FTT-specific V-spec front-end as **Open Question 2** ("What invariant must connect an I-address request to its arrangement-mediated (V-spec) phrasing…"), so the digest presents as settled what the note leaves open. Fix: keep the correct architectural advice (arrangement resolution belongs in a *separable* front-end; FTT itself is stable), but state that a V-spec front-end *for FTT* would be **analogous to** `findlinks_V`, not identical with it, and that the agreement invariant between FTT's I-address and V-spec phrasings is an open question — not an existing combinator to slot behind. This is also internally inconsistent with the digest's own later line that FTT is distinct from F-FIND and "neither is a restriction of the other," since F-FIND is exactly what `findlinks_V` wraps.

**2. "What must be built" / "Decisions for the builder" — surface the home-filter *placement* decision and sharpen repair (a).**
FL-RES makes `home(a)` a pure projection of the link's *address* (no store lookup), and the note explicitly enables home-*only* queries ("all links owned within a given document by leaving the endpoints unconstrained"). That implies a real builder decision the digest never names: **does the residence bound live as an index dimension or as a post-filter on the candidate set?** A post-filter (`home(a) ∈ coverage(H)`) is trivially correct and cheap precisely because home needs no lookup — but it forces a full scan for home-only queries; an index dimension on the link-address axis makes "links homed under d" a range query. This is exactly the axis Green tried to index (the ORGLRANGE/orgl dimension) and exactly where it broke (the `TRUE||!homeset` dead code, Q12). Add this as a builder decision, and tie repair (a) to it: "honor the home-set" should say *how* (post-filter is the simple correct default; the address-range index dimension is the performance alternative and the one Green botched), so the reviser doesn't leave repair (a) as a bare "restore the constraint."

**3. "Guarantees to uphold" (FL-JUNK) — the hypothesis stated is narrower than the lemma.**
The digest says junk is harmless for "non-matching, **non-retraction** additions." The note deliberately does *not* require non-retraction: its hypothesis is "*no existing link becomes nullified*" (`nullified(Σ') ∩ dom(Σ.L) = nullified(Σ)`), and it goes out of its way to say so — "*We deliberately do not demand the stronger `nullified(Σ') = nullified(Σ)`*" because an added junk link "*may be born-nullified*." So FL-JUNK *permits* added retraction links (born-nullified ones, or retractions targeting only ghosts/other new junk) — the digest's "non-retraction" excludes a case the note covers on purpose. The digest's version is sound (a subset of permitted additions) and its companion warning (a retraction hitting an *existing* link can remove a match, FL-WP(c)) is the operationally important part and is correct — but restate the hypothesis as "additions that fail the request and nullify no *existing* link" so the reviser doesn't propagate a tighter-than-true lemma.

**4. "Decisions for the builder" repair (c) — over-broad on what the reference actually collapses; the gap is the wire encoding only.**
Repair (c) says the reference "collapses both [`∗` and `∅`]… making `Θ = ∅` inexpressible." That's accurate for a **zero-member** type specset (serialized `0~` → NULL → NOSPECS, consultation Q2), but Q7 shows Green *does* distinguish a present-but-empty slot from NOSPECS for from/to: a vspec carrying an empty span-set resolves to nothing and **short-circuits to ∅** (the zero), distinct from the wildcard path. So Green's *engine* already realizes FL-EMP's short-circuit correctly (which is what the digest's combination engine asks for); the only true gap is the **wire encoding** of a grammar-level empty *type* slot collapsing to NOSPECS. Tighten the parenthetical to say the fix is purely the request encoding (let a grammar-level empty slot be expressible distinct from NOSPECS), not the short-circuit logic — otherwise repair (c) wrongly implies Green's zero-handling is broken when Q7 confirms it isn't.
