This is a strong, unusually faithful digest: the forced/conventional split is right, the spanfilade approach and the content-identity keying decision are well-grounded in the evidence, the "index as a derived hint over an append-only store" framing is exactly the Lampson move the note invites, and the three reference divergences to repair (dead home-set, all-wildcard → ∅, Θ=∅ inexpressible) are correctly identified and grounded. The revisions below are real, ordered most-valuable first.

---

**1. "Wildcard/empty" commitment, "What must be built", "Implementation approaches": the digest covers only the *request-side* empty constraint and misses the *link-side* empty endset — a load-bearing index-construction rule.** The note (FL-EMP second half, Trace 5; L3 constrains only `e₃ ≠ ∅`) and the evidence (second Q2: the empty slot is "simply absent from the per-slot link index") establish that a stored link may legitimately carry `e₁ = ∅` or `e₂ = ∅`, and such a link is excluded from any *constrained* from/to slot but must still surface under that axis's *wildcard*. The digest's FL-EMP treatment is request-side only ("a constrained-but-empty slot annihilates the result"). Add the symmetric link-side rule as a concrete index-construction instruction: when indexing a link, omit the slot whose endset is empty; a constrained from/to query then never returns it, a wildcard query does — the link-side zero. This is entirely absent today and directly builder-actionable.

**2. "Guarantees to uphold" / "Start with a full scan": FL-JUNK is mis-stated — the retraction hypothesis is dropped.** The digest says "junk neither enlarges nor displaces the answer." But the note's FL-JUNK holds only for additions that nullify no existing link (`nullified(Σ') ∩ dom(Σ.L) = nullified(Σ)`); it is explicit that a *retraction-kind* addition is precisely the case that **can** displace an existing match (FL-WP(c)), because addressability is not per-link. State the hypothesis: non-impedance covers non-matching, non-retraction additions; a retraction-bearing link can remove an existing match, so "junk is harmless to results" is false for retraction links. Separately, label the "degrade query time worse than logarithmically" target as the digest's own engineering goal — FL-JUNK is an answer-invariance lemma, not a complexity bound.

**3. "Implementation approaches" / "Recovery, snapshot": the Rust/`im`, `links.jsonl`, `paths.json` substrate specifics are ungrounded.** They appear in neither the note nor the evidence and carry no citation, yet two subsections lean on them. If they are real project context, cite the source; otherwise generalize ("an append-only journal + path registry recovered by replay; a persistent ordered-map structure") so the design does not hinge on an unverified substrate. (`intersectlinksets` and the spanfilade *are* grounded — they're in Q11/Q15/Q7/Q19 — keep those.)

**4. "The addressability filter": the maintained tombstone must store retraction to-*coverages*, not resolved addresses.** The digest says "record the addresses its to-coverage names," then immediately invokes born-nullified (a link allocated at an address a standing retraction *already* covers). A resolved concrete-address set cannot represent that — at retraction-append time the target may be a ghost/future address not yet in `dom(Σ.L)`. Fix the approach: the hint stores the retraction to-coverages (interval/span sets) and tests each candidate *and each newly-allocated* link address for membership; that is what makes born-nullified and self-nullifying fall out, and it is the same `touch`/membership machinery FL-DEC already provides.

**5. Surface two retraction subtleties the note stresses but the digest omits.** (a) *Non-fixpoint (R6b):* `nullified` is computed from **all** arity-3 retraction-type links in the store, *including those that are themselves nullified* — retracting a retractor removes it from results but does not restore the links its to-coverage excluded (FL-RET). Warn against the tempting-but-wrong optimization of filtering the retraction slice to addressable retractors. (b) *First-class retraction links:* a retraction link is itself a searchable link (FL-WP(b), Trace 7; note's consultation Q2 — a type-`Θ` query touching the retraction class returns one like any other), so index retraction links as ordinary links rather than treating them only as filter metadata.

**6. "FL-REACH guarantee" / "result shape" decision: specify that result dedup is by link *address*, never by value.** "Links deduplicated by identity" is ambiguous, and the note builds the exact counterexample — Trace 6's `a₁` and `a₅` carry byte-for-byte identical endsets but distinct addresses/homes and must remain two results. Dedup by link address (the same address reached via multiple spans collapses to one); a value/content-based dedup of links would wrongly merge `a₁`/`a₅`. Make this explicit so the builder does not introduce content-dedup.

**7. "The `touch` and `athome` tests": the fast-path dichotomy misses the single *wide* span.** The digest special-cases "single unit-depth prefix span" (one prefix-comparability test) and falls back to cell decomposition "only for genuine multi-span coverage" — but a single *wide* (non-unit-depth) span (the note's T12 order-convex sub-range / element-rooted-straddling-a-length-boundary case) is neither: the prefix reduction is invalid for it, yet it is not multi-span. Restate three tiers: unit-depth prefix → one prefix test; single wide span → one half-open interval test; multi-span → interval-union/cell-decomposition.

**8. "Design commitments" / "How it fits": draw the single-store boundary.** The "intrinsically global content-identity sieve" framing and FL-REACH are single-store; the note's federation open question means reach across independently-administered stores is unspecified. Add a line so the builder does not over-extend "global" to a federation the spec does not yet guarantee.
