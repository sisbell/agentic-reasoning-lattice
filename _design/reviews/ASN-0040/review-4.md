## Revision list

1. **[DEFECT] — Durability section + "Journal contents" decision: the `links.jsonl` repo-substrate claim is uncheckable and used as load-bearing justification.** The digest twice asserts "the repo's own proven substrate (an append-only `links.jsonl` journal plus a replay-rebuilt derived registry)" and "matching `links.jsonl`'s self-describing records," presenting it as established fact and as the reason the WAL approach is "proven" and "the default." This specific source-level artifact appears in neither the note, the udanax-green evidence, nor documented Green structure, and carries no checkable citation — exactly the class of claim that must be flagged. Either cite a precise path so a builder can verify it, or remove the repo reference and rest the WAL recommendation on its *grounded* supports, which fully carry it on their own: B4 (a baptism is a single atomic append), B0 (growth is additive-only, so the log never needs deletion-compaction), and the udanax-green append-only-granfilade-lazily-checkpointed pattern (which *is* in the evidence).

2. **[SHARPENING] — Design commitments: "There is no batch-grow" is stated as forced and inviolable, but the note explicitly leaves bulk allocation open.** The note's open question — "Under what conditions may bulk allocation — baptizing a contiguous range of k positions in a single operation — satisfy B4's atomicity and B1's contiguity?" — contemplates batch-grow as an extension, and the digest's own Guarantees section says "any bulk/batch path you add must preserve gap-freeness." Reconcile the two: reframe as "*as specified*, the registry grows one address per operation; bulk allocation is an explicit open extension that, if added, must preserve B1 contiguity and B4 atomicity."

3. **[SHARPENING] — "How it fits" / `allocated(s)`: state the alignment obligation for the layered-design path.** The note draws an explicit distinction between `s.B` (baptism's committed registry) and the foundation's `allocated(s)` (the allocator's realized domain), and asks "under what activation discipline does `allocated(s) ⊆ s.B` hold." The digest's layered alternative ("feeds a distinct registry") gestures at this but omits the consequence: if allocator and registry are layered rather than unified, every allocator-extension must be matched by a baptism (and the seed must cover the genesis allocator domain), or addresses become allocated-but-unbaptized. The recommended unified approach sidesteps this — say so, and state the obligation for the alternative.

4. **[SHARPENING] — B9 / encoding scope: unboundedness applies to *every* tumbler integer, not just the ordinal.** The digest pins arbitrary-precision need on "the count `m` and the tumbler ordinal." But Nelson's "Each integer has no upper limit" (and the ASN-0034 tumbler structure) makes every component unbounded — so the "Key encoding for the counter map" decision must require variable-length encoding of the *parent* components too, not only the ordinal. The conclusion (variable-length, never fixed-width) is right; broaden its justification.

5. **[SHARPENING] — Design commitments / "no external counter" reads in tension with the recommended counter.** Listing "no randomness, no external counter, no clock" under determinism sits awkwardly next to recommending a per-namespace counter as the primary representation. Clarify it means no *authoritative* counter independent of the registry — `next` is a pure function of registry state (B2), and the evidence confirms "no session-local counter" — whereas the recommended counter is a *derived hint* (as your durability section already frames it).

6. **[SHARPENING] — Make explicit that baptism imposes no parent-baptized precondition (Bop PRE).** This is the commitment that makes empty-start genesis work — the first baptism's parent is an unbaptized virtual position — and is exactly the "must a parent be baptized first?" question the digest defers to ownership. It is currently only implied; state it as a commitment of this layer.

7. **[SHARPENING] — Counter representation: note that it makes B1 unrepresentable-to-violate.** A count `m` can only denote `{c₁…cₘ}`, so the counter form converts contiguity from an invariant-to-enforce into an invariant-by-representation — a genuine design advantage worth stating. (Minor adjunct: decomposition presupposes length ≥ 2; the non-child roots that need the auxiliary set are exactly the length-1 node roots.)
