One material problem, plus several tightenings.

**1. [DEFECT] — "Contiguous runs (clause 5) — writer-side only," the "reserve m slots, fill atomically" sub-option is a category error that contradicts the section's own opening.** The bullet correctly opens that clause 5 is writer-side only and "a reader can land mid-run on a valid-looking partial state" (OQ4 is the separate, harder reader-atomicity contract). It then offers, as a "cheaper" clause-5 mechanism, "reserve m consecutive slots in one frontier-advance … the fill must commit atomically (no reader may observe the interval until it is full)." But in this model the frontier *is* the population (φ_S = |P_S|), so "advance the frontier by m" must deposit m addresses; the only non-buggy way to do that is one atomic m-deposit — which makes the run **atomic to readers (OQ4), strictly stronger than clause 5**, and forbids exactly the mid-run reads the opening says clause 5 permits. So this option is mislabeled and self-contradictory: it is not a cheaper way to get contiguity, it is the OQ4 answer. A builder is misled either way — implementing OQ4 while believing they've only done clause 5, or "saving" the atomic fill and depositing reserved-but-empty placeholders (the non-𝔼 states the digest itself warns against). Fix: present holding the per-`(d, s_C)` critical section across the m deposits as *the* clause-5 mechanism (readers may land mid-run); relabel the reserve+atomic-fill option as an OQ4-answering / reader-atomic option (over-satisfies clause 5, at the cost of one indivisible m-step), and drop the "cheaper" framing.

**2. [SHARPENING] — State representation: make explicit that persistent immutable state's "free" win is read-side only.** It is recommended as "the biggest lever" for clauses 1/4/6, which is right *for readers* (capture one root, read all constituents off it). But concurrent per-home **writers** sharing a single persistent root contend on root installation — persistent state alone does not deliver the write concurrency G1 blesses. State that write concurrency still comes from the sequencing mechanism (per-home actors with per-home roots + merge, or a single applier), so a builder doesn't pair "persistent state" with "per-home actors" and expect free concurrent writes.

**3. [SHARPENING] — Frontier-aggregate "hint" framing conflates two different things.** The digest says "maintain an aggregate frontier … as a cache — a hint in Lampson's sense, check-and-recompute … recompute on a miss," citing the reference's apex `cwid` aggregate. But the reference's aggregate is **eagerly maintained** (propagated by `setwispupwards` after every insert) — always exact, never "misses." That is an authoritative-derived aggregate, not a Lampson hint (which may be stale and is verified on use). Distinguish the two and note the reference does eager maintenance; "recompute on a miss" doesn't fit a frontier aggregate.

**4. [SHARPENING] — "a reader can land mid-run on a valid-looking partial state" needs the note's content-run qualifier.** For a *content* run specifically, the note (A5/W2/§8) is explicit that the partiality is structural and "witnessed by no read the note models" — §8's read surface is link-only. The digest's statement is true in the abstract but should add that no *currently-modeled* read witnesses a content-run partial, so the OQ4 concern is forward-looking (any read surface that would witness content population), not a present read-visible hazard.

**5. [SHARPENING] — "the lone exception of commit-before-acknowledge" is undercut one sentence later.** The clause-6 rider ("free only if the handler bundles all constituent reads into a single compound access") is a second thing the single loop does not give for free. Reword to name both: A7 ordering, and bundling a verdict's reads into one dispatch (else the §8 drift occurs even under the single loop, as the digest itself then says).

**6. [SHARPENING] — Elevate register-before-allocate.** The note treats it as the one thing attaching to `K.σ` *unconditionally* (a genuine ≺-ordering independent of the shared-frontier conditional). The digest mentions it only inside the per-home-actors bullet; surface it as a general scheduling obligation in "What must be built," since it binds every realization, not just per-home actors.

**7. [SHARPENING] — Multi-store atomicity: name it as an implementation artifact.** "When one logical step touches two stores (content + index)" is slightly off-model — each abstract step touches one store; the two-store divergence arises only because a builder maintains a *derived index* (the reference's spanfilade) alongside the authoritative store. Frame the WAL advice as preserving per-step atomicity across the builder's chosen derived-index layout, not as a model step spanning two stores.
