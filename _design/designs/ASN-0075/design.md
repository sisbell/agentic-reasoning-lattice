# Design Digest — ASN-0075: SHOWDELETIONS

## What this is

SHOWDELETIONS is a read-only, two-document query that reports the content each document deleted while the other still holds it. It is the operation that makes the provenance relation `R` *load-bearing* — the note's central result is that this capability cannot be built from the four foundation state components `(C, L, E, M)` alone.

## Design commitments

The load-bearing decisions this note locks in:

- **Deletion is a three-way classification, not a set-difference.** Every (content-address, document) pair is exactly one of CURRENT / DELETED / NEVER_INCLUDED. **Forced** (D-EXH for the exhaustive three-way partition; D-DISCR, with proof, for why the DELETED/NEVER_INCLUDED boundary cannot be computed from `(C, L, E, M)`): a naive `ran(M(d_B)) \ ran(M(d_A))` conflates content `d_A` once held and deleted with content `d_B` merely acquired — it is provably wrong. The DELETED vs. NEVER_INCLUDED distinction *must* consult provenance.
- **The system must carry durable state beyond `(C, L, E, M)`.** **Forced** (D-NEED): `R` suffices, and reusing the provenance relation rather than introducing a fresh component is the cheapest mechanism that meets the contract. This is the constraint of the whole note: any conforming substrate must persist a provenance record that *survives removal from arrangements*.
- **Provenance is monotone and permanent** (`R ⊆ R'`, P2). Deletion never retracts provenance; that permanence is exactly what keeps DELETED detectable forever. Inherited from ASN-0047, but this note depends on it absolutely — it forbids ever garbage-collecting `R`.
- **Provenance is historically faithful** (P4a). Every `(a,d) ∈ R` witnesses a real past state in which `a` was arranged in `d`. This is what makes the word *DELETED* honest: `(a,d) ∈ R ∧ a ∉ ran(M(d))` means "was present and removed," not merely "is in the provenance set." Inherited from ASN-0047 — its *maintenance* belongs there — but the operation's semantics rest on it absolutely, so the consumer relies on `R` being appended *only* for genuine placements; spurious provenance would degrade DELETED to a misnomer.
- **Classification is at I-address-set granularity.** **Scoping decision** (rationale: transclusion multiplicity, ASN-0058/0036, makes set-granularity coherent): `CURRENT` and `DELETED` read only the *set* membership condition `a ∈ ran(M(d))` — the *range* of `M(d)`, which discards V-position multiplicity — never the number of V-positions at which `a` occurs. That masking conjunct lives in the `ran(M(d))` read, never consulting `R`, so an occurrence-aware `R` would not change the result; the foundation's provenance relation being over element×document pairs with no occurrence-level record is a true but secondary corroboration. Per-occurrence removal stays invisible while any occurrence of `a` survives, and the note deliberately scopes that finer operation out as a Vstream concern needing finer state. Builder consequence: extending to per-occurrence deletion needs *new historical occurrence state* — it is not in `R` (no occurrence record) and not recoverable from current `M` (which carries only *current* multiplicity, not what it was before removal).
- **The contract is purely observational and state-functional.** **Forced** (D-OBS, D-STORE, D-RECONS): writes nothing, persists no artifact, depends only on current state not on history. Deterministic and repeatable per state.
- **Output is existing I-addresses, not copies or values.** **Forced** (D-IDENT, D-ORIG): identity preserved by reference, origin derivable from the address. Not merely conventional — it is what lets the report feed an identity-preserving restoration.
- **Two directional halves are meaningful; the A/B labelling is convention.** That a document *lost* content (vs. its partner) is real directional information; *which* half is named "A" is purely operand-order convention (D-SYM). The content-level guarantee is the symmetric union.
- **Meaning is licensed only at a composite boundary.** Computing the answer needs only finiteness, but *trusting* it (three-state exhaustion, D-EXH; the witness lemma, D-WIT) requires the boundary where `R` and `M` are mutually coupled (P4★).

## What must be built

- **An arrangement-range membership test** (CURRENT): given `(a, d)`, decide whether `a` is referenced anywhere in `d`'s current arrangement — the *set* of distinct content-addresses, multiplicity discarded.
- **A per-document provenance projection** (the `R` read-path) — needed *only if* you adopt the recommended set-algebra computation below, not by the spec. For a fixed `d`, it obtains `{a : (a,d) ∈ R}` (the content `d` ever held), which that strategy reads instead of testing point membership. The spec itself is defined on point membership `(a,d) ∈ R`, so this projection is an efficiency structure for the chosen strategy, not a requirement of the operation.
- **The provenance relation `R` as durable, monotone, queryable state.** Forced by D-NEED. Its *maintenance* belongs to the placement operations (ASN-0047); this note forces its *existence* — durable, monotone, and queryable at point membership; the document-forward read path is the recommended strategy's requirement, not the spec's.
- **The witness-filtered assembly:** the two report halves — content DELETED from one document and CURRENT in the partner — the partner's still-live copy being the recoverability witness.

## Implementation approaches

**The provenance relation `R` — the one piece this note forces into existence.**
Model `R` as an *append-only journal of provenance facts* (one record per "content `a` placed into document `d`"), recovered by replay on load, with an in-memory index built over it. This is the abstract shape that fits the spec, and it matches udanax-green's spanfilade, whose DOCISPAN entries are verified append-only and untouched by deletion. The journal gives monotonicity (P2) and durability by construction; the index is a *hint* — the log is authoritative, the index is recomputable on a miss or reload. You cannot derive `R` away (D-DISCR forbids it), so storing it is the simplest thing that honors the spec. (If the host substrate already carries an append-and-replay journal — e.g. a `links.jsonl`-style log with a replayed registry — `R` is naturally a projection of it; that is project context, not something this note establishes.)

Two real choices here. **Granularity:** singleton addresses vs. contiguous content-address *spans*. Spans are far more compact (content is allocated in runs), mirror DOCISPAN's I-span entries, and set up span-coalesced output later; singletons are simpler but cost O(content). I'd store spans and pay a little interval logic at query time. **Access path:** SHOWDELETIONS needs the *document-forward* projection `d → {a}`. Udanax-green's spanfilade is 2D-indexed (docISA-prefix × I-span), so the document dimension is present in the structure; per the evidence, what it lacks is a *composed* function that enumerates one document's DOCISPAN entries — the read primitives are there (`retrievesporglsetinrange`, `retrieverestricted`), the composite is the gap. So compose the read path the structure already supports, keyed by document — the way this operation reads it. If address-forward lookup is also needed (link resolution), maintain both as two hints over the one journal rather than inverting at query time.

**Current arrangement range `ran(M(d))`.**
`M` comes from the foundation (ASN-0036); the operation needs its deduplicated content-subspace *range* — distinct content-addresses, multiplicity discarded (verified: green's *comparison* collapses to I-space set membership, corroborating set-granularity classification, while green's *deletion* operates per-V-occurrence in V-space — itself the per-occurrence operation the note scopes out — with occurrence count tracked nowhere). Recompute it by a POOM-style V→I arrangement traversal per query, or maintain a per-document range-set as a cached derived view over `M`. This is *not* a self-correcting hint: a stale cached range-set yields a *wrong* `CURRENT` (hence wrong DELETED/NEVER_INCLUDED), and a stale entry is a cache *hit*, so a recompute-on-miss policy never fires. The cached view must therefore be **invalidated on every `M(d)` edit** — i.e. on composite commit — with `M` authoritative. (Under the recommended persistent-DS snapshot this invalidation is automatic, since a new root carries the recomputed view.)

**The computation — set algebra, not a `dom(C)` scan.**
The spec's comprehension scans all of `dom(C)`, but the answer is three set operations over per-document content-address sets:

```
DeletedFromAWithB = ( Rproj(d_A) ∩ ran(M(d_B)) ) \ ran(M(d_A))
DeletedFromBWithA = ( Rproj(d_B) ∩ ran(M(d_A)) ) \ ran(M(d_B))
```

The `∩ ran(M(partner))` is the witness condition; the `\ ran(M(self))` is "absent now"; anchoring on `Rproj(self)` supplies the provenance that excludes never-included content (and, since `R ⊆ dom(C)×E_doc` by P7, keeps the result content-only by construction). This is precisely the set-difference udanax-green never composed — it shipped only the *intersection* (compare-versions / SHOWRELATIONOF2VERSIONS, verified) and left the difference to client-side arithmetic with no list-level subtract primitive. We compose it directly. The common case (two related versions with small divergence) touches only the documents' own sets, not the corpus; the pathological case stays bounded and correct by finiteness. A cheap short-circuit falls out of D-DISJ: non-empty output *requires* `Rproj(d_A) ∩ Rproj(d_B) ≠ ∅` (at a boundary, any witness `a ∈ ran(M(d_B))` forces `a ∈ Rproj(d_B)` by D-WIT), so a disjointness pre-check on the two `R`-projections rules out unrelated documents before any arrangement is read. This is a *necessary screening* condition for the note's first open question, not its full answer: non-disjoint projections rule unrelated documents *out*, but shared provenance alone does not predict non-empty output — an address CURRENT in both documents contributes to neither half. The actual non-emptiness predicate is sharper — some `a ∈ Rproj(d_A) ∩ Rproj(d_B)` that *diverges in arrangement*, present in exactly one of `ran(M(d_A))`, `ran(M(d_B))` and absent from the other. The note's edge cases need no special-casing — the algebra subsumes them: `d_A = d_B` yields two empty halves (`(Rproj(d) ∩ ran(M(d))) \ ran(M(d)) = ∅`); both-arrangements-empty empties both halves (an empty `ran(M(partner))` kills the witness intersection); and asymmetric population — rich `Rproj(d_A)` but empty `ran(M(d_A))`, against a witness-rich `ran(M(d_B))` — yields a large `DeletedFromAWithB` and an empty `DeletedFromBWithA`, mirroring the editing asymmetry.

Represent the per-document sets as *ordered* sets keyed by tumbler order (T1). Ordered representation buys three things at once: D-ORD's output ordering for free, sorted-merge intersection/difference (linear in the operands), and clean coalescing into spans. A hash representation wins only for isolated point-membership, which this query doesn't dominate. A persistent (structurally-shared) ordered-set structure is the obvious carrier.

**Snapshot and concurrency — lean on D-OBS.**
Because the query writes nothing, it can run against an immutable snapshot with no locking. Persistent (structurally-shared) state makes this free: committing a composite swaps in a new immutable root, and the query reads whatever root is current — but "always reads a boundary" holds *only if the root swap is composite-granular*; an elementary-step swap would expose the torn read below. The note lists the consistency model as an open question (and a separate foundation concern), so this is the *minimal sufficient* condition for this read, not a full answer: SHOWDELETIONS needs a *consistent joint `(M, R)` snapshot* (an MVCC-style read), not full snapshot isolation — it never writes, so there is nothing to serialize against. The hazard to design out is a *torn read*, and the corrupting direction is `R` *ahead of* `M` — a composite's provenance append visible before its arrangement edit. A freshly placed address then satisfies DELETED's definition exactly (`(a,d) ∈ R ∧ a ∉ ran(M(d))`), fabricating a phantom deletion. Note this tear lands on the *legitimate* DELETED row, so D-WIT does not catch it — the other direction (`M` ahead of `R`) is benign, since `a ∈ ran(M(d))` makes `a` CURRENT regardless of `R`. That benign direction is exactly D-EXH's "impossible row" (`a ∈ ran(M(d)) ∧ (a,d) ∉ R`) made transiently visible: the exhaustion table forbids that combination at a boundary, so observing it is itself the signature of a non-boundary read. Closing it is the standard atomic-commit discipline: a composite must publish its arrangement edit and its provenance-journal append in one root swap, which closes both directions at once — composite-granular commit is precisely what keeps every read on a boundary, restoring the exhaustion invariant the meaning rests on.

**Output representation — address-based, because the reported content has no V-position in the document it was deleted from.**
Return the addresses themselves (D-IDENT — the output *is* the existing I-addresses, so identity is preserved by reference); origin is derivable (S7), and the address prefix structurally names its originating document (verified). Do *not* attempt to return the *deleted-from* arrangement positions: the reported content has no current V-position *in the document it was deleted from* — that absence is exactly what DELETED asserts — so the deleted-from side can only be named in I-address terms. (It *is* CURRENT in the witness partner, so it has a V-position *there* — but that position belongs to the witness and is not part of the abstract output.) Green's span-with-origin (a sporgl, not a position spec) is the representation for the strictly *no-witness* case — content with no live V-position *anywhere* — i.e. the no-witness leg (sub-case (b) in the guarantees table), not the witness-backed report this operation emits. D-ORIG is explicit that the output need carry no origin annotation — `origin(a)` is recoverable from the address alone — so the natural enriched encoding, (content-address-span, `origin(a)`), is a *denormalization for the restoration consumer's convenience*, not a correctness requirement. The *deleted-from* document need not be carried at all: it is already encoded positionally by *which half* an address lands in, so `origin(a)` is the only non-positional enrichment worth carrying. (Contrast green's sporgl, whose `sporgladdress` is the *holding* document — for transcluded content that is **not** derivable from the I-address, unlike `origin(a)`, so green's field is not an instance of denormalizing a derivable value.)

## Guarantees to uphold

| Guarantee | Holds by… |
|---|---|
| **Provenance permanence** (DELETED stays detectable) | construction — append-only `R`; never GC a provenance fact, even when content leaves every arrangement |
| **Discrimination** (DELETED ≠ NEVER_INCLUDED) | active — you must actually consult `R`; the arrangement set-difference shortcut is provably wrong (D-DISCR) |
| **Identity, no copies** | construction — return existing addresses |
| **Origin determinacy** | construction — origin read from the address (S7) |
| **T1 ordering of each half** | construction *if* ordered-set representation; otherwise active sort |
| **Disjoint halves / symmetry** | construction — definitional (contradictory partner-membership; name substitution) |
| **Observationality, no persisted artifact** | construction — read-only query path |
| **Content-subspace restriction** | construction — output ⊆ `dom(C)` and P7 grounds `R` in `dom(C)`, so links cannot enter. Structurally, cross-document comparison is meaningful *only* over `s_C`: content addresses can be shared across documents, so a partner can serve as the still-current witness, whereas by CL-OWN a document's link V-positions reference only its *own* link addresses — no document ever holds another's link as witness, so deletion comparison over `s_L` is impossible, not merely absent. The only active care is not commingling link provenance in the index. (This is where green crashes; the spec's subspace algebra removes the hazard outright.) |
| **Consistent-snapshot meaning** | active — publish each composite's `M` edit and `R` append in one atomic root swap; then reads are boundary-consistent by construction |
| **Witness-backed existence of every reported address** | construction — output ⊆ `dom(C)` and the partner copy is CURRENT, so every *reported* address still exists and has a live witness *in the pair*; the operation does not itself recover — it guarantees the witness-backed existence that *enables* the handed-off identity-preserving COPY. *Coverage limit:* both halves require `CURRENT(a, partner)`, so an address DELETED from both compared documents appears in neither half — and the two sub-cases route to different recovery legs. (a) Deleted from both *compared* documents but still CURRENT in a *third* document outside the pair (surfaced by the note's >2-document generalization): it *has* a live witness, just not in the pair, so ordinary witness-based V-space COPY from the third document recovers it. (b) Deleted from *every* document: no live witness anywhere, hence no live V-position, so only the direct-I-address COPY — the genuine no-witness recovery path — reaches it. Both are scoped to the note's open questions. |

## How it fits

- **Leans on ASN-0047** for the provenance relation `R` and its laws (P2 permanence, P4★ bounds, P4a historical fidelity, P7 grounding, the subspace convention, CL-OWN link ownership). The critical dependency: `R` is defined there; SHOWDELETIONS is the operation that makes it load-bearing.
- **Leans on ASN-0036** for the content store `C`, the arrangement `M(d)`, and `origin` (S7) — supplying `ran(M(d))` and origin derivation.
- **Leans on ASN-0034** for T1, which orders each output half.
- **Leans on the transclusion-multiplicity results (ASN-0058 / ASN-0036)** for the licence to classify at set granularity.
- **Hands to a restoration / undelete operation** (a spec open question and the obvious downstream): SHOWDELETIONS produces the candidate set; an identity-preserving COPY-style operation consumes a subset to reintroduce content from the witness, preserving origin and links — verified as the mechanism (COPY shares addresses; INSERT would allocate fresh and sever identity). The document-forward `R` projection the recommended strategy builds also yields the *no-witness* recovery primitive directly — `Rproj(d) \ ran(M(d))` is all content ever deleted from `d`, witness or not — so the same substrate is the basis for the note's open questions on recovering content that has left every arrangement. Its restoration leg is the direct-I-address COPY (verified), since no-witness content has no live V-position for the witness-based, V-space COPY above to reach.
- **Hands to a presentation layer** that renders deletions in a witness-derived reading order (a spec open question).
- Sits in the operations layer as a read-only observational query, above the foundation state and the provenance layer.

## Decisions for the builder

Genuinely open *engineering* choices (distinct from the note's spec-level open questions):

- **`R` granularity:** singleton-address set vs. content-address spans. Prefer spans (compact; enables coalesced output); accept interval logic.
- **`R` access path:** document-forward index (what this query needs) vs. address-forward (what link resolution needs) vs. both as hints over one journal. Build document-forward at minimum; most substrates will want both.
- **`ran(M(d))` materialization:** recompute by arrangement traversal vs. cache a per-document range-set. Cache for read-mostly workloads; keep `M` authoritative and invalidate the cached view on composite commit.
- **Set representation:** ordered (T1 — free ordering, sorted-merge ops, coalescing) vs. hash (point membership). Prefer ordered.
- **Candidate strategy:** literal `dom(C)` scan vs. the `Rproj ∩ ran(M) \ ran(M)` set algebra. Prefer the algebra; it is bounded by the documents' sizes, not the corpus. A disjointness pre-check on the two `R`-projections (D-DISJ) short-circuits unrelated documents before any arrangement read.
- **Output encoding:** bare address set vs. enriched origin-tagged spans. Origin is derivable from the address either way (D-ORIG), so enrichment is a denormalization, not a correctness need; decide by the consumer — restoration wants the enriched form.
- **Snapshot mechanism:** immutable-root swap (persistent DS) vs. read-lock vs. MVCC. With persistent DS the read is lock-free — the cheapest mechanism meeting the contract.
- **Result caching:** results are memoizable keyed by (state-version, `d_A`, `d_B`) — this rests on D-RECONS (the output is a function of state alone, independent of history), with D-OBS giving the per-state repeatability. Persisting a result is *optional*, not forbidden: D-STORE only says the result is *not required* to be stored as a document, and the operation itself writes nothing (D-OBS), so any persistence is a separate downstream write — a volatile cache needs none. Decide if the workload warrants it.
