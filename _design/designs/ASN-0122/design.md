## What this is

The COMPARE / SHOWRELATIONOF2VERSIONS operation: the read-only query that answers "show me, word for word, what parts of these two regions are the same." It takes two spec-sets (each a set of documents with windows onto their content) and returns an aligned list of span-pairs that resolve to the same stored occurrence — the same content *address*, not merely an equal value. It is a pure observation — it reads the arrangements of the documents named in the two spec-sets and changes nothing. The same machinery, pointed at one document with two disjoint windows, becomes an internal-sharing detector, so inter-version compare and intra-document "where is this reused" are one operation, not two.

## Design commitments

These are locked in; nothing downstream may violate them.

- **Correspondence is address equality, never value equality.** Two positions "are the same part" *iff* they resolve to the same stored content address. This is **forced** (X1/X2): value-matching over-reports — two independently authored, byte-identical passages have distinct addresses and must *not* correspond — and it would break the "same part" reading. The practical consequence is the operation's most striking property: **it never opens the content store.** The entire computation lives in address space.
- **The operation is a pure observation — total frame.** It allocates nothing, arranges nothing, links nothing, records nothing; the post-state equals the pre-state. **Forced** (X12). It therefore needs no journaling, no recovery, no locking beyond a consistent read.
- **It is local: a function of exactly the two regions' resolution maps.** It reads neither content values, the link store, the entity set, provenance, nor any other document's arrangement. **Forced** (X5). This is what buys determinism, indifference to every edit elsewhere in the docuverse, and memorylessness (no past arrangement can manufacture a pair).
- **Both soundness *and* completeness are binding.** Unlike a diff, the report must contain *every* correspondence and *only* true ones. Because the relation is finite and decidable, approximation is no excuse. **Forced** (R1+R2). Completeness has more than one obligation — the in-window portion of a boundary-crossing run must survive (window-exactness, X4), which is by-construction if you clip-then-join — but the hard case, and the one the reference implementation gets wrong, is *fan-out* (the same content arranged at several positions).
- **Restricting to the content subspace is semantic and lossless.** Link positions can carry no cross-position, cross-document, or cross-operand correspondence, so the content-only restriction discards no correspondence information — **lossless by X9**, and **made binding by X12's precondition**. The precondition that rejects link-subspace spans is correctness, not a limitation.
- **Edits transport correspondence; they never re-pair it.** Every arrangement edit moves addresses verbatim and induces an injective, address-preserving position map, so a prior correspondence is conserved element-for-element under that map — only V-coordinates and run-fragmentation change. Transclusion chains transport it undiminished regardless of length; there is no hop count to attenuate. **Forced** by the substrate (X6/X7/X-T); load-bearing for any caching and for the whole system's model of versioning.
- **Denotation is fixed; presentation *granularity and packing* are free — but the presentation must be deterministic.** *Report* conformance is denotational (R1+R2): any list of consistent, confined pairs whose union is the relation conforms. But a conforming *implementation* must additionally emit its report as a deterministic function of the inputs — **R3 is binding** — so "free" means free to choose granularity and record packing (R4), *not* free to let pair ordering vary run to run. The canonical maximal-run form, the lexicographic list order, and the (document·V-start) record packing are the *reference* presentation, **conventional** not required (R4); the implementation must fix *one* deterministic presentation of the relation. The one convention you must honor is that within-pair slot *i* draws from operand *i* — that is what makes the symmetry claim (compare(A,B) is the transpose of compare(B,A)) contentful.

## What must be built

- **A region resolver/clipper.** For each named document, clip the operand spans against the *current* content-subspace arrangement and yield each surviving position with the address it now holds — walking only the requested window, not the whole document. Empty operands, spans that clip to nothing, and empty results are all legal and must answer with the empty report, never an error.
- **A precondition gate.** Verify each named document exists and each span is T12-well-formed; the subspace precondition is on the span's *start* only (`subspace(start) = s_C`). A span that starts in the content subspace but whose width reaches into link positions — the note's `σ = ([1,5],[3])` — is **legal**, and the gate must not reject it: the region resolver's `∩ V_{s_C}` clip discards the link positions it denotes. Only a span whose *start* is in the link subspace is a precondition matter; whether to reject it or leniently strip it is a builder decision (below).
- **A matcher** — the equi-join of the two resolutions on address — **complete under fan-out**: when an address occurs at *k* positions on one side and *m* on the other, all *k×m* aligned pairs are members.
- **A presenter** that compresses the relation into lockstep runs (or any chosen granularity), orders them deterministically, and emits each as (document, start) per side plus one shared width — as a pure function of the operands and the two restrictions.
- **The operation wrapper** that produces the value while touching no state.

## Implementation approaches

**Resolving a region.** A region is a union of windows — one per document the spec-set names — each over that document's content arrangement, and you need each position's address. Hold the arrangement as an ordered index keyed by V-position (the POOM is the proven structure: a 2-D enfilade over the (V, address) pair) and do a **bounded traversal** — descend only into nodes overlapping the query window. The udanax-green reference does exactly this, and the verified evidence confirms the restriction is applied *pre-walk*, not as a post-filter: a sub-range query performs a sub-range walk. This is the computational dividend of the locality commitment — never scan a whole document to answer a windowed question. A persistent ordered map (V-position → address) gives the same shape: a windowed range-scan with O(1), lock-free snapshots from structural sharing. Either way the resolver's natural output is a sequence of (V-position, address) in V-order, arriving in **runs** — contiguous V-positions backed by a contiguous address interval. Represent each region as a set of (document, V-start, address-start, width) blocks — a multi-document spec-set contributes blocks from each named document; that is the compact form and the unit the matcher wants.

**Matching — this is the heart, and the one place the reference design is wrong.** The contract is a relational equi-join keyed on address, complete under fan-out. Keyed on address *alone*: a block's document rides along but is never matched on, so a left foot in one document may correspond to a right foot in another, and a single report legitimately spans documents whenever a spec-set names several. The reference implementation's pairing step instead advances both cursors in lockstep against a per-interval width budget — a *merge*, not a join — which emits one pair per shared address-unit and orphans every repeated occurrence. The verified consequence is that self-comparison there reports only the diagonal; it is structurally incapable of an off-diagonal pair. It conforms *exactly on injective windows* and under-reports everywhere else. The loss is isolated to that single step: the verified evidence confirms the resolution machinery beneath the pairing already enumerates *every* fan-out occurrence faithfully — it is solely the final pairing loop's per-interval width budget, exhausted after the first occurrence, that drops the rest. So the entire enumeration is reusable wholesale, and exactly one step — the budget-bounded merge — is the thing you replace. The fix is to treat this as a real join. **This is a pure post-resolution decision, independent of bounded traversal:** the bounded, sub-range walk lives in the resolver (above) and is required either way — every matcher here reads only the resolved window, never the whole document — so it is *not* a reason to prefer one matcher over another. The join options:

- *Interval (spatial) join on the address axis, cross-product per overlap* — for each overlapping address sub-interval emit the **full cross-product** of the left blocks and right blocks covering it, refined to the overlap (offset-aligned, single shared width); find overlaps with a sweep or interval tree rather than all-pairs. Because D-SEQ★ and the POOM enfilade make block representation the substrate's general shape — the resolver's own output is `(document, V-start, address-start, width)` blocks — this is the natural **production** default for any non-trivial region, not a fallback: it consumes the resolver's blocks directly and **expands only where fan-out forces it** (the overlap-refinement step), emitting address-aligned blocks that leave the presenter little to coalesce. It is the corrected reference with exactly its one broken step replaced.
- *Hash/sort join on per-position address* — build a multimap address → positions for the smaller side, probe with the larger, emit cross-products. O(|P|+|Q|+|output|), obviously fan-out-complete, no interval bookkeeping. But to build and probe it **expands every block to its constituent positions unconditionally**, discarding the block structure the resolver just produced — so treat it as the simplicity baseline and the cleanest oracle to test any other matcher against, not the production default. One trap: **output slot order is semantic (X3) — slot *i* must draw from operand *i* regardless of which side is built and which is probed.** Building the smaller side and then emitting in build/probe order silently transposes the report (compare(B,A) mislabeled as compare(A,B)); fix slot order to operand order, never to scan order.
- *Nested scan* — the literal definition, O(|P|·|Q|). Tiny cases and tests only.

Whichever you pick, the matcher reads only addresses — give it no path to content bytes. That is simultaneously a correctness property (value-matching over-reports) and a performance one (you never fault in content). Note that completeness can make the output genuinely super-linear (heavy internal sharing is the worst case); keep the matcher complete and push compression into the presenter. The open question of a smaller *multiplicity-annotated* report is real, but the note warns it may not be information-equivalent — so don't sacrifice the matcher's completeness to shrink it. To verify completeness, the sharpest test is **equal-window self-comparison of a region with internal repetition**: in the note's worked example, comparing d₁'s whole extent with itself must return six elements — the four-element diagonal plus the two off-diagonal pairs `(p,q)` and `(q,p)` (X8b) that witness the content arranged at two positions — where the merge-based reference returns only the four. The disjoint-window detector (X8c) is the operational instrument; this equal-window case is the test that exercises the exact fan-out bug.

**Presenting.** Run-length-coalesce the relation along the successor relation (both feet advance by one and stay in the relation), then sort by (first foot, second foot). If the join already emits address-aligned blocks they are mostly maximal; coalescing is a linear pass. The reference already emits in first-operand V-order (Q14), and that order **coincides with X11's canonical order exactly on injective (no-fan-out) windows** — so a resolver that yields blocks in operand-1 V-order is already canonical for the common case, and the second-foot tie-break is the *one* point where the two can diverge. That tie-break is therefore load-bearing, not cosmetic: under fan-out several runs land on one first-foot start, and only the tie-break separates them. The sharpest test for the tie-break in isolation is a fan-out region where two runs share a first-foot start — exactly the worked example's swap (X3), where γ₁ᵀ and γ₂ᵀ both start at (d₂,[1,1]). Rearrangement that scatters a shared run simply produces more, shorter pairs (refragmentation): denotation conserved, presentation split, exactly as observed in the reference's one-pair-per-arrangement-block output.

**Caching — treat it as a hint.** The relation is cheap and local, so the simple thing is to **recompute** it and keep no authoritative duplicate. If profiling ever shows repeated identical compares, a stored correspondence index is a Lampson *hint*: recomputable on a miss, never trusted blind. Its consistency contract under an edit to either compared document is precisely the transport theorems — permute feet on reorder, intersect with survivors on contraction, apply the gap-closing shift on shifting contraction, only-add on extension — or, simpler and always correct, invalidate and recompute. Default to no cache.

**Snapshot and access discipline.** Being a pure read, it needs only a consistent view of the arrangements it touches — but that view must be **one consistent snapshot (a single Σ) spanning *all* documents named across the two spec-sets**, not a separately-timed read per document: corr is defined at one Σ (X5 reads `res_Σ|P` and `res_Σ|Q` at the same Σ), and resolving two named documents at different states yields a relation valid at no single Σ and breaks determinism (R3). With persistent structures, one reference to current state gives this for free — lock-free, isolated from concurrent edits; an explicit-lock approach must arrange the single consistent view deliberately. Keep the access pattern tight — read *only* those arrangements, never a document-membership or span index. The reference implementation gets memorylessness for free this way: stale membership entries that survive deletion can't fabricate a pair because that path is never opened. Enforce locality by what you read, not by filtering after.

## Guarantees to uphold

- **Certification of "sameness"** — *by construction*: binding both feet to one store entry makes equal value an entailment, never a check.
- **Soundness** — *mostly by construction* if you join the clipped regions; the presenter must preserve per-pair consistency and confinement when it coalesces.
- **Completeness** — *actively enforced*, and the hard one: the fan-out cross-product is where it is won or lost. (Window-exactness is also a completeness obligation, but it is by-construction from clip-then-join — see below.)
- **Determinism** — *enforced*: fix one presentation and one iteration order; no hidden input.
- **Symmetry** (compare(A,B) transposes compare(B,A)) — *by construction* if the join is symmetric and slot *i* = operand *i*.
- **Window exactness** (sub-range queries report exactly the in-window part — no invention, no silent loss) — *by construction* from clipping plus joining the clipped regions. Clipping a single-span window against a maximal run yields **at most one contiguous pair** (X4c) — one block in, one block out — so refragmentation arises *only* from rearrangement (X7), never from the clipper.
- **Purity/frame** — *by construction*: give the operation no write capability over the state.
- **Edit-stability** (correspondence transports, never re-pairs) — *inherited* from immutable bindings and verbatim address transport; you must honor it only if you maintain a cache.

## How it fits

- **Consumes** one foundation capability — resolution of a windowed arrangement (position → address) over the documents' POOMs (arrangement indexes into, but not part of, the content store `C`) — and the tumbler/address algebra (ASN-0034: address equality via intrinsic comparison, ordinal shift for runs/offsets, shift-monotonicity for the maximal-run argument) and span algebra (ASN-0053: the operand language, clipping, the canonical sequential arrangement shape that makes runs dense).
- **Leans on, but does not call,** the edit operations (extension/contraction/reorder, ASN-0082 shifting contraction) — only via their frame and position-map clauses, to know correspondence transports.
- **Reads neither** the link store, provenance, nor any document-membership/spanfilade index — and the design should keep it that way.
- **Hands** its report up to intercomparison consumers — version diff/merge views, transclusion-provenance displays, and (pending the n-way composition question) multi-document alignment built from pairwise reports. **A single pair asserts a bounded fact** (X10): its two spans realize the *same address sequence* — hence the same value sequence — in the *same order*, and *nothing else* — nothing about neighbouring positions, nothing about how the sharing arose, nothing about any other state component. Consumers must not over-read a pair as implying contiguity, provenance, or neighbor-correspondence; this bound is *why* the minimal record — (document, start) per side plus one shared width — suffices, with deliberately no provenance or neighbor fields. It sits at the read/query tier of the operations layer beside the other content-region-query observers.

## Decisions for the builder

- **Matching algorithm**: interval-join-with-cross-product (consumes the resolver's blocks directly, expands only on fan-out, emits address-aligned blocks so the presenter coalesces less; closest to the corrected reference) vs. hash/sort join on per-position address (simplest and obviously fan-out-complete, but expands every block to positions unconditionally — the simplicity baseline and test oracle). Bounded traversal is a resolver property shared by both, not a matcher discriminator. Default to the interval/block join for non-trivial regions because block representation is the substrate norm (D-SEQ★ + POOM); keep the hash join as the oracle.
- **Region representation**: (document, V-start, address-start, width) blocks vs. a flat (document, position, address) sequence. Resolve to blocks; expand only where fan-out forces it — that expand-on-fan-out-only discipline is the interval join's, whereas a per-position hash join expands every block unconditionally.
- **Presentation granularity**: maximal co-advancing runs vs. allocation-interval-aligned runs vs. finer. Any conforms; fix one and document it (the engineering side of the interop-granularity open question).
- **Cache or not, and how**: default recompute; if you cache, choose incremental transport via the edit position maps vs. invalidate-and-recompute. Either way, a hint, never authoritative.
- **Record packing**: composite (document·V-start) tumbler per side (reference) vs. explicit (document, start) fields — packing is representation; keep the width shared.
- **Output under heavy fan-out**: stream the report (it can be large) vs. materialize; pick a streaming order consistent with your deterministic presentation.
- **Width precision**: the reference truncated multi-digit tumbler widths to machine integers — a latent bug for very large windows. Decide your width representation carries full tumbler magnitudes, or document the bound.
- **Snapshot mechanism**: a persistent-structure reference (lock-free, the simple choice) vs. an explicit read lock.
- **Link-start spans**: reject them as a precondition violation (loud) vs. leniently strip them with a content-subspace front-filter up front (what the reference added, implementing X12's precondition). Either honors the contract. (Spans that merely *denote* link positions from a content start are always legal — the resolver clips them — so this decision is only about spans whose *start* is in the link subspace.)
