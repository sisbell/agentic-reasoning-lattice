## What this is

The windowed (paginated) link-search read protocol — `FINDNEXTNLINKSFROMTOTHREE`. It defines how the substrate hands back a potentially huge set of query-matching links a bounded batch at a time, letting a reader resume exactly past where it stopped, and states what *resumable enumeration of a state-dependent matching set under a total order* must guarantee. It is the contract on delivery, not the index that does the matching.

## Design commitments

These are the locks. I'm explicit about what is *forced* versus merely conventional.

- **The protocol is stateless; the entire continuation lives in the client's cursor** (W3). No server-side iterator, no cached result list, no per-reader generation counter. **Forced** given the crash/reconnect/concurrent-reader goals the note names — this is the central architectural decision against which every other property is read. A server-side materialized list is permitted *only* as a droppable hint that never becomes authoritative.
- **The cursor is a link identity (a permanent address), never a positional offset** (W2). Resumption is "past *that link*," not "items 100–200." **Forced** over a mutable set: an offset cursor's correctness precondition (no net count change at or below the cut) is silently broken by any insertion or orphaning at or below the cut between calls; an identity cursor's only precondition is that its key still be computable.
- **The matching set is a live, present-tense view, not a frozen snapshot** (M-mut, W7). It gains members (links created) and loses them (links orphaned when their endpoint content leaves the consulted region). **Adopted, not merely inherited**: the note *chooses* the discoverability (live-view) reading — Nelson's "show me what's arrived since I last looked" — over the monotone, historical *fixed-`I`* store-membership reading ASN-0127 also supplies. This is the pivotal semantic fork: it is what makes Match non-monotone and forces the whole orphaning/resurrection apparatus (W8 cursor-survival, W9b inflow). The monotone alternative would obviate half of it — no orphaning means the cursor trivially survives and there is no resurrection inflow. Completeness is therefore *per-call-state*, never against one global population.
- **Enumeration is by a single total, injective ordering key, drawn from permanent identity, not current position** (W0/W1, W5/W8). **Forced for correctness**: a position-derived key skips live links a rearrangement moves below the cursor, goes dark when the cursor's content is deleted, and makes the empty window ambiguous. *Which* permanent key — link address vs least-covered content tumbler — is a genuine **design parameter**, not forced — though the note names the **link-address key as its *intended* one** (Nelson's arrival-order reading), parameterizing the formal key only to admit Gregory's content-drawn alternative.
- **Termination is a short window (fewer than N, zero included), with no terminal marker** (W9). **Forced** minimal mechanism; the exact-multiple case must be read as "≤ N including 0" or the reader loops forever.
- **The reply carries no absolute progress** — no rank, no total (W10). "k of m" is a front-end synthesis over a separate cardinality query. Convention (Nelson's "handled invisibly"), but locked here as a frame condition.
- **Window boundaries are objective** (W11): same `(q, c, N, Σ)` → same batch and same next cursor for every reader. Follows by construction from determinism.

## What must be built

Described functionally:

- A **discoverability query** that, given a query (from/to/type content region) and the current state, yields the finite set of links presently reachable. (This is ASN-0127's `findlinks_V`; windowing consumes it whole.)
- An **ordering key** assigning every matching link a value in a totally-ordered space — defined on every matcher (total) and separating distinct ones (injective), with an address tiebreaker restoring injectivity when the primary key is content-drawn.
- A **windowing function**: given (query, cursor, N, state), compute the successor set (matchers whose key exceeds the cursor's), return its ≺-least `min(N, |successor|)`, and report the batch's ≺-max as the next cursor (or the cursor unchanged when empty).
- **Cursor evaluation**: recompute the cursor's key against the current state and take the successor cut (the ≺-least matchers whose key strictly exceeds it) — never an exact-match scan for the cursor link — robustly, even after the cursor link has itself left the matching set.
- **Exhaustion detection**: recognize a short/empty batch as terminal.
- (Referenced, out of scope) a **cardinality query** for progress, and the front-end tally that pairs with it.

## Implementation approaches

**1. The matching-set query — how much to recompute per window.**

- **(A) Full re-materialization each call** — re-execute the full search and build the entire ordered list, then resume. udanax-green's literal resume is an *exact-match linear scan* for the cursor link followed by truncate — and that is the one thing **not** to copy: when the cursor link has orphaned out of the re-materialized list, the scan finds nothing and returns an empty batch with count 0, *indistinguishable from genuine exhaustion* (Q12, Q17). That failure lives in the *resume mechanism*, not the key, so even an address (identity) cursor goes dark under it — exactly the W8 ambiguity the note otherwise pins on the position key. The correct stateless version re-materializes but resumes by **key-cut / successor search**: deliver the ≺-least matchers whose key is *strictly greater than* the cursor's key, never an exact-match scan for the cursor link. Per key: address key → "first matcher with address > c," the cursor link need not be present; content-composite key → re-derive the cursor's content boundary from its immutable endset (L12/LP13, still readable after orphaning) and successor-search by (boundary, address). With that cut it is simple, trivially stateless, and correct. Cost is O(|Match|) per window, O(|Match|·W) over W windows — quadratic in the very avalanche windowing exists to tame. Pick for small/medium result sets or a first cut.
- **(B) Cursor-seeked index walk** — exploit that the cursor is a *key*: seek into a key-ordered index and walk only N matches forward, O(N + seek) per window. This is available precisely *because* W2 made the cursor a key rather than an offset. The walk must be restricted to the query's *current image* — the I-addresses the query region resolves to through the consulted arrangement (`findlinks_V = findlinks(image(W, d_q, Σ), Σ)`); a bare global index walk is not `Match`, and this restriction is exactly where orphaning enters (the image shrinks when matched content leaves the region). udanax-green pointedly does **not** do this (the cursor never enters the spanfilade search; it is consumed as a post-materialization linear-scan bookmark), but the design permits it. Requires the index's native order to coincide with the enumeration key; multi-endpoint intersection (from ∩ to ∩ type) turns it into a merge of ordered streams — and that merge must *re-establish the total enumeration key order*, not merely intersect: order-preservation across the combine is load-bearing (without it W0's unique listing and W4's partition both break), automatic only when every stream is sorted on the same key (for a content key, the `(boundary, address)` composite). The evidence does not settle whether Green's `intersectlinksets` preserves order (Q11 flags it open), so the builder must guarantee it. Pick when result sets are large and the index is key-aligned.
- **(C) Hint-cache** — keep a materialized ordered list keyed by (query, state-generation); seek on hit, re-derive on miss. Honors W3's *observable* statelessness while amortizing repeat paging. But the keying assumes a *state-generation* the substrate does not provide: W3 records that Green keeps no generation counter, and Match is non-monotone in the consulted arrangement, so cheaply and correctly detecting a query-relevant change — the validity signal a hit/miss check needs — is the *hard* part, not the seek-on-hit. Without it the check costs a full re-derivation, defeating the cache; so (C) pays off only if you first add versioning the substrate lacks. It must also stay a true hint — droppable, never authoritative; the moment it becomes the system of record you've reintroduced the eviction/invalidation/divergence costs W3 was built to avoid. Use only as an optimization atop (A) or (B).

Recommendation: **(B) when index order matches your key; (A) as the correct fallback for intersection-heavy queries; (C) sparingly.** Caveat (see *Key/index coupling* below): no *permanent* key is the spanfilade's free native (matched-slot) order, so (B) on a correct key always presupposes a purpose-built address-ordered or derived index — its native-order speed is available only against a *frozen* set; fold that index cost into the choice.

**2. The link index.** The proven structure is the **spanfilade**: a content-address-keyed index recording each link under all three of its endsets (from/to/type) at fixed structural tags written once at creation — the query selects which tag to filter on, never re-indexing. It is **append-only**: orphaning never deletes index entries; a link leaves the *view* by losing its content mapping, not by leaving the index.

A **raw index walk is not `Match`, but a current-image lookup is.** The spanfilade is append-only, so walking it globally returns every link whose endpoint I-addresses were *ever* indexed — not the present matchers; you must search the query's *current* image, not the index at large. That restriction is sufficient as well as necessary: `Match = findlinks_V = findlinks(image(W, d_q, Σ))`, and the image is the query region's *current, reachability-resolved* V→I map, which Green builds through the consulted document's POOM as stage 1 of the search, *before* the spanfilade lookup (Q15/Q20). Restricting the lookup to that image yields *exactly* `Match` — no per-candidate post-filter: a link overlapping the reachable image has a matched endpoint still in `ran(Σ.M(d_q))`, hence non-orphaned, hence in `Match`, and conversely. Orphaning shows up as the image *shrinking* (matched content leaving the region), dropping the link automatically (= W7) — precisely what approach (B) demands. The genuine **ghost** (Q20) is a *separate, downstream* matter: a delivered link that truly matches the query that found it — its *matched* endpoint sits in the reachable image — yet whose *other*, non-matched endpoints have orphaned, so that *following* it to render its endsets yields empty endsets once the link's own I→V conversion drops the now-unmapped addresses. That conversion is a display-only step downstream of windowing, **not** a window-build-time filter: the link belongs in `Match` and in its window slot; filtering it would make windows carry fewer than `Match`, miscounting N and mis-signalling exhaustion. Layer accordingly — the spanfilade is the matching/ordering *index*; `findlinks_V` is the discoverability layer above it (query region → reachable I-addresses, then index lookup against that image); endset rendering on *follow* is a third layer, where the ghost surfaces.

A persistent, structurally-shared **ordered map keyed by (endset-slot, content I-address) → link address** realizes Green's *matched-slot* order — links ordered by the content address they matched in the queried slot. This is the map's *native* order and the cheap one for approach (B), but it is *query- and state-dependent*: it keys on the *matched, in-image* endpoint, whose key **moves both ways under mutation**. Partial orphaning (a link's least matched endpoint leaves the image while a higher one survives) slides its key *up*: a below-cursor link re-ascends above the cursor → **re-delivery (duplicate)**, never a skip; a tail link merely lands later, still reachable. An arrangement extension or resurrection that draws a *lower* matched address *into* the image (LP9) slides its key *down*: a tail link falls below the cursor → **skip**. Both are clause-1 cut-point violations (W5) committed *while the link stays in `Match`*, so matched-slot order is safe only against a *frozen* set (W4), not a mutating one. It is *not* the note's a-priori least-covered-tumbler key (a single value per link, fixed independent of which slot a query matches); ordering by *that* key instead requires a *derived* `link → least-covered-tumbler-of-designated-slice` index — the native order does not supply it. Recovery should keep the index a *hint*: journal link creations to an append-only write log and **rebuild the index by replay on load**, so it is recomputable from the journal plus content/arrangement state and never the system of record. The note and evidence are silent on index durability, so this is a design recommendation, not a derived requirement.

**3. The ordering key — the central choice.**

- **Address key** κ(a)=a: value-total (key computable from the held cursor value with *zero* state lookup → W8 free), state-stable (both cut-point and tail-order frozen by construction → W5 free), and allocation-monotone within one home document (new links append at the tail → delivered in later windows, W6). Cost: not globally monotone across multiple home documents (blind spot reopens cross-document, Open Q1), and it does **not** align with a content-addressed index, so approach (B) needs a separate address-ordered index or a per-window sort. Pick when "show me what's arrived since I last looked" matters most and results cluster in a home document.
- **Least-covered-tumbler key** (least content tumbler covered by a fixed endset slice, with link address as low-order tiebreaker): permanent, hence state-stable (W5) and computable through orphaning (W8) — nearly the address key's robustness. Crucially it is *immune to the image-shrinkage hazard* that afflicts Green's matched-slot order (§2): keyed on the *covered* address of a fixed slice rather than the matched-in-image endpoint, its value cannot slide when partial orphaning shrinks the image — which is exactly why the note builds it. Cost: it is **not** the spanfilade's native order, so approach (B) needs the *derived* `link → least-covered-of-slice` index of §2, not a free seek into the content map; and it is not allocation-monotone (W6), so a newly created link whose covered content sorts below the cursor is **silently skipped for this pass** — a permanent blind spot. To stay total the slice must include the type slot (every link has a non-empty type endset), so even links with empty from/to endsets get a key. Pick when state-stable paging outweighs the derived-index cost and the new-link blind spot.
- **Content-position (V-position) key**: **rejected.** Mutable — fails cut-point stability (skips live links), fails cursor survival (κ(c) uncomputable once the cursor's content is deleted → empty window indistinguishable from exhaustion), fails append-at-tail. The only structure that yields it naturally is a position-ordered POOM walk; do not route link search through it. *(Evidence note: udanax-green orders results by the matched endpoint's content I-address — the spanfilade's content (SPANRANGE) dimension — not by any V-position; that much is well-grounded. One evidence answer (Q11) calls that dimension "V-address," but that is terminological: the sorted SPANRANGE holds content I-addresses, not V-positions, as the dedicated sort-key consultation and Q15 confirm. Two riders the evidence corrects: Green keys on whichever slot the query **matched** (query- *and state*-dependent — each content I-address is permanent, but *which* is the least matched address, and so the key, moves with the image under partial orphaning; the key is **not** a function of the immutable link value alone), so it realizes the **matched-slot** order, distinct from the note's a-priori-fixed-slice least-covered-tumbler key; and link-ISA serves only as a **dedup** key (each distinct link appears once), which **corrects the source note**'s reading that "the link's permanent address is the de facto low-order key, not a traversal accident" — the order among distinct links sharing a content boundary is in fact enfilade traversal order with **no** address tiebreak, the very traversal accident the note denies. The (boundary, address) composite W0/W1 require to make a content key cleanly injective is therefore a design obligation the builder must add, not behavior Green already realizes.)*

**Key/index coupling.** The spanfilade's *native* (matched-slot) order serves *neither* recommended permanent key directly — the address key is content-misaligned (needs an address-ordered index or per-window sort), the least-covered key needs a derived index, and the native order itself is state-dependent and safe only on a frozen set. There is no permanent, state-stable key that is *also* the index's free native order, so the key choice (decision 1) and the index representation (decision 3) must be settled together.

**4. Cursor token format.** The cursor is a link address. Minimal token = the bare address; recompute κ(c) on resume (zero lookups for the address key; one immutable-endset read for the least-covered key — always available by L12/LP13). Builder option: a **fattened opaque token** carrying (link address, cached key) to skip the lookup — safe *precisely because a permanent key never goes stale*; this is the cheapest correct optimization, a hint cached in the client. Never fatten a position-derived key: it would resume against a stale cut.

**5. Exhaustion signaling.** Short window = terminal, zero included. Either return the delivered count explicitly (friendlier) or let the client compare batch size to requested N (udanax-green drops the count on the wire and relies on the client). Whichever — the client must stop on `|batch| < N` *including* `|batch| = 0`, or it loops forever on exact multiples. With a permanent key *and key-cut resume*, the empty window is unambiguous (the cursor key stays computable and the cut is taken against it, so empty = exhaustion); a position key — *or* an exact-match scan that resumes by locating the cursor link (§1A) — creates the empty-vs-invalid ambiguity, which then needs an extra signal.

## Guarantees to uphold

- **No duplicate / no skip of continuously-matching links** (W4/W5) — for either permanent key (their comparisons never move): *no re-delivery* is unconditional, *no skip* holds given the pass terminates (W5's termination hypothesis). Requires active enforcement only if you stray to a position key.
- **Cursor survives orphaning** (W8) — needs *both* a computable key *and* a key-cut resume (successor search on κ(c), never an exact-match scan for the cursor link). A permanent key supplies the computable key by construction; the key-cut resume is on the implementation — udanax-green has the former but not the latter, which is exactly why its address cursor still suffers the empty-vs-exhausted ambiguity. Lost outright for position keys (κ(c) becomes uncomputable on deletion).
- **Append-at-tail for new links** (W6) — by construction *only* for the allocation-monotone address key, and *only* within a home document; not guaranteed for content keys. State the blind spot, don't hide it.
- **Determinism / boundary objectivity** (W3/W11) — by construction from a pure windowing function reading no hidden state.
- **Termination** (W9a/W9b) — by construction against a fixed set; over mutation it requires finite cumulative tail inflow *plus* cut-point preservation. A permanent key discharges *cut-point preservation* by construction and forecloses the W9c re-ascension livelock (a still-matching *delivered* link re-rising above a later cursor **cannot occur** — a permanent key returns any resurrected link *below* the advancing cursor, W9b). It does **not** make *finite inflow* free: that is a separate, workload-dependent condition, and its violation is *legitimate* unbounded cumulative inflow (new matchers genuinely keep arriving) — correct non-termination, not a livelock. So W9c is a reason to *reject the position key*, not a guard to implement; bounded *instantaneous* tail size is never sufficient for termination (W9b).
- **Index permanence** — links never renumber, never reuse addresses, endsets immutable; orphaning is view-loss, not deletion. By construction from ASN-0043.

## How it fits

A *read protocol* layered above the link index and the arrangement/content stores. It leans on:
- **ASN-0127** for the matching predicate (which links are discoverable from a content region) — windowing delivers that set, never re-derives it.
- **ASN-0043** for the link store's permanence: finite, append-only domain, immutable entries, total tumbler line (T1) — the bedrock the permanent keys stand on.
- **ASN-0098** for content-region projection and its monotonicity (LP9), orphaning (LP12), and link residence after orphaning (LP13).
- **ASN-0093** for the creation frame (a new link disturbs no delivered link — W6a).
- **ASN-0086** / query construction for the type refinement and which region a query fixes — both upstream, out of scope.

It hands to a separate cardinality operation and the front-end, which synthesize "k of m" (W10), and to a journaling/recovery layer (the recommendation of §2) that rebuilds the index as a hint.

## Decisions for the builder

1. **Which permanent key** — address (strongest delivery, append-at-tail, but content-index-misaligned and not cross-document monotone) vs least-covered-tumbler (state-stable and robust, but needs a derived index and has a new-link blind spot). Neither is the spanfilade's free native (matched-slot) order, so this is coupled to decision 3. The note's central open parameter.
2. **Re-derive vs seek-walk vs hint-cache** per window — simple-correct vs fast-common-case vs amortized.
3. **Index representation** — port the spanfilade, or a persistent ordered map keyed by (slot, I-address); recovery by journal replay. Coupled to decision 1: the native (slot, I-address) order is Green's matched-slot order — *neither* permanent key — so an address-ordered or derived least-covered index is an added cost.
4. **Designated endset slice** (least-covered key only) — which slots; must include the type slot for totality.
5. **Cursor token shape** — bare address vs fattened opaque token carrying the cached key.
6. **Count signaling** — explicit delivered-count field vs client-side item count.
7. **Variable window sizes** — the operation already permits per-call N (W4 is schedule-independent); decide whether to expose it.

These are distinct from the note's own spec-level open questions (multi-document monotone ordering; an eventual-delivery guarantee under a non-monotone key; the cross-call completeness invariant over a mutating set; distinguishing empty from invalid for position keys; delivery/sizing correspondence) — those remain unknowns to resolve in the spec, not choices to make at the keyboard.
