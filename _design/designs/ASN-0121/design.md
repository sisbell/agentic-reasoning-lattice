## What this is

ASN-0121 defines the system's **link-discovery query** — the read side of the link subsystem. Given a four-part description of links (where they reside, what they are *from*, what they are *to*, and their *type*), it returns exactly the currently-addressable links that match. It is an inverse lookup over the link store: read-only, and — by the note's own result — a pure function of the link store alone.

## Design commitments

- **The query depends on the link store and nothing else.** (FL-LOC) *Forced.* It never reads content, arrangements, entities, or provenance. Link discovery is therefore *intrinsically global and content-identity-based*, served from a link index without touching documents or content — not a per-document walk. "Global" here means *across the single store Σ.L*; reach across a federation of independently-administered stores is not specified (an open question), so do not over-extend "global" to a federation the spec does not yet guarantee.
- **The answer is forced — exactly the satisfying, addressable subset.** (FL-DEF/SND/CMP) Soundness and completeness meet with no slack: an implementation has freedom in *how*, none in *what*.
- **Matching is the AND of the ORs.** *Forced.* Within a slot, one address-overlap suffices (existential/OR); across slots, every constrained slot must hold (conjunction/AND). The result is the intersection of per-slot matches.
- **Matching is by address overlap, never by value.** *Forced.* `touch` is coverage-intersection; the type slot especially is matched by *address identity* — content at type/endpoint addresses is never read. Ghost addresses (no stored content) are valid, matchable endpoints. And because a prefix-rooted type span covers a whole subtree, subtype/supertype search falls out of the *same* coverage-overlap test, with no type registry or ontology required (FL-TYP(c)) — whether that subtree reading is *exact* (admitting no addresses outside the intended supertype subtree, omitting no intended subtype) is an open question.
- **Residence and endpoints are orthogonal axes.** *Forced.* Home is a projection of the link's *address* (who owns it / where it lives); endpoints are the link's *value* (what it connects). Either may be constrained without the other.
- **Directionality is positional.** *Forced.* From matches slot 1 only, to matches slot 2 only; reversing them is not a no-op. "Links from X" and "links to X" are different queries.
- **Wildcard is the unit of the conjunction; an empty constraint is its zero.** *Forced, and must be distinguished.* A wildcard (NOSPECS) slot drops out; a constrained-but-empty slot annihilates the whole result. The all-wildcard request returns *all addressable links*, not nothing. The same zero applies on the *link's* side: L3 lets a stored link carry an empty from- or to-endset (`e₁ = ∅` or `e₂ = ∅`; only the type slot must be non-empty). Emptiness on one endset suppresses constrained matching *on that axis alone*: a link with `e₁ = ∅` fails any constrained *from*-request (admitted on the from axis only under the from-wildcard), yet its non-empty `e₂` still matches a constrained *to*-request normally — "from nothing is not a from-match," but such a link remains an ordinary to-match.
- **Addressability (retraction) gates the result, monotonically and permanently.** *Forced.* A retracted link is permanently and completely absent from current-state inquiry; the nullified set only grows.
- **The result is a current snapshot, and link allocation is the only thing that can move it.** *Forced.* Content appends, document registration, arrangement edits, rearrangement, and provenance writes leave every link-query answer unchanged; only a link write (K.λ) can change it.
- **Slot positions and address rooting are convention, not enforced.** First-three-slots-are-from/to/type and home-rooted-at-organizational-prefixes are conventions; the grammar permits higher arity (matched on its first three slots) and any rooting.

## What must be built

- A **request decoder / grammar** — parse the four-part request into per-slot values carrying the three-way distinction the conjunction needs: *wildcard* (`∗`/NOSPECS — drops out), *empty-constrained* (`∅` — annihilates), and *populated* (a set of address-spans). This is a first-class component, not an afterthought: FL-WILD and FL-EMP are both unrealizable if the encoding collapses `∗` and `∅` into one absent slot (the reference's flaw — see repair (c)), under which the all-wildcard request wrongly returns ∅ and `Θ = ∅` becomes inexpressible.
- A **link-store lookup** — given a link address, its endset-tuple and (by address projection) its home. Mostly upstream; the query consumes it.
- A **per-slot link finder** — given a request component (a set of address-spans), find the links whose corresponding endset *overlaps* it, for each of from/to/type, kept positionally distinct. When indexing a link, *omit the slot whose endset is empty*: a link with `e₁ = ∅` contributes no *from*-index entry, so a constrained *from*-request never returns it — but its non-empty `e₂` is indexed and matched normally, so a constrained *to*-request still returns it. Emptiness suppresses a link on its empty axis alone; a wildcard request on that axis admits it.
- A **coverage-overlap test** (`touch`) — decide whether two endsets' coverages (finite unions of half-open tumbler intervals) intersect.
- A **residence test** (`athome`) — decide whether a link's home (computed from its address) lies in a requested region; no store lookup needed.
- An **addressability filter** — compute the nullified set (links named by a standing retraction tuple) and exclude them, evaluated against the *current* retraction relation.
- A **combination engine** — AND across constrained slots, drop wildcard slots, short-circuit to ∅ on any empty constrained slot, return all-addressable when every slot is wildcard.
- A **recovery path** — rebuild whatever index/derived state the query uses from the authoritative link store on load.

## Implementation approaches

**The query engine / link index — the core choice.**

- *Start with a full scan.* FL-DEC makes `sat` decidable per link and the store is finite; FL-LOC makes the scan embarrassingly parallel, and `sat` being per-link means a non-matching link costs only its own evaluation. A scan over `addressable(Σ)` evaluating `sat` is the simplest thing that honors the spec exactly — keep it forever as the **reference oracle** the index is tested against. Pick this when the store is small or query rate is low.
- *Add an inverted index when latency demands it.* The proven approach is the udanax-green **spanfilade**: a content-addressed index where each link contributes *one entry per contiguous coverage region per slot*, keyed by the *I-addresses* (content identity) of that endset and tagged by which slot it is (the from/to/type subspaces) — an endset spanning *k* disjoint I-regions (e.g. content transcluded from several sources) lays down *k* entries in that slot's subspace. A link whose from- or to-endset is empty simply contributes no entry in that slot's subspace — the link-side zero of FL-EMP, realized as index absence: a constrained query on that slot never finds it, a wildcard query (which skips the subspace) still does. A query resolves each request component to address-spans, looks up each slot's subspace independently, and intersects the resulting link-sets — exactly the AND-of-the-ORs. Because a single slot's lookup can return the same link-address from several of its own regions, dedup-**by-address** is intrinsic *within one query*, not merely a cross-document artifact. This keying is what buys stability-under-editing and cross-document reach *for free* (below), so prefer content-identity keys over arrangement-relative ones.
- *Or per-slot interval indexes.* Because coverage is a finite union of half-open tumbler intervals and `touch` is interval-overlap, an ordered/interval structure per slot (keyed on the tumbler total order) answers each slot with a range/stab query, then intersect across slots. A persistent ordered-map structure fits well: append-only writes yield a new, structurally-shared version cheaply, giving MVCC snapshot reads (the "current snapshot" of FL-CMP) without locking writers — and laying groundwork for version-qualified inquiry later (an open question).
- *Treat the index as a hint, not authoritative state.* The append-only link store is the truth; the index is a cache recomputable by rescan/replay. Don't maintain it through a second authoritative write path you must keep consistent — derive it, and rebuild on a miss or on load. This is the cheapest way to keep exactness honest. And **never GC an index entry because its endpoint content has left every arrangement:** content is never destroyed (S0) and the link store never shrinks, so the orphaned link must stay findable by content identity — the udanax-green spanfilade is write-only, with no `deletespanf` (Q18). Tying entry lifetime to arrangement presence would forfeit FL-REACH's orphan reach and collapse this query into the fragile `findlinks_V`.
- *Intersection algorithm:* nested-loop (the reference's `intersectlinksets`) is fine for small per-slot result sets; switch to sort-merge or hash-set intersection as results grow. Short-circuit *before* intersecting if any constrained slot resolved to nothing (FL-EMP).

**The `touch` and `athome` tests — make the common case fast.**

- The general algorithm is cell decomposition over the sorted span endpoints, run for intersection-nonemptiness — O(n log n) in span count.
- Special-case by coverage shape, in three tiers. (i) A single *unit-depth* prefix span ("this address's subtree") is the dominant case: `touch` reduces to **prefix-nesting** of two addresses (one comparison) and `athome` to a single **prefix-containment** check on `home(a)`. (ii) A single *wide* (non-unit-depth) span — the order-convex sub-range an element-rooted span straddling a length boundary denotes — is *not* a subtree, so the prefix reduction is invalid; but it is still one half-open tumbler interval, answered by a single interval-membership/overlap test. (iii) Genuine multi-span coverage falls back to the interval-union/cell-decomposition algorithm above.
- `home(a)` is a field projection of the address — compute it, never look it up.

**The addressability filter.**

- *Maintain a derived nullified/tombstone hint* — as each retraction-bearing link is appended, record its *to-coverage* (the interval/span set it names, **not** a resolved address list); query-time exclusion tests a candidate address for membership in that coverage. Storing coverages rather than resolved addresses is what makes the spec's two hazards fall out: a link can be **born-nullified** (allocated at an address a standing retraction's coverage already names, before that address was in the store) and a retraction can be **self-nullifying** — so every newly-allocated address must also be tested against the standing coverages, not just pre-existing links. The hint must be applied against the current relation and updated on every link write — addressability cannot be decided once at creation.
- *Or compute on demand* from the retraction slice of the store (the arity-3 links whose type matches the retraction class), unioning their to-coverages. Always correct, costs a scan. Critically, the slice includes *every* such link, **including retraction links that are themselves nullified**: `nullified` is a non-fixpoint operation (R6b) — retracting a retractor removes *it* from results but does not restore the links its to-coverage excluded. Do not "optimize" by filtering the slice to addressable retractors; that would wrongly resurrect their targets.
- *A retraction link is itself a first-class, searchable link* — a type-`Θ` query touching the retraction class returns one like any other. **Index retraction links as ordinary links**, not only as filter metadata: they live in both the search index (as results) and the addressability hint (as the source of nullification).
- Either way it is a *hint over the link store*, rebuilt on load by replay. Prefer maintaining it (the filter runs on every query) but never treat it as the source of truth.

**Recovery, snapshot, concurrency.**

- An append-only journal with a path/address registry, recovered by replay, is the right model and maps directly: the link store is the journal; on load, replay to reconstruct the in-memory link map and rebuild the index and nullified-set as hints. Neither derived structure needs to be journaled.
- Because values are immutable (L12/LP13) and the store append-only, persistent structurally-shared structures let each post-K.λ version share almost everything with the prior one. Optionally checkpoint the index for fast restart — but a checkpoint must be recomputable on a miss, so it stays a cache of a cache.
- Cache invalidation is cheap: **K.λ is the unique result-changing transition** (FL-WP). Link-query results survive every content append, registration, arrangement edit, and provenance write; refresh only on a link allocation.

## Guarantees to uphold

- **Exactness (soundness + completeness):** return precisely the satisfying addressable subset. *By construction* if the index faithfully realizes FL-DEF; the live risk is index/oracle drift — *actively enforce* by testing the index against the scan.
- **Stability under editing (FL-STB):** content edits and rearrangement never change which link identities are returned. *The guarantee itself is unconditional* — the operation never reads Σ.M (FL-LOC), so the true answer cannot move under an arrangement edit. The keying choice does not create the guarantee; it only decides whether the *index* stays faithful to it: a content-identity (I-address) index tracks the stable answer, whereas an arrangement-relative one would drift from it. So key by content identity — not to *make* the answer stable, but to keep the index honest about an answer that already is.
- **Cross-document reach, transclusion found once (FL-REACH):** *by construction* if the index is global and content-addressed, with results deduplicated by link **address** — never by value. "Found once" means the same link reached via several shared spans/documents collapses to one *address*; two distinct links with byte-for-byte identical endsets but different addresses/homes (Trace 6's `a₁`/`a₅`) are two results and must not be merged. The reach is also *strictly* more complete than any document-by-document enumeration: a **satisfying orphan** — a link whose endpoint content has left every arrangement — is still returned here (FL-REACH(d)), found by content identity rather than by any document surfacing it. Uphold this by keeping orphan index entries (the "never GC" rule above); losing them is exactly what separates this stable query from the fragile `findlinks_V`.
- **Directionality (FL-DIR):** *by construction* if from/to/type are kept positionally distinct in the index.
- **Permanence & monotone accumulation (FL-MON):** found stays found absent retraction — *by construction* from immutable values + append-only store.
- **Non-impedance (FL-JUNK):** an arbitrary quantity of *non-matching, non-retraction* additions neither enlarges nor displaces the answer. *By construction* (per-link `sat`). Mind the hypothesis: addressability is *not* per-link, so a retraction-bearing addition **can** remove an existing match (FL-WP(c)) — "junk is harmless to results" is false for retraction links. Separately, the digest's own engineering goal — not part of FL-JUNK, which is an answer-invariance lemma, not a complexity bound — is that junk matching nothing should cost nothing in the intersection: it never enters any per-slot result set, so it adds only index-lookup *depth* (≈ logarithmic in store size), while the intersection's polynomial cost stays a function of the *matching* result sizes alone.
- **Retraction absence (FL-RET):** retracted links permanently and completely gone from current inquiry. *Requires active enforcement* — apply the addressability filter on every query and keep the nullified set monotone (never "un-retract").
- **Read-only frame:** the query mutates nothing. *By construction.*

## How it fits

- Reads **Σ.L** from the ASN-0047 state model; leans on **ASN-0034** (tumbler total order, spans, half-open interval representation, partition independence), **ASN-0043** (coverage, endsets, `home`, prefix-span subtree coverage, type-hierarchy-by-containment, ghost permission), **ASN-0086** (the retraction relation, `nullified`, and the decidability machinery the `touch`/membership tests reuse), **ASN-0093** (link-allocation precondition and store finiteness), and **ASN-0098** (value persistence and store monotonicity across reachability).
- Sits *behind* **ASN-0127's V-spec front-end** (`findlinks_V`): a V-region request is first resolved through the arrangement (Σ.M) to an I-address set, then handed to this query. Place arrangement resolution in that separate layer — its fragility under full deletion (a link drops when an entire endset's content leaves every arrangement) is a property of *resolution*, not of this query, which is stable.
- Distinct from ASN-0127's slot-agnostic, unfiltered `findlinks` (F-FIND): different slot regime, range, and dynamics — neither is a restriction of the other. Don't implement one as a special case of the other.
- The write side it implicitly depends on is link allocation (K.λ) and the retraction discipline that populates `nullified`.

## Decisions for the builder

- **Scan vs index, and when to cross over.** Ship the scan first (it is the oracle); introduce an inverted index when query latency forces it. Then pick the structure: content-addressed enfilade-style 2D index, per-slot persistent interval/ordered maps, or a hybrid.
- **Index keying.** Content identity (I-address) is effectively forced if you want stability and reach for free — but you choose the concrete order-preserving tumbler encoding, trie, or interval scheme.
- **Nullified set: maintained vs computed.** A derived tombstone hint of retraction to-coverages (fast filter, updated on every link write) or on-demand computation (always correct, costs a scan). Either way, rebuilt on load.
- **Intersection algorithm and result shape.** Nested-loop vs sort-merge vs hash; and the spec returns a *set* — you choose ordering (address order, index order, unordered), streaming vs materialized, and dedup **by link address, never by value** (required for "transclusion found once"; a value-based dedup would wrongly merge distinct links with identical endsets).
- **Snapshot & concurrency policy.** Checkpoint the index for fast restart or always replay; queries pin an immutable version (MVCC) or read latest. The append-only, immutable-value substrate makes lock-free snapshot reads natural.
- **Common-case fast paths.** Whether to special-case unit-depth prefix spans (one nesting test) and single wide spans (one interval test) for `touch`/`athome` before falling back to cell decomposition. The prefix fast path doubles as type-hierarchy search: a supertype-rooted type request matches its whole subtree of subtypes through the *same* nesting test, so subtype/supertype lookup needs no separate registry — don't build one.
- **Repair the reference's divergences.** A faithful implementation must (a) actually *honor the home-set* (the reference's residence bound is dead code — every search is global), (b) return *all addressable links* for the all-wildcard request (the reference returned ∅), and (c) choose a request encoding that can express a present-but-empty constrained slot distinct from NOSPECS (the reference collapses both, making `Θ = ∅` inexpressible) — so that FL-EMP and FL-WILD are both realizable.
